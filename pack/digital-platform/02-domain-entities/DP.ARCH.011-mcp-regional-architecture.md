# DP.ARCH.011 — Региональная архитектура MCP-поверхностей и хранилищ знаний

> Решения прошли пир-сессию (Claude писатель + Kimi критик приватности + Codex верификатор по коду), 2 содержательных раунда, консенсус с оговорками. Полная стенограмма: `MC-sessions:2026-10/20/2026-10-20-03-wp542-mcp-russia-infra-plan/`. Пилот подтвердил запись в Pack 20.10.2026.

## Р1 — Два независимых контура

Мир и Россия — два независимых контура без репликации между ними. Контур данных определяется **владельцем источника** (личный аккаунт или организация, которая его подключила), не адресом сервера, на котором крутится код. Перенос аккаунта между контурами — экспорт/импорт по явному запросу владельца, без фоновой синхронизации.

**Открыто (юридическая проверка, не архитектурный факт):** конкретные правовые основания (152-ФЗ, GDPR) для привязки контура к резидентству владельца; условия и механика экспорта/импорта.

## Р2 — Три класса хранилищ по типу данных, не по региону

| Класс | Что хранит | Кто читает | Регионы |
|---|---|---|---|
| (а) Публичный корпус | Открытые источники (FPF, руководства, шаблон ИИ-среды, открытые паки) | Только гостевой вход | Две языковые копии — RU в России, EN в мире |
| (б) Личное + командное знание | Данные пользователя/команды, построчно разграниченные по владельцу | Личный вход через шлюз, после авторизации | Своё хранилище в каждом контуре |
| (в) Память (производные факты) | Результат фреймворков памяти (см. Р7), после spike | Личный вход | Отдельный сервис, не начат |

**Целевое требование, не текущий факт:** гостевой вход не имеет доступа к классам (б) и (в). Построчное разграничение (б) сегодня частично реализовано (`knowledge-mcp src/rls.ts`), но полнота покрытия всех путей чтения (включая `public`, `fetch`) не подтверждена кодом — это входная проверка фазы Ф2 (WP-542), не завершённое состояние.

## Р3 — Три категории доступа к репозиториям

1. **Открытые** — через гостевой вход, без аккаунта.
2. **Личные, с уровнем доступа** — владелец выбирает: только себе / выбранным людям / всем желающим / всем по подписке. Граница по аккаунту годится как правило выбора контура при регистрации; для фактического доступа к конкретному источнику действует модель прав (п. 4).
3. **Командные** — через тот же личный шлюз, с проверкой прав по команде/организации (модель — WP-604). Внешний MCP команды со своим инженером подключается как внешний источник (как сервер Анатолия для FPF), платформа его не хостит.

## Р4 — `knowledge-mcp` остаётся именем, роль сужается

Имя `knowledge-mcp` сохраняется (у него живые потребители: реестр бэкендов шлюза, инструкции агентов, журнал `mcp_access_events`, каталог DP.MAP.004). Роль — личное и командное знание (б); методология (а) выезжает в гостевой вход. Переименование (например, в `personal-knowledge-mcp`) — одним ходом вместе с появлением сервиса памяти (в), не раньше.

**Проверка по коду перед переключением (не выполнена):** маршруты режима `public`, состав `sources.json`, назначение `account_id` в `ingest.ts`, выбор бэкенда в `gateway-mcp`.

## Р5 — Гостевой вход: две поверхности, без серверной склейки

Два независимых технических пути, не один «шлюз шлюзов»: (1) наш сервис над отдельной публичной базой (Qdrant, RU/EN копии); (2) прокси к серверу Анатолия (`mcp.fpf.tools`) для FPF. Одна входная страница показывает оба источника с понятными названиями. Серверная склейка результатов в один ответ — не делается до отдельного решения и согласия Анатолия на такой вызов (риск: SLA чужого сервера, утечка параметров запроса третьей стороне, единая точка отказа).

## Р6 — Класс и владелец обязательны при индексации

Источник не индексируется без явного класса (`methodology` / `personal` / `team` / `public_user`) и владельца. Это первое изменение фазы разметки (WP-596) — подготовка миграции, не переключение маршрутов.

## Р7 — Новые технологии индексации и памяти — только спайк

Hindsight, Mem0, Graphiti и аналогичные фреймворки памяти рассматриваются только для класса (в) — личной производной памяти пользователя, не для платформенного знания (руководства, паки остаются на RAG/чанках). Решение о внедрении — после спайка (WP-579) с критериями, зафиксированными до старта: точность извлечения на известном наборе событий, стоимость LLM-вызовов на 1000 событий, возможность развёртывания в VK Cloud без внешних API.

## Р8 — Порядок работ (детали фаз → WP-542)

Инвентарь российской инфраструктуры с координатором (Ильшат) и сборка публичного гостевого контура идут параллельно, не последовательно. Перенос личного/командного знания в российский контур — после инвентаря. Перенос уже затронутых данных (после утечки, найденной в WP-604) — только после аудита охвата этой утечки, но аудит не блокирует подготовку пустой инфраструктуры. Методология удаляется из старого индекса `knowledge-mcp` только после подтверждения полноты нового гостевого индекса.

## Р9 — Шаблон ИИ-среды по регионам

Мир — `iwesys/IWE`. Россия — личный аккаунт пилота (`FMT-exocortex-template`).

## Открытые вопросы (не решения, не менять статус без нового ArchGate)

- Правовые правила резидентства данных и миграции аккаунта между контурами.
- Совместный доступ к одному источнику из двух контуров одновременно — не поддерживается в первой версии.
- Полнота журнала `mcp_access_events` как единственного аудиторного следа — проверка по коду.
- Контракт и доступность прокси к серверу Анатолия перед запуском.
