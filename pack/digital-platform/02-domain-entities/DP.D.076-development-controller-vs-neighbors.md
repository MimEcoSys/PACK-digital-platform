# DP.D.076 — Контролёр развития и его соседи

## Зачем это различение

При формализации R46 «Контролёр развития» (бывший «IWE Stage Controller») возник вопрос: не дублирует ли он работу уже существующих ролей? Ответ — нет, но границы тонкие. Это различение фиксирует, чем Контролёр отличается от каждого соседа, чтобы не сваливать функции в одну роль.

Общее правило различения ролей: **разный pace-слой ИЛИ разный источник истины ИЛИ разный объект внимания = разные роли**. У Контролёра развития с каждым из шести соседей нарушено как минимум одно из этих условий.

## Сводная матрица

| Роль | Pace-слой | Триггер | Объект внимания | Чем отличается от Контролёра |
|------|-----------|---------|------------------|------------------------------|
| **R46 Контролёр развития** | плановый, день | systemd timer 05:30 | фактический профиль vs маркер по оси | — |
| R22 Оркестратор | плановый, день | утренний цикл + события | весь цикл развития пилота | **Родитель**. Контролёр = специализация для одной оси. Оркестратор координирует между несколькими Контролёрами (если их будет N). |
| R13 Проводник | реактивный, миллисекунды | нажатие кнопки / ввод команды | FSM-state + tier | **Реактивный** vs плановый. Живёт в боте, не на сервере. |
| MIM.R.007 Навигатор | по запросу / по обращению | префикс «Навигатор, ...» или сигнал от Контролёра | методологическая траектория, ритм, мемы | **Методология** vs техническое сравнение. Пишет осмысленный текст; Контролёр шлёт шаблонный нудж. |
| R12 Оценщик | реактивный, секунды | пилот отправил ответ/ДЗ | правильность одного ответа | **Точечная оценка** vs обобщённый профиль. Не сравнивает с маркером ступени. |
| R41 Аттестатор | реактивный (event-driven) | новое событие Activity Hub | переход между ступенями | **Назначает** ступень vs **читает** ступень. Контролёр у Аттестатора читает результат. |
| R42 Диагност | по запросу пилота | пилот вызывает `/diagnose` | cp-профиль пилота | **Pull-mode** vs daily обход. Не работает в фоне; Контролёр использует его результат. |

## Подробные границы

### Контролёр развития ≠ Оркестратор (R22)

| | Контролёр развития | Оркестратор |
|---|---|---|
| Что делает | Сканирует одну ось, выдаёт сигнал «gap есть» | Принимает сигналы со всех Контролёров, решает приоритеты, делегирует |
| Аналогия | Один прибор измерения (термометр) | Дежурный диспетчер скорой |
| Holder сейчас | tsekh-1 + `iwe-stage-controller.py` | TBD (Ф3 MVP) |
| Множественность | Можно иметь несколько (по числу осей) | Один на пилота |
| Логика принятия решения | Детерминированная таблица маркеров | Контекстная (с учётом всех сигналов) |

Контролёр развития формально объявлен `specializes: DP.ROLE.022` — родительская роль.

### Контролёр развития ≠ Проводник (R13)

| | Контролёр развития | Проводник |
|---|---|---|
| Pace-слой | плановый, ежедневный обход | реактивный, миллисекунды |
| Holder | сервер (systemd) | бот (aiogram middleware) |
| Что замечает | «пилот неделю не двигается, gap к маркеру» | «пилот нажал кнопку — куда дальше» |
| Действие | Инициирует задание адресату | Меняет state в FSM, показывает кнопки |
| Когда работает | 1 раз в сутки | каждое касание UI |

Принципиально разные слои. Бот не умеет «раз в день обойти всех», сервер не умеет «реагировать на нажатие кнопки в реальном времени». Это физика разных runtimes, не архитектурный выбор.

### Контролёр развития ≠ Навигатор (MIM.R.007)

| | Контролёр развития | Навигатор |
|---|---|---|
| Слой | Технический | Методологический |
| Триггер | Daily scan | Префикс «Навигатор, ...» или сигнал от Контролёра |
| Текст ответа | Шаблонный («попробуй сегодня X») | Свободный, с учётом фазы и мемов |
| Цель | Инициировать действие | Объяснить «зачем» и удержать в движении |

Контролёр **зовёт** Навигатора, когда обнаруживает методологический разрыв (3+ дня без активности при наличии истории `/slot`). Сам Контролёр не пишет осмысленный текст.

### Контролёр развития ≠ Оценщик (R12)

| | Контролёр развития | Оценщик |
|---|---|---|
| Объект | Профиль пилота за период | Один ответ / одна ДЗ |
| Масштаб | Дни-недели | Секунды-минуты после ответа |
| Сравнение | Профиль vs маркер ступени | Ответ vs эталон / рубрика |
| Действие | Делегирует адресату | Возвращает оценку в диалог через Консультанта |

Не пересекаются: разные объекты оценки, разные масштабы времени.

### Контролёр развития ≠ Аттестатор (R41)

| | Контролёр развития | Аттестатор |
|---|---|---|
| Что делает | Читает текущую ступень | Назначает ступень при переходе |
| Триггер | Daily timer | Новое событие Activity Hub (push) |
| Источник истины | `stage_transitions` (читает) | `stage_transitions` (пишет) |

Контролёр — потребитель данных Аттестатора. Аттестатор НЕ является downstream-consumer'ом Контролёра (Контролёр не пишет в его таблицы).

### Контролёр развития ≠ Диагност (R42)

| | Контролёр развития | Диагност |
|---|---|---|
| Что делает | Сравнивает cp-профиль с маркером | Измеряет cp-профиль через диалог |
| Триггер | Daily timer | Пилот вызвал `/diagnose` |
| Режим | Pull-mode (читает результат) | Pull-mode (по запросу пилота) |

Контролёр **читает** результат Диагноста и **может** напомнить о повторной диагностике (если cp-профиль устарел). Но сам диагностику не проводит.

## Тест разделения (применять при создании похожих ролей)

При появлении новой роли в зоне Контролёра задать три вопроса:

1. **Pace-слой:** реактивный, плановый, по запросу или по событию?
2. **Источник истины:** какую таблицу/событие/сигнал роль считает основой решения?
3. **Объект внимания:** один артефакт, профиль за период, или цикл/процесс?

Если хотя бы один параметр совпадает с Контролёром — нужно либо склеить в Контролёра (если все три совпадают), либо явно сформулировать различение здесь.

## Эпизод формализации

20 мая 2026: при обсуждении автоматизации онбординга (WP-343) возник вопрос «не повторяет ли Контролёр работу Проводника / Оркестратора / Навигатора». Ответ — нет, они на разных pace-слоях с разными источниками истины. Параллельно решили убрать продуктовый префикс «IWE» из имени роли (см. DP.ROLE.046 v0.3) и заложить расширение оси контроля от ступеней Ученика на степени квалификации / стиль / домены через параметризованный «профиль контроля».

Различение «Контролёр стиля ≠ Контролёр развития»: это **не разные роли**, а один Контролёр с разными профилями. Объект параметризуется, роль остаётся одной (Single Responsibility сохраняется).
