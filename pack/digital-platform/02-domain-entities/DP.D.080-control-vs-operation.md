# DP.D.080: Контрольная роль ≠ Операционная роль

> Роль, которая **наблюдает и сообщает**, и роль, которая **воздействует и изменяет**, — два несовместимых типа. Смешение лишает контроль независимости, а операцию — идемпотентности.

## Различение

| Аспект | (а) Контрольная роль | (б) Операционная роль |
|--------|----------------------|----------------------|
| **Что производит** | Отчёт (артефакт) для получателя | Изменение состояния целевой системы |
| **Результат** | Знание о системе | Новое состояние системы |
| **Отношение к объекту** | Read-only: не трогает проверяемое | Write: приводит состояние к норме |
| **Получатель** | Есть явно: кто-то получает отчёт | Нет внешнего получателя — действие само и есть результат |
| **Инвариант** | Независимость + context isolation | Идемпотентность (N запусков = тот же результат) |
| **Примеры в IWE** | R23 Верификатор, R24 Аудитор, R25 Рецензент, R26 Приёмщик | R8 Синхронизатор, R11 Наладчик бота |
| **Аналоги вне IWE** | Финансовый аудитор, регулятор | Kubernetes reconciler, Terraform apply, prettier |

## Тесты

**Тест 1 (основной):** «Изменилось ли что-то в аудитуемых артефактах после работы роли?»
- Нет → контрольная роль (output-канал роли — отчёт — не считается изменением аудитуемого)
- Да → операционная роль (если изменение было целью) или нарушение (если роль должна быть контрольной)

**Тест 2 (получатель):** «Есть ли кто-то, кому роль передаёт результат своей работы?»
- Да, явный получатель отчёта → контрольная роль
- Нет, результат = изменённое состояние → операционная роль

**Тест 3 (инвариант):** «Что ломается при многократном запуске при неизменных входных данных?»
- Контроль: не ломается ничего — повторный аудит даёт тот же coverage % и не меняет состояние аудитуемых артефактов
- Операция: конвергирует к норме — третий запуск Синхронизатора ничего не меняет (идемпотент)

## Почему важно (проблема смешения)

**Если контрольная роль изменяет наблюдаемое:** она теряет независимость. Аудитор, который исправляет то, что проверяет, создаёт два дефекта: (1) он закрывает gap'ы, которые должен был сообщить, и (2) его последующий аудит тех же артефактов недостоверен.

**Если операционная роль отчитывается вместо действия:** она создаёт WIP (work in progress) — артефакт, который не делает системного изменения, но занимает ресурс. Синхронизатор, который пишет отчёт «что нужно синхронизировать», а не делает синхронизацию, является инвентарём, не throughput.

**Ключевое:** обе роли **необходимы**, они ортогональны. Контроль + операция = полный цикл управления. Ошибка — назначить одну роль обоими типами одновременно.

## Применение в IWE

| R24 Аудитор | Контрольная | Аудит | Owner Role ≠ Платформа (особый Owner); методологическая независимость |
| R23 Верификатор, R25 Рецензент, R26 Приёмщик | Контрольная | Аудит | Owner Role = Платформа; методологическая независимость |

| DP.KR.030 Триада: Учёт, Аудит | Контрольные ветки | — | Контрольный слой в целом; не изменяют аудитуемые артефакты |

## Границы применения

**Разделение логическое, не обязательно физическое.** Один агент (или Пилот) может исполнять контрольную и операционную роли в разных сессиях, если соблюдаются инварианты: изолированный контекст, read-only к аудитуемым артефактам, scope freeze. См. DP.ROLE.024 §1 (методологическая vs организационная независимость).

**Граничный случай — R12 Оценщик:** фиксирует оценку (write), но сама оценка и есть отчёт. Для таких «гибридных» ролей требуется дочернее различение (DP.D.081, WP-224).

**Не применяется к самому output-каналу:** контрольная роль пишет отчёт в inbox/выходной артефакт — это не нарушение read-only. Read-only = к аудитуемым артефактам, не к любому файлу в системе.
