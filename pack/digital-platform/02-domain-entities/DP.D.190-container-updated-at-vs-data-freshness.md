# DP.D.190 — `updated_at` строки-контейнера ≠ актуальность данных внутри строки

| Аспект | `updated_at` строки | Актуальность данных (payload) |
|--------|--------------------|-----------------------------|
| **Что отражает** | Когда процесс в последний раз ТРОГАЛ строку (даже no-op) | Когда данные внутри payload реально ИЗМЕНИЛИСЬ |
| **Пример** | Профайлер пересчитывает строку ежедневно — дата сегодняшняя | Payload заморожен с марта: последнее событие датировано мартом |
| **Риск смешения** | «Строка свежая» → на самом деле данные устарели | Правильный диагноз требует проверки payload |
| **Как проверить** | `max(datetime)` внутри JSON-поля или связанных событий | — |

## Инвариант

`updated_at` в таблице-контейнере отражает mtime процесса (когда агрегатор касался строки), а не актуальность данных. Агрегатор может пересчитывать строку с неизменными входными данными — `updated_at` обновляется, payload не меняется.

## Применение

При аудите data-pipeline: вывод «данные свежие» на основании `updated_at` считается недостаточным. Проверка свежести = смотреть последний datetime внутри payload (последнее событие, последний timestamp в JSON), а не mtime строки-обёртки.

## Тест

«Строка обновлена сегодня — значит данные актуальные?»
- Не обязательно → проверить: что именно пересчитывал агрегатор? Изменился ли payload?
- Если профайлер/агрегатор пересчитывает на одних и тех же входных данных → `updated_at` = артефакт работы процесса, не обновление данных.
