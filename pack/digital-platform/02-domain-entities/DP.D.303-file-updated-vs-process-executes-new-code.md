# DP.D.303 Файл на диске обновлён ≠ живой процесс исполняет новый код

| Аспект | Файл на диске | Живой процесс |
|--------|---------------|----------------|
| **Что меняется** | Содержимое файла скрипта/бинаря; mtime может измениться и без изменения содержимого | Исполняемая версия меняется при загрузке нового кода — через поддерживаемый reload или перезапуск |
| **Наблюдаемый факт без проверки** | «Файл обновлён» | Ошибочно принимается за «изменения уже действуют» |
| **Возможный разрыв** | — | Процесс может продолжать исполнять ранее загруженный код, пока не загрузит новую версию; одного времени старта для вывода недостаточно |

## Правило

Три уровня свежести деплоя долгоживущего демона: репозиторий → диск (проверенное содержимое) → исполняемая версия процесса. Время изменения файла и время старта — диагностические признаки, а не идентификаторы исполняемого кода. Отчёт о доставке изменений («задеплоено», «обновил копию») обязан называть, до какого именно уровня дошло и чем это проверено.

## Тест

«Когда стартовал процесс, и раньше ли это mtime файла?» Любой ответ — только диагностический признак: mtime может измениться без изменения кода или быть намеренно/ошибочно установлен в прошлое, а процесс мог выполнить reload. Сверить хеш или явную версию загруженного компонента либо наблюдаемое поведение, отличающее старую версию от новой. Если старая версия подтверждена, выполнить предусмотренный reload либо перезапуск; затем повторить проверку версии/поведения. Сам факт перезапуска не доказывает загрузку нужной версии.

## Пример

Напарник отчитался «детектор в репозитории, нужно обновить копию» — реальный разрыв был не в репозитории/диске (файл уже обновлён с 09:10), а в том, что живой процесс сторожа был запущен 3 сентября и продолжал крутить старый код в памяти. Фикс — перезапуск процесса, не синхронизация файлов.

## Второй пример: проверка сразу после выкатки (РП-614, 29.10.2026)

После записи переменных окружения и выкатки бота пилот проверил команду, и ответ выглядел так, будто переменных нет («Настройки» вместо результата). Сообщение пришло в 12:10, а новый экземпляр поднялся в 12:11 (времена по записи, журнала экземпляров под рукой не было): ответил старый экземпляр, без переменных, команда ушла общему обработчику. Ложный сигнал мог увести в разбор настроек. Порядок проверки: (1) сравнить время сообщения со временем подъёма нового экземпляра, прежде чем разбирать настройки; (2) вторая независимая проверка по журналу службы-получателя («запросов от бота не было»), а не по ответу окна; (3) повторить проверку после подъёма. Основание: один случай, доверие среднее.

## Применимо к

Эксплуатации любого долгоживущего демона (launchd, systemd, supervisord), где код обновляется через git pull/копирование файла независимо от запусков и остановок процесса. Смежные failure modes: DP.FM.194 (launchd не перезапускает сервис из-за stale-pid на порту — иной механизм: там launchd явно пытается и не может перезапустить; здесь launchd вообще не пытается, процесс формально «жив и здоров»), DP.FM.143 (PPID-fallback на stale PID в pidfile).
