# DP.D.307: Путь для мутации ≠ Путь для диагностики

| Путь для мутации | Путь для диагностики |
|---|---|
| Резолвер активного (одноразового) worktree годится | Нужно устойчивое каноническое место |
| Существует, пока идёт операция | Должен пережить исчезновение temp-объекта |
| Пример: `resolve_active_worktree()` | Пример: `resolve_canonical_checkout()` |

**Пример:** пайплайн писал полный диагностический лог в `$GOV_REPO/machine/logs`, где `$GOV_REPO = resolve_active_worktree()` — тот самый одноразовый worktree, который другой механизм (`session-guard.sh`, orphan-reap) сам удаляет целиком, как только решает, что владелец сессии мёртв; `machine/logs/` к тому же в `.gitignore`. Живой прогон подтвердил: оба worktree, созданных тем утром, уже физически отсутствовали на диске к моменту, когда «фикс» вроде бы заработал — лог писался в никуда. Решение развело резолверы по смыслу: путь пайплайна (мутирующая операция) остался через `resolve_active_worktree()`; путь лога для человека переведён на `resolve_canonical_checkout()`.

**Тест:** «Функция резолвинга пути возвращает временный/одноразовый объект (worktree, tmp-каталог, ephemeral-контейнер)?» Да → пригодна для операций, срок работы которых совпадает с этим объектом, но НЕ для артефактов, которые должны пережить его исчезновение (диагностика, аудит, лог для человека). Эти два назначения требуют двух разных резолверов, даже если раньше казалось, что один и тот же путь и так работает.

## Связи
- `DP.FM.384` (canonical repo path breaks under worktree isolation) — зеркальный случай той же более общей проблемы «резолвер пути должен соответствовать семантике задачи, а не быть одним дефолтом на всё»: там ошибкой было использование захардкоженного canonical-пути вместо активного worktree; здесь ошибкой было обратное — использование активного (эфемерного) worktree там, где требовался устойчивый canonical-путь. Разные направления одной дисциплины, не дубль — взаимно дополняющие примеры.
