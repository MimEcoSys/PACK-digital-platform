# DP.D.314 Потребитель «перечитывает при использовании» ≠ потребитель «снимок при записи»

## Критерий разграничения

«В момент, когда потребитель принимает решение по этому полю, откуда он берёт значение — перечитывает живое состояние (файл на диске, строка в БД) или использует то, что захватил раньше (переменная, кэш, parse-once массив, снимок при open)?»

| | Read-at-use (перечитывает при использовании) | Snapshot-at-write (снимок при записи) |
|---|---|---|
| Источник значения в момент решения | Живое состояние: диск, БД, состояние процесса-владельца | Копия, захваченная в момент записи/старта: переменная, кэш, bash-массив, снапшот-файл |
| Постфактум-правка поля | Безопасна до первого решения потребителя: следующее чтение увидит исправленное значение | Опасна: потребитель уже держит старое значение и не узнает о правке |
| Цена | Лишнее чтение при каждом использовании (см. DP.METHOD.145 про N×fork) | Скорость, но окно рассинхрона между записью и использованием |
| Пример | `session-guard.sh close` и pre-commit хуки перечитывают `close_path` семафора с диска при каждом вызове | Parse-once конфиг (DP.METHOD.145); переменная окружения, прочитанная при старте демона |

## Живой случай (WP-561 Ф9)

`session-open` открывает семафор Kimi-писателя ДО того, как известно, перерастёт ли сессия в пир-сессию — поле `close_path` неизбежно записывается как `unknown`. Вопрос «можно ли поправить его позже без риска рассинхрона» решён не интуицией («поле важное, лучше не трогать»), а проверкой потребителей: `session-guard.sh close` и pre-commit хуки читают поле заново с диска в момент вызова, а не из снимка при open. Раз каждый потребитель актуален на момент чтения, ранняя заглушка безопасно корректируется сразу после того, как `kimi-peer-writer` распознал пир-сессию, и до первого коммита — никто не успел принять решение на основе `unknown`.

## Второй живой случай: льготное закрытие сессии (РП-484 Ф267 п.2, 29.10.2026)

Сессии лечения, чтения и диагностики проходили то же тяжёлое закрытие с карточкой, что и сессии с правками. Коммит `c11fa163` (iwe-local-config; пир-сессия 2026-10-29-28-wp484-f267-guard-six) добавил путь `close_path: no-code-changes`: закрытие обходит раннер quick-close, только если обещание доказано фактами на момент закрытия (заявки в семафоре только свои, изолированная копия чиста, HEAD не сдвигался с создания копии). Не доказано: закрытие не падает, а идёт обычным более строгим путём, причина выводится текстом (принцип AR.296: неопределённость понижается к более строгой проверке, не к проходу). Холодное ревью нашло критический дефект именно по этой оси: продолжение закрытия после промежуточного состояния PREPARED использовало обещание как снимок и не перепроверяло его, хотя состояние могло измениться за паузу. Исправление: при продолжении обещание доказывается заново, провал останавливает продолжение с отдельным кодом (7). Вывод: декларация, дающая льготный путь, действует только пока её можно доказать на момент использования, и потребитель обязан читать при использовании.

## Почему важно

Безопасность постфактум-исправления поля определяется не важностью поля и не тем, как давно оно записано, а режимом чтения его потребителей. Без этого различения возникают две симметричные ошибки: (а) боятся править заглушку там, где все читатели живые — и тащат `unknown` до конца сессии, ломая close-гейт; (б) спокойно правят поле, у которого есть хотя бы один «снимочный» читатель — и получают тихое расхождение между записанным и уже использованным значением.

## Тест

«Перечислены ВСЕ потребители поля, и каждый читает его из живого состояния в момент своего вызова?» Да → постфактум-правка безопасна до первого решения потребителя. Нет / есть хотя бы один потребитель со снимком → правка требует либо инвалидации снимка (перезапуск, событие), либо запрета правки после первого чтения.

## Практическое правило

Перед тем как разрешить «записать заглушку, уточнить позже» для любого поля семафора/state-файла/конфига — grep всех читателей и классификация каждого по этой оси. Появление первого snapshot-читателя (например, оптимизация parse-once по DP.METHOD.145) переводит поле в класс «правка после записи запрещена» — это фиксируется в контракте поля, а не обнаруживается по инциденту.

## Отличие от смежного

- **DP.METHOD.166 (читать канон из таблицы engine, не из локального файла):** ось «канонический источник ≠ копия»; здесь ось «момент чтения относительно записи» — потребитель может читать из канона, но захватить его при старте и всё равно быть snapshot-читателем.
- **DP.METHOD.145 (parse-once shell config):** метод намеренно делает читателя snapshot-типом ради скорости и сам называет цену «файл может измениться между вызовами»; это различение говорит, когда цена реально платится — когда кто-то правит поле после снимка.
- **AR.268 (хук читает staged-индекс, не диск):** ось «какая версия авторитетна для валидации» (index vs working tree), не «когда захвачено значение».
- **DP.M.074 (provisional payment_id):** частный случай «записать заглушку, потом уточнить» с явным механизмом связки provisional↔real; это различение — общий критерий, когда заглушка безопасна без такого механизма.
- **DP.D.049 (Лог ≠ Инцидент ≠ State file):** классифицирует артефакты; здесь классифицируются потребители одного поля.

## Применимо к

Семафоры и state-файлы сессий, поля конфигурации, читаемые хуками/гейтами, любые ситуации «записать до того, как факт известен» в скриптах с несколькими читателями.
