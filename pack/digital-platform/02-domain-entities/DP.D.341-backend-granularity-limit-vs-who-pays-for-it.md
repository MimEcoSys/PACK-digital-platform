# DP.D.341 — Ограничение бэкенда ≠ место, где за него платят

## Различение

| | «Это ограничение бэкенда» — неполный ответ | «Вот где за ограничение платят» — рабочий ответ |
|---|---|---|
| Что утверждается | Нижний слой умеет только грубую операцию, значит грубый интерфейс неизбежен | Нижний слой умеет только грубую операцию, и остаётся вопрос, какой слой выполняет цикл «прочитать-изменить-записать» |
| Кто несёт издержку | Не называется | Называется прямо: либо надстройка внутри себя, либо агент клиента |
| Следствие для контракта | Грубость API объявляется свойством мира | Грубость API объявляется выбором надстройки, который можно пересмотреть |
| Ошибка, если не так | Обоснованная жалоба клиента закрывается ссылкой на чужое ограничение | — |

## Механизм

Наблюдавшийся случай: у инструмента записи есть только полная перезапись файла; у инструмента чтения — потолок 32 КБ на ответ и чтение страницами с начала. Отсюда цена любой правки равна весу файла, а не весу правки.

Проверка по исходному коду подтвердила диагноз буквально и дала ключевое уточнение. Нижний слой (GitHub Contents API) действительно умеет только GET/PUT файла целиком, и это не лечится. Но из этого не следует, что целиком должен работать и клиент: цикл «прочитать-изменить-записать» кто-то обязан выполнить, и надстройка способна выполнять его внутри себя, продавая наружу дешёвый интерфейс (секционное чтение, дописывание, замена фрагмента). Вместо этого она переложила цикл на агента клиента — то есть на самый дорогой слой, контекст LLM.

## Замер (одно утро резидента экосистемы)

- Две правки строк в списке задач: 45 КБ прочитано, 48 КБ перепечатано.
- Недельный дневник 40 КБ перепечатывается при каждой записи.
- Растущий файл телеметрии вот-вот перейдёт потолок чтения — чтение станет невозможным, а не просто дорогим.

## Тест различения

«Названо ли в ответе на жалобу, какой слой выполняет цикл "прочитать-изменить-записать", и почему именно он?» Если ответ останавливается на «бэкенд умеет только целиком» — различение не проведено: сказано про ограничение, не сказано про плательщика.

## Симптом на стороне клиента

Клиенты начинают перестраивать свою архитектуру данных под гранулярность инструмента: дробить файлы, выносить хвосты в отдельные документы, держать теневые копии. Перестройка данных под API — признак того, что издержка переложена наружу.

## Границы

Различение о распределении работы между слоями, не о выборе бэкенда. Оно не утверждает, что надстройка обязана скрывать любое ограничение нижнего слоя: ограничения, меняющие семантику (атомарность, порядок, согласованность), скрывать нельзя — см. `DP.M.499`, где порядок поставки частичных операций выводится из контракта согласованности.
