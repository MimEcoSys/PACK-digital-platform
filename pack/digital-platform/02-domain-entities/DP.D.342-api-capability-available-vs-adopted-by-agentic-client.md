# DP.D.342 — API-возможность доступна ≠ агентный клиент её принял

## Различение

| | Доступна — недостаточно | Принята клиентом — то, что нужно измерять |
|---|---|---|
| Что доказывает | Деплой выполнен, фича включена на сервере | Доля реальных вызовов, пошедших новым путём |
| Кто решает использовать | Код с фиксированным путём вызова (нет решения) | LLM-клиент, заново оценивающий каждый шаг по описанию инструмента |
| Рычаг поставщика | Код, конфигурация | Текст схемы инструмента (tool description) |
| Обратная совместимость | Не помогает адопции | Старый дорогой путь остаётся валидным → клиент может не переключиться |

## Механизм

Доработка разворачивается на стороне сервиса и становится доступна всем резидентам без действий с их стороны — но «доступна» и «используется» расходятся, потому что вызывающая сторона не код с фиксированным путём, а языковая модель, заново решающая на каждом шаге, каким способом вызвать инструмент. Старый дорогой вызов остаётся валидным (обратная совместимость), поэтому клиент, привыкший к старому пути, продолжит так делать, пока описание инструмента не убедит его в обратном. Единственный рычаг сервера — формулировки в схеме инструмента, то есть текст, а не принуждение.

## Тест различения

«Код развёрнут и доступен — значит ли это, что клиенты его используют?» Для агентного клиента — нет: нужно отдельно измерить долю вызовов, пошедших новым путём, после релиза.

## Границы

Применимо к любому API, чей потребитель — агент (LLM, самостоятельно решающий о способе вызова), а не детерминированный код. Не применимо, если вызывающая сторона — обычный клиентский код с фиксированной логикой вызова (там «доступно» = «используется» сразу после деплоя и обновления клиента).
