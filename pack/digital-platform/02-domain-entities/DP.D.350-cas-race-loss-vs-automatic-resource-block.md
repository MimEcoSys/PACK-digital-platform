# DP.D.350 — Проигрыш CAS-гонки ≠ автоматическая блокировка ресурса

## Различение

| | Автоматический переход в «заблокирован» | status_conflict + отдельное решение владельца |
|---|---|---|
| **Что фиксирует проигрыш CAS** | Сразу доменное состояние ресурса (блокировка) | Только факт конфликта — событие `status_conflict` |
| **Кто решает дальнейшую судьбу элемента** | Механизм сравнения версий неявно, как побочный эффект | Владелец процесса — явно, отдельным шагом (блокировка/повтор/отмена) |
| **Риск отклонённого варианта** | Доменное состояние меняется как побочный эффект чисто технического события версионирования | — |

## Механизм

Два агента пытаются опубликовать конкурирующие изменения одного элемента плана; compare-and-swap относительно ожидаемой версии P определяет, кто опубликован первым. Отклонённая альтернатива — автоматически переводить проигравшую сторону в состояние «заблокирован», раз её попытка публикации не прошла. Принятое решение разделяет два уровня: само событие проигрыша гонки (`status_conflict`) — техническое и автоматическое, а любое изменение доменного состояния элемента (блокировка, повтор, отмена) — отдельный, обдуманный шаг владельца процесса, не каскадирующий автоматически из факта проигрыша.

## Тест различения

«Проигрыш CAS сам по себе меняет видимое для всех состояние ресурса, или только порождает событие конфликта, на которое владелец процесса отдельно реагирует?» Первое → смешаны технический уровень версионирования и доменный уровень состояния.

## Границы

Общий паттерн для любой optimistic-concurrency схемы: отказ записи по версии — сигнал на уровне механизма согласования, не решение на уровне домена. Применимо там, где после проигрыша гонки возможны разные легитимные реакции (повтор, отказ, эскалация), а не одна предопределённая.
