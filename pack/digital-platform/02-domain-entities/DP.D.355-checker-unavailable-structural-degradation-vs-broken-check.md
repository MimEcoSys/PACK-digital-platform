# DP.D.355 — Деградация по конструктивной причине ≠ остановка по сбою

## Различение

| | Checker unavailable трактуется молча (неверно) | Checker unavailable как контракт (верно) |
|---|---|---|
| Причина недоступности | Не различается — любая причина = одно состояние | Входит в контракт: machine-readable причина (`reason=library_missing` и т.п.) |
| «Невозможно по конструкции этой среды» (напр., библиотеки нет на чистой установке) | Потребитель трактует как stop-condition наравне с реальным сбоем | Пропускается с явной пометкой «не проверялось» — деградация, не остановка |
| Реальный сбой (сеть, повреждённый файл и т.п.) | Может быть принят производителем за штатный пропуск (exit 0) | Остаётся stop condition — исключение не расширяется на другие причины |
| Контракт между производителем и потребителем статуса | Каждая сторона читает своё | Обе стороны читают один инвариант; тестируется с обеих сторон |

## Механизм

Два независимых случая за один день, один принцип:

1. **FMT #1196 (issue #1144).** Sync Gate bundle в чистой установке не находит библиотеку проверки свежести git-синка рабочей копии и честно отдаёт «degraded, exit 0» — физически невозможно в этой установке. Субагент-актуализатор читал тот же статус `checker_unavailable` как стоп-условие — ветка B Sync Gate молча не работала у ВСЕХ новых установок шаблона.
2. **FMT #1200 (issue #1155).** `mount_readonly_packs()` останавливал весь прогон экстрактора, когда ни один Pack не подключён из-за намеренных пропусков (Pack frozen / без origin) — без единого реального сбоя клонирования. Теперь WARN и продолжение с нулевым покрытием (с явной пометкой «свежесть не подтверждена»), а по-настоящему пустой workspace остаётся ERROR.

## Тест различения

«Checker-статус `unavailable`/`degraded` — это (а) проверка физически невозможна по конструкции ЭТОЙ установки/среды, или (б) проверка попыталась выполниться и не смогла?» (а) → пропустить с пометкой причины, продолжить. (б) → stop condition, не расширять исключение на другие причины того же статуса.

Дополнительно: «производитель статуса и его потребитель читают причину одинаково (по машинной строке, не по одному лишь коду возврата)?» Нет → drift между сторонами контракта неизбежен.

## Третий случай: «пропущено» в журнале квитанций публикации (РП-539 Ф21 Б5, 29.10.2026)

Плановый публикатор без сессии засорял журнал квитанций «потерями» и маскировал реальные. Эвристика «нет агента, значит автоматика» превращала бы любую настоящую потерю привязки к сессии в «пропущено». Исправление (коммит `087783829` в DS-my-strategy, пир-сессия 2026-10-29-16-wp539-convergence-b5-b4): исход `skipped` записывается только при явном объявлении вызывающего (`IWE_PUBLICATION_SESSIONLESS=1`), пустом `IWE_AGENT` и существующем охраннике isolate-push; без объявления или без охранника остаётся `failure`. Добавлены сценарии 6 и 7 теста журнала. Причина пропуска — машинная строка контракта на вызове, не вывод журнала. Масштаб засорения по данным сессии 2026-10-29-01 (факты сессии): запись «no bound publishing agent/guard» встречалась 379 раз на Маке (окно 22-29.10) и 261 раз на Цехе (окно в facts.md не указано). Это отдельный механизм от DP.D.331 (там сбой самой проверки): здесь решается, кто вправе объявить пропуск.

## Границы

Инвариант — `reason=library_missing` (или эквивалент) пропускает ТОЛЬКО ту конкретную проверку, для которой причина подтверждённо конструктивна; любая другая причина того же статуса `checker_unavailable` остаётся stop condition. Пропуск не означает «всё проверено» — вывод явно помечается как неполный.
