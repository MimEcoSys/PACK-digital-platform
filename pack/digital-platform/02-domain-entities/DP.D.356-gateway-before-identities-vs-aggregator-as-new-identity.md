# DP.D.356 — Шлюз-перед-идентичностями ≠ агрегатор-как-идентичность

## Различение

| | Шлюз ПЕРЕД самостоятельными идентичностями | Агрегатор КАК собственная новая идентичность |
|---|---|---|
| **Что объединяется** | Несколько уже самостоятельных, чужих друг другу сервисов/идентичностей | Несколько источников данных внутри ОДНОГО сервиса |
| **Ради чего** | Удобство клиента — не держать несколько подключений | Сервис сам решает fan-out как часть своей функции |
| **Атрибуция источника** | Размывается или теряется за прокси | Сохраняется явно на каждом результате |
| **Архитектурный статус** | Отвергнут | Нормальный, уже реализованный паттерн |
| **Пример на платформе** | (не реализуется) | Aisystant MCP (`gateway-mcp`): fan-out на `knowledge-mcp`, `digital-twin-mcp`, `checklist-mcp` и др. под одним именем шлюза |

## Почему важно

Оба устройства снаружи выглядят одинаково: «сервис обращается к нескольким другим серверам». Но решается разный вопрос. Шлюз-перед-идентичностями склеивает сервисы, которые уже были самостоятельными идентичностями (со своим именем, владельцем, контрактом) — ради удобства клиента, не трогая их природу; это стирает различимость источников и создаёт лишний слой косвенности без новой функции. Агрегатор-как-идентичность — это сам сервис, спроектированный как fan-out: он не склеивает чужие идентичности, а строит одну новую, которая честно называет, откуда взят каждый результат.

## Тест различения

«Источники, которые объединяет этот сервис, были самостоятельными идентичностями ДО объединения, и объединение сделано только ради удобства клиента (не завести N подключений)?» Да → шлюз-перед-идентичностями, архитектурно отвергнут. «Сервис с самого начала спроектирован как одна новая идентичность, которая внутри себя обращается к нескольким источникам и явно атрибутирует каждый результат?» Да → агрегатор-как-идентичность, допустимый паттерн.

## Прецедент

Различение явно сформулировано при проектировании единого реестра MCP-серверов платформы (`DP.MAP.004`, WP-589 Ф23, пир-сессия Claude+Kimi+Codex 2026-10-08-05-mcp-gateway-tserenov-split) как критерий для колонки «Тип» в реестре: агрегатор = ДА, самостоятельный источник без фан-аута = НЕТ. На платформе паттерн агрегатора-как-идентичности реализован как минимум дважды: прод Aisystant MCP (`gateway-mcp`, собирает `knowledge-mcp`/`digital-twin-mcp`/`checklist-mcp` и другие backend-сервисы под одним именем с сохранённой атрибуцией) и план «Российский персональный MCP» (`mcp.system-school.ru`), переиспользующий тот же шлюзовой код для российского контура.

## Границы

Не описывает техническую реализацию fan-out (протоколы, таймауты, retry) — только архитектурный статус двух устройств по критерию «были ли источники самостоятельными идентичностями до объединения и ради чего объединены». Не относится к простому прокси ровно одного источника (это не агрегация ни в каком смысле).
