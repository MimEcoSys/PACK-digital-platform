# DP.D.360 — Маршрутизация по типу решения ≠ маршрутизация по каналу

## Различение

| | По типу решения | По каналу/типу события |
|---|---|---|
| **Критерий выбора исполнителя** | Обязательное по сроку → детерминированный сервис; инициативное → вендорский голос | Какой канал доставки или какой тип сообщения — переменная величина |
| **Устойчивость к смене канала** | Переносится без изменений при смене канала доставки | Ломается при любом изменении канала — приходится перепроверять правило |
| **Надёжность** | Обязательства со сроком получают проверенный сквозным тестом механизм | Жёсткое деление по типу сообщения «передаёт надёжность механизму, чей контракт доставки не проверен» |

## Механизм

Секретарь (DP.ROLE.098, РП-389) — одна сущность с двумя отправителями: детерминированный сервис `secretary.py` и вендорский голосовой канал. Решение: детерминированный сервис продолжает сам исполнять обязательные по сроку напоминания (проверено живьём, доставка до 5 минут); вендорский голос берёт только необязательные инициативные сообщения — и только после того, как сквозной тест доставки пройдёт живьём, включая проверку отсутствия дубля при конкуренции двух отправителей за один момент. Защита от дубля — не булев флаг «канал занят» (оставляет гонку между двумя отправителями), а атомарная аренда в общем реестре отправок: единая точка, через которую проходят оба отправителя перед отправкой.

## Тест

«Критерий, который решает, какой из двух отправителей обрабатывает сообщение, — тип решения (обязательное по сроку/инициативное) или канал доставки/тип события?» Первое переносится при смене канала, второе — нет.

Отдельно: «Защита от дубля при двух конкурирующих отправителях — это булев флаг, который каждый читает перед отправкой, или атомарная операция аренды в общем реестре?» Флаг оставляет гонку (оба могут прочитать «свободно» одновременно); аренда в общем реестре — нет.

## Fix / переносимый принцип

При двух кандидатах на одну роль делить полномочия по типу решения, а не по каналу доставки — канал меняется, тип решения нет. Каждая функция сервиса размечается на политику (что и когда решить) и механику (как исполнить): переносить можно политику, механику с подтверждённой надёжностью лучше оставить на месте. Детерминированный таймер дешевле LLM на каждый тик, а привязка всей механики доставки к одному вендору — отдельный риск.
