# DP.D.361 — Новый писатель использует существующий контракт источника ≠ отдельный канал

## Различение

| | Подключение к существующему контракту кандидата | Отдельный канал/эндпоинт |
|---|---|---|
| Полномочия писателя | Только создание кандидата; состояние, статус и отправка принадлежат потребителю | Права и границу доверия нужно определить отдельно |
| Условие выбора | Контракт подходит новому писателю, а узкие права проверены | Существующий контракт не покрывает нужные операции или ограничения |
| Проверка риска | Происхождение записи, права и отзыв доступа проверяются для нового писателя | Проверяются новый интерфейс и его полномочия |

## Механизм

В проектном решении DR-03 для секретаря новый вендорский писатель создаёт кандидата в общем формате. Единственный потребитель (`secretary.py`/`tick()`) управляет состоянием, статусами и транспортом. Писатель не читает `state.enc`, не меняет статус доставки и не отправляет сообщения напрямую. Поле `source_type` не привязывает формат к одному вендору.

Переиспользование контракта уменьшает число новых интерфейсов, но само по себе не доказывает равенство рисков для разных источников. До допуска писателя нужно проверить фактическое ограничение операций созданием кандидата, подтверждение авторства/происхождения записи и возможность отозвать доступ. Эти проверки — условия применения различения; исходный DR-03 фиксирует проектный выбор, а не доказательство реализации всех контролей.

## Тест

Может ли новый писатель через свои фактические права изменить состояние, статус или вызвать отправку, минуя потребителя? Если да, заявленная узкая граница не выдержана. Если нет, дополнительно проверить происхождение кандидата и отзыв доступа. Только после этого сравнивать подходящий существующий контракт с новым каналом.
