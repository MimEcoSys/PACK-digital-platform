# DP.D.381 — Остановка в ожидании человека ≠ успешное завершение

## Различение

У прогона конвейера, в котором есть шаг человека, три исхода, а не два.

| Исход | Что произошло | Что нужно от надзирающей службы |
|---|---|---|
| Успех | результат получен | ничего |
| Сбой | результата нет из-за ошибки | цепочка отказа: запись в сводку, повтор, запасная доставка |
| Ждёт человека | прогон штатно остановился на шаге человека, результата ещё нет | при человеке рядом — ничего; в прогоне без присмотра — та же цепочка отказа |

Код выхода различает только «ноль» и «не ноль». Остановка на шаге человека — не ошибка программы, поэтому она легко уходит наружу нулём. Для прогона без присмотра это неверно: служба выглядит здоровой, цепочка отказа не запускается, а результата нет.

## Случай-источник

Ночное открытие дня (РП-568 Ф12 П4). Программа запуска процессов завершалась кодом 0, когда прогон останавливался на блокирующем шаге пилота. Ночная обёртка передавала этот 0 дальше. Служба считалась успешной, и её цепочка отказа (строка в сводку → один повтор → запасная доставка плана) не запускалась. Сообщение «сам продолжить не могу» при этом уходило в чат сразу.

Исправление (git commit `b07084635c` в DS-my-strategy):

1. Обёртка прогона без присмотра читает состояние прогона из его карточки, а не из вывода программы запуска. При исходе «ждёт человека» она публикует результат как прежде и завершает службу отдельным ненулевым кодом (в источнике 3). Код общей программы запуска не менялся.
2. Состояние не прочиталось — считается тем же исходом с причиной «неизвестно».
3. Причина остановки попадает в текст запасного сообщения через файл-отметку. Отметка стирается в начале каждого прогона и пишется только после успешной публикации, чтобы другой сбой не получил чужую причину.
4. Все сообщения, завершающие прогон, идут через одну функцию: ночью при читаемой сводке — только строка в сводку, иначе сразу в чат. Иначе на один сбой пришло бы два сообщения.
5. До выкладки проверено, что служба не считает новый код успехом и что повтор осмыслен: он запускает новый прогон, а не упирается в «уже выполняется».

## Тест

«Что увидит надзирающая служба, если прогон без присмотра остановился на шаге человека: успех или отказ?» Успех → повтор и запасная доставка не сработают.

«Откуда обёртка знает, что прогон ждёт человека: из записанного состояния или из текста вывода? Что она делает, если состояние не прочиталось?» Из вывода или «считаю успехом» → исход может потеряться.

## Границы

- Различение относится к прогону без присмотра, у которого есть цепочка отказа. В прогоне при человеке остановка на его шаге — обычное состояние, тревога не нужна.
- Один случай и одна среда (служба по расписанию с цепочкой отказа). Число 3 — значение источника, не норма.
- Новый код выхода меняет поведение всех, кто его читает; опись читателей и проверка на стыке — по DP.M.609.

## Отличие от соседей

- DP.FM.591 — код 0 при потерянной записи: звено скрывает ошибку. Здесь ошибки нет: остановка штатная, но в прогоне без присмотра она требует той же цепочки, что и сбой.
- DP.FM.230 — ошибка инициализации уходит обычным выходом, и перезапуск не срабатывает. Здесь обычный выход общей программы честен; переводить исход в отказ должна обёртка прогона без присмотра.
- AR.325 — обратная сторона: отказ по политике не должен выглядеть сбоем и получает свой код для тихого пропуска. Здесь остановка не должна выглядеть успехом и получает свой код для запуска цепочки отказа.
- DP.FM.396 — аварийный путь уведомления в обход общего слоя; пункт 4 исправления закрывает тот же риск для сообщений, завершающих прогон.
- DP.FM.747 — обратная ошибка: намеренный ненулевой выход принят за аварию. Новый код исхода «ждёт человека» должен быть известен всем его читателям, иначе он сам станет таким ложным сигналом аварии.
- DP.ARCH.001 §9.4 — другое следствие того же состояния: запись задания, ждущая пилота, не занимает место в лимите исполнителей. Здесь — каким исходом прогон без присмотра сообщает об этом состоянии.
