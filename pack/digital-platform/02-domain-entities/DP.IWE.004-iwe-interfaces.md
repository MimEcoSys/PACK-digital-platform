# Интерфейсы IWE — различения клиентов

## 1. Определение

IWE-интерфейс — тонкий клиент, через который пользователь получает доступ к знаниям, Цифровому Двойнику и инструментам платформы. Интерфейс сменная деталь (DP.ARCH.001 принцип 15: Multi-surface). Бизнес-логика живёт в MCP-серверах, не в клиенте.

## 1.1. Сборка сеанса (уточнение 2026-09-05)

Интерфейс — точка входа человека, не точка сборки. Между интерфейсом и Gateway всегда стоит **агент** — рантайм, который в конкретном сеансе связывает три вещи: сменную модель (LLM-ядро без состояния между сеансами), IWE пользователя (среда, которая переживает сеанс) и сервисы Aisystant, доступные через Gateway.

Агент варьируется по интерфейсу: в боте и на iwe.system-school.ru — платформенный агент, вызывающий модель от имени Aisystant; в claude.ai — агент Anthropic, вызывающий модель напрямую по подписке пользователя; в Cursor/Codex/VS Code — пользовательский или сторонний агент на машине пользователя. Во всех случаях Aisystant подключён как сервис через Gateway, а не как то, что вызывает модель.

Смена интерфейса или модели не меняет среду: IWE и подключение к сервисам Aisystant остаются теми же независимо от того, через какого агента человек вошёл в сеанс. Источник и полный разбор → DP.IWE.001 §1.2.

## 1.2. Окно, агент, дом — тонкий клиент «без своего» (уточнение 2026-10-03)

Источник: концепция удалённого тонкого клиента РП-262 (`DS-my-strategy/inbox/WP-262/CONCEPT-remote-thin-client-2026-10-03.md`, пир-сессия Claude + Kimi + Codex, утверждена пилотом 03.10.2026). Граница слоёв — ADR-IWE-014 v3.4.

**Три слова, которые нельзя смешивать.** **Окно** (интерфейс) — точка входа человека. **Агент** (рантайм, §1.1) — собирает сеанс. **Дом** — слой с источником истины и правилами доступа: открытое ядро (Open MCP, без аккаунта, только чтение одобренного корпуса), управляемая платформа (Aisystant MCP, от имени пользователя по Ory), личный IWE (локально агентом на машине; через проекцию `personal_*` по акту «доверить»; кандидат — собственный MCP владельца).

**Тонкость — требование к окну:** у окна нет ничего своего из данных IWE — истины, личных правил, доменной логики, права прямой записи в доверенное хранилище (DP.D.210). Собственная память и инструменты помощника вендора допустимы, но важные результаты и договорённости не остаются единственной копией внутри помощника.

**Класс — у конкретного режима исполнения агента** (не у бренда и не у места запуска самого по себе; учитываются фактические права и передача данных):

| Класс | Режим исполнения агента | Требование |
|---|---|---|
| А. Вендорский | облако вендора (claude.ai, ChatGPT, Codex App) | агент тонкий; память вендора — не источник истины |
| Б. Платформенный | серверы платформы (бот, стенд LibreChat) | агент тонкий: без доменной логики и без хранения полномочий в клиенте |
| В. Собственный | машина или сервер пользователя (Claude Code, Codex CLI, Cursor, Hermes, службы и раннеры) | доверенный представитель личного IWE: разрешено то, что разрешено самому IWE; состояние производное, с источником и давностью |

Одно приложение может иметь режимы разных классов (Codex App — А, Codex CLI — В). **Роль ≠ исполнитель:** например, роль Секретаря (DP.ROLE.098) может исполнять собственная служба (класс В) или помощник вендора (класс А); требования к данным одинаковы.

**Серверный режим.** Служба личного IWE может работать с личным IWE на сервере без открытого ноутбука; экземпляр собственный или доверенный (ADR R10). Это кандидат в спецификацию IWE (решение — РП-552), не обязательное условие: сохранность данных при смене окна требуется всем классам, непрерывность работы службы — только серверному варианту.

**Тест замены окна.** Окно исчезло — потеряно только незаписанное в чате. Проверяется протоколом continuity-теста (РП-512) и метрикой РП-592, не декларацией.

**Типовые нарушения:** окно класса Б само обменивает код OAuth на токены и хранит их у себя (бот, возвраты Ory/ЦД/GitHub/Calendar/Linear/WakaTime — до выноса в сервис подключений); помощник при отказе персонального входа повторяет закрытый запрос через Open MCP.

## 3.1. Матрица «окно × дом» — полномочия по домам (срез 2026-10-03)

Дополняет таблицу §3 (возможности клиента) осью «какие дома доступны окну и по какому механизму». Клетка — факт с датой или «не проверено». Способы подключения и кнопки ведёт отдельная матрица РП-589 Ф1, здесь не дублируются.

| Окно (класс) | Открытое ядро (Open MCP) | Платформа (Aisystant MCP) | Личный IWE локально | Служба личного IWE на сервере | Личный MCP владельца |
|---|---|---|---|---|---|
| Бот `aist_me_bot` (Б) | не развёрнут (РП-581, прототип) | да, Bearer Ory | — | — | кандидат, не реализован |
| claude.ai (А) | не развёрнут | да, коннектор OAuth (личное подключение) | — | не проверено | кандидат |
| ChatGPT (А) | не развёрнут | личное подключение есть, публичной карточки нет (РП-589, 26.09) | — | не проверено | кандидат |

| Telegram-канал Секретаря (окно класса В) | — | — | — | да, сводка и команды (РП-389, 03.10); свободный диалог включён, польза не подтверждена | — |

«—» означает, что механизм для этого окна не предусмотрен концепцией. Вход окон класса А в Aisystant MCP обслуживает сам шлюз как сервер авторизации поверх Ory (хранит и обновляет refresh-токены Ory этих клиентов) — это не «подключение» и не нарушение «тонкости»; сервис подключений РП-262 Ф3б держит только делегированные токены платформы для вызова других систем от имени пользователя. Матрицу обновлять фактами по мере приёмок РП-581 (Open MCP), РП-589 (помощники), РП-389 (Секретарь), РП-590 (личный MCP).

## 4. Режим подключения

| Интерфейс | Как подключается к Gateway |
|-----------|--------------------------|
| Бот | HTTP-запросы с Bearer token (Ory) |
| Браузер (claude.ai) | MCP Connector + OAuth |
| Codex (OpenAI) | config.toml `url` + `codex mcp login` (OAuth) |
| IDE (Cursor) | mcpServers конфиг + OAuth |
| VS Code | .claude/settings.json + OAuth |
| Antigravity (Gemini) | ⚠️ MCP OAuth не поддерживается (known limitation). Workaround: ручной Bearer token или прокси (Rube) |

## 5. Принцип: бот = точка входа

Бот — самый доступный интерфейс (Telegram, нулевая установка). Роль бота:

1. **Точка входа** — новый участник начинает здесь
2. **Онбординг** — бот помогает подключить остальные клиенты (claude.ai, Cursor, Codex, GitHub)
3. **Мобильный доступ** — быстрый вопрос к знаниям с телефона
4. **Консультант** — отвечает на вопросы про IWE, используя знания из Gateway

Бот НЕ заменяет другие интерфейсы — он ведёт к ним. Сложная работа (протоколы, git, файлы) = VS Code. Работа со знаниями из браузера = claude.ai. Код + знания = Cursor/Codex.

## 6. Что бот может и не может

| Может | Не может |
|-------|----------|
| Поиск по платформенным знаниям (L2) | Запись в личные репо |
| Чтение личных знаний (L4) | Удаление из личных репо |
| Цифровой Двойник (чтение/запись) | Git-операции |
| Роли (Навигатор, Диагност) | Протоколы ОРЗ |
| Онбординг (инструкции по подключению) | Выполнение bash/скриптов |

Ограничение на запись через бот — осознанное решение. Запись = ответственное действие, требующее контекста (файловая структура, commit message). Бот для быстрых вопросов, не для управления знаниями.
