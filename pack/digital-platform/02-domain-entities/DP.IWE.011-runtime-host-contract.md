# DP.IWE.011 — Контракт хоста для IWE

> IWE = дистрибутив (слой 4). Для работы он требует от хоста (слой 3) выполнения минимального контракта.
> Этот документ описывает **что любой хост ОБЯЗАН предоставить**, чтобы ОРЗ-протоколы IWE работали без изменений.

---

## 1. Назначение контракта

**Проблема:** Сейчас протоколы open/work/close написаны под Claude Code напрямую. При смене хоста (CC → Hermes → бот) протоколы ломаются, потому что используют конкретные инструменты (TodoWrite, ScheduleWakeup), хук-события (PostToolUse/Stop) и переменные окружения (CLAUDE_TASK_ID).

**Решение:** Специфицировать минимальный HOST CONTRACT — абстрактный интерфейс, который любой хост реализует в своём адаптере. IWE-протоколы пишутся против контракта, не против конкретного хоста.

**Аналогия:** POSIX для Unix. Каждый хост реализует POSIX-совместимый слой; программы (IWE-протоколы) работают на любом POSIX-хосте.

---

## 2. Обязательный интерфейс (HOST CONTRACT v0.1)

### A. Tool API — инструменты пилота

Хост ОБЯЗАН предоставить следующие инструменты или их функциональные эквиваленты:

| Инструмент | Назначение | Текущая реализация (CC) | Требования к эквиваленту |
|------------|-----------|------------------------|--------------------------|
| `task_tracker.create(tasks[])` | Создать список задач | `TodoWrite` с массивом объектов | Атомарно создаёт N задач; возвращает список ID |
| `task_tracker.update(id, status)` | Обновить статус задачи | `TodoWrite` с обновлёнными полями | `status ∈ {pending, in_progress, completed}` |
| `task_tracker.list()` | Получить текущий список | `TodoWrite` (чтение) | Возвращает все незакрытые задачи |
| `scheduler.schedule_at(ts, msg)` | Запланировать напоминание | `ScheduleWakeup` | Доставляет сообщение в канал пилота в момент `ts` |
| `fs.read(path)` | Читать файл | `Read` | Возвращает содержимое файла; ошибка если не существует |
| `fs.write(path, content)` | Записать файл | `Write` | Перезаписывает целиком; создаёт директории |
| `fs.edit(path, old, new)` | Точечная правка файла | `Edit` | Находит `old` в файле, заменяет на `new`; ошибка если не уникально |
| `shell.exec(cmd)` | Выполнить shell-команду | `Bash` | Возвращает stdout+stderr+exit_code |
| `agent.delegate(model, prompt)` | Делегировать субагенту | `Agent` tool | Запускает LLM-агент с изолированным контекстом; возвращает ответ |
| `skill.invoke(skill_id, args)` | Вызвать скилл IWE | `Skill` tool | Ищет SKILL.md по `skill_id`, исполняет инструкции |

**Замечание:** хост НЕ обязан реализовывать инструменты с теми же именами. Достаточно предоставить функциональный эквивалент, зарегистрированный в адаптере (§4).

### B. Lifecycle Events — события работы агента

Хост ОБЯЗАН эмитить следующие события; IWE-хуки подписываются на них:

| Событие | Когда возникает | Обязательный payload | CC-эквивалент |
|---------|----------------|---------------------|---------------|
| `SESSION_START` | Начало новой сессии пилота | `session_id`, `agent_model`, `timestamp` | `UserPromptSubmit` |
| `SESSION_END` | Завершение сессии (явное или по таймауту) | `session_id`, `duration_sec`, `exit_reason` | `Stop` |
| `TOOL_EXECUTED` | После выполнения любого инструмента | `session_id`, `tool_name`, `result_summary`, `timestamp` | `PostToolUse` |

**Расширенные события (опциональные для v0.1, обязательные для v1.0):**

| Событие | Когда возникает | Payload |
|---------|----------------|---------|
| `TASK_CREATED` | Вызов task_tracker.create | `task_ids[]`, `session_id` |
| `TASK_COMPLETED` | Статус задачи → completed | `task_id`, `session_id` |
| `SKILL_INVOKED` | Начало выполнения скилла | `skill_id`, `session_id` |

### C. Environment Variables — переменные окружения

Хост ОБЯЗАН предоставить следующие переменные в окружении хуков и скриптов:

| Переменная | Тип | Описание | CC-реализация |
|------------|-----|----------|---------------|
| `IWE_RUNTIME` | string | Имя хоста: `claude-code` \| `hermes` \| `bot` \| `headless` | Устанавливается CC-адаптером как `claude-code` |
| `AGENT_SESSION_ID` | string | Уникальный ID текущей сессии | Берётся из payload CC-хука или генерируется |
| `AGENT_TASK_ID` | string\|empty | ID задачи, если сессия запущена через task-dispatcher | `$CLAUDE_TASK_ID` |
| `AGENT_MODEL_ID` | string | Идентификатор модели LLM | `$CLAUDE_AGENT_ID` или `claude-sonnet-4-6` |
| `IWE_STATE_DIR` | path | Директория для state-файлов хуков | `~/.iwe/state/` (дефолт) |

### D. Configuration — конфигурация

Хост ДОЛЖЕН предоставить механизм для:

1. **Регистрации хуков на события** — хук = shell-скрипт, вызываемый при событии типа B.
   - CC: `settings.json → hooks → [{matcher, hooks: [{type, command}]}]`
   - Hermes: свой формат (TBD в Ж-Ф4)

2. **Регистрации скиллов** — скилл = директория с SKILL.md и точкой входа.
   - CC: `.claude/skills/<id>/SKILL.md` + `/slash-команда`
   - Hermes: своя конфигурация (TBD)

## 4. Адаптер — структура

Каждый хост поставляет **адаптер** — тонкий слой, который:
1. Устанавливает переменные окружения (§C) при старте сессии
2. Регистрирует хуки на нативные события хоста, транслируя в Lifecycle Events (§B)
3. Регистрирует алиасы инструментов для Tool API (§A)

**Адаптеры:**
- `DP.IWE.011-adapters/claude-code-adapter.md` — референсная реализация (Ж-Ф3, готово к написанию)
- `adapters/hermes.md` — после Встречи 20 с Андреем (Ж-Ф4)
- `adapters/bot.md` — по мере необходимости
- `adapters/headless.md` — по мере необходимости

**Принцип:** адаптер НЕ меняет протоколы IWE. Адаптер — это клей между нативным API хоста и контрактом IWE.

## 5. Контракт ОРЗ-протоколов

После внедрения Host Contract протоколы open/work/close ДОЛЖНЫ писаться через абстрактный API:

```
# Было (CC-специфично):
TodoWrite: [{content: "шаг 1", status: "pending"}]

# Должно быть (абстрактно):
task_tracker.create([{content: "шаг 1", status: "pending"}])
```

**Переходный период:** CC-адаптер (Ж-Ф3) транслирует `task_tracker.*` → `TodoWrite`, `scheduler.*` → `ScheduleWakeup`. Протоколы продолжают работать в CC без изменений.

**Правило резолюции (закреплено пир-сессией WP-564, 11.09.2026, Claude+Codex).** Абстрактные операции (`task_tracker.*`, `scheduler.*` и т.п.) резолвятся ИСКЛЮЧИТЕЛЬНО через адаптер, соответствующий текущему `$IWE_RUNTIME`. Прямой вызов host-native инструмента (`TodoWrite`, `ScheduleWakeup` и т.п.) в тексте протокола или скилла в обход адаптера — нарушение контракта; конкретное имя инструмента хоста допустимо только внутри самого файла адаптера (`DP.IWE.011-adapters/*.md`).

**Пошаговые инварианты `task_tracker.*` для многошагового протокола (Day/Week Open, Close).** Один прогон протокола = N единиц отслеживания (по одной на шаг алгоритма), не одна на весь прогон:
1. хост-раннер верно распознан (`$IWE_RUNTIME` соответствует фактическому хосту);
2. перед первым содержательным шагом создан полный список шагов;
3. каждый шаг проходит `pending → in_progress → completed` либо помечается `blocked` (не пропускается молча);
4. одновременно не более одного шага в статусе `in_progress`;
5. следующий шаг не начинается до терминального статуса предыдущего (`completed`/`blocked`);
6. нет вызова host-native инструмента в обход адаптера;
7. прогон достигает предусмотренной протоколом контрольной точки (не обрывается раньше);
8. по завершении прогона число units со статусом `completed`/`blocked` равно числу шагов алгоритма.

Эти 8 инвариантов — единственный обязательный список для проверки соответствия (§9) в любом хосте, включая headless; §9 не дублирует их отдельным перечнем.

## 8. Headless-режим (claude -p)

**Ключевой инсайт:** хуки IWE (PostToolUse/Stop из settings.json) срабатывают при `claude -p` без изменений конфигурации. Headless-режим = полноценный runtime-хост по DP.IWE.011.

**Практические следствия:**
- `TOOL_EXECUTED` (PostToolUse) эмитируется в headless-режиме — хуки получают события штатно
- `SESSION_END` (Stop) эмитируется при завершении `claude -p` — close-хуки выполняются
- TaskTracker в headless реализуется через файловую систему (tasks/*.md) вместо встроенного TodoWrite
- Scheduler в headless = внешний cron/launchd с параметром `due:` в task-файле

**См. также:** DP.SOTA.028 (Claude CLI headless hook inheritance), DP.D.083 (Persistent TaskTracker ≠ Ephemeral TodoWrite).

Если считать единицей отслеживания 4 запрошенных шага алгоритма (как того требует §5 и headless-adapter.md таблица A) — агент создал ровно 4 файла и все 4 отметил `completed`, то есть **на уровне поведения агента инвариант выполнен** (4=4) — но см. находку ниже: эти 4 файла никогда не попадают в официальную (закоммиченную) историю.

**НАХОДКА (эмпирически подтверждена прогоном, не спекуляция по коду) — ПОЧИНЕНО (WP-564 Ф3, 12.09.2026, пир-сессия Claude+Kimi+Codex):** агент действительно создал 4 файла-шага (`wp564-smoke-step-01.md` … `-04.md`) и файл журнала прямо в рабочей копии — это ровно то поведение, которое `headless-adapter.md` таблица A обещает («создаётся... внутри `claude -p` через `Write`»). Но диспетчер (`iwe-agent-dispatcher.py`, комментарий «Dispatcher is the single writer of result files», RC3-fix — номер строки сдвинулся после вставки фикса Ф3, искать по тексту комментария) сразу после возврата `claude -p` делал `git fetch` + `git reset --hard origin/<branch>`, а затем стейджил только два жёстко прописанных пути — `TASK-*.md` и `RESULT-*.md`, из-за чего файлы, созданные агентом, оставались untracked и терялись.

**Фикс:** добавлена функция `_collect_extra_task_files()` (safety-net, вызывается перед финальным `commit_and_push` в LLM-ветке `process_task()`) — подбирает любые untracked/modified `.md` в `inbox/agent/tasks/` (кроме `task_path`/`result_path`, кроме удалений), без фильтрации по `id`/`task_id` (проверено эмпирически: у внешней задачи и у файлов-шагов разные поля frontmatter, фильтр по значению не совпал бы).
