# DP.KR.002 — Пользовательская карта маршрутизации знаний

## 1. Определение

**DP.KR.002** — карта, отвечающая на вопрос «куда положить X» для любой единицы материала пользователя IWE. Для каждого онтологического класса материала определяет: дом (где хранится), режим (как IWE с ним работает) и обоснование.

**Отличие от DP.KR.001:** KR.001 — агентская карта (~22 платформенных типа: Pack, DS, memory, skills). KR.002 — пользовательская: разнотипный материал жизни и работы пилота (код, ресёрчи, документы, инвентарь, таски).

## 2. Таксономия материала — 4 класса + Praxis

> **Первичная ось:** онтологический тип объекта (стабильная, не зависит от реализации IWE).
> **Производная ось:** режим IWE (для карты маршрутизации, меняется с реализацией).

### Класс 1: Активное знание
- **Онтология:** истинностное утверждение о мире — универсальное, применимое через инстанции (паттерн, метод, концепт).
- **Режим:** `index` — граф отвечает на семантические вопросы.
- **Дом:** Pack (личный домен) / Base (универсальное).
- **Тест:** «Применимо ли это к другим системам такого же типа?»

### Класс 2: Состояние системы
- **Онтология:** текущее состояние КОНКРЕТНОГО артефакта/системы под контролем пользователя. Particular — про эту систему, не про «такие системы вообще».
- **Режим:** `pointer` синхронизируемый (DP.SC.022 — индексация личных репо).
- **Дом:** DS-репозиторий системы (git).
- **Тест:** «Про конкретную систему или про класс систем?»

### Класс 3: Факт мира
- **Онтология:** событие или юридический/физический факт — внешний, пользователем не изменяется, fiduciary nature.
- **Режим:** `pointer` статический (не анализируем содержимое) или `external` (целиком снаружи, только упоминание).
- **Дом:** личный Vault (копия документа) или внешнее хранилище (только адрес).
- **Тест:** «Могу ли я это изменить? Нет → факт мира.»

### Класс 4: Субъективная оценка
- **Онтология:** знание, ещё не прошедшее рефлексивную обработку — сырые заметки, наблюдения, черновая рефлексия. Не определяется через «личная позиция» (оформленная декларация — устав, миссия, зафиксированная позиция — не подходит под класс 4, даже если она сугубо личная и никуда не переносится: см. класс 1/2, дом определяется формой, не приватностью). Потенциально пересматриваемая и расширяемая.
- **Тест:** «Это уже осмыслено и оформлено, или ещё сырой материал?» Оформлено (устав, декларация принципов, зафиксированное решение) → НЕ класс 4, даже если не предназначено для других систем.
- **Режим:** `pointer` с `indexing_intent: candidate` — указатель, флагируется кандидатом в класс 1.
- **Дом:** внешний (Notion/заметки) + карточка-указатель в IWE.
- **Upgrade-путь:** класс 4 → класс 1 при Pack-формализации (FPF-форма + систематическое изучение).
- **Согласовано с типом 2.4** (`CONCEPT-data-pipelines.md`, WP-476) — единое определение в обоих документах (пир-сессия Claude+Kimi 22.07, `DS-my-strategy/sessions/2026-07/22/2026-07-22-03-triage-476-455-448/report.md`).

### Praxis — вне таксономии
Таски, планы, РП — обязательства агента, а не знание о мире (Epistemology ≠ Praxis). IWE знает о задаче через указатель на инструмент (Linear/inbox-реестр РП). Управление задачами — отдельный контур.

### Карантин — вне оси
Чужие PII, секреты, платёжные данные — не класс, а блокировка (fail-closed, наследует И1 DP.SC.055). Неуверенность «не карантин ли это» → карантин.

## 3. Карта: класс → дом + режим

| Класс | Дом | Режим | Обоснование |
|---|---|---|---|
| 1 Активное знание (личный домен) | `PACK-<домен>` | `index` | Форма FPF обязательна; граф отвечает содержанием |
| 1 Активное знание (универсальное) | Base (FPF/SPF) / платформенные Pack | `index` | Методологический канон |
| 2 Состояние системы (код) | `DS-IT-systems/<repo>` | `pointer` sync (DP.SC.022) | Про эту систему; git = SoT, IWE синхронизирует |
| 2 Состояние системы (архитектура экосистемы) | `DS-ecosystem-development` | `pointer` sync | Дизайн этой системы, не методология |
| 3 Факт мира (юридический) | личный Vault / внешнее хранилище | `pointer` static | Fiduciary, содержимое не анализируем |
| 3 Факт мира (физический: инвентарь) | внешний (Notion/список) | `external` | Нет потребителя содержимого в IWE; только адрес |
| 4 Субъективная оценка (ресёрчи) | внешний + карточка-указатель в IWE | `pointer` + `indexing_intent: candidate` | Кандидат в класс 1; upgrade через Pack-формализацию |
| Карантин (чужие PII/секреты) | вне индекса | blocked (вне оси) | Fail-closed (DRR WP-483, И1 DP.SC.055) |
| Praxis (таски) | Linear / inbox-реестр РП | `pointer` на инструмент | Не знание; контур управления задачами |

## 4. Когда принимается routing-решение

Ось «когда решение» ортогональна оси «какой режим». Оба подхода легитимны:

- **Curate-at-capture:** решение о месте в момент захвата. Обязателен для класса 1 (форма Pack требует решения сразу) и карантина (fail-closed до любого сохранения).
- **Store-everything, search-later:** сначала указуемая запись, индексация ленивая по запросу. Легитимен для класса 4: не известно, что понадобится → `pointer + candidate`, индекс при первом реальном запросе.
- **Граница:** store-everything не отменяет карантин (PII третьих лиц — никогда) и не делает fiduciary-факты индексируемыми.

**Wire-совместимость:** режимы `index | pointer | external` — одна словарная проекция на две системы (Разметчик размечает базу по 2.1–2.4; DP.KR.002 маршрутизирует новый материал по классам).

## 6. Vault — разрешение натяжения

- **Было:** «Vault = хранилище read/write/find, привязанное к проекту/команде».
- **Решение:** Vault — интерфейсный контракт (read/write/find + owner-контекст). Личный Vault = тот же контракт, owner=user. Pack ортогонален Vault: Pack задаёт форму (FPF), Vault — инфраструктуру доступа.
- **Подтверждено:** ArchGate WP-483 Ф0 (13.07, DRR-storage-abstraction) — read/write/find поверх Vault со сменными адаптерами прошёл ЭМОГССБ.

## 7. Границы применения

**Применима:** при любом новом материале пользователя — агент спрашивает «какой класс», карта даёт дом + режим.

**Не применима:** к платформенным артефактам (DP.KR.001), к разметке существующей базы (Разметчик WP-483, DP.SC.055), к управлению задачами (Praxis-контур).

## 8. Стадии конвейера после размещения

Эта карта отвечает на вопрос «куда положить» (дом + режим) в момент создания материала. Что происходит с материалом дальше — проверка, свежесть, сохранность, потребление — задаёт отдельная стадийная модель [[DP.ARCH.010]] (С1-С9), владелец WP-476. Ось этой карты не переопределяется: DP.ARCH.010 работает поверх уже выбранного дома, не выбирает его заново.
