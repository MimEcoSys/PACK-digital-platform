# Принцип триады учёт-доступ-аудит (DP.KR.030)

## 1. Определение

**Триада учёт-доступ-аудит** — принцип организации институционального контроля: три функции, которые необходимо структурно разделить, чтобы контроль работал без конфликта интересов.

| Функция | Фокус | Задача | Инвариант |
|---------|-------|--------|-----------|
| **Учёт** | Что происходит? | Фиксировать события, состояния, транзакции | Полнота + append-only (нет удалений/правок) |
| **Доступ** | Кто что видит? | Управлять правами на чтение и запись к ресурсам | Минимальные привилегии + явное разрешение |
| **Аудит** | Соблюдаются ли правила? | Проверять соответствие учёта и доступа нормативу | Методологическая независимость + read-only к проверяемому |

> Этот файл (KR.030) — foundation триады: принцип разделения трёх функций. KR.031–033 = refinement-принципы каждой ветки; создаются при отдельном РП по необходимости (см. «Deferred refinement» §9).

## 2. Проблема

Без явного разделения три функции естественно «слипаются» в одну роль:
- Роль, которая **ведёт учёт**, хочет сама же **ограничивать доступ** к своим данным.
- Роль, которая **управляет доступом**, заинтересована в **положительном аудите**.
- Роль, которая **аудирует**, при совмещении с учётом проверяет сама себя.

Результат слипания: аудит теряет независимость, учёт — полноту, доступ — непредвзятость. Система переходит из «Парламента» (три независимых контроля) в «Президента» (один агент всё видит и всё контролирует). Подробнее: distinctions.md «Парламент-модель ≠ Президент-модель».

**Конкретная проблема IWE (исходная):** До WP-224 роли R23-R26 (VR-контроль) не были отделены от операционных ролей (R8 Синхронизатор, R11 Наладчик бота). Аудитор мог запускаться тем, чьи артефакты проверяет. Учёт событий (Activity Hub) и управление доступом к нему жили в одном сервисе без явного разделения.

## 3. Принцип (ядро триады)

**Триада — не иерархия, а три независимые оси контроля:**

```
       ┌─────────────────────────────────────────┐
       │    Операционный слой                     │
       │  R8 Синхронизатор, R11 Наладчик бота, R6 ...  │  ← создаёт, изменяет
       └──────────────────┬──────────────────────┘
              ↓ события/логи     ↑ audit-query
       ─────────────────── граница контроля ──────
       ┌──────────────────────────────────────────┐
       │              Контрольный слой             │
       │  ┌─────────┐   ┌──────────┐  ┌─────────┐ │
       │  │ Учёт    │   │ Доступ   │  │ Аудит   │ │
       │  │ KR.031  │   │ KR.032   │  │ KR.033  │ │
       │  │ «что?»  │   │ «кто?»   │  │ «верно?»│ │
       │  └─────────┘   └────┬─────┘  └─────────┘ │
       └──────────────────────│────────────────────┘
                              │ фильтрует
                    [периметр доступа]
```

Учёт и Аудит наблюдают операционный слой (read-only, события и запросы). Доступ — на периметре: фильтрует обращения к ресурсам, не изменяет бизнес-состояние данных. Всё три — контрольный слой (DP.D.080: контроль ≠ операция).

## 4. Элементы триады в IWE

### 4.1 Учёт — «Что происходит?» *(refinement: KR.031)*

**Задача:** регистрировать события, состояния, транзакции в append-only журнале.

**Архетип:** бухгалтерская книга — каждая запись неизменна (нет удалений, нет правок), список записей полный.

**В IWE:** Activity Hub (`learning.domain_event`), R32 Event Ingester. R10 Статистик — производная аналитика поверх учёта (агрегация метрик).

**Инвариант:** Учётчик не удаляет и не редактирует внесённые записи (append-only). Иначе аудит не имеет смысла — нечего проверять.

### 4.2 Доступ — «Кто что видит?» *(refinement: KR.032)*

**Задача:** управлять правами на чтение и запись к ресурсам по принципу минимальных привилегий.

**Архетип:** привратник — разрешает или запрещает обращение к ресурсу, не создаёт и не изменяет содержимое. Фильтрует поток, не меняет данные.

**Инвариант:** Управляющий доступом не является потребителем данных, к которым управляет доступом. Иначе появляется мотивация для злоупотреблений.

### 4.3 Аудит — «Соблюдаются ли правила?» *(refinement: KR.033)*

**Задача:** проверять соответствие учёта нормативу и полноту покрытия.

**Архетип:** аудитор бухгалтерии — проверяет книги, не ведёт их.

**В IWE:** DP.ROLE.024 Аудитор (VR.R.002), R23 Верификатор (VR.R.001), R25 Рецензент (VR.R.003), R26 Приёмщик (VR.R.004). Методы: VR.M.002 (кросс-контекст), VR.M.004 (полнота).

**Инвариант:** Аудитор не является учётчиком и не управляет доступом к проверяемым данным. Нарушение любого из двух разделений делает аудит недействительным.

## 5. Применение к ролям IWE

### 5.1 Маппинг ролей на ветки триады

| Ветка | Роли в IWE | Выход | Owner |
|-------|------------|-------|-------|
| **Учёт** | R10 Статистик (аналитика), R32 Event Ingester (сырые события) | events, metrics | Платформа |
| **Доступ** | ORY auth + Neon RLS-политики (не формализовано как роль) | permission grants/denies | Платформа |
| **Аудит** | R23 Верификатор, R24 Аудитор, R25 Рецензент, R26 Приёмщик | verdict, отчёт, решение | R23/R25/R26: Платформа; **R24: Внешний заказчик** |

> **R24 — единственная аудитная роль с Owner Role ≠ Платформа** (DP.ROLE.024 §1). Остальные аудитные роли (R23, R25, R26) принадлежат платформе. R24 выделен потому, что именно «полнота покрытия Pack» — задача с наивысшим требованием независимости.

> **Пограничный случай — DP.ROLE.041 Аттестатор:** вычисляет ступень (присваивает статус) на основе событий учёта. Это ближе к верификации/оценке, чем к учёту. Маппинг на контрольный слой: Аттестатор ≈ «контроль соответствия нормативу ступени», а не «фиксация событий». Детальный маппинг — при создании KR.031 (Принцип Учёта).

### 5.2 Тест применения

| Вопрос | Ответ «да» → | Ответ «нет» → |
|--------|-------------|---------------|
| Может ли одна роль и вести учёт, и аудировать? | Нарушение KR.030 | Триада соблюдена |
| Может ли учётчик удалить запись? | Нарушение инварианта учёта | Полнота обеспечена |
| Совпадает ли заказчик аудита с аудитуемым субъектом? | Конфликт интересов (организационный); самоаудит допустим только при методологической независимости (см. DP.ROLE.024 §1) | Полная независимость |

## 6. Инварианты принципа

1. **Разделение учёта и аудита:** Роль, ведущая учёт, не аудирует свои же записи.
2. **Разделение доступа и аудита:** Роль, управляющая доступом, не может быть единственным аудитором системы доступа.
3. **Разделение учёта и доступа:** Роль, ведущая учёт, не управляет правами чтения к своим записям.
4. **Контрольный слой не меняет бизнес-данные:** Учёт и Аудит не изменяют бизнес-состояние операционного слоя. Доступ фильтрует обращения, но не меняет содержимое данных (DP.D.080).
5. **Одна функция на роль:** Одна роль совмещает не более одной из трёх функций триады.
6. **Append-only учёт:** Записи учёта не удаляются и не редактируются — только добавляются.

## 7. Примеры нарушений

| Нарушение | Следствие |
|-----------|-----------|
| Аудитор = создатель проверяемого | Независимость нулевая |
| Учётчик удаляет записи | Аудит на неполных данных |
| Доступ-роль сама заказывает аудит себя | Аудит может быть заказан в удобное время |
| *Гипотетически:* Платформа назначена Owner R24 | Платформа проверяет свои же компоненты — нарушение §5.1 |

## 8. Границы применения

**Триада применима:** при проектировании агентных ролей, сервисных контрактов (SC), архитектуры данных. Обязательна, когда система хранит пользовательские данные или принимает решения с внешними последствиями.

**Триада избыточна:** для одноразовых скриптов, CLI-инструментов без side effects, временных рабочих артефактов (DayPlan, inbox). Принцип масштабируется с ростом последствий нарушения.

| KR.032 | Доступ | Принцип управления доступом (минимальные привилегии) | Появление конкретной задачи по ветке Доступа (см. WP-212 ФС1 Cedar) |
