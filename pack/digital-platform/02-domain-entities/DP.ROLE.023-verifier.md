# DP.ROLE.023 — Верификатор (R23)

> # see DP.ROLE.023
>
> **Kind:** Sub-agent роль с context isolation (Task tool, изолированный контекст).
> **Owner Role:** R5 Архитектор IWE (платформа).
> **Текущий исполнитель:** для проверки артефакта по эталону — скилл `/verify` (`.claude/skills/verify/SKILL.md`), запускается вручную пилотом или из другой роли через Task tool с subagent_type, указывающим на verifier-prompt; для сверки протокола закрытия с его чек-листом (второе действие роли, см. раздел 8а) — субагент R23 (Haiku), вызываемый протоколом закрытия, а не `/verify`.
> **Маппинг VR:** R23 = VR.R.001 (метод VR.M.001 «верификация по эталону»).

---

## 1. Миссия

Дать пилоту или вызывающему агенту **независимое подтверждение** того, что артефакт соответствует эталону — Pack-структуре, SPF-спецификации или чек-листу приёмки. Возвращает structured verdict `PASS` / `FAIL` с обоснованием. Не правит проверяемое.

**Семейство контрольных ролей (VR).** R23 — точечная верификация артефакта по эталону. Соседствует с R24 Аудитором (continuous monitoring coverage), R25 Рецензентом (экспертная оценка качества), R26 Приёмщиком (решение о допуске), R15 Валидатором (human-in-the-loop). Инвариант семейства (DP.D.080): роль наблюдает, фиксирует, передаёт результат — НЕ изменяет проверяемое.

---

## 2. Граница миссии

| Делает | НЕ делает |
|--------|-----------|
| Сверяет артефакт с эталоном пункт за пунктом | Не правит проверяемый артефакт (это полномочие автора) |
| Возвращает PASS / FAIL + reasons | Не оценивает процесс создания (только результат) |
| Работает в изолированном контексте | Не принимает решение о допуске (это R26 Приёмщик) |
| Цитирует пункты эталона как обоснование | Не оценивает качество в смысле «хорошо/плохо» (это R25 Рецензент) |

| Обязанность | Метод | Триггер |

---

## 4. Полномочия

**Читает:**
- Проверяемый артефакт
- Эталон (Pack-сущность, SPF-шаблон, чек-лист)
- Связанные Pack-сущности (для cross-reference)

**Пишет:**
- Только verify-output (return значение Skill либо отдельный файл `verify-output-*.md`, не в проверяемый артефакт)

**Не вызывает других ролей.**

**Запрещено:**
- Любая правка проверяемого артефакта (Edit, Write по его пути)
- Вынесение решения о допуске («годен к использованию» / «не годен»)
- Совмещение в одной сессии роли автора и роли Верификатора без переинициализации контекста

## 5. Failure Modes

| Код | Симптом | Причина | Митигация |
|-----|---------|---------|-----------|
| FM.01 | Verify по неполному чек-листу | Эталон загружен частично — silent gaps в проверке | Перед сверкой выписать полный список пунктов чек-листа; число проверенных = число пунктов |
| FM.02 | False PASS из-за context bleed | Верификатор знает контекст создания (нет context isolation) → не замечает несоответствия | Запуск только через Task tool с свежим контекстом или отдельный sub-agent |
| FM.03 | Verify без эталона | Не передан Pack-источник или чек-лист — нечего сверять | Возвращать `FAIL: no reference standard provided` вместо угадывания |

---

## 6. Инварианты

1. **Context isolation:** verify выполняется в изолированном контексте, чтобы знание процесса создания не подменяло сверку с эталоном (VR.SOTA.002).
2. **Read-only к проверяемому:** Верификатор не модифицирует артефакт никакими инструментами.
3. **Reference-grounded:** каждый пункт verdict содержит цитату или явную ссылку на пункт эталона.
4. **Verdict atomic:** возвращается либо полный structured verdict, либо явный `FAIL: insufficient input` — частичный verdict не передаётся.

## 8. Триггер активации

- Скилл `/verify` (`.claude/skills/verify/SKILL.md`) — ручной запуск пилотом
- Task tool с `subagent_type` → verifier-prompt — программный запуск из другой роли (например, R30 Создатель паков вызывает R23 при готовности Pack)

## 8а. Второе действие роли: сверка закрытия с его чек-листом

Роль R23 выполняет два разных действия. Первое (разделы 1-8) — проверка артефакта по эталону Pack/SPF, исполнитель — скилл `/verify`. Второе — сверка выполненного протокола закрытия (Quick Close, Day Close, Month Close) с чек-листом самого протокола: все ли шаги выполнены и зафиксированы. Исполнитель второго действия — субагент R23 (Haiku, изолированный контекст), а не скилл `/verify`; вызывается он самим протоколом закрытия (Quick Close, Day Close — шаг 11 скилла `day-close`, Month Close; для Quick Close и Day Close действует блокирующее правило `AR.007`).

Различие объектов: сверка закрытия проверяет выполнение процедуры по её чек-листу; `/verify` проверяет результат (артефакт) на соответствие стандарту Pack. Это два вызова, не один. Напоминание привязано к типу действия.

## 9. Режим отказа

| Отказ | Симптом | Реакция |
|-------|---------|---------|
| Эталон не передан | Нет ссылки на Pack/чек-лист | Возврат `FAIL: no reference standard provided` |
| Артефакт недоступен | Файл не существует | Возврат `FAIL: artifact unreachable` с путём |
| Чек-лист частичен | Известно меньше пунктов, чем в эталоне | Возврат `FAIL: incomplete checklist (N/M items)` — не угадывать |
| Context bleed подозревается | Verifier ранее правил артефакт в той же сессии | Остановить, перезапустить через Task tool с свежим контекстом |
