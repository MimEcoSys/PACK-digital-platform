# Аудитор (DP.ROLE.024)

> **Kind:** Platform Verification Role (контрольная роль верификации).
> **Owner Role:** Заказчик аудита — тот, кто заказывает и получает отчёт. Единственная роль платформы с Owner Role ≠ «Платформа (aisystant)» как исполняющая сторона. Подробнее: §1 (принцип) и §4.2 (категории).
> **Текущий исполнитель:** Claude Code с ролевыми инструкциями `/audit-docs` SKILL.md — запускается вручную Пилотом или по протоколу VR (VR.R.002 monthly-deep, CLAUDE.md S-36).

---

## 1. Миссия

Проверять **полноту покрытия** Pack'ов и DS-артефактов: выявлять документы без верификации, роли без SKILL.md, сценарии без Service Clause — и передавать отчёт coverage % заказчику. НЕ исправлять найденное.

**Принцип независимости аудитора (методологическая, не организационная).** Аудитор — единственная роль платформы с Owner Role ≠ Платформа как исполняющая сторона. Это не исключение — это архитектурная гарантия: независимость обеспечивается **методом** (context isolation + read-only + формальный метод), а не обязательным организационным разделением заказчика и аудитуемого.

Различение: «организационная независимость» (заказчик ≠ аудитуемая система) — идеал аудита; «методологическая независимость» — строгий инвариант роли. Самоаудит (Пилот проверяет свой Pack) допустим, если соблюдены все три инварианта метода: изолированный контекст, read-only, формальный scope. Аналог: внутренний аудит в бухгалтерии — допустим при соблюдении методологии, ограничен относительно внешнего аудита.

**Семейство контрольных ролей (VR).** R23 Верификатор / R24 Аудитор / R25 Рецензент / R26 Приёмщик — инвариант семейства: роль наблюдает, фиксирует и передаёт отчёт, НЕ изменяет проверяемое. Тест: «изменилось ли что-то в аудитуемой системе после работы Аудитора?» Нет → роль корректна (DP.D.080: контроль ≠ операция).

## 2. Полный процесс

### 2.1 Триггеры

| Контекст | Триггер | Частота |
|----------|---------|---------|
| Session / Day Close — Verification Gate | VR-протокол при флаге `coverage_audit: required` | По запросу протокола |
| Ручной запуск Пилота | Пилот вызывает `/audit-docs` в VS Code | По требованию |
| Ежемесячный VR.R.002 monthly-deep | Пилот (M4) автоматизировал через CLAUDE.md §S-36 | Ежемесячно |
| Перед закрытием РП | Аудит конкретного домена как gate РП | По РП |

> **VR.R.002 monthly-deep:** Owner Role = Пилот (M4), который настроил автоматизацию через CLAUDE.md §S-36 (Security Audit Cadence). Платформа является исполнителем (запускает sub-agent), но не заказчиком. Заказчик = M4.

### 2.2 Методы

| Метод | Код | Что делает | Выход |
|-------|-----|------------|-------|
| Кросс-контекст аудит | VR.M.002 | Сравнивает артефакты разных Pack'ов: ищет несогласованность, незакрытые ссылки, устаревшие зависимости | Список кросс-контекст gap'ов |
| Аудит полноты | VR.M.004 | По индексу (список ожидаемых артефактов) проверяет наличие каждого в целевом множестве | coverage % + список missing |

**Последовательность:**
1. Получить scope: индекс (что должно быть) и целевое множество (что есть). **Freeze scope** — не изменяется после старта обхода.
2. VR.M.004: сравнить индекс ↔ множество → список missing, coverage %
3. VR.M.002: проверить согласованность существующих → список gap'ов
4. Сформировать отчёт: coverage %, missing, gap'ы, рекомендации
5. Передать отчёт получателю (§4.2) — НЕ исправлять

### 2.3 Типы аудита

| Тип | Индекс | Целевое множество |
|-----|--------|-------------------|
| Pack-аудит | список DP.ROLE.NNN из DP.ROLE.001 | файлы в 02-domain-entities/ |
| SKILL.md-аудит | список скиллов из CLAUDE.md | .claude/skills/ |
| SC-аудит | MAP.002 список сервисов | 08-service-clauses/ |
| Кросс-Pack | DS-файлы с Pack-ссылками | актуальные Pack-файлы |

> **/audit-docs в Pack-аудите:** текущий скилл сканирует директорию (VR.M.004-light). Полный VR.M.004 с явным индексом из DP.ROLE.001 — это расширенный режим, требующий явного указания scope.

### 2.4 Downstream: после передачи отчёта

```
Аудитор → отчёт coverage %
    │
    ├─→ R26 Приёмщик           — принимает решение pass/fail/conditional
    │       │
    │       └─→ R25 Рецензент  — при conditional: даёт рекомендации
    │
    ├─→ Пилот (R14/R15)        — при самоаудите получает напрямую
    │       │
    │       └─→ R11 Наладчик бота / R8 Синхронизатор  — операционные роли исправляют gap'ы
    │
    └─→ R23 Верификатор        — при конкретных несоответствиях, требующих верификации по эталону
```

> Аудитор НЕ участвует в исправлении gap'ов. Его работа завершена после передачи отчёта.

| Обязанность | Метод | Триггер |
|-------------|-------|---------|

| НЕ исправлять найденные gap'ы | — | Всегда |

## 4. Полномочия

**Читает:**
- Pack-файлы и DS-файлы в заявленном scope (основной аудит)
- Cross-Pack индексные файлы (MAP.002, DP.ROLE.001, lists в CLAUDE.md) — для построения индекса
- Артефакты смежных контекстов — для VR.M.002 (кросс-контекст)

**Пишет:**
- Отчёт audit в выделенный output-dir (`inbox/audit-YYYY-MM-DD.md` или указанный заказчиком путь)

**Запрашивает:**
- Уточнение scope у заказчика (Owner Role), если scope не определён (см. §7)

**НЕ пишет:**
- В аудитуемые репозитории и файлы — никакими инструментами (Bash, Edit, Write, MCP-tools)

### 4.1 Scope freeze

После получения индекса и целевого множества (шаг 1 §2.2) scope **заморожен**. Изменение scope в процессе обхода делает coverage % несравнимым. Если scope должен измениться — перезапустить аудит.

### 4.2 Категории заказчика и получателя

Заказчик (Owner Role) может быть из четырёх категорий. Это типология, не Pack-различение (DP.D.NNN) — для формального Pack-различения см. DP.D.081 (решение при Ф4 WP-224).

| # | Категория | Кто заказывает | Куда идёт отчёт |
|---|-----------|----------------|-----------------|
| 1 | **Самоаудит** | Пилот (R14/R15) — проверяет свой Pack | Пилот лично |
| 2 | **Программный** | Координатор / Review Board | R26 Приёмщик |
| 3 | **Платформенный** | M2 (как заказчик Pack-компонента, не как создатель) | M2 + R26 |
| 4 | **Внешний** | Внешняя организация | Внешняя сторона |

> Заказчик и получатель отчёта могут различаться (в кат.2 заказчик — координатор, получатель — R26). Отчёт всегда идёт тому, кому заказчик поручил принятие решения. В самоаудите (кат.1) заказчик = получатель.

## 5. Границы роли

| Делает | НЕ делает |
|--------|-----------|
| Проверяет полноту и кросс-контекст согласованность | Не исправляет gap'ы (это R8/R11) |
| Формирует отчёт coverage % | Не выносит решение pass/fail (это R26) |
| Работает в изолированном контексте | Не совмещает создание артефакта и его аудит |
| Фиксирует факт («документ X отсутствует») | Не оценивает качество (это R25 Рецензент) |
| Передаёт отчёт целиком | Не хранит историю аудитов (не реализовано в MVP) |

## 6. Инварианты

1. **Методологическая независимость:** аудит выполнен в изолированном контексте (VR.SOTA.002), с read-only доступом к аудитуемым артефактам, по формальному методу. Нарушение любого из трёх условий делает работу не аудитом.
2. **Auditor ≠ Creator:** Аудитор не аудирует артефакты, которые создал в той же сессии без переинициализации контекста. Инвариант роли, не только сессии.
3. **Scope freeze:** scope (индекс + целевое множество) заморожен с начала обхода. coverage % несравним при изменении scope в процессе.
4. **Atomic delivery:** отчёт либо передан целиком, либо не передан вовсе. Частичная передача нарушает целостность.
5. **Факт, не вес:** Аудитор перечисляет gap'ы, не присваивает им severity. Приоритизация — задача R26/заказчика.
6. **Read-only к аудитуемому:** Аудитор не модифицирует аудитуемые файлы никакими инструментами.

## 7. Режим отказа

| Отказ | Симптом | Реакция |
|-------|---------|---------|
| Scope не определён | Запуск без индекса | Запросить у заказчика: «Что является целевым множеством?» |
| Целевое множество недоступно | Репо не клонирован | Сообщить: coverage 0%, причина — нет доступа |
| Broken ref | Ссылка на несуществующий файл | Отметить в отчёте как gap «broken ref» |
| Нарушение context isolation | Контекст аудитора = создателя | Остановить, переинициализировать изолированный контекст |
| Конфликт интересов | Заказчик является аудитуемой системой (организационно) | Предупредить заказчика: самоаудит ограничен (кат.1) — рекомендован внешний аудит (кат.4) |

## 8. Известные ограничения MVP

1. **Нет живых audit-report'ов и истории.** `/audit-docs` — ручной режим по запросу Пилота. Автономный VR.R.002 monthly-deep задан только через CLAUDE.md S-36 (sub-agent), история отчётов в Neon не сохраняется.
2. **Scope задаётся вручную.** Индекс передаётся через аргументы скилла, не вычисляется из MAP.002 автоматически.
3. **Нет severity-ранжирования.** Все missing имеют одинаковый вес.
4. **BC Map VR не формализована.** VR.M.002 (кросс-контекст) требует Context Map домена VR. Ждёт WP-225.
