# Диагност — DP.ROLE.042

> **Прежний заголовок** — «Диагност (R28)»; номер R28 убран решением пилота 07.11.2026 (DP.ROLE.001 §3.6, РП-616 Ф4).

> # see DP.SC.132, DP.ROLE.042
>
> **Kind:** Interactive Dialogue Role + Background Monitoring Role (платформенная роль диагностики ученика).
> **Owner Role:** Платформа (aisystant) — исполнитель ConversationHandler (TG), REST endpoint (браузер), MCP tool (VS Code), Сигнальщик инвалидации профиля (фоновый режим, см. §3.4).
> **Источник алгоритма:** `role-prefixes.md R28` (R28 — номер шаблона; в паке R28 — Профилировщик, DP.ROLE.001 §3.2, соответствие — §3.7), `PD.FORM.089 §6.1`.

---

## 1. Миссия

Дать пилоту (Ученику) и платформенным ролям **точный cp-профиль** — оценку уровня понимания и навыков, независимую от накопленных часов. Устранить ситуацию, когда Аттестатор повышает ступень «только по часам», без проверки понимания.

**Три функции:**
1. **Диалоговая диагностика** — пилот сам инициирует, получает cp-профиль + рекомендацию потока (skip-level).
2. **Gate-подтверждение** — Аттестатор запрашивает cp при переходе ступени (двойной gate FORM.089 §5.1).
3. **Фоновый помощник** — silent-monitoring сигналов инвалидации → подсказки активным ролям (не пилоту напрямую).

**Граница:** Диагноcт не ведёт обучение, не строит personal-guide, не рассчитывает bh-метрики — только диагностирует cp-состояние.

## 2. Алгоритм (три фазы)

> Источник: `PD.FORM.089 §6.1`. Здесь — сводка для инженерной реализации.

### Фаза 1 — Первичный срез (2-3 вопроса)

Якорные вопросы, начиная **со среднего уровня (ст. 3)** — не с ст. 1 (опытных нельзя «сажать в первый класс»).

| cp-слот | Код | Якорный вопрос (ст. 3-ориентир) | Рубрика 1-5 |
|---------|-----|--------------------------------|-------------|
| Ритм (Систематичность) | cp.rhy | «Как вы ведёте учёт инвестированного времени и есть ли регулярный ритм?» | 1: нет, 2: иногда, 3: еженедельно, 4: ежедневно + WakaTime, 5: автоматически + артефакты |
| Мировоззрение | cp.wld | «Как принимаете решения — через ценности, системный анализ или интуитивно?» | 1: интуиция, 2: пробую, 3: через мировоззрение, 4: системно, 5: передаю другим |
| IWE-практики | cp.iwe | «Используете ли VS Code + Pack + Claude как единую среду? Есть протоколы ОРЗ?» | 1: нет, 2: слышал, 3: базово, 4: систематически, 5: развиваю IWE |
| Интеграция знаний | cp.int | «Приведите пример применения системного мышления к реальной ситуации.» | 1: нет опыта, 2: слышал, 3: базовые различения, 4: системный разбор, 5: формализую |

Ответы — структурированные (chip/radio/keyboard 1-5), не свободный чат.

### Фаза 2 — Уточнение bottleneck (1-2 вопроса)

Задаётся только для слота с наименьшим значением из Фазы 1. Уточняющие вопросы — по `PD.FORM.089 §6.1`. Цель: точнее калибровать именно слабый слот.

Если Фаза 1 дала однозначную картину (все слоты ≥ 3) — Фаза 2 пропускается.

### Фаза 3 — Аудит bh-прокси (0 вопросов, автоматически)

Запрашивает bh-данные из Аттестатора (DP.ROLE.041):

| bh-порог | Прокси | Правило |
|----------|--------|---------|
| `bh.inv ≥ 4` | `cp.skl baseline ≥ 2` | Много инвестированного времени → ритм есть |
| `bh.sys ≥ 3` | `cp.rhy baseline ≥ 2` | Систематичность → базовый ритм подтверждён |
| `bh.awr ≥ 2` | `cp.wld baseline ≥ 2` | Осведомлённость → мировоззрение базовое |

Правило: `cp_final_slot = max(cp_from_dialogue, cp_from_bh_proxy)` — bh-прокси только повышает, не понижает.

### Вычисление результата

```python
mandatory = [cp.rhy, cp.wld, cp.skl, cp.iwe, cp.int, cp.agt]
cp_confirmed_stage = min(mandatory)        # FORM.089 §5.1
bottleneck_slot = argmin(mandatory)
skip_to_stage = cp_confirmed_stage         # skip-level вход

if cp_confirmed_stage >= 4: recommended_stream = "S4"
elif cp_confirmed_stage >= 3: recommended_stream = "S3"
elif cp_confirmed_stage >= 2: recommended_stream = "S2"
else: recommended_stream = "S1"
```

**cp.skl и cp.agt**: заполняются на основе якорного вопроса cp.rhy (skl) и дополнительного вопроса про РП/агентность (agt). Если cp.agt не спрашивался — используется bh.agn как прокси.

## 3. Четыре режима работы

### Режим 1: Активная диагностика (user-initiated)

```
Пилот → /diagnose (TG / браузер / VS Code)
    ↓
Диагност: 3 фазы, ≤5 вопросов
    ↓
cp-профиль → learning.cp_assessments (Neon)
    ↓
Пилот видит: ступень + bottleneck + поток + skip-вход (на русском, без кодов cp.NNN)
```

Три интерфейса:
- **TG (Ф6):** `/diagnose` → ConversationHandler, ReplyKeyboardMarkup с кнопками 1-5
- **Браузер (Ф7):** `/diagnose`-страница, chip/radio UI, anonymous-режим + CTA
- **VS Code (Ф8):** `IWE: Diagnose`, markdown-карточка в чате, autowrite в personal-guide

### Режим 2: Gate Аттестатора (passive, triggered)

```
Аттестатор: bh_recommended > current_stage
    ↓
Запрос get_latest_cp_assessment(account_id)
    ├── есть валидный срез (TTL не истёк) → использовать кэш
    └── нет / устарел → отправить пилоту CTA «пройти диагностику»
    ↓
cp_confirmed ≥ bh_recommended → переход ПОДТВЕРЖДЁН
cp_confirmed < bh_recommended → переход ОТЛОЖЕН + пилоту: «метрики говорят о росте, диагностика показывает gap»
```

### Режим 3: Вход для Портного

Портной читает cp-профиль при генерации personal-guide:
- `bottleneck_slot` → приоритет в выборе контента
- `recommended_stream` → нарратив ступени (PD.FORM.087)
- `skip_to_stage` → стартовая точка руководства (не начинать с базовых занятий если skip > 1)

Fallback: нет cp-данных → B-lite (stage_raw из Аттестатора), не ломается.

### Режим 4: Фоновый помощник (silent monitoring)

Сигнальщик инвалидации профиля (`diagnostician-watcher`, WP-316, ежедневный тик):

**Триггеры инвалидации:**
- `bh.inv ≥ +50%` за неделю vs baseline (рост активности)
- `cp_assessment.age ≥ 90 days` (всегда предлагать повторную диагностику)
- `bh.sys ≥ +2` (резкий скачок систематичности)
- Аттестатор: bh-переход без cp-подтверждения (gate-сигнал)

**Что делает при триггере:**
- Пишет событие `diagnostic.invalidation_proposed` в `learning.domain_event`
- **НЕ** пишет пилоту напрямую
- Навигатор / Портной / Аттестатор читают событие при следующем взаимодействии с пилотом и **сами** инициируют разговор о повторной диагностике

## 4. Обязанности

| Обязанность | Метод | Триггер |
|-------------|-------|---------|

| Подсказать активной роли (фоновый) | emit `diagnostic.invalidation_proposed` | При триггере инвалидации |

## 5. Полномочия

- **Читает** `learning.domain_event` (только bh-прокси для Фазы 3 — event_type, не raw-текст).
- **Читает** `learning.stage_transitions` (текущая bh-ступень для gate).
- **Читает** `learning.tracking_consent` (проверка opt-in).
- **Пишет** в `learning.cp_assessments` (INSERT, не UPDATE).
- **Пишет** в `learning.domain_event` (тип `diagnostic.invalidation_proposed` — только фоновый режим).
- **НЕ меняет** ступень пилота (это Аттестатор).
- **НЕ читает** raw-текст ответов пилота — только цифры (1-5) и выбранный вариант. **Исключение:** внутри связки Наставника (`MIM.R.001` Режим 2, `DP.SC.197`, WP-498) Диагност как роль-компонент читает свободный текст пилота — TTL на сессию ответа, маскирование перед логом. Вне этой связки исключение не действует, базовый запрет в силе.
- **НЕ инициирует** прямой диалог с пилотом в фоновом режиме.

## 6. Границы роли

| Делает | НЕ делает |
|--------|-----------|
| Диагностирует cp-состояние через диалог | Не ведёт обучение (это потоки S1-S4) |
| Рекомендует поток и skip-уровень | Не строит personal-guide (это Портной) |
| Подтверждает gate Аттестатора | Не рассчитывает bh-метрики (это Аттестатор) |
| Подсказывает активным ролям в фоне | Не пишет пилоту напрямую в фоновом режиме |
| Кэширует cp-срез (TTL 6 мес) | Не хранит raw-текст ответов (кроме сессии ответа внутри связки Наставника, `MIM.R.001` Режим 2 — TTL+маскирование, см. §5) |

---

## 7. Инварианты

1. **Точность min-gate:** cp_confirmed_stage = min(6 mandatory-слотов) — без исключений (FORM.089 §5.1).
2. **Монотонность skip-level:** skip_to_stage ≤ 5, ≥ 1.
3. **bh-прокси только повышает:** `cp_final = max(cp_dialogue, cp_bh_proxy)`.
4. **TTL соблюдён:** `valid_until = assessed_at + 6 months` (mandatory-срезы).
5. **Фоновый режим молчит:** в фоновом режиме нет прямых сообщений пилоту.
6. **Privacy:** только UUID, числа, event_type в хранилище.

## 8. Режим отказа

| Отказ | Симптом | Реакция |
|---|---|---|
| Пилот бросил диалог на полпути | Нет финального ответа | Не сохранять частичный результат; предложить `/diagnose` снова |
| БД недоступна | `asyncpg.ConnectionError` | Сохранить результат локально, записать при восстановлении |
| bh-прокси недоступен (Аттестатор) | Timeout | Использовать только диалоговые cp_scores; Фаза 3 skip |
| Аттестатор запрашивает cp, среза нет | `cp_assessment = None` | Отправить CTA «пройти диагностику», не блокировать gate |
| Фоновый: инвалидация не обработана | Нет события в domain_event | Silent fail, следующий тик (не блокирует работу) |
