# DP.ROLE.059 — Маршрутизатор задач

> **Прежний заголовок** — «R30 Маршрутизатор»; R30 — исторический псевдоним (DP.ROLE.001 §3.7). Переименовано решением пилота 07.11.2026 (DP.ROLE.001 §3.6, РП-616 Ф4).

## Описание

Агентная роль — единая точка маршрутизации задач IWE. Получает любой входящий запрос
(с routing-тегом или без), определяет единственного исполнителя по executor-catalog.yaml
и вызывает его с минимально необходимым контекстом. Не классифицирует задачи самостоятельно —
исполняет routing-решения, принятые WP Gate или Артефактором-Постановщиком (DP.ROLE.058).

## Вход → Выход

- **Вход:** запрос с routing-тегом `{class, task_type}` (проставлен WP Gate или Артефактором);
  или неструктурированный запрос без тега
- **Выход:** результат исполнителя + `routing_path` (tag → executor, для метрики) + статус
  (`OK` / `EXEC_FAILED` / `STRUCTURE_FAILED` / `NO_MATCH`)

## Обязанности

1. **Получить routing-tag** из запроса (проставлен WP Gate или Артефактором-Постановщиком)
2. **При отсутствии тега** — вызвать DP.ROLE.058 Артефактор-Постановщик → получить structured
   request с тегом → повторный lookup (max 1 раз; при повторном отсутствии → `STRUCTURE_FAILED`)
3. **Lookup в executor-catalog.yaml:** `{class, task_type}` → исполнитель; lookup O(1) по хешу
4. **При неоднозначности** (несколько исполнителей с одним тегом) — Haiku для финального выбора;
   при fail Haiku → первый по алфавиту (детерминированный fallback)
5. **Вызвать исполнителя** с минимально необходимым контекстом + `warnings_key` из каталога
6. **При отказе исполнителя** (exit ≠ 0 / timeout) → `EXEC_FAILED` + тип задачи + код ошибки
   → `routing-errors.log`; автоматический retry **запрещён**
7. **Экспортировать метрику** `routing-path-distribution` (tag → executor → success/fail) при
   каждом вызове
8. **При `task_type=AGENT_FAULT`** — routing в `iwe_checklist_memory.py record` (WP-316 L1);
   не передавать в LLM

## Полномочия

- Читать `executor-catalog.yaml` (lookup)
- Вызывать любого исполнителя из каталога
- Вызывать DP.ROLE.058 Артефактор-Постановщик для структурирования неоформленных запросов
- Запускать Haiku для разрешения неоднозначности тега (не для классификации)
- Отклонять запросы без task_type после двух попыток структурирования (`STRUCTURE_FAILED`)
- Записывать в `routing-errors.log` без уведомления пилота (кроме `STRUCTURE_FAILED`)

## Надсистема

Экзокортекс (DP.ARCH.001). Подсистема «Система исполнения задач IWE» (WP-350).

## Исполнитель

Скрипт `route-task.sh` (реализуется в Ф12 WP-350). До реализации — inline-логика в Opening-протоколе.

## Триггер

Каждый структурированный запрос к IWE через Opening-протокол (или задача, поднятая Диспетчером
из agent inbox).

## Ограничения scope (явные)

- **Stateful multi-turn скиллы** (intrasession rerouting) — вне scope текущей версии; реализовать
  в Ф12 WP-350 и отдельном DP.SC на stateful execution.
- **Динамический инжект fault-warnings при routing** — отклонён; используется статическое поле
  `warnings_key` в executor-catalog.yaml (минимальный IO, без усложнения роли).
- **Payload AGENT_FAULT** (граница Session Memory Injector vs iwe_checklist_memory.py) — открытый вопрос,
  разрешить в Ф12 WP-350.

## Номер в иерархии ролей

Блок R30–R39 резервируется для ролей маршрутизации и исполнения задач (не смешивать с
аналитическими R20–R29 и надзорными R40+).

| Роль | Функция |
|------|---------|
| R23 Верификатор | Проверяет результат по эталону |
| R29 Декомпозитор | Разбивает РП ≥3h на этапы с физическими артефактами |
| **R30 Маршрутизатор** | **Направляет задачу к единственному исполнителю** |
| R31+ | резерв блока routing/execution |
