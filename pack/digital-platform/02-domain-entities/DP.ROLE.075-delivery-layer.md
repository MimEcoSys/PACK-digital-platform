# Распорядитель доставки (DP.ROLE.075)

> # see DP.SC.177, DP.ROLE.075
>
> **Уровень владельца:** часть платформы (DP.ROLE.001 §3.6); функциональная часть подсистемы «Вестник» (DP.ROLE.122).
> **Прежние имена:** Доставщик (Delivery Policy Layer) (до 18.11.2026). Решение пилота 18.11.2026: прежняя роль объединяла две функциональные части Вестника - Приёмщика и Распорядителя доставки; Приёмщик вынесен в DP.ROLE.123, имя «Доставщик» убрано (он не доставляет и созвучен «Доставщику обновлений», DP.ROLE.111).

---

## 1. Миссия

Решать по каждому принятому выпуску, как его доставить: отправить сейчас, после тихих часов, только в ленту или отсечь - и в какой канал. Распорядитель читает только метаданные выпуска (владелец правила, класс важности, срочность и точность, вид) и снимок настроек человека; содержимое по смыслу не интерпретирует.

**Граница.** Распорядитель доставки не принимает выпуск, не проверяет отправителя и не отсекает повтор - это Приёмщик (DP.ROLE.123). Не держит очередь и не повторяет при сбое - это Диспетчер очереди (DP.ROLE.125). Не доставляет в канал - это Почтальон (DP.ROLE.044). Не решает, что и когда слать по смыслу; перечень видов и категории отписки заданы в DP.SC.116, Распорядитель их применяет.

## 3. Классы важности платформенных уведомлений

Пять классов с политикой - DP.SC.177, раздел «Класс-модель» (`critical`, `must-deliver`, `transactional`, `capped`, `ops-alert`). Потолок 2 в день действует только для класса `capped` (платформенные необязательные), суммарно по всем отправителям. Свои правила человека этим потолком не ограничиваются (решение пилота 18.11.2026).

---

## 4. Ограничения (инварианты роли)

1. **Единая точка решения.** Решение «слать ли толчком» принимает только Распорядитель доставки; окна и отправители его не принимают.
2. **Не решает, сколько своих сообщений получит человек.** Отсечение по количеству - только для платформенных необязательных.
3. **Не молчать при отсечении.** Каждое отсечение записывается с причиной (Учётчик доставки, DP.ROLE.126).
4. **Канало-независимый вход.** В выпуске нет специфики канала (`chat_id`, `reply_markup`); канал выбирает Распорядитель, отрисовку делает Почтальон.

## 6. Текущая реализация (до переноса в программу «Центр уведомлений»)

Сейчас Приёмщика и Распорядителя доставки вместе выполняет служба уведомлений внутри Telegram-бота (`NotificationService`); целевое - программа «Центр уведомлений» (DP.ROLE.122, раздел «Модули»; перенос - DP.SC.177, раздел «Реализующие программы»).

```python
NotificationService.send(
    user_id: str,
    klass: str,           # critical | must-deliver | transactional | capped | ops-alert
    content_spec: dict,   # channel-neutral: {"text": ..., "actions": [...]}; no chat_id/reply_markup
    priority: int,        # 1..4
    dedup_key: str,
) -> dict  # {notification_id, status, reason?}
```

Выход: `status: queued | suppressed | sent | failed`, `reason` при `suppressed` (`cap-exceeded` / `opt-out` / `duplicate`). Очередь - приватная таблица `notification_queue`; журнал - `public.domain_event`. Будущий внешний вход - узкий `enqueue`-контракт, которым владеет Вестник (DP.D.231).

- **18.11.2026, РП-568 Ф17** (решение пилота): роль «Доставщик» разделена по функциональным частям Вестника: приём выпуска вынесен в DP.ROLE.123 «Приёмщик», очередь - в DP.ROLE.125 «Диспетчер очереди», запись исходов - в DP.ROLE.126 «Учётчик доставки»; эта карточка переименована в «Распорядитель доставки» и сужена до решения о доставке и выбора канала. Для своих уведомлений квот нет.
