# Разметчик типов пользовательских данных / Data Structurer (DP.ROLE.085)

<!-- see DP.SC.055, WP-483 Ф0, родитель-концепция WP-289 -->

> **Kind:** Функциональная роль (FPF A.2) — детерминированная программа. Тест «Скрипт ≠ Агент» (`DP.D.048`): базовая разметка (по месту + структурные эвристики) работает БЕЗ LLM — убрать LLM, основная функция не ломается. Опциональный Grade 2 (LLM-ассист) — только для явно неоднозначных файлов, не участвует в решении о карантине.
> **Owner Role:** Платформенный архитектор (bootstrap) — до формализации отдельного продуктового владельца комплекта guide-kit (по аналогии с `DP.ROLE.083`).

## 1. Миссия

Быть единственным шагом, который делает произвольную файловую базу пользователя пригодной для генерации персонального руководства — без изменения исходных файлов, без утечки чужих данных, без обращения к нашим серверам. Разметчик не содержит доменного знания и не принимает решений о содержании руководства — только о ТИПЕ и ДОПУСТИМОСТИ материала.

**Отличие от роли Портной/Генератор (`DP.ROLE.001`, R27):** Разметчик — upstream, работает с сырой базой и производит структурированный индекс + профиль. Портной — downstream, потребляет этот индекс и профиль, ничего не знает о внутреннем устройстве исходной базы. Границу нельзя стирать: Портной не должен сам классифицировать файлы, Разметчик не должен сам решать, что писать в руководство.

## 2. Обязанности

| Обязанность | Метод | Триггер |
|-------------|-------|---------|
| Разметить базу по месту (дом/папка → тип) | `homes.yaml`-маппинг + frontmatter-override | Вызов `structure_base` |
| Классифицировать по структурным сигналам (per-file) | Эвристики: дата события→2.2, self-declared→2.1-declared, вывод из потока→2.1-derived, FPF-форма→2.3, след решений носителя→2.4 | Файл не покрыт `homes.yaml` или требует уточнения |
| Карантинировать «вне оси» | Детерминированные признаки чужого PII/секретов/платежей | Обнаружен файл вне допустимой оси |
| Присвоить freshness | `valid_from`+TTL/`superseded_by` из frontmatter (2.1); append-only (2.2); supersede-цепочка (2.3) | Каждый размеченный файл |
| Поднять и самовалидировать `search()`-endpoint | MCP-контракт `search(query, limit?, source?, source_type?)` + Knowledge Gate KG-01..13 | После разметки |
| Классифицировать явно неоднозначные файлы через LLM (опц.) | BYOK/локальный LLM-вызов, результат помечен `source: llm-assisted` | Файл не классифицирован детерминированно |

## 3. Полномочия

- **Читает** файловую базу пользователя (путь) или существующий MCP `search()`-backend.
- **Пишет** `.structurer/type-index.json`, `profile.yaml` (секция 2.1-declared), `residency.yaml`, карантинный bucket-лист — все локально, в пространстве пользователя.
- **Не решает** содержание руководства — это исключительно Портной (`DP.ROLE.001`).
- **Не отправляет** содержимое файлов на внешние серверы, кроме явного, управляемого пользователем BYOK-вызова LLM для неоднозначных файлов.
- **Не разрешает** карантин «вне оси» самостоятельно — снятие карантина требует явного действия пользователя, не входит в обязанности роли.

## 4. Границы роли

| Делает | НЕ делает |
|--------|-----------|
| Классифицирует файлы по типам 2.1-2.4 | Не решает, что из этого попадёт в конкретное занятие руководства (это Портной) |
| Карантинирует подозрительные данные | Не удаляет и не изменяет исходные файлы пользователя |
| Присваивает freshness по frontmatter | Не выдумывает freshness для файлов без даты (оставляет `unknown`, не текущую дату) |
| Поднимает локальный `search()`-endpoint | Не хранит и не индексирует данные на наших серверах |
| Использует LLM для неоднозначных файлов (опц.) | Не использует LLM для решения о карантине (И4 — детерминировано) |

## 5. Артефакты

**Входы:**
- Путь к файловой базе пользователя ИЛИ существующий MCP `search()`-backend.
- `.structurer/homes.yaml` (опционально; есть разумный дефолт).
- Frontmatter-override в файлах пользователя (опционально).

**Выходы:**
- `.structurer/type-index.json` — путь → `{type, subtype, mode, freshness, confidence, source}`.
- `profile.yaml` (частично — секция 2.1-declared).
- `residency.yaml`.
- Карантинный bucket-лист «вне оси».
- Локальный MCP `search()`-endpoint над размеченной базой.

## 6. Носители (carriers)

**Целевой носитель:** открытый Python-пакет `structurer/` внутри публичного репозитория guide-kit (WP-483 Ф1-Ф2) — детерминированный код, ноль обязательных бэкенд-зависимостей. Migration Path: роль переносима на любой рантайм (headless CLI, MCP-инструмент внутри стороннего ИИ-помощника) — тест переносимости «уберу конкретный host — роль работает?» да, так как контракт `search()` и формат `profile.yaml` — vendor-neutral.

**Требование к дефолтному адаптеру (ArchGate storage-абстракции, WP-483 Ф0, решение пилота 2026-07-13):** файловая система + SQLite+vec0 — обязательный zero-config адаптер, работает без настройки и без внешних сервисов (сценарий «Марина» — незарегистрированный пользователь без поддержки). Notion+Git/GitHub/pgvector-адаптеры опциональны, не блокируют базовый сценарий. Обоснование и полный профиль ЭМОГССБ — `DS-my-strategy/inbox/WP-483/f0-gates/DRR-storage-abstraction.md`.

## 7. Открытые вопросы

- **Q1 (Owner Role):** временно назначен «Платформенный архитектор (bootstrap)» по аналогии с `DP.ROLE.083` — при выделении guide-kit в самостоятельный продукт с отдельным владельцем требуется пересмотр.
- **Q2 (граница с WP-449 таксономией):** Разметчик реализует ось 2.1-2.4 (изменчивость + данные/знание), НЕ ортогональную 4-классовую онтологию WP-449 (индекс/указатель/снаружи) — смешение осей даёт противоречивые метки (см. концепция §6.2 «Осевая дисциплина»). Зрелая версия может выдавать обе метки как разные классификаторы — не решать сейчас.
- **Q3 (тип 2.4):** трактовка «выразимость vs переносимость» не финализирована (см. `DP.SC.055` «Открытые задачи», WP-449 Ф2). Ось `2.4` помечена `provisional`.
