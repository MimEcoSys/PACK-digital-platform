# Разметчик типов пользовательских данных / Data Structurer (DP.ROLE.085)

<!-- see DP.SC.055, WP-483 Ф0, родитель-концепция WP-289 -->

> **Kind:** Функциональная роль (FPF A.2). Тест «Скрипт ≠ Агент» (`DP.D.048`) применяется по схеме: для схемы руководства базовая разметка (по месту + структурные эвристики) работает БЕЗ LLM — убрать LLM, основная функция не ломается; опциональный Grade 2 (LLM-ассист) — только для явно неоднозначных файлов. Для стратегической схемы смысловая метка ставится LLM (неудовлетворённость или обязательство по месту файла не определить), а детерминированным остаётся определение нового с даты; чужое и секретное в шаге сессии стратегирования показывается пользователю, программы-карантина там нет (§1а). Решение о карантине LLM не принимает ни в одной схеме.
> **Owner Role:** Платформенный архитектор (bootstrap) — до формализации отдельного продуктового владельца комплекта guide-kit (по аналогии с `DP.ROLE.083`).

## 1. Миссия

Быть единственным шагом, который размечает произвольное хранилище пользователя для любого потребителя и согласует разметку с пользователем — без изменения исходных файлов, без утечки чужих данных, без обращения к нашим серверам. Разметчик не содержит доменного знания и не принимает решений о содержании руководства или плана — только о МЕТКЕ и ДОПУСТИМОСТИ материала.

## 1а. Схемы меток — предписание запуска (РП-518 Ф25, АрхГейт и решение пилота 26.11.2026)

Функция роли одна — разметка. Набор меток задаётся запуском, а не ролью: новая цель потребителя — новая схема, не новая роль («функция одна — разметка», пилот 26.11.2026). Один проход по хранилищу может ставить метки сразу по нескольким схемам; пользователь в данной работе видит только схему её потребителя.

| Схема | Метки | Потребитель | Когда запускается |
|---|---|---|---|
| Руководство | 2.1 устойчивые факты / 2.2 поток событий / 2.3 доменные знания / 2.4 остаток | роль Портной (`DP.ROLE.001`, R27) | вызов `structure_base` перед сборкой руководства |
| Стратегия | цель / неудовлетворённость / обязательство (с датой или зависшее) / предложение / история / в архив / отложено | сессия стратегирования (Стратег и Плановик, `DP.SC.011`) | первым содержательным этапом каждой сессии стратегирования; новое — с даты прошлой сессии, в первой — всё хранилище |

**Общее для всех схем:**
- Новое с даты определяется без LLM — по истории сохранений, а где её нет (браузерный помощник) — по ответу пользователя. Карантин чужого и секретного (чужие личные данные, секреты, платёжные данные; упоминание другого человека основанием не служит) там, где работает программа разметки (схема руководства), выполняет программа (И1, И4 `DP.SC.055`); чужие личные данные она надёжно не определяет, это ограничение программы, а не схемы. В шаге сессии стратегирования такой программы пока нет ни в одной среде: агент сам не решает, а показывает подозрительное пользователю с путём и причиной, решение принимает пользователь — принятый риск АрхГейта 26.11.2026.
- Каждая смысловая метка несёт источник и уверенность; низкая уверенность показывается отдельно.
- **Согласование с пользователем** — общий шаг: карта показывается группами (5–7), не больше 40 меток за одно согласование, остальное — «отложено» с возвратом; запись в документы потребителя — только после согласования. Учёт: число меток, изменённых пользователем, отложенных; три согласования подряд при ≥20 метках без единой правки — сигнал, что согласование идёт не глядя.
- **Постоянная карта.** Результат разметки не живёт одну сессию: каждый элемент получает пометку области (проект или сфера жизни, как их называет пользователь) и после решения пользователя записывается в постоянный дом своей метки. Дом определяет личная карта маршрутизации пользователя — документ в его хранилище стратегирования, образец и дома по умолчанию — [[DP.KR.002]] §9; своей таблицы домов роль не держит. Вместе дома образуют карту материала пользователя для всех потребителей: перед сессией стратегирования разметка дописывает в неё только новое, а любая работа берёт из неё своё по пометке области. Рабочий продукт роли — [[DP.WP.017]]. Решения пилота 26–27.11.2026.
- Где описан шаг стратегической схемы для агента: шаблон IWE, шаг «Разметка нового» сессии стратегирования (`roles/strategist/prompts/strategy-session-weekly/steps/02-inbox.md`).

**Отличие от роли Портной/Генератор (`DP.ROLE.001`, R27):** Разметчик — upstream, работает с сырой базой и производит структурированный индекс + профиль. Портной — downstream, потребляет этот индекс и профиль, ничего не знает о внутреннем устройстве исходной базы. Границу нельзя стирать: Портной не должен сам классифицировать файлы, Разметчик не должен сам решать, что писать в руководство.

## 1б. Методы разметки (РП-526 Ф14, решение пилота 27.11.2026)

Основная редакция, согласованная пир-сессией 27.11.2026 (Claude, Kimi, Codex) и принятая пилотом; варианты «принимать по правилу без согласования» и «личная карта как собираемое представление из реестра и файла отклонений» отклонены. Общие правила схем — §1а; здесь — как Разметчик ставит метки.

1. **Две оси для пользователя.** Пользователь видит вид материала (метка схемы запуска, §1а) и область. Свежесть — служебные метаданные. Чувствительность — отдельная политика допуска: из вида материала она не выводится.
2. **Область — контекст использования:** «в каком проекте или сфере жизни ты этим пользуешься», а не «о чём материал».
3. **Правка → правило только после подтверждения.** Правка метки элемента применяется сразу как решение пользователя. Повторение одной правки — повод предложить обобщение отдельным пунктом текущего или следующего согласования: с областью действия, исключениями и 2–3 примерами. Правило появляется только после «да»; правило маршрута пишется в личную карту ([[DP.KR.002]] §9), правило классификации маршрутом не считается. Мерило — доля правил, которые потом не исправлялись.
4. **Порядок показа.** Неуверенное и противоречащее карте показывается первым. Метки, поставленные по подтверждённому правилу, — одной строкой «предложено по правилу, N штук»; их можно поправить до записи, согласование §1а сохраняется.
5. **Охват по поводу запуска.** Первая сессия стратегирования — всё хранилище по правилам шага «Разметка нового» (§1а). После установки новой версии — опись по месту без LLM и сводка словами пользователя («у тебя 15 проектов, 200 файлов без дома») с разделением «установлено / предполагается», затем разметка активного материала; остальное получает статус «не размечено, вне охвата» (не метку «история»).
6. **Ось 2.1–2.4 без кодов.** В схеме руководства пользователь видит названия «устойчивые факты», «события», «доменные знания», «остаток (предварительная категория)».
7. **Изъяны структуры — сигналом, не исправлением.** Разметчик передаёт Архитектору личной структуры ([[DP.ROLE.131]]) сигналы: неоднозначный маршрут (у материала два возможных дома, карта их не различает), расхождение карты и факта, повторно нет дома; и наблюдения с числом без диагноза — размер дома, давность использования. Структуру Разметчик не меняет.
8. **Реестр и личная карта.** Реестр доменов задаёт общие виды и допустимые дома по ролям; личная карта хранит подтверждённые маршруты пользователя, его источники и области. Обновление реестра готовит различия на согласование и не меняет личные маршруты без подтверждения.
9. **Из внешних практик — принципы, не таблицы соответствия.** Ось действенности (PARA) уже есть в стратегической схеме — без отождествления меток с категориями PARA; навязанная нумерация (Johnny.Decimal) отклонена, потому что собственная раскладка пользователя остаётся на месте; прогрессивное резюмирование — работа с материалом после разметки, вне этой роли.

## 2. Обязанности

| Обязанность | Метод | Триггер |
|-------------|-------|---------|
| Разметить базу по месту (дом/папка → тип) | `homes.yaml`-маппинг + frontmatter-override | Вызов `structure_base` |
| Классифицировать по структурным сигналам (per-file) | Эвристики: дата события→2.2, self-declared→2.1-declared, вывод из потока→2.1-derived, FPF-форма→2.3, след решений носителя→2.4 | Файл не покрыт `homes.yaml` или требует уточнения |
| Карантинировать «вне оси» | Детерминированные признаки чужого PII/секретов/платежей | Обнаружен файл вне допустимой оси |
| Присвоить freshness | `valid_from`+TTL/`superseded_by` из frontmatter (2.1); append-only (2.2); supersede-цепочка (2.3) | Каждый размеченный файл |
| Поднять и самовалидировать `search()`-endpoint | MCP-контракт `search(query, limit?, source?, source_type?)` + Knowledge Gate KG-01..13 | После разметки |
| Классифицировать явно неоднозначные файлы через LLM (опц.) | BYOK/локальный LLM-вызов, результат помечен `source: llm-assisted` | Файл не классифицирован детерминированно |
| Разметить новое по стратегической схеме и согласовать карту с пользователем | Детерминированно — новое с даты прошлой сессии стратегирования; чужое и секретное — показом пользователю (§1а); LLM — смысловая метка с уверенностью; группировка и согласование по §1а | Начало каждой сессии стратегирования; черновые метки — ночная подготовка черновика недели |

## 3. Полномочия

- **Читает** файловую базу пользователя (путь) или существующий MCP `search()`-backend.
- **Пишет** `.structurer/type-index.json`, `profile.yaml` (секция 2.1-declared), `residency.yaml`, карантинный bucket-лист — все локально, в пространстве пользователя.
- **Не решает** содержание руководства — это исключительно Портной (`DP.ROLE.001`).
- **Не отправляет** содержимое файлов на внешние серверы, кроме явного, управляемого пользователем BYOK-вызова LLM для неоднозначных файлов.
- **Не разрешает** карантин «вне оси» самостоятельно — снятие карантина требует явного действия пользователя, не входит в обязанности роли.

## 4. Границы роли

| Делает | НЕ делает |
|--------|-----------|
| Классифицирует файлы по типам 2.1-2.4 | Не решает, что из этого попадёт в конкретное занятие руководства (это Портной) |
| Ставит стратегические метки и согласует карту с пользователем | Не решает, что войдёт в стратегию и план недели, и не пишет туда до согласования (это Стратег и Плановик с пользователем) |
| Карантинирует подозрительные данные | Не удаляет и не изменяет исходные файлы пользователя |
| Присваивает freshness по frontmatter | Не выдумывает freshness для файлов без даты (оставляет `unknown`, не текущую дату) |
| Поднимает локальный `search()`-endpoint | Не хранит и не индексирует данные на наших серверах |
| Использует LLM для неоднозначных файлов (опц.) | Не использует LLM для решения о карантине (И4 — детерминировано) |

## 5. Артефакты

**Входы:**
- Путь к файловой базе пользователя ИЛИ существующий MCP `search()`-backend.
- `.structurer/homes.yaml` (опционально; есть разумный дефолт).
- Frontmatter-override в файлах пользователя (опционально).

**Выходы:**
- `.structurer/type-index.json` — путь → `{type, subtype, mode, freshness, confidence, source}`.
- `profile.yaml` (частично — секция 2.1-declared).
- `residency.yaml`.
- Карантинный bucket-лист «вне оси».
- Локальный MCP `search()`-endpoint над размеченной базой.

## 6. Носители (carriers)

**Целевой носитель:** открытый Python-пакет `structurer/` внутри публичного репозитория guide-kit (WP-483 Ф1-Ф2) — детерминированный код, ноль обязательных бэкенд-зависимостей. Migration Path: роль переносима на любой рантайм (headless CLI, MCP-инструмент внутри стороннего ИИ-помощника) — тест переносимости «уберу конкретный host — роль работает?» да, так как контракт `search()` и формат `profile.yaml` — vendor-neutral.

**Требование к дефолтному адаптеру (ArchGate storage-абстракции, WP-483 Ф0, решение пилота 2026-07-13):** файловая система + SQLite+vec0 — обязательный zero-config адаптер, работает без настройки и без внешних сервисов (сценарий «Марина» — незарегистрированный пользователь без поддержки). Notion+Git/GitHub/pgvector-адаптеры опциональны, не блокируют базовый сценарий. Обоснование и полный профиль ЭМОГССБ — `DS-my-strategy/inbox/WP-483/f0-gates/DRR-storage-abstraction.md`.

## 7. Открытые вопросы

- **Q1 (Owner Role):** временно назначен «Платформенный архитектор (bootstrap)» по аналогии с `DP.ROLE.083` — при выделении guide-kit в самостоятельный продукт с отдельным владельцем требуется пересмотр.
- **Q2 (граница с WP-449 таксономией):** частично снят §1а (26.11.2026): несколько осей — это несколько схем меток одного запуска, а не смешение в одной схеме; ось WP-449 может стать третьей схемой. Исходная формулировка: Разметчик реализует ось 2.1-2.4 (изменчивость + данные/знание), НЕ ортогональную 4-классовую онтологию WP-449 (индекс/указатель/снаружи) — смешение осей даёт противоречивые метки (см. концепция §6.2 «Осевая дисциплина»). Зрелая версия может выдавать обе метки как разные классификаторы — не решать сейчас.
- **Q3 (тип 2.4):** трактовка «выразимость vs переносимость» не финализирована (см. `DP.SC.055` «Открытые задачи», WP-449 Ф2). Ось `2.4` помечена `provisional`. Пользователю ось показывается без кодов, названиями «устойчивые факты / события / доменные знания / остаток (предварительная категория)» (§1б п. 6).
