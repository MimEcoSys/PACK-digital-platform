# DP.ROLE.103 — Верификатор допуска (admission class verifier)

## Kind / Owner

- **Kind:** специализированный исполнитель (read-only функция, детерминированный код, не LLM-решение — убери функцию, вызывающий агент просто не может проверить допуск, ничего не «решает» за него).
- **Owner Role:** DP.ROLE.001 (IWE Creator) — владелец надсистемы IWE, тот же прецедент, что DP.ROLE.102 (Сторож намерения).

## Обязанности

- По запросу вызывающего агента (действие, ресурс) — прочитать реестр классов допуска, найти неистёкшую запись, покрывающую ОБА идентификатора с учётом `constraints`.
- Неизвестное/непонятное ограничение в `constraints` → не разрешение, отказ.
- Отсутствующий/повреждённый реестр и валидный пустой реестр дают одинаковый внешний ответ «нет подтверждённого допуска» — но с разными внутренними причинами для диагностики (не путать по логам).
- Отказ самой проверки (реестр недоступен) → откладывает только действия, требующие этой конкретной проверки; разрешённая и уже проверенная работа продолжается (Protective Procedure Fallback, CLAUDE.md).
- Не интерпретировать «нет записи, покрывающей действие» как «класс не существует вовсе» без различения причины (producer bug vs. легальное «ещё не утверждено»).
- Не подключать и не переиспользовать механизм объявления намерения (DP.ROLE.102/DP.SC.204) — разные вопросы («связан ли вызов с объявленным РП» vs. «покрыто ли действие утверждённым допуском»), разводятся явно по решению пир-сессии 15.10.

## Полномочия

- Read-only к реестру классов допуска. Не мутирует реестр — создание/утверждение нового класса делает отдельный процесс с человеком-владельцем (контракт 15.10: write token даёт право инициировать запрос, не утверждать).
- Write только в собственный лог отказов/причин (для диагностики, не для принятия решений).

## Входы / Выходы (артефакты)

- **Вход:** запрос вызывающего агента (действие, ресурс); реестр классов допуска (запись: `id`, `allowed_actions`, `allowed_resources`, `constraints`, `approved_by`, `approval_date`, `expiry`).
- **Выход:** да/нет-ответ с причиной (покрыт/не покрыт, или причина отказа проверки); запись в лог отказов/причин.

## Граница с соседними ролями

- **DP.ROLE.102 (Сторож намерения)** — тот же Kind (детерминированный код, владелец DP.ROLE.001), другой домен и другой триггер: Сторож перехватывает КАЖДЫЙ вызов инструмента (PreToolUse-хук), этот верификатор вызывается агентом САМИМ, когда агент не уверен в допуске на конкретное действие — не на каждый вызов. Прохождение одного слоя не означает прохождения другого.
- **Контракт класса допуска (карточка РП-561, секция Ф35, раунд 2, 15.10)** — этот верификатор РЕАЛИЗУЕТ проверку по уже согласованному формату полей, не меняет и не расширяет сам формат.
- **Процесс утверждения нового класса допуска** — смежный, но отдельный от этой роли: утверждает только заранее назначенный человек-владелец, полный IntegrationGate на расширение; эта роль не участвует в утверждении, только в проверке уже утверждённого.
