# Runtime Tool Discovery через JSON-RPC (DP.M.017)

## Назначение

Метод определяет, как LLM-клиент должен получать список доступных инструментов (tools) от MCP-сервера — динамически, без hardcoded описаний в коде клиента.

Применим к любому LLM-клиенту, интегрирующему MCP-сервер с изменяемым каталогом capabilities.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Актуальность каталога tool ↔ latency повторных обращений | TTL-кэш 15 мин (Bootstrap-загрузка, шаг 4) даёт свежий список без запроса `tools/list` на каждый вызов, но между обновлениями клиент может работать с устаревшим каталогом до 15 минут |
| Устойчивость к недоступности MCP (last-known-good) ↔ риск работы со stale tool | Режим отказа отдаёт кэш до 1 часа, чтобы не ронять клиента (инвариант 4), но сервер за это время мог убрать или изменить tool — клиент продолжает предлагать их пользователю |
| Отказ от hardcoded списка ↔ предсказуемость/тестируемость клиента | Динамическое построение списка из ответа сервера (инварианты 1-2) даёт эволюционируемость платформы, но лишает клиент compile-time проверки: ошибка в JSON-Schema сервера обнаруживается только в runtime у пользователя |

## Алгоритм

### Bootstrap-загрузка (при старте клиента)

1. Отправить `tools/list` JSON-RPC к целевому MCP-серверу
2. Получить список `ToolDescriptor` с JSON-Schema
3. Применить tier-фильтрацию (naming convention: `admin_*`, `subscriber_*` или explicit tags в tool-descriptor)
4. Сохранить в local cache с TTL = 15 мин

### Периодическое обновление (TTL-refresh)

1. По истечению TTL — повторить bootstrap-загрузку
2. При успехе — обновить кэш, сбросить TTL
3. При ошибке — сохранить last-known-good, зафиксировать в лог

### Режим отказа (MCP-сервер недоступен)

1. Вернуть last-known-good кэш (max TTL: 1 hour)
2. Если кэш пуст после неудачной Bootstrap-загрузки → это сбой обнаружения, а не пустой каталог: пока идёт фоновый повтор (см. «Пустое обнаружение при старте»), вернуть `essential: true` subset или пустой список и записать в журнал тип исключения. Пустой список как каталог — только если сервер его действительно вернул
3. Не блокировать работу клиента из-за недоступности MCP

## Пустое обнаружение при старте — сбой, а не пустой каталог (дополнение 2026-11-18, РП-170)

Прецедент (aist_bot_newarchitecture `0d5b183c`, PR #378; на пилотной ветке `f0e0a077`, PR #372; WP-5 Ф70). Сразу после старта контейнера `tools/list` шёл под общим бюджетом вызова (3 с) против ещё «холодного» шлюза. Через ~3 с он падал с пустым текстом ошибки (у `TimeoutError` пустой `str()`), и бот работал без инструментов, пока первый вопрос пользователя не запускал обновление. В журналах пилотного бота это видно 29.10, 02.11 и 04.11. Исправление выпущено 09.11; что пустых загрузок после него нет, пока не проверено (то же записано в DP.SC.129).

Отсюда правка «Режима отказа», п. 2: пустой кэш **после неудачной** Bootstrap-загрузки — не «у сервера нет инструментов», а сбой обнаружения. Пустой список **как каталог** допустим только как ответ сервера, который действительно получен.

Добавления к Bootstrap-загрузке:

1. У `tools/list` свой таймаут (в прецеденте 15 с), не бюджет обычного вызова инструмента.
2. Старт не ждёт обнаружения. Пока кэш пуст, фоновая задача повторяет запрос с нарастающей паузой (в прецеденте 30/60/120 с).
3. Обнаружение идёт вне семафора пользовательских вызовов, не больше одного запроса за раз. Медленное обновление не ставит в очередь вопросы людей.
4. В журнал пишется тип исключения, а не только его текст: у части исключений текст пуст, и без типа причина теряется.

Тест: «Что делает клиент, если `tools/list` при старте не ответил: ждёт пользователя или повторяет сам?» Ждёт пользователя — первый вопрос после каждого перезапуска обслуживается без инструментов.

## 4 инварианта

1. **Клиент не знает схему tool заранее** — список строится только из ответа сервера
2. **Список запрашивается при каждом bootstrap** — не hardcoded при компиляции/деплое
3. **TTL-кэш снижает latency** — повторные обращения ≤ 500ms
4. **Fallback на last-known-good** — недоступность сервера не роняет клиента

| _(tentative)_ Happy-path TTL-refresh перевешивает ветку ошибки | Внимание смещается на успешное обновление кэша (шаг 2 «Периодическое обновление»), а требование шага 3 «при ошибке — сохранить last-known-good, зафиксировать в лог» реализуется без логирования, потому что тестируется обычно только успешный прогон |
| _(tentative)_ Пустой кэш читается как пустой каталог | Ветка «кэш пуст → пустой список» выглядит как штатная, хотя после неудачной Bootstrap-загрузки это сбой обнаружения; без фонового повтора клиент работает без инструментов до первого запроса пользователя (aist_bot `0d5b183c`) |

## Антипаттерн

**Hardcoded список tool** в коде клиента:
- Не подхватывает новые tool на сервере без правки кода клиента
- Требует синхронного деплоя клиента и сервера
- Нарушает эволюционируемость L2 платформы (DP.ARCH.001)
