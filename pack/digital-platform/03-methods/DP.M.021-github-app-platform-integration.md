# DP.M.021 — GitHub App для платформенной интеграции с пользовательскими репо

## Проблема

Manual webhook не масштабируется на 50+ пользователей: ручная регистрация, общий HMAC-секрет (уязвимость), нет самообслуживания при уходе пользователя.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Самообслуживание пользователя (uninstall = автоматический отзыв, инвариант 4) ↔ контроль платформы над доступом | App-модель отдаёт пилоту полный контроль над включением/выключением через Install-flow, но платформа теряет возможность централизованно и мгновенно отозвать write-permission без участия пользователя |
| Масштабируемость (App регистрируется один раз, инвариант 1) ↔ изоляция инцидента | Один App на всех пользователей радикально проще ручной регистрации 50+ webhook, но компрометация App-credentials платформы потенциально затрагивает все installation_id одновременно, а не одного пользователя |
| Write-permission по согласию (инвариант 3, Install-flow) ↔ скорость онбординга | Явное согласие на write-доступ защищает от неявного расширения прав, но добавляет шаг трения по сравнению с гипотетическим «тихим» webhook без клика Install |

## Метод

Платформа регистрирует GitHub App один раз. Каждый пилот ставит App на свой репо (один клик Install). App получает write-permission и push events. Каждый installation_id уникален → per-installation user mapping. Уход пилота = uninstall (самообслуживание).

## Инварианты

1. Платформа регистрирует App один раз — не per-user
2. Каждый installation_id уникален → изолированный user mapping
3. Write-permission выдаётся по согласию пользователя (Install-flow)
4. Uninstall = автоматический отзыв доступа (без ручных шагов платформы)

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Внимание смещается на инвариант 1 как «технически сложную» часть | Регистрация App один раз кажется главной работой, а инвариант 2 (per-installation user mapping через installation_id) недооценивается — единственный механизм изоляции пользователей реализуется небрежно, например через repo name вместо installation_id |
| «Уход пилота = uninstall» воспринимается как решённое GitHub-платформой | Внимание смещается на install-сторону потока (регистрация, первый webhook, installation_id) и не доходит до симметричного uninstallation-события — практик по умолчанию считает создание и развитие mapping завершёнными установкой, хотя инвариант 4 требует такой же явной обработки на отзыве доступа |

## Применимость

Любая платформа, интегрирующаяся с GitHub-репозиториями множества пользователей (50+).
