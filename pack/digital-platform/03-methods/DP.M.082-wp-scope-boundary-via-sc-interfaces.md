# DP.M.082: WP scope boundary через DP.SC interfaces

## Когда применять

У РП появляются «соседние» родственные работы (Q&A history, Trace store, Session Memory Injector, real-time channel, системные правила, общие компоненты). Соблазн merge: «это близко по теме, объединим в один РП». Результат: scope инфлируется до неподъёмного, обещание размывается, owner перегружен.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Компактность собственного обещания РП ↔ покрытие смежных работ | Merge scope даёт единого owner'а и единое место, но инфлирует РП до неподъёмного (пример из карточки: umbrella на 50ч, ArchGate не проходит); разнесение по SC-интерфейсам держит каждый РП маленьким, но каждый сосед добирает своё в своём темпе — координация через `uses/realizes/extends` вместо общего scope |
| Документальная явность границы ↔ скорость проектирования | Таблица «Что НЕ входит в этот РП» требует письменного ответа на каждую возможную работу (строка за строкой, как в примере WP-324), а не решения «в голове owner'а» — метод платит временем на таблицу за то, что при закрытии достаточно проверить только собственное SC-обещание |

## Метод

1. **Каждый РП реализует своё обещание** (`realizes: DP.SC.NNN`).
2. **Связки с соседями — через явные SC-ссылки**:
   - `uses: DP.SC.MMM` — потребляет обещание соседа.
   - `realizes: DP.SC.NNN` — реализует это обещание (выход своего РП).
   - `extends: DP.SC.KKK` — расширяет обещание соседа (specialization).
3. **При закрытии РП** достаточно проверить, что собственное SC-обещание выполнено. Соседи доберут своё в своих РП.

## Артефакт паттерна

Раздел «**Что НЕ входит в этот РП (граница scope)**» в WP-context-файле с таблицей:

| Возможная работа | Куда относится | Почему не сюда |
|------------------|----------------|----------------|
| Q&A history | WP-XXX (отдельный РП) | Другое обещание (хранение vs маршрутизация) |
| Trace store | WP-295 (planned) | Inbox = транзит, Trace = архив (разные рабочие процессы) |
| Session Memory Injector | WP-316 | Память агента ≠ inbox задач |
| Real-time channel | WP-203 Ф6 | Режим артефакта, не новый артефакт (см. DP.D.069) |

## Тест

**«Если читатель спросит "почему не объединили X с этим РП" — есть ли явный ответ в WP-context?»**

- **Только в голове owner'а** → недостаточно. Нужна таблица «Что НЕ входит».
- **В таблице** → scope boundary защищена документально.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| Выделение соседнего РП затмевает объявление interface-ссылки | Внимание практика фиксируется на декомпозиции («вынесли работу в отдельный РП — готово»), а явная SC-ссылка (`uses` / `extends`) между соседями остаётся необъявленной: формально scope разделён, фактически связь существует только в голове owner'а, и тест карточки («есть ли явный ответ в WP-context») не проходит |
| Реализация своего обещания затмевает заполнение таблицы «Что НЕ входит» | Усилия уходят в `realizes: DP.SC.NNN` собственного РП, а таблица отклонённых работ пишется «потом» или не пишется вовсе; при закрытии оказывается, что граница scope существует только как намерение, и вопрос «почему не объединили X» снова требует устного ответа owner'а |

## Анти-паттерн

«Соседние темы — все вместе» → 1 zonтик-РП на 50ч с размытым обещанием. Owner не знает, когда РП закрыт; ArchGate не проходит (несколько архитектурных решений в одном).

## Пример (WP-324 Agent Inbox)

5 соседних работ:
- Trace store (WP-295) — `extends: DP.SC.NNN-agent-trace`
- Session Memory Injector (WP-316) — separate WP, no interface (разные scope)
- Notification Dispatcher (WP-320) — `uses: DP.SC.MMM-notification-dispatch` для P0-уведомлений
- Real-time channel — `extends: DP.SC.NNN` (WP-203 Ф6, не отдельный РП — см. DP.D.069)
- Системные правила (CCR ↔ inbox protocol) — `uses: DP.SC.KKK-ccr-runtime`

Каждая работа сохраняет связь через interface, не через merge scope.

## Применимость

- Любой crowded scope (Agent Inbox, Session Memory, ЦД→Память migration).
- Zonтик-РП с подфазами — каждая подфаза имеет своё SC, родитель агрегирует.
- Обсуждения «расширим scope или новый РП».
