# DP.M.301 — Sync workflow для derived-файлов

## Описание

Архитектурный паттерн для двух копий одного контентного файла, синхронизируемых односторонне (sync-скрипт автор → потребитель): explicit «direction of truth», READ-ONLY маркер в derived, обязательный commit перед sync.

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость правки на месте ↔ дисциплина commit-перед-sync | Проще поправить derived-копию прямо там, где её видишь (бот, потребитель); правило «правь только в source, коммить перед sync» требует лишнего шага и переключения контекста |
| Удобство локальной правки потребителя ↔ единственность источника истины | Потребитель derived-файла может локально исправить очевидную ошибку быстрее, чем донести её до автора; но эта правка обречена быть перезаписанной при следующем sync |
| Явный READ-ONLY маркер ↔ отсутствие enforcement на уровне инструмента | Маркер в CLAUDE.md — это соглашение, а не техническое ограничение; ничто не мешает отредактировать derived-файл напрямую, если маркер не подкреплён pre-condition в самом sync-скрипте |
| Своевременный sync ↔ незакоммиченное состояние источника | Частый sync держит производную копию свежей; но если автор ещё не закоммитил текущую правку, sync в этот момент разносит неполное/промежуточное состояние как «истину» |

## Failure mode

Если правка сделана в обеих копиях одновременно (автор не закоммитил, кто-то правит копию-потребитель), последующий sync перезатирает правки потребителя незакоммиченным состоянием источника.

## Конкретный инцидент

9 июня 2026 sync (commit `138a760`) перезаписал правильные правки бота (commit `db243c0`: IWE→ИИ-помощник) незакоммиченным авторским файлом. Авторский файл без коммита = undefined state при sync.

## Правила

1. **Source-of-truth (авторский файл)** — единственное место правок.
2. **Derived (бот-копия)** — read-only, помечена маркером READ-ONLY в CLAUDE.md потребителя.
3. **Workflow:** edit → commit → push в авторском репо → sync-скрипт → commit+push derived. Sync без коммита источника блокируется pre-condition в скрипте или варнингом.

## Архитектурный маркер

В CLAUDE.md обеих сторон — explicit «direction of truth»:
- автор: «source-of-truth для X — этот файл; sync пушит в потребитель»
- потребитель: «READ-ONLY копия X из автора; правки сюда — потеряются при следующем sync»

## Применимость

Любые derived-файлы: marathon-content.json, config.json, generated-data, pre-rendered шаблоны, скопированные части документации.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Это же derived, но исправить проще прямо тут» | Локальное удобство правки в моменте перевешивает знание о том, что derived — read-only; практикующий у потребителя чинит симптом на месте, а не идёт к source-of-truth |
| «Sync — фоновая механика, я о ней не думаю при правке» | Внимание сосредоточено на самой правке контента, а не на её судьбе при следующей синхронизации; момент sync воспринимается как отдельное, не связанное с текущей правкой событие |
| «Коммит сделаю чуть позже, сейчас доработаю» | Естественное желание довести правку до готового вида перед коммитом создаёт окно незакоммиченного состояния; именно в этом окне может сработать sync и разнести промежуточную версию |
| «В CLAUDE.md написано READ-ONLY — этого достаточно» | Текстовый маркер воспринимается как решённый вопрос, хотя он не технический guard; внимание не идёт дальше — к вопросу, действительно ли sync-скрипт технически блокируется при незакоммиченном источнике |
