# DP.M.308 — Проверка читателей перед удалением sender-side гейта

## Обещание

При миграции логики в централизованный сервис — предотвращает ослепление downstream-readers, которые читали данные удаляемого sender-side гейта (дедупликатор, cooldown, журнальный write).

## Forces

_Какие конкурирующие давления удерживает метод._

| Force | Tension |
|-------|---------|
| Скорость миграции ↔ полнота проверки readers | Grep + документирование каждого reader занимает время, но пропуск этого шага рискует ослепить downstream-потребителей молча |
| Локальная видимость sender-side гейта ↔ распределённость readers | Разработчик, удаляющий гейт, видит только код отправителя; readers могут находиться в других модулях/сервисах, не связанных явной зависимостью в коде |
| Атомарность коммита ↔ объём изменений за раз | Атомарный коммит (новый writer + удаление старого гейта + smoke-test) безопаснее, но требует координировать больше движущихся частей одновременно, чем поэтапное удаление |
| «Тесты зелёные» как сигнал готовности ↔ реальная миграция readers | Зелёные тесты проверяют текущий код-путь, но не гарантируют, что все реальные readers (включая внешние по отношению к test-suite) учтены |

## Алгоритм

1. **Grep readers по формату записи:**
   ```bash
   grep -rn "<journal_key>\|<event_type>\|<external_id>" --include="*.py" .
   ```
2. **Задокументировать каждого reader:** что читает, зачем, SLA
3. **Оценить безопасность удаления:**
   - Нет readers → безопасно удалять
   - Есть readers → сохранить контракт: semantic key переезжает в новый writer (drain/central service)
4. **Атомарный коммит:** новый writer + удаление старого гейта + smoke-test readers

## Когда применять

- Перед удалением любого sender-side state (дедупликатор, cooldown гейт, журнальная запись)
- При выносе логики в централизованный сервис (notification drain, central dedup)
- При рефакторинге event pipeline

## Тест

«Кто ещё читает то, что пишет этот гейт?» Если есть reader → контракт сохранить в новом writer'е.

## Bias-Annotation

_Куда систематически съезжает внимание практикующего._

| Bias | Direction of distortion |
|------|--------------------------|
| «Это мой гейт, я его писал, я знаю всех, кто его читает» | Автор кода переоценивает собственное знание о downstream-потребителях; readers, добавленные другими за время жизни гейта, выпадают из памяти |
| «Grep ничего не нашёл — значит readers нет» | Grep по буквальному ключу не находит readers, которые получают данные через промежуточный слой (очередь, кэш, дериватив) — отсутствие прямого текстового совпадения принимается за отсутствие зависимости |
| «Централизация — это всегда улучшение, детали потом» | Фокус на архитектурной цели (вынести логику в central service) отвлекает от тактического вопроса «а что сломается прямо сейчас у существующих readers» |
| «SLA каждого reader не важен, главное — что он есть» | При документировании readers внимание останавливается на факте существования, не доходя до вопроса, насколько критичен reader и что случится, если он временно ослепнет |

## Дополнение: фактическое чтение после изменения формата записи

После миграции проверить источник чтения и наблюдаемый результат на нужной свежей записи каждым заявленным путём. Общая база данных не доказывает совместимость формата, версии и фильтров потребителя. Зафиксировать проверенный охват и оставшиеся гипотезы; отсутствие найденных прямых читателей само по себе не доказывает полноту инвентаризации зависимостей.

Один ответ старого формата — симптом. Он может зависеть от версии, кэша, отсутствия нового события или другого источника; по нему нельзя объявить разрыв для всех пользователей.
