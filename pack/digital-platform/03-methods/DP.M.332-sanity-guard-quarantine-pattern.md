# DP.M.332 — Паттерн карантина sanity-guard

## Описание

Sanity-guard для append-only хранилища проектируется двухслойно:
1. **Карантин, не финальный статус** — аномальная запись помечается «требует проверки»; решение о финализации отделено от детекции.
2. **Durable инцидент-запись** — каждое срабатывание guard'а создаёт запись в отдельной инцидент-таблице (не только уведомление).

Это уточняет более раннее DP.FM.186: сам guard тоже требует проектного решения.

## Forces

| Force | Tension |
|-------|---------|
| Немедленная защита данных ↔ риск отбраковки валидных значений | Жёсткий отказ (reject) на аномалию защищает хранилище от мусора сразу, но легитимный системный сбой (законный ноль) выглядит так же, как ошибка — guard не может различить их автоматически |
| Простота единственного финального статуса ↔ разделение детекции и финализации | Один шаг «принять/отклонить» проще реализовать, но не оставляет места для человеческого ревью; карантин добавляет промежуточный статус ценой усложнения состояний записи |
| Дешевизна эфемерного уведомления ↔ стоимость durable инцидент-таблицы | Telegram-алерт дёшев и достаточен для немедленного внимания, но пропадает без следа; инцидент-таблица требует схемы и хранения, зато переживает момент срабатывания |
| Скорость закрытия инцидента ↔ качество ревью аномалии | Быстрая финализация (авто-accept/reject) снижает нагрузку на ревьювера, но именно нестандартные значения чаще всего требуют вдумчивой проверки — торопливость конфликтует с целью guard'а |

## Algorithm

### Step 1: Детектировать аномалию

Порог guard'а срабатывает на входящую запись (отклонение от медианы, нулевое значение в не-нулевом домене, значение вне допустимого диапазона).

### Step 2: Карантин — не отказ и не пропуск

```sql
-- Записать в хранилище со статусом карантина, не отбрасывать и не принимать финально
INSERT INTO metrics (..., status = 'quarantined', review_required = true)
```

### Step 3: Создать durable инцидент-запись

```sql
INSERT INTO metric_incidents (ts, source, anomalous_value, reason, status)
VALUES (now(), 'panel_worker', :value, 'sigma_threshold_exceeded', 'open')
```

Уведомление (Telegram-алерт) — эфемерно, пропадёт. Инцидент-запись — durable.

### Step 4: Финализировать отдельно

Ревью инцидента → принять значение / скорректировать / отклонить. Финализация не автоматическая.

## When to Use

- Append-only хранилища с финальными значениями (DP.FM.186)
- Метрики, где аномалия может быть валидной (системный сбой → законный ноль)
- Любой расчётчик, где порог срабатывания не различает «данные некорректны» и «данные нестандартны»

## Тест применимости

«Guard может ошибочно отклонить реальное значение?» Да → карантин обязателен (аномалия ≠ ошибка). «Уведомление — единственный след срабатывания?» Да → нужна инцидент-таблица.

## Bias-Annotation

| Bias | Direction of distortion |
|------|--------------------------|
| «Аномалия — значит ошибка, отклоняю сразу» | Порог срабатывания guard'а систематически трактуется как доказательство некорректности, хотя он лишь сигнализирует отклонение от нормы — не различает «неверно» от «нестандартно» |
| «Алерт отправлен — значит инцидент зафиксирован» | Внимание успокаивается на факте уведомления, упускается, что Telegram-сообщение эфемерно и не оставляет проверяемого следа для постмортема |
| «Guard — это разовая настройка порога» | Проектирование guard'а сводится к подбору числового порога (sigma, диапазон), не доходит до вопроса о двухслойной архитектуре (карантин + инцидент-запись) |
| «Раз данные в карантине — можно не спешить с ревью» | Промежуточный статус «требует проверки» снижает ощущение срочности; накопление нефинализированных инцидентов остаётся незамеченным без отдельного контроля очереди |
