# DP.M.413 — Файловая блокировка: освобождение через trap на любом выходе

## Проблема

Первая версия защиты планового скрипта от параллельного запуска (файловая блокировка) освобождала лок только на success-ветке выполнения. При ошибке скрипт завершался, не дойдя до строки освобождения, — лок оставался висеть и блокировал все последующие запуски, включая штатные.

## IPO

- **Вход:** скрипт, защищённый файловой блокировкой от параллельного запуска
- **Процесс:** освобождение лока регистрируется через `trap ... EXIT` сразу после захвата, а не отдельной командой в конце success-пути
- **Выход:** лок освобождается при любом варианте завершения скрипта — успех, ошибка, прерывание сигналом — следующий запуск не блокируется висящим локом

## Паттерн

```bash
LOCK_FILE="/tmp/my-script.lock"
exec 200>"$LOCK_FILE"
flock -n 200 || { echo "Already running, exiting"; exit 0; }
trap 'flock -u 200' EXIT   # снимает лок на любом пути завершения, включая ошибку
# ... тело скрипта, которое может упасть на любом шаге ...
```

## Антипаттерн

```bash
flock -n 200 || exit 0
# ... тело скрипта ...
flock -u 200   # выполнится только если весь код выше не упал — при ошибке лок повиснет
```

## Применимо

Любой плановый (cron/launchd/systemd) скрипт с защитой от параллельного запуска через файловую блокировку, где тело скрипта может завершиться ошибкой до достижения явной команды освобождения.

## Второй прецедент: именованный семафор с TTL — флаг захвата, единая точка освобождения, очистка устойчива к повторному сигналу

Оркестратор месячного такта (`month-open-orchestrator.sh`, DS-my-strategy `3186dd962`, WP-561) закрывал housekeeping-семафор вручную в ветках. Завершение по сигналу (код 143, SIGTERM) после успешного `open` не проходило через эти ветки, и семафор удерживался до истечения TTL.

Отличие от базового паттерна выше: здесь ресурс — именованный семафор с TTL, который переживает процесс (а не `flock` на дескрипторе). Поэтому к «освобождению через `trap ... EXIT`» добавляются три требования:

1. **Флаг захвата.** Флаг выставляется только после успешного `open`; обработчик выхода освобождает семафор только при выставленном флаге. Иначе обработчик, зарегистрированный раньше захвата, снимет чужой семафор (см. `DP.FM.491`). В источнике флаг называется `SG_OPEN`: `open ... && SG_OPEN=true || log "open failed (continuing)"`.
2. **Единая точка освобождения.** Закрытие выполняется централизованно в `on_exit` (`trap on_exit EXIT`); точечные `close` в ветках удалены.
3. **Очистка устойчива к повторному сигналу.** В начале `on_exit` стоит `trap '' HUP INT TERM`: второй сигнал не должен обрывать очистку на полпути.

Сопутствующее: перед `touch` lock-файла такта добавлен `mkdir -p "$(dirname "$LOCK_FILE")"` (в журнале WP-561 зафиксирован отказ из-за отсутствия каталога 30.09). Тест в источнике: завершение по SIGTERM, который падает на старой версии скрипта.

Иллюстрация схемы (не дословный код источника; имена `SEM_OPENED`, `semaphore_open`, `semaphore_close` условные):

```bash
SEM_OPENED=0
on_exit() {
  trap '' HUP INT TERM              # a second signal must not cut the cleanup short
  if [ "$SEM_OPENED" = 1 ]; then
    semaphore_close "$SEM_FILE"     # the only place that releases
  fi
}
trap on_exit EXIT
semaphore_open "$SEM_FILE" && SEM_OPENED=1
```

Тест: «Есть ли путь завершения (сигнал, не предусмотренная ветка), который не проходит через единственный обработчик освобождения? Может ли обработчик освободить ресурс, который процесс не захватывал?»
