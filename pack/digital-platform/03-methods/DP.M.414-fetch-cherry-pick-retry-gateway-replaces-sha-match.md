# DP.M.414 — Общий шлюз координации публикации: fetch + cherry-pick + retry вместо точного совпадения SHA

## Проблема

Изолированная worktree-сессия отказывалась коммитить/публиковать, если её HEAD расходился с общей веткой хоть на один коммит (точное совпадение версии как предусловие публикации). При параллельных сессиях общая ветка почти всегда успевала уйти вперёд за время анализа одной сессии — штатная гонка параллельной работы систематически превращалась в постоянный отказ публикации.

## IPO

- **Вход:** изолированная (worktree) сессия с готовым к публикации коммитом; общая ветка могла продвинуться вперёд за время работы сессии
- **Процесс:** публикация идёт через единый шлюз координации (уже использовавшийся открытием/закрытием дня для той же гонки) — забрать свежую общую ветку → перенести подготовленный коммит поверх неё → опубликовать с ограниченным числом повторов
- **Выход:** коммит публикуется, несмотря на то что общая ветка продвинулась за время работы сессии; проверка точного совпадения версии убрана как предусловие

## Паттерн

```bash
git fetch origin main
git cherry-pick <prepared-commit-sha>   # поверх свежего origin/main
for attempt in 1 2 3; do
  git push origin HEAD:main && break
  git fetch origin main   # ретрай: подтянуть то, что успело уйти вперёд, и повторить
done
```
Конкретная реализация — общий шлюз координации, уже используемый открытием/закрытием дня для той же гонки (не новый отдельный механизм).

- **Потолок попыток на один run.** Retry шлюза под общим замком ограничен числом попыток на один запуск клиента; по исчерпании — терминальный статус попытки и ровно один алерт по DP.M.420, а не алерт на каждую попытку (см. AS.FM.070, AS.M.083). Иначе один упавший клиент, не проходящий защиту от затирания, десятки минут занимает общий замок и превращает один сбой в серию алертов (случай 2026-09-29, WP-530: 41 минута).
- **Идентичность попытки в audit_log.** Каждая попытка пишется с PID + run_id, чтобы серия попыток одного клиента читалась как один инцидент, а не как много (см. DP.FM.200, DP.M.331).

## Применимо

Множественные параллельные (изолированные worktree) агентские сессии, публикующие в одну общую ветку, где предусловие «точное совпадение версии перед публикацией» превращает нормальную гонку параллельной работы в систематический отказ.

Также: любой скрипт/раннер, который коммитит в ОБЩИЙ checkout (разделяемый несколькими параллельными сессиями) и должен опубликовать свой коммит — см. вариант ниже. Сырой `git pull --rebase && git push` с такого checkout — не вариант метода, а его отсутствие.

## Вариант: вызывающий код коммитит в общий checkout (`--from-commit`)

**Проблема.** Плановый скрипт (развёрнутая копия strategist.sh) публиковал недельный обзор сырым `git pull --rebase` + `git push` прямо с checkout, которым параллельно пользуются другие сессии агентов. На таком checkout сырой путь регулярно упирается в грязное дерево чужой сессии, non-fast-forward или граничный случай pre-push хука (здесь — падение хука на необъявленной переменной), а обвязка логировала это как WARN и шла дальше. Итоги недели W36 были закоммичены локально, до `origin/main` не дошли и пережили только на резервной ветке; обнаружено фактчеком отдельного РП, не логом (WP-7 Ф101, commit 06e37c00e).

**Приём.** Шлюз принимает не путь к подготовленному изолированному worktree, а SHA коммита (`--from-commit <sha>`): сам создаёт одноразовый worktree на именованной ветке, указывающей на этот коммит, переносит диапазон merge-base(sha, origin/main)..sha поверх свежего origin/main, публикует с ограниченными повторами и всегда удаляет worktree и временную ветку. Общий checkout вызывающего кода не трогается ни на одном шаге. Поверхность публикации отделена от места, где коммит был сделан.

**Правило области.** Переход на шлюз делается для **всех** точек записи общего checkout, не только той, где потерю заметили (DP.FM.347, DP.FM.151 §вариант, DP.FM.394): в источнике оба push-сайта strategist.sh переведены одним коммитом (8ec5c04, FMT-exocortex-template), на тот же механизм, которым уже пользовался extractor.sh. Сбой шлюза — ошибка с кодом, не WARN (DP.M.415).

**Сигнатура симптома (для диагностики).** Артефакт «есть локально/на резервной ветке, нет на origin/main» + в логе раннера одна строка WARN без остановки конвейера + checkout разделяется с другими сессиями → сырой pull+push на общем checkout, применить этот вариант. Смежные, но другие механизмы: DP.FM.415 (чужой rebase подменяет базу коммита в окне check→commit), DP.FM.154 (push вообще не вызывается), AS.FM.026 (non-fast-forward при headless push; fetch+rebase перед push помогает только на СОБСТВЕННОМ checkout — на общем сам rebase небезопасен).
