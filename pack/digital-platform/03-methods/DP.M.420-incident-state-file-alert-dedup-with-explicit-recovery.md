# DP.M.420 — Файл состояния инцидента: один алерт на сбой, окно повторов, явное сообщение о восстановлении

## Описание

Периодическая проба (health-check раз в N минут) без памяти о предыдущем результате шлёт по алерту на каждый неудачный прогон и молчит при восстановлении: часовой сбой = 8 одинаковых сообщений и ни одного «всё в порядке». Метод — маленький файл состояния инцидента рядом с исполнителем пробы: переход «ок → сбой» алертит один раз, повторные сбои внутри окна подавляются, переход «сбой → ок» шлёт одно явное сообщение о восстановлении. Дедупликация здесь допустима без человеческого подтверждения (ср. `DP.METHOD.110`), потому что закрытие инцидента наблюдается машинно — самой пробой.

## Forces

| Force | Tension |
|-------|---------|
| Шум повторных алертов ↔ сигнал «инцидент всё ещё открыт» | Подавление повторов убирает шум, но повтор — единственный сигнал незакрытого инцидента, если закрытие никто не наблюдает; окно повторного алерта (напр. 60 мин) удерживает оба давления: тишина внутри окна, напоминание после |
| Простота stateless-пробы ↔ необходимость памяти о прошлом прогоне | Проба без состояния — одна функция, легко тестируется; но «переход» (ок→сбой, сбой→ок) невозможно распознать без памяти о предыдущем результате — файл состояния минимальная цена за события-переходы вместо событий-прогонов |
| Устойчивость к битому состоянию ↔ строгость чтения | Строгое чтение файла состояния (обязательные поля) ловит ошибки формата, но роняет саму пробу; битый файл состояния — отбрасывать как «состояние неизвестно», не падать |

## IPO

**Вход:** периодическая проба с бинарным исходом (ок / сбой), канал уведомлений, состояние предыдущего прогона (файл рядом с исполнителем: статус, время первого сбоя, время последнего алерта).

**Процесс:**
1. Прочитать файл состояния; если отсутствует или не парсится — считать состояние неизвестным и продолжить (не падать)
2. Выполнить пробу
3. Классифицировать переход:
   - «ок → сбой»: отправить алерт, записать статус, время первого сбоя и время алерта
   - «сбой → сбой»: если с последнего алерта прошло меньше окна (напр. 60 мин) — молчать; иначе повторить алерт с длительностью инцидента и обновить время алерта
   - «сбой → ок»: отправить одно явное сообщение о восстановлении с длительностью, записать статус «ок»
   - «ок → ок»: ничего
4. Ветка «проверить нечем» (нет учётных данных, недоступна сама проба) — отдельный статус «неизвестно», не «ок»: она не должна закрывать инцидент сообщением о восстановлении (fail-closed, ср. `DP.METHOD.164`)

**Выход:** на один инцидент — ровно один стартовый алерт, напоминания не чаще окна, одно сообщение о восстановлении; шум пропорционален числу инцидентов, а не числу прогонов пробы.

## Правило

Алерт — событие *перехода* состояния, а не событие прогона. Если у пробы нет памяти о прошлом прогоне, она физически не способна отличить «новый сбой» от «тот же сбой» и «восстановилось» от «никогда не ломалось».

## Тест

«Сколько сообщений придёт за часовой сбой при пробе раз в 5 минут, и придёт ли сообщение, когда всё починится?» 12 одинаковых и ни одного финального — метод не применён. Одно стартовое (+ напоминание после окна) и одно о восстановлении — применён. Дополнительно: «Что случится, если файл состояния окажется пустым или битым?» Проба падает — нарушена третья Force.

## Bias-Annotation

| Bias | Direction of distortion |
|------|--------------------------|
| Внимание на сбое, не на восстановлении | Алерт «сломалось» пишется первым и тестируется; «починилось» кажется отсутствием события и не реализуется — оператор узнаёт о восстановлении только по тому, что алерты перестали приходить |
| Happy path чтения состояния | Файл состояния «всегда есть, потому что мы его пишем» — сценарии первого запуска, ручного удаления и обрыва записи на середине не рассматриваются; строгий парсинг роняет пробу именно тогда, когда она нужнее всего |
| «Не смогли проверить» читается как «ок» | Ветка без учётных данных возвращает нейтральный результат, который по умолчанию выглядит как успех и закрывает инцидент ложным «восстановилось» |

## Дополнение 2026-09-21 (РП-170)

**Конкретизация: хэш содержимого набора как ключ перехода состояния.** Когда наблюдаемое состояние — не бинарный «ок / сбой», а набор (например, файл отклонённых записей периодической синхронизации), файлом состояния служит хэш содержимого этого набора. Хэш файла сравнивается с хэшем, сохранённым при последнем уведомлении: уведомлять на изменение набора (новые или снятые отклонения), а не на каждый тик опроса. Тот же приём делает видимым восстановление: исчезновение строк из набора — тоже изменение хэша, а значит одно явное сообщение, а не тишина.
- Мотив: синхронизация перешла с «упасть всей пачкой на одной плохой строке» на «пропустить только плохие строки» (`DP.FM.487`). Штатный failure-alert (общий шаблон на 32 сервиса) для этого класса перестал срабатывать, и без замены сигнала тихо пропавшая строка осталась бы незамеченной навсегда.
- Решение не трогает общий alert-шаблон, а добавляет точечную обёртку: одно Telegram-сообщение, когда набор отклонённых записей реально изменился, а не раз в 15-минутный тик.
- Смежно: `DP.M.453` (состав ключа окна дедупа — класс инцидента, не идентификатор вызова): здесь ключом служит хэш содержимого набора.

## Дополнение 2026-10-24 (гранулярность ключа дедупа на единицу; тихий сбой записи state при несанитизированном имени)

**Дефект гранулярности.** Хэш всего набора `failed[]` как ключ перехода (см. «Дополнение 2026-09-21») меняется, когда ОДИН элемент набора вылечился, а ДРУГОЙ заболел, — алерт уходит заново по всем элементам набора, включая те, чей diff не менялся: неизменный личный еженедельный черновик (коммитится раз в неделю by design) получил одно и то же предупреждение в Telegram 8 раз за ночь, потому что TTL сбрасывался на каждую смену состава множества, а не на изменение конкретного элемента.

**Исправление:** отдельный state-файл и TTL НА КАЖДЫЙ элемент набора, не на набор целиком. Повтор после TTL уходит с пометкой «[без изменений Nч]», а не как новая находка; state элементов, вышедших из набора (вылечившихся), убирается. Запись state — только при фактической отправке алерта (безусловная запись на каждом тике продлевала бы окно бесконечно, и длящаяся проблема замолчала бы навсегда).

**Второй, независимый дефект (найден холодным ревью).** Имя элемента, используемое как имя state-файла, не было санитизировано: 4 имени из 16 содержали `/` и превращали путь state-файла во вложенный несуществующий каталог — запись падала молча (`|| true`). Дедуп не работал именно для этих элементов: они слали алерт на каждом тике без TTL-защиты вовсе, и отказ записи ничем не сигнализировался.

Переносимо: (1) ключ дедупа = единица, о которой идёт алерт, а не контейнер этих единиц; (2) запись состояния дедупа не должна быть тихой — иначе защита от спама отключается ровно там, где ключ-имя «необычный» (содержит разделитель пути или другой спецсимвол).

Источник: git commit `9755330` в iwe-server-config (`modules/systemd-timers.nix`, pull-repos). Связь: WP-568/WP-538, peer-session 2026-10-23-01-razbor-dampa-bota.

## Дополнение 2026-11-10 (РП-170, отчёт 2026-11-09-inbox-check-6, кандидат 1): точка отсчёта длительности и счётчик повторов

**Длительность от первого замеченного сбоя занижена.** По шагу 3 файл состояния хранит время первого сбоя — момент, когда проба впервые его увидела. Неисправность началась раньше, где-то после последнего подтверждённого успеха. В ночь 03→04.11 счётчик «обмена нет N ч» для платёжного реестра был занижен примерно на 7,5 часа: его вели от первого сбоя, который увидел сторож, а не от последнего успеха. Вместе с длительностью запаздывает и эскалация по суммарной длительности (DP.FM.444): порог срабатывает позже на задержку обнаружения.

**Счётчик уведомлений читается как длительность.** В той же ночной выгрузке алерт о «грязи» шёл с отметкой «1167 ч 47 м». Это счётчик уведомлений с 16.09, который ни разу не сбрасывался. Его читали как 49 суток одной поломки, а за ним стояли повторяющиеся причины (порядок шагов, таймаут обращения к удалённому репозиторию).

**Правило (уточняет шаг 3 и «Вход»).**
1. Файл состояния хранит время последнего подтверждённого успеха и обновляет его на каждом успешном прогоне.
2. Длительность неисправности в тексте алерта считается от последнего подтверждённого успеха, и точка отсчёта названа: «нет успеха с <время> (N ч), сбой впервые замечен в <время>».
3. Счётчик повторов называется счётчиком повторов («уведомлений с <дата>: K»), не оформляется как длительность и сбрасывается на переходе «сбой → ок».

**Тест.** «От какого события отсчитано число часов в тексте алерта, и сказано ли это в тексте?» Отсчёт от первого замеченного сбоя или от первого уведомления без пометки — правило не выполнено.

Оговорки: один разбор (одна ночь, два алерта); цифры «≈7,5 ч» и «1167 ч 47 м» взяты из захвата и по журналам не перепроверялись.

## Дополнение 2026-11-11 (РП-170, отчёт 2026-11-11-inbox-check-5, кандидат 3): исполнитель, вызываемый только при сбое, не видит перехода «сбой → ок»

**Механизм.** Шаг 3 и п. 3 дополнения 2026-11-10 закрывают инцидент и сбрасывают счётчик повторов на переходе «сбой → ок». Это работает, только если исполнитель вызывается и при успехе. Обработчик systemd `OnFailure=` (и любой скрипт, который зовут только из ветки сбоя) успеха не видит и сигнал «ок» не подаёт. Инцидент не закрывается никогда: следующий сбой через недели дописывается к старому, и счётчик сшивает разные поломки в одну. Это и есть происхождение счётчика «1167 ч 47 м с 16.09» из дополнения 2026-11-10: в ночь 05→06.11 тот же механизм дал «повторяется 11 раз, 1216 ч» — 50 дней, сшитых из отдельных сбоев.

**Правило.** Для исполнителя, который вызывается только при сбое, переход «сбой → ок» заменяется политикой закрытия, не требующей наблюдать успех. В источнике две такие политики:
1. **По давности последнего сбоя.** Каждый сбой перезаписывает файл состояния, поэтому его время изменения — время последнего сбоя. Нет сбоев дольше порога (в источнике 7 суток, `NOTIFY_ESCALATION_STALE_AFTER_SEC`) → прошлый инцидент считается закрытым, следующий сбой — новый инцидент (общий помощник `notify_escalation_drop_if_stale`).
2. **По естественной границе цикла.** Для ежедневного процесса один день — один инцидент: счётчик повторов живёт в пределах одной даты (`reset_stale_dayopen_incidents` в тревоге открытия дня).
Где успех наблюдаем дёшево, лучше подать «ок» явно: в том же исправлении конвейер открытия дня стал звать «ок» на нефейловых путях.

**Смежное (покрыто, не новое).** В той же правке дедупликация при подавлении повтора возвращала успех, и вызывающий ставил отметку «уже написано в чат», хотя ничего не ушло, — сторож 06:30 не повторял настоящую тревогу. Исправление: отметка ставится только на окончательном исходе аварийной доставки и только при реальной отправке; функция дедупа при подавлении возвращает ненулевой код. Это класс DP.FM.726 (флаг ставится по возврату, а не по результату) и DP.FM.591 (код 0 не отличает «сделал» от «не сделал»); ср. дополнение 2026-10-24 выше: запись состояния — только при фактической отправке.

**Тест.** «Кто вызывает исполнитель пробы при успехе источника?» Никто (только `OnFailure=` или ветка сбоя) → переход «сбой → ок» ненаблюдаем; нужна политика закрытия по давности или по границе цикла, иначе счётчик повторов растёт без предела. Проверка от обратного: два сбоя с промежутком больше порога дают два инцидента с счётчиком 1, а не один со счётчиком 2.

**Границы.** Порог 7 суток и граница «одна дата» — выбор источника, не обоснованные универсальные значения: порог должен быть больше самого длинного ожидаемого промежутка между сбоями одного длящегося инцидента, иначе длящаяся поломка с редкими пробами распадётся на «новые» инциденты. Закрытие по давности не даёт сообщения о восстановлении (шаг 3, «сбой → ок»): успеха никто не видел, поэтому и сообщать «починилось» нельзя. Эффект на живом потоке уведомлений после 06.11 не замерялся; подтверждено тестами коммитов (эскалация 37/37, `day-open-alert` 27/27 и 17/17).
