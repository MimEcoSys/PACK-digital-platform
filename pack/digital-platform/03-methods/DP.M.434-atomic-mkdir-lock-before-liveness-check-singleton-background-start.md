# DP.M.434 — Атомарный `mkdir`-замок до любой проверки состояния при идемпотентном старте фонового процесса

## Определение

Атомарный захват общего замка до чтения PID-файла сериализует проверку состояния и запуск фонового процесса. `mkdir` каталога-замка — один из примитивов; `flock` и `ln` требуют своих правил владения и освобождения. Сам отказ захвата не доказывает ни конкуренцию, ни наличие живого процесса. Единственность требует, чтобы все пути запуска использовали один namespace замка и проверяли идентичность процесса, а не только существование PID.

## Проблема

Идемпотентность старта фонового маяка проверялась схемой «прочитать PID-файл → `kill -0` → если процесс мёртв, запускать новый». Между чтением и запуском есть окно: два почти одновременных `SessionStart` (например, после сжатия контекста в двух параллельных агентах) оба видят «процесса нет» и оба стартуют. Второй экземпляр становится осиротевшим — его PID никто не записал, и ни одна последующая проверка того же PID-файла его не увидит. Схема check-then-act на PID-файле не атомарна по построению и не закрывается «более аккуратной» проверкой.

## Структура

Схематично (порядок шагов — суть метода):

```text
попытаться атомарно создать каталог-замок
если не удалось:
    сохранить причину отказа и вернуть «старт не подтверждён»
    не запускать процесс и не удалять чужую блокировку
после успешного захвата:
    подготовить освобождение собственного замка при штатном завершении
    проверить PID и идентичность ожидаемого процесса
    если состояние неопределённо: сообщить об этом, новый процесс не запускать
    если нужный процесс подтверждён живым: завершить без повторного запуска
    иначе: запустить процесс и подтвердить его готовность/запись PID под замком
освободить собственный замок; сбой освобождения явно сообщить
```

## Ключевые свойства

1. **Атомарность — свойство примитива ОС, не логики скрипта.** `mkdir` на POSIX либо создаёт каталог, либо отказывает — только один из двух конкурирующих вызовов может его создать. Никакая последовательность «прочитать → проверить → записать» этого не даёт.
2. **Замок — до чтения состояния, не после.** Проверка «жив ли предыдущий» остаётся, но выполняется уже внутри критической секции; иначе она сама и есть окно гонки.
3. **Отказ захвата — отдельный результат, не успех старта.** `mkdir` может отказать из-за существующего пути, прав доступа или ошибки ввода-вывода. Существующий каталог может быть оставлен умершим владельцем. Даже подтверждённый конкурент ещё только запускает процесс: без подтверждения готовности нельзя отвечать «уже запущено». Допустимый контракт «другой запуск выполняется» требует доказанной конкуренции; неизвестность возвращается явно. Решение о повторе или восстановлении принимает протокол вызывающего кода.
4. **Замок короткоживущий, отдельный от PID-файла.** Каталог защищает критическую секцию старта; освобождает его только подтверждённый владелец. `trap` помогает при штатном выходе и обрабатываемых сигналах, но не гарантирует очистку при SIGKILL, падении машины или ошибке файловой системы. Восстановление оставленного замка требует отдельной проверки владения, а не удаления по одному возрасту каталога или отрицательному `kill -0`. Долгоживущая идентичность процесса проверяется отдельно (DP.FM.143, DP.FM.217).
5. **`mkdir` не требует утилиты `flock(1)`**, которой может не быть в базовой поставке платформы (примечание экстрактора; в источнике `mkdir`/`flock`/`ln` названы равноправными атомарными примитивами).

Здесь «атомарный» означает: для одного пути и в рамках подтверждённого контракта целевой файловой системы ровно один конкурент успешно создаёт отсутствующий каталог. Для сетевой, виртуальной или иной файловой системы с неизвестными гарантиями это предусловие сначала проверяется; без него метод не обещает единственность и должен вернуть неопределённость либо использовать поддерживаемый этой средой примитив координации.

## Когда применять

**Тест:** «Старт фонового процесса может быть инициирован двумя независимыми событиями почти одновременно (два хука, два таймера, два агента)? Гарантия единственности опирается на чтение файла состояния перед запуском?» Да на оба → check-then-act недостаточен, нужен атомарный примитив первым шагом.

## Отличие от смежного

- **DP.M.413 (освобождение замка через `trap`):** там — организация снятия замка; здесь — атомарность захвата и его место до проверки состояния. Границы очистки при необрабатываемом завершении сохраняются.
- **DP.M.372 (`flock`: гранулярность замка):** там — на каком уровне держать замок при обходе ресурсов; здесь — зачем замок вообще нужен там, где раньше была «проверка живости».
- **DP.FM.143 (stale PID → PPID-fallback) и DP.FM.217 (PID оболочки ≠ PID сессии):** оба — о неверном содержимом PID-файла; этот метод — о гонке при его чтении, которая воспроизводится и при верном содержимом.

## Применимо к

Любой идемпотентный старт «не больше одного экземпляра» фонового процесса из хуков, таймеров или параллельных агентов: маяки сессий, watcher'ы, локальные демоны синхронизации, фоновые очереди.
