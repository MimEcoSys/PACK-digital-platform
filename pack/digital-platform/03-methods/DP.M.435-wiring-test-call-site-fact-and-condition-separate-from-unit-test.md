# DP.M.435 — Тест проводки: проверка факта и места вызова, отдельно от теста извлечённой функции

## Определение

Для критичного вызова, чья корректность зависит не только от логики функции, но и от того, что она действительно вызывается в нужном месте под нужным условием — юнит-теста извлечённой функции недостаточно. Нужна отдельная проверка «проводки» (wiring test): статический разбор подтверждает наличие вызова и его связь с нужным условием; выполнение через реальный вход подтверждает достижимость и наблюдаемый эффект. Наличие вызова в тексте само по себе второго не доказывает.

## Проблема

Юнит-тест, проверяющий поведение функции в изоляции, остаётся зелёным, даже если реальный вызов этой функции на call site удалён, переименован или обёрнут в другое условие — риск «функцию отвязали от места вызова» тестом функции не покрывается (конкретный пример такой отвязки — `DP.FM.420`).

## IPO-паттерн

| Элемент | Описание |
|---------|----------|
| Входы | Исходный файл с предполагаемым call site; имя вызываемой функции; ожидаемое условие/guard перед вызовом |
| Обработка | Статический разбор исходника (grep/AST) — найти вызов функции, посчитать количество вхождений, извлечь условие непосредственно перед вызовом |
| Выходы | Результат статической проверки связи: вызов найден в ожидаемом количестве и контексте либо указано расхождение. Это не вердикт о фактическом выполнении |

## Шаги метода

1. Определить критичный call site (обычно — обязательный побочный эффект/cleanup, для которого уже есть юнит-тест самой функции).
2. Написать отдельную статическую проверку наличия и условия вызова; не считать совпадение текста доказательством достижимости. Для grep-проверки учитывать совпадения в комментариях и строках.
3. Подать контролируемый вход через реальную точку входа и проверить наблюдаемый результат критичного вызова; также проверить вход, при котором эффект не должен происходить. Прямой вызов извлечённой функции эту проверку не заменяет.
4. Запускать проверки совместно: юнит-тест покрывает логику функции, статическая проверка — структуру связи, поведенческая — её исполнение на выбранных входах.

## Отличие от юнит-теста

Юнит-тест показывает поведение функции на проверенных входах при прямом вызове. Статическая проверка проводки показывает, что исходник содержит ожидаемую связь. Даже корректный AST-вызов может лежать за ранним `return` или недостижимым условием; только наблюдаемый эффект при входе через настоящий call site подтверждает выполнение для этого сценария. Ни один отдельный сценарий не доказывает корректность на всех возможных входах.

## Применимо к

Любой критичный побочный эффект (cleanup, обязательство, audit-запись), извлечённый в отдельную функцию — риск «отвязки от call site» существует для каждого такого случая, не только для session-guard.
