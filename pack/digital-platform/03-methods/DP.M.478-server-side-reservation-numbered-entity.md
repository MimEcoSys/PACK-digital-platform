# DP.M.478 — Резервация номера на снимке origin перед выдачей

## Назначение

Устранить коллизию номера, когда несколько несинхронизированных локальных копий могут независимо создать сущность со сквозным номером (документ, публикация, тикет) — не после коллизии (реактивно), а структурно исключить её до создания.

## Метод

1. Сквозной номер выдаёт сервер по постоянному UUID черновика — не локальное вычисление `max(id)+1`.
2. Перед записью локальный скрипт проверяет пару (UUID, номер) в журнале резерваций на снимке `origin/main` через авторизованный `gh`.
3. Дополнительно сверяет с историческими постами на том же снимке — старая ошибочная резервация не разрешает занять уже использованный номер.
4. Повтор запроса с тем же UUID/номером возвращает существующий путь, не перезаписывает и не создаёт дубликат.
5. `--dry-run` — только превью, не резервация.
6. Правила формирования имён вынесены в один нормативный конфиг (JSON), который читают все три потребителя (сервер, локальный скрипт, pre-commit-проверка) — захардкоженного fallback нет, «по аналогии» невозможно.

## Тест применимости

«Сущность с последовательным номером может быть создана из нескольких мест (разные копии, разные агенты)?» Да → одной проверки `grep max_id` недостаточно, нужна резервация на неизменяемом снимке ДО создания.

## Отличие от DP.METHOD.123

`DP.METHOD.123` описывает реактивную реакцию на уже произошедшую коллизию номера (прочитать занятый номер, оценить пересечение, адаптироваться). Этот метод — превентивный: коллизия становится структурно невозможной, потому что номер выдаётся только после подтверждённой резервации, а не вычисляется локально.

## Связь с DP.M.477

Общий meta-принцип с `DP.M.477` (версионирование ядра знаний из заимствованной и собственной части): координация происхождения сущности, которая может создаваться/изменяться из нескольких несинхронизированных мест. Разные механизмы (резервация номера здесь vs content-hash sidecar там) и разные отказные паттерны (коллизия нумерации vs рассинхрон частей корпуса) — не дубль, смежный случай.

## Миграция: засев журнала до первого вызова

Если выдача номеров вводится поверх уже существующей последовательности, журнал резерваций нужно засеять текущим максимумом (историческими номерами) до первого живого вызова. Иначе новый журнал не знает об истории и выдаёт номера с начала.

Случай из практики: первый в истории вызов `allocatePostNumber` (24.09) стартовал с пустого `docs/_allocator-log.jsonl` и вернул `post_number: 1`, хотя в репозитории уже было 231 пост, пронумерованный старым скриптом `scripts/new-post.py`. Журнал аллокатора стартовал пустым: при введении инструмента (WP-560 Ф12) его не засеяли историческим максимумом.

Проверка при введении такого механизма: «выполнен ли явный шаг засева журнала историческим максимумом до первого живого вызова?» Нет — первый же вызов коллизирует с историей.
