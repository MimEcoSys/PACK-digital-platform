# DP.M.490 — Тихий режим для функции-стража под чужим локом

## Проблема

Функция-страж вызывается и из-под общего коммит-лока (с коротким таймаутом ожидания для других претендентов), и из обычного пути, и по пути может отправить сетевое уведомление о статусе. Сетевая доставка иногда занимает ощутимое время (до минуты при деградации сети); пока страж держит лок и ждёт эту доставку, остальные претенденты на лок простаивают дольше своего собственного таймаута — лок, рассчитанный на короткие операции, становится бутылочным горлышком из-за непредсказуемой внешней задержки внутри него.

## Метод

1. **Разделить «решить и залогировать» от «доставить».** Решение стража (вычисление статуса, запись строки в журнал) и собственно сетевая доставка уведомления — два разных шага с разной стоимостью и разной предсказуемостью по времени.
2. **Тихий режим для вызова под локом.** У функции-стража появляется флаг/режим `quiet`: при вызове из-под короткого лока решение и запись в журнал выполняются как обычно, но сетевая доставка не выполняется вовсе.
3. **Доставка — только вне критической секции.** Собственно сетевое уведомление отправляется из вызова без `quiet`, то есть из пути, не держащего чужой лок.

## Тест

«Функция принятия решения вызывается и внутри короткого лока, и снаружи, и у неё есть побочный эффект с непредсказуемой задержкой (сеть, диск, внешний процесс)?» Да на оба — нужен тихий режим: вычислить и залогировать можно всегда, доставить — только снаружи лока.

## Границы

Метод применим, когда у функции ЕСТЬ дешёвая часть (решение, запись) и дорогая часть (доставка) с разной предсказуемостью задержки, и обе части сейчас вызываются синхронно одним вызовом. Не применим, если доставка сама обязана быть атомарной с решением (например, при эксклюзивной публикации результата) — там нужен другой механизм, не разделение на тихий/обычный режим.
