# DP.M.499 — Порядок поставки частичной записи из контракта согласованности

## Проблема

Заказчик проранжировал три доработки частичной записи по убыванию ощутимой пользы и попросил такой порядок поставки:

1. дописывание в конец файла (append) с тем же `expected_sha`;
2. замена фрагмента;
3. чтение хвоста.

Ранжирование по пользе здесь не совпадает с ранжированием по выполнимости, и разойтись они могут молча: первая фича поставляется, замер экономии не сходится, работа выглядит дискредитированной.

## Разбор контракта

Запись защищена оптимистичной блокировкой через `expected_sha`: писатель обязан доказать, что пишет в известную ему версию ресурса. Этот sha агент обязан откуда-то взять, и единственный доступный способ — прочитать ресурс. Если чтение умеет только «страницами с начала» и ограничено потолком ответа, то за токеном версии каждый раз читается весь файл.

Отсюда: дешёвое дописывание не экономит ничего, пока чтение остаётся полным. Первая по пользе фича функционально бесполезна без третьей — зависимость не по вкусу, а по контракту согласованности.

## Метод

1. **Выписать контракт согласованности.** Чем писатель доказывает, что пишет в известную ему версию: токен версии, дайджест содержимого, номер ревизии, lease.
2. **Найти поставщика токена.** Какая операция выдаёт этот токен и какой у неё полный объём обмена. Если токен выдаёт только дорогая операция, все «дешёвые» записи наследуют её цену.
3. **Посчитать полный объём обмена для каждой операции.** Включая получение токена версии, а не только полезную нагрузку самой записи. Это и есть проверка метода.
4. **Поставлять в порядке зависимости.** Сначала операция, выдающая токен дёшево (секционное/хвостовое чтение), затем операции, его потребляющие (дописывание, замена фрагмента).
5. **Предъявить пересортировку владельцу с расчётом.** Порядок, запрошенный по пользе, меняется не «потому что инженеру удобнее», а с посчитанным объёмом обмена на руках.

В наблюдавшемся случае итоговый порядок: чтение хвоста и секции по заголовку → дописывание в конец → замена фрагмента.

## Тест

«Для операции, которую я называю дешёвой, назовите полный объём обмена, включая получение токена версии». Если в ответе фигурирует полный размер ресурса — операция не дешёвая, и ставить её первой нельзя.

## Что метод не разрешает

- Поставить дешёвую запись первой, отложив дешёвое чтение, с обещанием «экономия появится позже». До появления дешёвого чтения экономии нет вовсе.
- Обойти оптимистичную блокировку, чтобы не читать: это замена задачи о цене на задачу о согласованности.

## Границы

Метод о порядке поставки частичных операций над версионируемым ресурсом. Он не выбирает механизм блокировки — для привязки разрешения к дайджесту содержимого см. `DP.M.480`. Он не отвечает на вопрос, какой слой обязан выполнять цикл «прочитать-изменить-записать» — это `DP.D.341`.
