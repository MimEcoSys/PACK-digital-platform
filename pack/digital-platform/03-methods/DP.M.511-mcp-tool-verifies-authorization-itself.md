# DP.M.511 — MCP-тул стейтлес: авторизация проверяется на каждом вызове, не наследуется от более раннего тула

## Описание
MCP-тулы по архитектуре независимы друг от друга в рамках одного разговора: более ранний успешный вызов одного тула (например, проверивший доступ к потоку) не является доказательством авторизации для последующего вызова другого тула. Каждый тул, которому нужна авторизация, проверяет её сам, своим собственным запросом к источнику правды (например, отдельная SQL-функция с явной проверкой доступа), и отвергает весь запрос целиком при чужом идентификаторе — не возвращает частичный результат по разрешённым элементам.

## IPO
**Вход:** вызов MCP-тула с параметром идентичности (например, `participantId`); новый тул добавляется рядом с существующим в том же домене.

**Процесс:**
1. Не расширять существующий тул (`get_stream_overview`) дополнительной параметризацией, если новый запрос требует собственной проверки доступа — завести отдельную точку входа с собственной явной проверкой (`app.assert_stream_reader` и т.п.).
2. При чужом/невалидном идентификаторе — отклонить запрос целиком, не отдавать частичный результат по тем элементам, которые разрешены.
3. Проверить (например, холодным ревью), что у нового проверочного хелпера нет побочных путей вызова без прохождения проверки (напр. `REVOKE ALL FROM PUBLIC` + явный grant только владельцу проверки).

**Выход:** каждый MCP-тул независимо авторизует свой вызов; ошибка или пробел в одном туле не даёт доступ через соседний.

## Правило
MCP-тул — stateless относительно авторизации: наличие более раннего успешного вызова в том же разговоре не освобождает от собственной проверки.

## Тест
«Может ли тул выдать результат, если авторизация проверялась только ДРУГИМ, более ранним вызовом?» Да → нарушение. Дополнительно: «При чужом идентификаторе тул возвращает частичный результат по безопасной части запроса?» Да → нарушение (должен отвергать целиком).
