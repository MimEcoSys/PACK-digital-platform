# DP.M.521 — Чувствительный session-артефакт хранится вне рабочей копии проекта

## Проблема

Для восстановления контекста после сжатия сессии (PreCompact) сохраняется снимок последних реплик пользователя и ответа ассистента. Первая версия хранила это в рабочей копии проекта под `.gitignore`, но доставка `.gitignore` при обновлении шаблона (`update.sh`) не гарантирована на всех установках — чувствительный артефакт (реплики пользователя со всем контекстом) риск уйти в коммит, если на конкретной установке файл правила не доставлен.

## Метод

Хранить артефакты с чувствительным содержанием сессии вне дерева проекта — в директории конфигурации платформы (`$CLAUDE_CONFIG_DIR/iwe-checkpoints/checkpoint-<session_id>.md`), а не под `.gitignore` внутри рабочей копии. Восстановление читает из того же места при старте сессии, с одноразовым потреблением (файл удаляется после выдачи агенту).

## IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Артефакт, содержащий чувствительные данные пользователя/сессии, который нужно сохранить между двумя моментами одной или смежных сессий |
| Обработка | Запись в директорию конфигурации платформы вне дерева проекта вместо gitignored-пути внутри репозитория; чтение при восстановлении + удаление после потребления |
| Выходы | Артефакт недостижим для `git add`/коммита независимо от состояния `.gitignore` конкретной установки |

## Когда применять

Любой артефакт с пользовательским/сессионным содержанием (реплики, пароли, токены), который теоретически может быть прочитан `git add` на установке, где файл правил `.gitignore` не доставлен или устарел.

## Отличие от смежного

`DP.FM.237` (provenance-стейт стража вне репо: работает на одной машине, невидимо CI) — **не дубликат и не противоречие, противоположная ось**: там state, НА ОСНОВАНИИ которого guard принимает решение, обязан быть виден всем инстансам guard (поэтому хранение вне центрального/shared-хранилища — проблема, решение — сделать видимым). Здесь — артефакт с чувствительным пользовательским содержанием, которому видимость не нужна и опасна; вынос вне репозитория — решение, а не проблема. Критерий различия: это состояние, на основании которого принимается решение enforcement (нужна видимость всем инстансам), или контент с риском утечки приватных данных (видимость нужно ограничивать)?
