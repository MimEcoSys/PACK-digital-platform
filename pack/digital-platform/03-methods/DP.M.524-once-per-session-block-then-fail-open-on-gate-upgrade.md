# DP.M.524 — Разовая блокировка per-session при апгрейде наблюдателя до гейта

## Проблема

Детектор ритуала согласования был чистым наблюдателем: всегда `exit 0`, только пишет в ledger. В результате ритуал фактически предъявлялся лишь в ~1.6% нетривиальных сессий. Прямая замена на безусловный жёсткий блок при каждом срабатывании рискует подвесить сессию навсегда, если сам детектор содержит баг (ложное срабатывание на каждом Stop).

## Метод

При первом `Stop` с `ritual_status=absent` на нетривиальной сессии гейт возвращает `{"decision":"block"}`. Факт блокировки фиксируется state-файлом по session_id (`ritual-gate-enforced-<session_id>`). Второй и последующие `Stop` той же сессии не блокируют повторно — fail-open: несогласие пилота или баг самого детектора не блокирует сессию навечно.

## IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Детектор-наблюдатель (always-pass, только логирует) + решение проапгрейдить до блокирующего гейта |
| Обработка | Первый Stop с отсутствующим ритуалом → `block` + запись маркера `enforced` по session_id; последующие Stop той же сессии проверяют маркер → fail-open |
| Выходы | Ритуал предъявлен минимум один раз за сессию; ни один баг детектора не создаёт бесконечную блокировку |

## Когда применять

Апгрейд существующего always-pass наблюдателя (любой мониторинг/ritual-гейт, который раньше только логировал) до реально блокирующего поведения — особенно когда код детектора ещё не проверен на разнообразии реальных сессий и есть риск ложных срабатываний.

## Границы

Правило не применяется к гейтам на операцию, где однократное срабатывание за сессию — известный самостоятельный дефект (см. `AS.FM.136`); сверять оговорку `AS.FM.138` перед использованием этого метода для гейтов такого типа.
