# DP.M.525 — Новый блокирующий гейт выкатывать сначала warn-only

## Проблема

Новый широкий enforcement-гейт (перехватывает вызовы инструментов любого агента) рискует сломать автоматизации, не видимые во время разработки в обычной интерактивной сессии (отложенные задачи, вотчдоги, cron/headless-запуски). Включить гейт сразу в жёстком режиме — узнать об этих вызывающих только когда они уже заблокированы на проде.

## IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Новый блокирующий PreToolUse/admission-гейт, готовый к включению |
| Обработка | Включить сначала в режиме warn-only: гейт вычисляет вердикт как обычно, но вместо блокировки пишет в отдельный лог «было бы заблокировано»; период наблюдения даёт всем автоматизациям шанс проявиться через строки лога |
| Выходы | После периода наблюдения — включение жёсткого режима с известным списком легитимных вызывающих, не угаданным |

## Когда применять

Перед переводом ЛЮБОГО нового admission/enforcement-механизма (не только hook) из состояния «написан» в состояние «блокирует» — особенно если механизм перехватывает широкий класс событий (каждый вызов инструмента, а не узкий список известных операций).

## Прецедент

WP-561 Ф33: новый PreToolUse-гейт `intent-gate-check.sh` (DP.SC.204, DP.ROLE.102) включён первым warn-only — пишет в `.iwe-runtime/intent-gate-warnings.log`, ничего не блокирует. Пилот также явно развёл этот журнал от `wp-gate-check.sh` (узкие правки Registry) — разные по природе гейты не объединены в одном механизме. Решение закрывает открытый вопрос, оставленный в `DP.SC.204` («жёсткий блок с первого дня или warn-only запуск сначала») — выбран warn-only.

## Связи

- `DP.SC.204` — обещание, для реализации которого принято это решение; открытый вопрос карточки этим методом закрыт в пользу warn-only.
- `DP.ROLE.102` — роль, реализующая гейт.
