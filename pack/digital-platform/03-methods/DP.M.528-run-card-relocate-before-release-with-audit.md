# DP.M.528 — Перенос артефакта в канонический каталог с аудитом ДО релиза изолированной копии

## Проблема

Шаг, завершающий работу с изолированной git-копией (worktree), освобождает/удаляет её раньше, чем содержательный результат (например, карточка состояния) перенесён за пределы этой копии. Крах процесса между освобождением и переносом создаёт две плохие ветки: результат теряется вместе с копией, либо повторный запуск не находит прежний результат и порождает второй логический RUN на тот же процесс.

## IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Изолированная копия, которая будет освобождена/удалена; артефакт внутри неё, который должен выжить релиз |
| Обработка | Перенести артефакт в канонический каталог ДО вызова шага освобождения; сделать перенос атомарным (fsync файла и каталога перед `rename`); оставить аудиторскую запись перехода (`relocated` → `written`, с owner/hash) |
| Выходы | Артефакт доступен в каноническом месте независимо от судьбы изолированной копии; резюме после краха ищет артефакт по аудиторской записи (совпадение владельца+хеша), а не создаёт новый |

## Когда применять

Любой пайплайн, где изолированная копия (worktree, временная директория, песочница) — это транзитный носитель результата, а не его постоянное хранилище, и где возможен краш между «результат готов» и «копия освобождена».

## Антипаттерн

Освобождать/удалять изолированную копию сразу по завершению содержательной работы, перенося результат отдельным, более поздним шагом «на всякий случай» — окно между этими двумя шагами ничем не защищено, и крах в нём либо теряет результат, либо (при наивном resume «просто начать заново») плодит дубликат.

## Прецедент

Quick Close освобождал изолированную git-копию сессии (`session-guard-release.sh` удаляет worktree) до того, как карточка RUN была перенесена за пределы копии. Фикс: перенос в канонический каталог до вызова релиза, атомарный (fsync перед rename), с аудиторской записью (`relocated`→`written`, owner/hash); резюме после краха ищет уже перенесённую карточку по этой записи (`_find_relocated_run`, совпадение владельца+хеша) вместо создания нового RUN. Пир-проверка (частичная) подтвердила достаточность порядка fsync/audit для окна после unlink.
