# DP.M.529 — Разовая миграция как временная admin-команда за существующим гейтом

## Проблема

Разовая data-миграция (дошифровка, backfill, формат-конверсия) на небольшом объёме данных не оправдывает отдельную migration-инфраструктуру (новый gate, новый pipeline, отдельный скрипт деплоя), но и ручной прогон SQL в проде без защиты и проверки — риск. Нужен способ сделать разовую операцию безопасной без постоянных затрат на инфраструктуру, которая не будет использована повторно.

## IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Разовая, небольшая по объёму задача миграции данных; существующий admin/dev-гейт в системе (например, команда бота за проверкой роли) |
| Обработка | Реализовать миграцию как команду за УЖЕ существующим гейтом; сделать её идемпотентной по построению (условие в `WHERE`, не внешний чек «уже выполнено»); переиспользовать тот же формат/ключ, что и обычный путь операции; проверить изолированным dry-run (temp-таблица, `ROLLBACK`, тестовый файл не коммитится) и независимым холодным ревью до реального запуска |
| Выходы | Миграция выполнена на проде; команда удаляется тем же днём после подтверждённого успеха — не остаётся постоянным кодом |

## Когда применять

Разовая, небольшая по объёму операция над данными, для которой заводить полноценную migration-инфраструктуру избыточно, но и неконтролируемый ручной SQL-прогон в проде недопустим.

## Антипаттерн

Либо строить отдельную migration-инфраструктуру для операции, которая выполнится один раз, либо прогонять SQL в проде вручную без dry-run и без удаления временного кода после использования — временный код остаётся висеть в кодовой базе как мёртвый, непроверяемый путь.

## Прецедент

Нужно было дошифровать старые plaintext-токены (22 access + 16 refresh), записанные до перехода на `pgp_sym_encrypt`. Реализовано как `/migrate_tokens` — команда бота за тем же гейтом `_is_developer`, что и у `/reset`, идемпотентная по построению (`WHERE ... NOT LIKE 'pgp:%'`), переиспользующая формат/ключ обычного пути шифрования. Проверена изолированным dry-run (temp-таблица, `ROLLBACK`) и независимым холодным ревью до реального запуска; после подтверждённого успеха на проде команда удалена тем же днём. Второй случай этого паттерна в проекте — первый был `/broadcast_reconnect`.
