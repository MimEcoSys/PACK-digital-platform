# DP.M.533 — «Не показано» ≠ «не собирается»: проверка существующих источников до нового конвейера

## Проблема

Запрос «добавить метрику X на дашборд» по умолчанию читается как «данные X не читаются вообще» → консенсус сразу проектирует новую синхронизацию и новое хранилище. Если метрика уже тихо собирается существующим механизмом под другим именем/эндпойнтом, спроектированный «полный» конвейер — избыточная работа и лишняя поверхность отказа.

## IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Запрос на показ метрики, которой сейчас нет на экране/дашборде |
| Обработка | Перед проектированием нового конвейера — поиск по существующим источникам/архивам: читает ли что-то уже нужные данные под другим именем, в другом эндпойнте или в другом окне синхронизации |
| Выходы | Установленное состояние метрики — одно из трёх: не собирается / собирается, но не проецируется / проецируется, но не показана — и соответствующий минимальный объём работы |

## Три состояния «метрика не отображается»

1. **Не собирается** — источник вообще не тянет эти данные. Нужен новый конвейер.
2. **Собирается, но не проецируется** — данные приходят в архив, но не превращены в читаемую проекцию/хранилище. Нужна только проекция.
3. **Проецируется, но не показана** — всё уже есть, дашборд просто не читает. Нужен только UI-шаг.

Ошибка — спроектировать решение для состояния 1, когда реальное состояние 2 или 3.

## Прецедент

Запрос «добавить HRV/пульс покоя/температуру на дашборд Секретаря» (WP-389) прочитался как «данные не читаются из Oura» → консенсус с напарником спроектировал новую синхронизацию и новое зашифрованное хранилище с направленными порогами. При реализации выяснилось: `lib/health/source_oura.py::_pull_sleep_periods` (эндпойнт `sleep`, не `daily_sleep`, как предполагалось) уже тянет и архивирует `average_hrv`/`lowest_heart_rate` каждые 15 минут — дашборд их никогда не читал. Фактически реализован облегчённый вариант: дашборд читает последнее окно уже существующего архива через переиспользование существующего класса синхронизации, без новой трубы.

## Тест применимости

«Данные этой метрики могли прийти через существующий синк под другим именем/эндпойнтом/окном?» Да → grep/чтение существующих источников и архивов ДО проектирования нового конвейера, не после.

## Связи

- `DP.M.503` (контракт нормализации метрики) — тот же кластер WP-389/Oura, другой механизм: там — согласованность сырого/округлённого значения при сравнении с порогом; здесь — проверка, не собраны ли данные уже, прежде чем строить новый конвейер.
- `DP.M.500` (reuse content-based classifier over parallel heuristic) — тот же общий принцип «проверь существующий механизм прежде, чем строить параллельный», в другой предметной области (классификатор, не данные/конвейер).
- `DP.M.523` (подключать новую метрику к уже читаемому пути агрегации, не к новому потребителю) — смежный, не дубль: DP.M.523 — про выбор пути ПОКАЗА для сигнала, который уже собран и записан; DP.M.533 — про проверку, не собран ли сигнал уже вообще, прежде чем проектировать сбор.
- `DP.M.520` (присоединять новый сигнал к обязательному шагу конвейера) — смежный, не дубль: тот же общий класс «не строить новый параллельный путь», другой конкретный аспект (обязательность шага показа vs существование самого сбора).
