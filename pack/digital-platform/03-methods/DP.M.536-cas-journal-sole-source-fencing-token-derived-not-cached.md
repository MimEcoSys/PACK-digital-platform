# DP.M.536 — CAS-журнал решений как единственный источник истины

## Проблема

Индекс или кэш поверх журнала CAS-решений (для быстрого доступа к текущему состоянию или следующему fencing-токену) может устареть между собственным append в журнал и обновлением индекса — классический источник рассинхрона производного значения с источником истины, особенно под конкурентной записью.

## Метод

1. Журнал (append-only JSONL под `flock`) — ЕДИНСТВЕННЫЙ источник истины для каждого CAS-решения; на пути решения нет отдельного индекса или кэша.
2. Fencing token выводится как `max(каждый fencing_token в журнале) + 1` — вычисляется из самого журнала при каждом обращении, а не хранится отдельным счётчиком рядом с ним.
3. Любой производный результат (текущее состояние, следующий токен) читается из журнала целиком под локом на каждый вызов, а не из промежуточного представления.

## Инвариант

Поскольку fencing token — чистая функция содержимого журнала (а не независимо поддерживаемое значение), он физически не может разойтись с журналом, из которого выведен: расхождение индекса с источником истины становится структурно невозможным, а не просто маловероятным.

## Применимость

Любой CAS/consensus-журнал, где нужна гарантия «один победитель на конкурентную заявку» и где объём журнала допускает полное перечитывание под локом на каждую операцию. Для журналов, где полное перечитывание становится дорогим (большой объём, высокая частота операций) — метод не покрывает этот случай, требуется отдельное решение о снапшотах.
