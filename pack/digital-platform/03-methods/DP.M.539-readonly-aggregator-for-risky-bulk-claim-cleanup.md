# DP.M.539 — Read-only агрегатор вместо массовой автоматизации рискованного списания

## Проблема

Полная автоматизация массового рискованного действия (списание N зависших заявок/claim'ов разом) рискует гонкой между моментом поиска кандидата и моментом выполнения: новая заявка могла появиться, или собственная ошибка в идентификаторе (`wp:`) может привести к списанию не той подготовки. Доверить агенту одной сессии решение «списать все найденные разом» — превышает разумные полномочия этой сессии для необратимого массового действия.

## IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Набор потенциально зависших заявок/claim'ов, подлежащих ручной проверке перед списанием |
| Обработка | Read-only сканер проходит по всем кандидатам без единой мутации; для каждой однозначной находки печатает готовую к копированию команду списания; записи без валидного идентификатора (напр. `wp:`) помечает отдельно как неоднозначные, не выполняет для них ничего |
| Выходы | Список готовых команд на каждого однозначного кандидата + отдельный список неоднозначных; подтверждение и фактическое исполнение каждой команды — отдельный ручной шаг |

## Когда применять

Когда для класса массовых действий автоматизация технически возможна, но риск одной ошибки (гонка, неверный идентификатор) способен задеть чужую/не ту подготовку, а исправление постфактум дорого или невозможно — промежуточная безопасная ступень между «ничего не автоматизировано» и «полная автономная массовая мутация» — агрегатор, который готовит, но не исполняет.

## Прецедент

WP-484 Ф190: два независимых пир-раунда (разные дни, не читая друг друга) сошлись на одном выводе про зависшие заявки `--abandon-prepared` — построен read-only `pending-abandon-claims.sh`. Тестирование на синтетических данных (не только happy path) поймало реальный баг самого сканера: `set -euo pipefail` + `grep | sed` без совпадения обрывал скрипт молча вместо попадания в ветку «неоднозначно» — закрыто добавлением `|| true`.
