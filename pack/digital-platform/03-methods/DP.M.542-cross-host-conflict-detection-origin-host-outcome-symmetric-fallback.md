# DP.M.542 — Конфликт решений между хостами по паре (origin_host, outcome)

## Проблема

WAL-слой решений нескольких хостов, пишущих в общий журнал, должен различать легитимный retry (тот же хост повторяет ту же операцию) от реального конфликта продюсеров (два хоста заявили разные решения по одной записи). Предыдущая версия считала только конфликты (C2-narrow); расширение до полного обнаружения (C2) выявило асимметрию fallback при отсутствующих полях у части продюсеров.

## IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Две или более записи решения по одному элементу, каждая с полями `origin_host` и `outcome` (оба могут отсутствовать у части продюсеров) |
| Обработка | Классификация по паре (origin_host, outcome): разные хосты → конфликт; тот же хост + разный outcome → конфликт (баг продюсера); тот же хост + тот же outcome → легитимный retry, не конфликт. При отсутствии `origin_host` у одной из записей — симметричный fallback (не сравнение значения как есть); то же правило применено к отсутствующему `outcome` |
| Выходы | Классификация пары записей: конфликт / легитимный retry |

## Когда применять

Любой многохостовый журнал решений (WAL, event log, decision ledger), где один и тот же элемент может быть обработан повторно легитимно (retry) и где нужно отличить это от реального конфликта независимых продюсеров — особенно если часть продюсеров структурно не заполняет одно из классифицирующих полей.

## Прецедент

Два раунда холодного ревью нашли асимметрию: отсутствие `origin_host` уже падало в fallback симметрично (не конфликт по умолчанию), но отсутствие `outcome` сравнивалось как обычное значение — что давало продюсерам, никогда не заполняющим `outcome`, бесплатный проход без конфликта (лазейка). Закрыто приведением обоих полей к одному симметричному правилу fallback.
