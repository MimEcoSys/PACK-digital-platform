# DP.M.548 — Условные переходы рекомендации и идемпотентное подтверждение

## Метод

Вход — рекомендация с сохранённым состоянием. Контракт проверенной реализации задаёт переходы `created → grounding_checked → shown → issued`, а также `shown → expired` и `created|grounding_checked → failed`. Терминальных состояний три: `issued`, `expired`, `failed`. Истечение задаётся отдельным вызовом `expire`; наличие состояния не доказывает автоматическую обработку срока.

Каждый переход обновляет строку SQLite только при совпадении ожидаемого состояния (`UPDATE ... WHERE state = expected`); победа определяется одной изменённой строкой. Доступ публичных методов к соединению дополнительно защищён `threading.Lock`. Условное обновление и мьютекс решают разные задачи; этот код не является реализацией «без блокировок».

При `confirm_issued` переход `shown → issued` сохраняется в БД до возврата события `RecommendationIssued`. Повтор для уже выданной рекомендации возвращает `None`, не второе событие. Между commit и возвратом остаётся окно аварии: повторное подтверждение не восстанавливает потерянное событие. Один победивший переход и идемпотентное подтверждение не доказывают доставку внешнему получателю ровно один раз.

## Проверка результата

Конкурирующие допустимые переходы из одного состояния дают одного победителя. Недопустимый переход не меняет строку. Повтор подтверждения не создаёт второе событие. Отдельная проверка аварии после commit нужна для любой заявленной гарантии внешней доставки; outbox или иной механизм её обеспечения в этом источнике не установлен.

## Forces

Повторяемость вызовов при сбоях ↔ отсутствие повторного изменения состояния. Сохранение перехода до возврата исключает повторный переход, но создаёт отдельную задачу надёжной передачи события.

## Bias-Annotation

Смещение успешного пути ведёт к отождествлению возвращённого события с гарантированной доставкой. Разбор точки аварии после commit ограничивает этот вывод.
