# DP.M.556 — Исключать запрещённые поля из запроса, не фильтровать постфактум

## Описание

Когда инструмент отдаёт потребителю урезанный набор данных (часть столбцов запрещена для этого адресата), запрещённые поля исключаются из самого SQL-запроса (проекции SELECT), а не выбираются вместе со всеми и вычищаются в коде перед ответом.

## IPO

**Вход:** запрос, отдающий потребителю данные из таблицы/вью, часть столбцов которой запрещена для этого адресата (например, комментарии наставника в данных участника).

**Процесс:**
1. Определить полный список разрешённых для адресата столбцов.
2. Явно перечислить их в SELECT (или view/функции) — не `SELECT *`.
3. Не полагаться на пост-обработку (удаление/маскирование ключей объекта после выборки) как единственную защиту.

**Выход:** запрещённые поля физически отсутствуют в результате запроса к БД.

## Тест применимости

«Если фильтр-после-выборки в коде забудут обновить при следующей правке (новое поле добавится в таблицу/маппинг) — утечёт ли запрещённое поле?» Да → перенести защиту в проекцию SELECT (там забытое поле не может протечь, потому что его там структурно нет). Нет (проекция и так явная и проверяется) → текущая защита достаточна.

## Антипаттерн

`SELECT * FROM learner_data WHERE ...`, затем в коде `delete result.mentor_comment` перед ответом — защита держится на том, что никто не забудет этот шаг при будущей правке схемы или добавлении нового чувствительного поля.

## Почему устойчивее

Забытый постфактум-фильтр — молчаливая утечка (код работает, тест может быть зелёным, поле просто протекает). Отсутствующий в SELECT столбец утечь не может ни при каком пропущенном шаге после запроса — класс ошибки устранён структурно, а не процедурной дисциплиной.

## Отличие от смежного

- `DP.M.342` / `DP.M.464` (SECURITY DEFINER вместо прямых прав / для не-читателя) — те же общие мотивы (сузить доступ на уровне БД, не доверять приложению), но другой механизм и другая гранулярность: там — какая РОЛЬ имеет право вызвать операцию целиком (table-level/function-level grants); здесь — какие КОЛОНКИ физически возвращает один конкретный запрос (column-level projection) независимо от роли вызывающего.
- `DP.M.511` (MCP-тул проверяет авторизацию сам) — про то, что каждый тул независимо проверяет личность/право вызывающего на каждый вызов. DP.M.556 — про то, что именно возвращает запрос уже авторизованному вызывающему. Ортогональны: можно пройти авторизацию (DP.M.511) и всё равно получить лишнее поле, если проекция не сужена (DP.M.556).
