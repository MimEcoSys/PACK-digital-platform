# DP.M.559 — Раздача сайта и канал деплоя — разные системы

## Входы и выходы

Вход: отчёт о статусе шага CI/CD (например, GitHub Actions) по обновлению публичной страницы. Выход: решение, считать ли изменение опубликованным для пользователя — принимается только по факту отдельной проверки живого ответа на целевом адресе, не по статусу шага CI.

## Метод

1. Установить, разделены ли архитектурно канал раздачи контента (веб-сервер/CDN, отдающий текущую версию сайта) и канал деплоя (CI/CD, обновляющий эту версию) — две разные системы, не один процесс.
2. Если разделены: падение/зависание шага деплоя (например, таймаут подключения к управляющему API кластера) не означает, что сайт недоступен — раздача может продолжать стабильно отдавать текущую (ещё не обновлённую) версию.
3. «Успешно» в логе CI тоже не достаточно — подтверждает, что шаг деплоя завершился, не то, что пользователь уже видит новую версию.
4. После каждой попытки публикации — явно проверять живой HTTP-ответ по целевому адресу, отделяя «деплой прошёл» от «пользователь видит изменение».

## Проверенный прецедент

WP-589: несколько подряд выпусков system-school.ru через GitHub Actions таймаутили на шаге подключения к API кластера VK Cloud («Ensure namespace exists»), при этом сайт продолжал стабильно отдавать 200. Ассистент не засчитал публикацию по зелёному статусу CI, проверял живую страницу на целевом адресе после каждой попытки.

## Forces

Скорость подтверждения публикации (доверять CI-статусу сразу) ↔ надёжность подтверждения (CI и раздача — разные системы, статус одной ничего не говорит о другой). Метод принимает лишний шаг отдельной проверки ради правильного вывода о видимом пользователю результате.

## Bias-Annotation

Смещение к удобству автоматического сигнала: зелёный статус шага CI воспринимается как достаточное доказательство публикации, потому что он есть и он автоматический — хотя относится к другой системе, чем раздача.

## Отличие от соседей

DP.FM.203 — задеплоенный консенсус/тесты не ловят скрытую ошибку в данных уже выполненного деплоя (деплой состоялся, но имеет дефект). Здесь иной случай: сам деплой мог не дойти до раздачи вовсе, потому что это архитектурно разные системы — проверяется не корректность данных, а сам факт видимости изменения. DP.FM.374 — артефакт задеплоен, но не подключён к вызывающему чек-листу (wiring gap внутри одной системы); здесь разрыв между двумя системами (CI и hosting), не между артефактом и его вызовом.
