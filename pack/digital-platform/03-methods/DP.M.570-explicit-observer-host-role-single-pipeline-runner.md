# DP.M.570 — Явная роль хоста: один исполнитель, остальные наблюдатели

## Проблема

Пользователь работает на нескольких хостах (в прецеденте — Мак и Цех), у которых общий конфиг дневного ритма. Если каждый хост по расписанию сам запускает пайплайн открытия дня, пайплайн выполняется дважды: два плана, два набора публикаций, конфликты в общих файлах. Если же хост просто ничего не делает, он не узнаёт, что его локальное состояние отстало от опубликованного плана.

## IPO

| Элемент | Описание |
|---|---|
| Входы | Один пайплайн по расписанию, конфиг которого развёрнут на нескольких хостах, общий origin |
| Обработка | В конфиге каждого хоста — явный флаг роли (`observer: true` для наблюдателя). Исполнитель (флаг не задан) запускает пайплайн и публикует результат. Наблюдатель пайплайн не запускает, а читает опубликованный план из origin и сверяет с ним локальное состояние |
| Выходы | Ровно один запуск пайплайна на цикл; каждый наблюдатель синхронизирован с результатом исполнителя |

## Тест применимости

«Если этот конфиг развернуть на втором хосте как есть — пайплайн запустится дважды?» Да → нужен явный флаг роли хоста, а не надежда на то, что второй хост выключен или расписание на нём не настроено.

## Операционный режим наблюдателя (merge 10-25-7#1)

Наблюдатель проверяет наличие результата через read-only fetch: результат есть → молчаливый skip; fetch упал → defer без сигнала тревоги (сетевой сбой ≠ «сервер не опубликовал»); окно истекло без результата → один дедуп-сигнал за день.

Прецедент (WP-568): серверный агент публиковал DayPlan к 03:04, launchd на втором хосте запускал тот же пайплайн в 04:00 — три дня подряд ложная тревога «план не собран» при живом плане. Решение: ключ `day_open.observer: true` переключает второй хост в read-only режим.

Паттерн применим к любому пайплайну с единственным легитимным издателем и несколькими потенциальными триггерами (launchd, cron, CI runner, peer agent). Недоступность канала проверки (fetch timeout, network error) обрабатывается отдельно от отсутствия результата. Флаг observer не исключает другие роли хоста (мониторинг, алертинг) — только право записи в общий ресурс.

## Граница

Метод задаёт, кто запускает пайплайн. Он не защищает от повторного запуска на самом исполнителе (это суточный штамп под замком, AS.M.123) и не сливает данные, которые хосты всё равно пишут в общие ленты (DP.M.488, DP.M.542). Передача роли исполнителя другому хосту — отдельное явное изменение конфига. Порядок такой передачи в источнике не описан.
