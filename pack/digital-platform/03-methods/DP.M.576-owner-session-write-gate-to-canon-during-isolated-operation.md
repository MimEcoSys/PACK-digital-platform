# DP.M.576 — Гейт записи в канон, ограниченный владением сессии

## Проблема

Агент может подставить путь канона вместо корня изолированной копии. `DP.FM.507` описывает последствие: правка уходит мимо копии, а раннер публикации доказывает доставку не по той копии. Тест обнаружения ловит это после факта. Советующий хук из `DP.M.436` проверяет результат правки постфактум и при сбое пропускает; адрес записи заранее он не отклоняет.

## Метод

Вход: идентификатор сессии и путь цели вызова Edit/Write; запись о владении операцией (какая сессия, какая копия).

1. Хук срабатывает перед вызовом инструмента записи.
2. Если сессия вызова совпадает с владельцем операции, реальный путь цели (после раскрытия символических ссылок) сравнивается с каноническим каталогом.
3. Цель в каноне → отказ с диагностикой: какой корень изолированной копии использовать. Иначе запись разрешена.

## Ключевые решения

- **Область — владение операцией, а не «любая изолированная сессия на хосте».** Сопоставление с любым активным семафором даёт ложные блоки (`DP.FM.590`).
- **Блокирующий, а не советующий.** Цель — не допустить запись, поэтому это guard, а не checker; fail-open здесь не подходит.
- **Сравнение после раскрытия ссылок.** Сравнение строк пропускает символические ссылки.

## Тест применимости

«Есть операция, во время которой сессия обязана писать только в контролируемую область, и запись этой сессии в канон ломает операцию?» Да → гейт по владению. Нет → достаточно проверок при публикации.

## Границы

- Подмена каталога между проверкой и записью и жёсткие ссылки не защищены: нужен механизм, проверяющий цель при открытии файла.
- Гейт действует только на вызовы инструментов одного рантайма; правки через bash и другие рантаймы проходят мимо.

## Отличие от соседей

- `DP.M.436` — советующий хук после правки, для общих файлов; здесь блокирующий хук до правки, ограниченный сессией-владельцем изолированной операции.
- `DP.FM.507` — отказ, который этот метод предотвращает.
