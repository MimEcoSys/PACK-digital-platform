# DP.M.581 — Различимые состояния отказа после проверки владения; неготовность — отдельным кодом

## Контекст

В сервис наставничества добавляли отдельный ответ для отозванного ключа опроса (`gone`, 410, `-32005`) и барьер готовности защитной подсистемы. Ревью (Codex и холодный субагент) нашло две ошибки проектирования: чужой вызывающий по разным ответам узнавал, существует ли объект (оракул существования); недоступная защитная база роняла всю карточку участника, а простое «при неготовности — отказ в правах» заставляло клиента принять неготовность за «нет прав».

## Метод

**А. Различимое состояние отказа — только владельцу.**

1. **Сначала владение, потом различение.** Проверка владения идёт до любого ответа, раскрывающего состояние объекта.
2. **Различимые состояния только владельцу.** `gone` получает только проверенный владелец и только для отозванного ключа в окне хранения.
3. **Единый отказ всем остальным.** Для не-владельца ответ одинаков по тексту, коду и форме на всех путях: «нет строки», «чужой», «отозван», «сбой основной базы».
4. **Не отдавать то, чего не знаешь.** Причину (`revoked|expired`) наружу не передавать: защитный слой её не хранит.
5. **Проверять фактическое условие выборки.** Сверка 22.10 ошибочно утверждала, что гард возвращает строку и для истёкшего ключа; условие `expires_at > clock_timestamp()` истёкшие строки не возвращает, поэтому «отозван» отличим от «нет или истёк» только в окне хранения.

**Б. Барьер готовности — отдельным кодом.**

1. **Барьер.** До первой успешной сверки защитной подсистемы сервис отвечает `unavailable` (503, код `-32004`) после проверки личности, чтобы неготовность не открывала анонимный канал.
2. **Отдельный код, не отказ в правах.** «Не готово» и «нет прав» — разные состояния с разной реакцией клиента (повторить позже или запросить доступ). Оба запрос не пропускают.
3. **Закрытие сразу.** Любая ошибка сверки немедленно закрывает барьер; открывает его только следующая успешная сверка.
4. **Одна сверка в полёте.** Параллельные сверки запрещены: ревью нашло гонку, при которой поздняя успешная сверка открывала барьер после свежей ошибки.
5. **Повтор после сбоя** — через фиксированный интервал (одна минута).
6. **Локальная деградация.** В составном ответе недоступным помечается только блок, зависящий от защитной подсистемы (опрос); остальная карточка отдаётся.

## Граница

- Метод не противоречит DP.FM.640, DP.FM.481 и DP.FM.517: там неразличимые ошибки мешают диагностике самому оператору. Здесь неразличимость нужна только снаружи, для не-владельца; владелец и операторская телеметрия различимые состояния получают. Для отрицательных проб доступа применять DP.FM.640.
- Барьер не ловит поломку хранилища между суточными проходами без перезапуска: состояние готовности обновляется только сверкой.
- DP.M.298 (fail-closed при недоступности policy-сервиса: `deny`) этот метод уточняет по коду ответа, не ослабляя fail-closed.

## Тест

- Чужой вызывающий получает побайтно одинаковые ответы на несуществующий, отозванный и существующий чужой ключ, а также при отключённой основной базе.
- Владелец отозванного ключа в окне хранения получает `gone`; вне окна — тот же отказ, что и все.
- До первой успешной сверки сервис отвечает `unavailable`; три намеренные поломки (ранний ответ до сверки, неисчезающий барьер после ошибки, параллельные сверки) краснят свои тесты (по отчёту источника: 775 тестов проходят).

## Связи

- DP.FM.640 — одинаковая ошибка не различает путь и отказ (граница: унификация может быть защитой)
- DP.FM.481, DP.FM.517 — неразличимые ошибки как дефект диагностики; порядок проверок задаёт семантику ошибки
- DP.M.511 — тул проверяет авторизацию сам на каждом вызове
- DP.M.298 — fail-closed scope sidecar
- DP.D.286, DP.D.355 — «нет состояния» ≠ отрицательный результат в других субстратах
