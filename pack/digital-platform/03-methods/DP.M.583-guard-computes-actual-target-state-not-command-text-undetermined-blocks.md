# DP.M.583 — Охранник вычисляет цель, а не угадывает по тексту

## Проблема

Хук искал `git add` в тексте команды. Текстовый поиск ошибается в обе стороны: блокировал `(cd <другой репозиторий> && git add)`, где индекс канона не затрагивается, и пропускал обходы через `$(…)`, `GIT_DIR`, `--git-dir`, `GIT_INDEX_FILE`. В базе уже шесть карточек об охранниках, слепых к устройству команды (DP.FM.417, 421, 423, 605, 624, AS.FM.147), но метода лечения в этом Pack не было. Правило AR.302 задаёт тот же принцип для удаления через рантайм-обёртку, проверяющую цель в момент исполнения; здесь разбор команды до исполнения с отказом при неопределённости.

## Метод

1. **Разбор как при исполнении.** Команда разбирается последовательно: подоболочки, `cd` через `&&` и `;`, цепочка `-C`, `env -u`, `bash -c`.
2. **Вычисление цели.** Определить файл индекса, который реально изменится, и сравнить его с индексом канона, а не искать слова в тексте.
3. **Неопределённая цель блокируется.** Если разобрать команду так, чтобы назвать цель, не удалось, охранник отказывает (решение пилота 29.10.2026). Отказ называет причину и просит указать репозиторий литерально. **Дополнение 2026-11-20: неопределённое слово ≠ неопределённая цель.** Неразрешённое слово (заглушка UNKNOWN) даёт отказ только там, где оно может скрыть стейджинг; где не может, разбор продолжается. Это уточнение решения пилота 29.10, а не его отмена: неопределённая цель по-прежнему блокируется. Прецедент (коммит 76d0f27 в iwe-local-config, РП-484 Ф298, 10.11.2026): заглушка доходила до строкового кода в четырёх местах (имя команды, аргумент обёртки или `env`, опции shell, аргумент `git restore`) и роняла помощник исключением; хук сообщал «внутренняя ошибка разбора» и блокировал даже безопасные вызовы, в том числе шаг 15 закрытия дня. После исправления каждое место даёт обоснованный вердикт; три холодных ревью безопасности, 104 случая теста замороженного стейджинга (оба числа из сообщения коммита 76d0f27). Отчёт `DS-my-strategy/inbox/extraction-reports/2026-11-19-inbox-check-2.md`, кандидат 3.
4. **Границы записаны.** Осознанно не закрыты склейки имени (`g''it`), алиасы и `cd` через `;` в отдельных формах. Граница зафиксирована в коммите, тест из 49 сценариев (коммит 0890a9e в iwe-local-config, РП-561 Ф54) покрывает ложные блоки и обходы. **Дополнение 2026-11-20:** после коммита 76d0f27 непокрытым остаётся (перечислено в коммите для пилота): экспорт через `declare -x` и `set -a`, `CDPATH`, функции shell, относительный `GIT_INDEX_FILE`, сокращённый `--staged`, другие команды, пишущие индекс.

## Граница слоёв (дополнение 2026-11-20)

Разбор текста команды до запуска не видит нарочной маскировки: функции, псевдонимы, `declare -x`, `CDPATH` подменяют команду уже после того, как текст прочитан. Перехват при исполнении работает другим слоем: обёртка над git срабатывает в момент запуска, видит настоящий каталог и раскрытые опции.

Решение 10.11 (РП-484 Ф298; пилот поручил решить агенту, коммит 357ee89d9 в DS-my-strategy): разборщик (iwe-local-config PR #149) дальше не расширяют, защиту от нарочной маскировки ставят в обёртку git. Обёртка уже перехватывает `add`, `stage`, `commit`, `stash`, `reset --hard`, `rebase`, `merge` и псевдонимы.

Обёртка тоже видит не всё:

- она видит только вызовы, которые проходят через неё; вызов git по абсолютному пути её обходит (возражение Кодекса при разборе кандидата 20.11, отдельной проверкой не подтверждалось);
- остальные команды, пишущие общий индекс (`rm`, `mv`, `restore --staged`, `apply --cached|--index`, `update-index`, `read-tree`, `reset <путь>`), обёртка не перехватывает. Собственный конвейер вызывает их на репозиториях управления, и не для каждого вызова доказан запуск под исполнителем, которого обёртка пропускает; расширение без такой проверки рискует остановить конвейер. Риск принят: агенты по ошибке пишут в индекс почти всегда через `add` и `commit`, а они перехвачены. Условие пересмотра: первый живой случай, когда чужой файл попал в общий индекс через одну из этих команд → новая фаза РП-484, в ней сначала проверяется каждый вызывающий скрипт.

Тот же принцип в AR.302: текстовая эвристика годится как первый фильтр, но не как источник исключений. Отчёт `DS-my-strategy/inbox/extraction-reports/2026-11-19-inbox-check-4.md`, кандидат 1.

## Forces

| Сила 1 | Сила 2 | Как метод их удерживает |
|--------|--------|-------------------------|
| Не мешать законной работе (ложные блоки) | Не пропускать обходы | Вычисление фактической цели вместо поиска слов |
| Разбирать любой синтаксис shell | Разбор всегда неполон | Неопределённость считается отказом, границы названы открыто |
| Простота охранника | Охранник становится мини-интерпретатором | Разбор вынесен в отдельный помощник под тестом |

## Bias-Annotation

- **Смещение к безопасности:** блокировка при неопределённости увеличивает число отказов в нетипичных, но законных командах; платой считается указание репозитория литерально.
- **Смещение одного прецедента:** метод выведен из запрета стейджинга; переносимость на другие охранники (удаление, запись) утверждается по сходству семейства, а не по замеру.
- **Неполнота разбора:** любой разбор shell обходим; границы названы, но не исчерпаны.

## Тест применимости

«Решает ли охранник по тексту команды или по тому, что команда изменит, и что он делает, когда цель определить не удалось?» Решает по тексту или пропускает при неопределённости → метод не применён.
