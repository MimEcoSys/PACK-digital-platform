# DP.M.592 — Усечение сводки целыми записями в единицах получателя

## Проблема

Сборщик сводки для отправки получателю с лимитом длины сообщения (напр. Telegram) считал длину в символах/байтах и резал текст по достижении лимита, не глядя на границы записей — обрезка приходилась на середину записи, и получатель видел обрывок.

## IPO

- **Вход:** список записей для сводки + лимит длины сообщения получателя.
- **Процесс:**
  1. Длину накопленного текста считать в единицах, в которых её считает САМ получатель (UTF-16 code units для Telegram), а не в символах или байтах исходной кодировки.
  2. Добавлять записи в сводку целиком; как только очередная целая запись не помещается в остаток лимита — не резать её, а остановиться перед ней.
  3. Непоместившиеся записи не отбрасывать молча: добавить строку-пометку «не поместилось записей: N» в конец сводки.
- **Выход:** сообщение в пределах лимита получателя, целое по границам записей, с явным счётчиком потерянного остатка.

## Тест применимости

«Сборщик сводки/дайджеста отправляет получателю с жёстким лимитом длины сообщения, и записи — самостоятельные смысловые единицы (не поток символов)?» Да → усекать по записям в единицах получателя, не по символам/байтам.

## Границы

Единицы длины зависят от получателя (мессенджер, API) — перед переносом на другой канал проверить, в чём считает лимит именно он.
