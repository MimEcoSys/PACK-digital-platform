# DP.M.594 — Доказательство дословного переноса кода

## Метод

Когда код переносится в другой файл или модуль «без изменения поведения», зелёные тесты подтверждают только то, что тесты покрывают. Изменение в непокрытой ветке (порядок проверок, пропавшее условие, другой код ошибки) проходит незамеченным. Поэтому дословность переноса доказывается отдельно и проверяемо: каждая удалённая строка должна найтись среди добавленных, а любое отличие должно попадать в заранее названный список разрешённых.

## Вход

- Изменение, заявленное как перенос без изменения поведения.
- Страж поведения на коде до переноса (снимки ответов).
- Список разрешённых отличий, заданный **до** сверки: например, `export`, строки импорта, обёртка перенесённого кода в функцию, отступ.

## Действие

1. **Разделить коммиты.** Дословный перенос и преобразование (перевод на таблицу обработчиков, переименование, упрощение) — отдельными коммитами, чтобы сверка и ревью видели их порознь. Шаг, который в одиночку оставляет мёртвый код (например, пустая таблица обработчиков), сливается со следующим, а не коммитится отдельно.
2. **Сигнал 1 — страж.** Страж поведения зелёный **без перезаписи снимков**. Перезапись снимка в коммите переноса — сам по себе признак, что поведение изменилось.
3. **Сигнал 2 — построчная сверка.** Взять удалённые строки (`-`) и добавленные строки (`+`) диффа коммита, нормализовать (обрезать пробелы по краям, убрать пустые строки), отсортировать и сравнить как мультимножества (`sort` + `comm -23` или аналог). Каждая удалённая строка, которой нет среди добавленных, и каждая добавленная, которой нет среди удалённых, должна попадать в список разрешённых отличий. Остальное — изменение поведения до тех пор, пока не доказано обратное.
4. **Сигнал 3 — холодное ревью** по каждой ветке перенесённого диспетчера или модуля: ревьюер без контекста автора сверяет старую и новую ветку.
5. Принять перенос, только если все три сигнала сходятся. Расхождение в любом — откатить коммит к дословному виду или вынести изменение в отдельный коммит с собственным обоснованием.

## Выход

- Коммит переноса с записанным результатом сверки: «отличия только `export` / импорты / обёртка», число перенесённых строк.
- Отдельные коммиты преобразований, каждый со своим ревью.

## Наблюдённый случай

WP-7 Ф284 п.7: вынос групп инструментов из главного файла шлюза (5272 → ~4000 строк) серией PR gateway-mcp#156–#158. Сверка первого PR показала, что изменились только слова `export`: каждая удалённая строка дословно нашлась в новых файлах. Дословный вынос и перевод на таблицу «имя → обработчик» шли отдельными коммитами.

## Пределы

- Сверка мультимножеств не видит **перестановки** строк внутри перенесённого блока. Если порядок важен (цепочка проверок, гейты перед обработчиком), это ловят ревью по ветке (сигнал 3) и страж с мутацией гейтов (`DP.METHOD.106`, дополнение 2026-11-02).
- Метод не применим к переносу с одновременной правкой; поэтому шаг 1 обязателен.
- Повторяющиеся тривиальные строки (`}`, `return;`) совпадают «сами собой»; сверка по ним ничего не доказывает, их вес — на стороне стража и ревью.

## Связи

- `DP.METHOD.106` — как убедиться, что страж поведения честен (мутация); здесь страж — только один из трёх сигналов.
- Отложенный метод выноса обработчиков из монолитного диспетчера (extraction-reports/2026-11-04-inbox-check.md, кандидат #4) — при записи ссылается на этот метод как на способ приёмки каждого шага.
