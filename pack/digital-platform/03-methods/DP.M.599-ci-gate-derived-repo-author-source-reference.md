# DP.M.599 — Проверка CI: правка производного файла ссылается на правку источника

## Проблема

Правило «шаблон — производный, правь источник» без механической проверки остаётся только декларацией. Пример: PR затронул 339 файлов, и ни одна из 17 проверок CI не знала, что у 22 из них есть авторский источник. О нарушении узнали только после слияния, когда вырос счётчик конфликтов синхронизации.

## Метод

**Вход:** PR в производный репозиторий (шаблон), список изменённых файлов, описание PR (тело из события, запустившего проверку) и полные сообщения коммитов PR.

1. **Список строит синхронизатор.** Перечень файлов с авторским источником генерирует сам инструмент синхронизации из своего манифеста или хешей. Ручной список отстанет от реального набора. Оговорка: и генерируемый список может отставать, если генератор переписывает его не на каждом прогоне (DP.FM.794: список не узнал об исключении файла из доставки).
2. **Проверка PR.** Если PR меняет хотя бы один файл из списка, в описании PR или в сообщении одного из коммитов PR должна быть строка `Author-Source:`, указывающая, где сделана та же правка в источнике. Проверка ищет строку в теле PR и в полных сообщениях коммитов (не только в темах). Допустимы три формы ссылки:
   - `Author-Source: iwe-local-config#141` — PR или задача в репозитории источника (имя репо без владельца);
   - `Author-Source: aff0613` — коммит источника (голый sha, 7–40 шестнадцатеричных знаков);
   - `Author-Source: pending #1499` — правка источника ещё не сделана, номер задачи о ней.
3. **Красный статус.** Нет строки — проверка падает до слияния.
4. **Исключение для синхронизатора.** PR, которые создаёт сам синхронизатор (доставка из источника), проходят без строки: для них источник уже задан.

**Выход:** нарушение направления правок видно до слияния, а не по счётчику конфликтов после.

## Тест применения

«Узнает ли CI до слияния, что PR правит производную копию файла с авторским источником?» Если нет, правило направления правок держится только на дисциплине.

## Ограничения (на 2026-11-03)

- Уточнение 2026-11-18: на 2026-11-03 живой PR через проверку ещё не проходил; позже живой PR FMT #1498 прошёл через неё: падение, падение при перезапуске после правки описания, успех на новом коммите с трейлером (см. «Перезапуск проверки»).
- Проверка не входит в обязательные для `main`, поэтому её можно обойти.
- Строка `Author-Source:` — заявление автора PR. Совпадение правки в источнике она сама не доказывает (см. DP.D.375).

## Перезапуск проверки (дополнение 2026-11-18, РП-170)

Проверка запускается на событие `pull_request` без типа `edited` (FMT `.github/workflows/author-source-gate.yml:8-10`), а тело PR берёт из события (`github.event.pull_request.body`, строка 27). Отсюда:

- **Перезапуск (rerun) читает то же событие, что исходный запуск, с телом PR на момент события.** Правка описания PR после запуска проверки и rerun не помогают: перезапуск видит старое тело PR.
- **Новое событие даёт новый push в ветку PR** (`synchronize`), и это событие несёт свежее тело PR.

Наблюдённый путь (FMT #1498, WP-406 Ф40, 09.11.2026): ссылку дописали в описание после запуска, перезапуск остался красным; тогда ту же ссылку дописали трейлером в сообщение своего последнего коммита и отправили ветку, проверка прошла. Наблюдался только этот путь (push с трейлером). Что любой новый push, даже без трейлера в коммите, подхватит исправленное описание, следует из устройства события `synchronize`, но не наблюдалось.

Трейлер в сообщении коммита служит проверке PR и не переживает squash-слияние (DP.FM.618): на main после squash его может не остаться.
