# DP.M.605 — Правила для хука: снимок на сессию, а не живая копия

## 1. Определение

Способ доставки правил агенту хуком, который срабатывает на каждом ходу. Правила читаются не из живой копии репозитория, а из снимка на коммитах, закреплённых за сессией при первом чтении.

## 2. Проблема

Хуки стиля подмешивают агенту правила из PACK-rhetoric и PACK-digital-platform на каждом ходу. Когда читательским копиям паков дали исполнителя обновления (фоновая перемотка, см. DP.FM.701), живая копия начала меняться прямо посреди сессии. Одна сессия могла получать на разных ходах разные правила: работа, начатая по одной версии, заканчивалась по другой.

Свежесть и постоянство — разные требования. Между сессиями нужна свежесть: новая сессия должна видеть новые правила. Внутри сессии нужно постоянство: правила не должны меняться без ведома агента и человека.

## 3. IPO-паттерн

| Элемент | Описание |
|---------|----------|
| Входы | Живые копии паков, которые фоново перематываются; сессия; хук, подмешивающий правила на каждом ходу |
| Обработка | При первом чтении закрепить коммиты паков, которые увидела сессия. Читать правила из снимка на этих коммитах. Обновлять закрепление не реже раза в 6 ч. При несохранённых правках пака, сбое сборки или выключенном закреплении читать живую копию |
| Выходы | На всех ходах сессии один набор правил (в пределах окна обновления); правки автора пака видны сразу |

## 4. Шаги метода

1. **Закрепить.** При первом чтении сессия запоминает коммиты паков, которые увидела, и дальше читает правила из снимка на этих коммитах. Снимок побайтно совпадает с содержимым живой копии на тех же коммитах.
2. **Ограничить устаревание.** Закрепление обновляется не реже раза в 6 ч, чтобы долгая сессия не работала по старым правилам неограниченно.
3. **Не трогать живые копии.** Снимок собирается отдельно, без `reset` и `stash` в живой копии: ею распоряжаются исполнитель обновления и автор.
4. **Вернуться к живому чтению, когда снимок вреден или недоступен:**
   - в паке есть несохранённые правки: автор правит пак локально и должен сразу видеть свои правки;
   - снимок не удалось собрать: прежнее поведение лучше, чем отсутствие правил;
   - закрепление выключено переключателем (`STYLE_PIN=0`).
5. **Избегать известных ошибок реализации.** Ревью первой реализации нашло две ошибки, обе исправлены: гонку при сборке снимка и повторную сборку на каждом ходу. Снимок для одних и тех же коммитов собирается один раз, а параллельные сессии не должны портить друг другу сборку.

## 5. Тест применения

- «Если во время сессии фоновая перемотка сдвинет пак на новый коммит, получит ли агент на следующем ходу другие правила?» Да → правила читаются из живой копии, метод не применён.
- «Если автор пака сохранил правку локально, без коммита, увидит ли её его же сессия на следующем ходу?» Нет → не работает возврат к живому чтению.
- «Что будет, если две сессии одновременно соберут снимок на одних и тех же коммитах? Не собирается ли снимок заново на каждом ходу?» Обе ошибки уже встречались в реализации.

## Forces

| Сила 1 | Сила 2 | Как метод их удерживает |
|---|---|---|
| Свежесть правил между сессиями | Постоянство правил внутри сессии | Снимок на сессию, обновление не реже раза в 6 ч |
| Автор пака видит свои правки сразу | Остальные сессии не видят непроверенное | Живое чтение только при несохранённых правках пака |
| Снимок даёт постоянство | Сбой сборки снимка не должен лишать правил | Возврат к живому чтению при сбое |

## Bias-Annotation

- **Смещение к постоянству:** долгая сессия до 6 ч работает по устаревшим правилам; исправление важного правила доходит до неё с задержкой.
- **Смещение реализации:** окно 6 ч взято из реализации без обоснования; значение может быть подогнано под конкретный ритм перемотки.
- **Эффект не наблюдён:** прекращение «смены правил посреди сессии» в эксплуатации не подтверждено, проверено только детерминированное свойство (§5, первый вопрос).

## 6. Границы

- Метод касается правил, которые хук подмешивает на каждом ходу. Переносить его на рабочие данные сессии без отдельного разбора нельзя: там другие требования к свежести (см. DP.D.314).
- Окно 6 ч взято из реализации; обоснование этого значения в источнике не приведено.
- Эффект в эксплуатации на момент записи не подтверждён. Источник фиксирует реализацию и исправленные по ревью ошибки, но не наблюдение «смены правил посреди сессии прекратились». Свойство «одна сессия — один набор правил» детерминированное и проверяется первым вопросом теста.

## 7. Связанные документы

- DP.D.314 — «перечитывает при использовании ≠ снимок при записи». Ось та же, но здесь снимок выбран намеренно ради постоянства внутри сессии. Цену снимка (окно рассинхрона) ограничивают окно 6 ч и возврат к живому чтению при локальных правках.
- DP.FM.701 — копии без владельца подтягивания. Перемотка читательских копий лечит отставание между сессиями, а этот метод не даёт той же перемотке менять правила внутри сессии. Меры дополняют друг друга.
- DP.SC.172 — хуки инжекции правил стиля кода; режим отказа «агент работает по последней загруженной версии».
- DP.METHOD.228 — закрепление версии чужого компонента в репозитории (вендоринг по тегу). Там копия лежит в репозитории и меняется только сменой тега. Здесь закрепление действует на время сессии и копии в репозитории нет.
