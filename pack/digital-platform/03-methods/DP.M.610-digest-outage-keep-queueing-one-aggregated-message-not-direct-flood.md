# DP.M.610 — Сбой сводки: копить дальше, одно сообщение о сбое

## 1. Определение

Способ деградации пакетного канала уведомлений: когда сводка не выходит, канал остаётся пакетным, а о самом сбое получатель узнаёт одним агрегированным сообщением.

## 2. Проблема

Рутинные уведомления копятся и уходят сводкой (три слота в сутки). Страховка от потери при мёртвой сводке пересылала каждое событие отдельно в чат. Один сорванный слот во время сбоя GitHub дал 31 сообщение за час: запасной путь умножил шум именно тогда, когда получателю нужен один ясный сигнал.

## 3. IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Поток рутинных событий; очередь сводки, которая очищается только после подтверждённой доставки (DP.M.472); файл статуса сводки со временем последнего успеха; срочные и помеченные «живое» сообщения |
| Обработка | Шаги 1–6 ниже |
| Выходы | Во время сбоя — одно сообщение о сбое с числом накопленных (не чаще окна) и срочные сообщения; после восстановления — сводка с накопленным; при затяжном сбое — возврат по политике накопителя-шлюза |

## 4. Шаги метода

1. Сводка не ушла — события продолжают копиться в очереди; очередь не очищается (DP.M.472).
2. Попытка повторяется внутри того же слота (в прецеденте — таймер в :10 и :20 каждого слота).
3. Если сводка так и не вышла, живьём уходит одно сообщение «сводка не выходит с <время последнего успеха>, накопилось K». Повтор — не чаще раза в несколько часов (тот же приём, что один алерт на инцидент, DP.M.420).
4. Срочные и помеченные «живое» сообщения идут напрямую, как и без сбоя.
5. Пороговый возврат (3 суток) — политика самого накопителя-шлюза; запасник вызывающего — по DRR WP-568 Ф12: вызывающий отправляет напрямую только при техническом отсутствии шлюза и ведёт счётчик таких отправок.
6. Свежесть сводки определяется по времени последнего успеха, записанному внутри файла статуса, а не по дате изменения файла: файл переписывается при каждой пропущенной попытке.

## 5. Тест применения

«Сколько сообщений получит человек за час, если сводка сорвалась во время массового сбоя внешнего сервиса?» Число растёт с числом событий — запасной путь умножает шум. Одно сообщение о сбое плюс срочные — метод применён.

## Forces

| Сила 1 | Сила 2 | Как метод их удерживает |
|---|---|---|
| Не потерять события при мёртвой сводке | Не залить получателя потоком | Копить в durable-очереди, о сбое — одно сообщение |
| Получатель должен знать о сбое | Повторные сообщения о сбое — тоже шум | Сообщение о сбое не чаще окна в несколько часов |
| Срочное не должно ждать | Рутинное не должно прорываться | Срочные и «живые» — напрямую, остальное копится |

## Bias-Annotation

- **Смещение к тишине:** во время сбоя рутинные события задерживаются до восстановления сводки или порогового возврата; ценой снижения шума становится задержка.
- **Смещение одного прецедента:** пороги (3 суток, «несколько часов», повторы в :10 и :20) — значения прецедента, не норма.
- **Смещение к шлюзу:** метод предполагает, что накопитель-шлюз сам жив; при его техническом отсутствии остаётся прямая отправка вызывающим по DRR WP-568 Ф12, и шум снова растёт.

## 6. Границы

- AR.271 метод не отменяет: «есть угроза» и «проверить не смог» в сводку не понижаются; сообщение о сбое сводки само идёт в чат.
- Порог 3 суток, окно «несколько часов» и повторы в :10 и :20 — значения прецедента, не норма.
- Сведение очередей нескольких хостов к одной сводке — DP.M.600; этот метод — поведение при сбое уже сведённой сводки.

## 7. Прецедент

Сессия 2026-11-04 (DS-my-strategy `9962c5019`, `bb051bebe`). Решение из двух частей предложил Fable: повторы таймера внутри слота и деградация в одно сообщение «сводка опоздала». Порядок запасного пути вызывающего согласован с DRR WP-568 Ф12 (06.11.2026).

## 8. Связанные документы

- DP.M.472 — durable-очередь: копить во время сбоя безопасно, потому что очередь очищается только после доставки.
- DP.M.420 — один алерт на инцидент и окно повторов: сообщение о сбое сводки применяет тот же приём к инциденту самого канала.
- AR.271 — разделение каналов по severity; срочное не понижается.
- DP.FM.691 — прошлый сбой той же сводки: два месяца молчания без сигнала.
- DP.M.588 — «последний» по логической дате, а не по mtime; шаг 6 — тот же принцип для свежести.
- DP.M.600 — сведение уведомлений нескольких хостов на концентратор.
