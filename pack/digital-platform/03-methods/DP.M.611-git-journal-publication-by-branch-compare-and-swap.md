# DP.M.611 — Публикация в общий git-журнал через compare-and-swap ветки

## Проблема

Несколько служб или хостов дописывают записи в один журнал в git-ветке. Общий замок между ними — отдельная точка отказа: залипает, требует лечения и доказательства смерти владельца. Обычный `push` после `pull --rebase` переписывает чужую базу локально и не гарантирует, что публикуется ровно то, что проверено.

## IPO

- **Вход:** набор новых документов журнала; база B — коммит origin main, прочитанный при подготовке.
- **Процесс:**
  1. Проверить, что URL push и fetch у origin совпадают. Публикация должна идти туда же, откуда читается журнал; иначе CAS сверяет не ту ветку.
  2. Каждый путь — внутри разрешённого каталога журнала, без компонентов `.`/`..`, и **отсутствует** в B. Журнал только дописывается.
  3. Построить кандидата без рабочего дерева: blob'ы через `hash-object -w`, временный индекс (`GIT_INDEX_FILE`) от `read-tree B`, `update-index --add`, `write-tree`, `commit-tree -p B`. Единственный родитель — B.
  4. Сверить `diff-tree --name-status B кандидат`: ровно набор строк `A <путь>` по заявленным файлам. Любое иное изменение — отказ.
  5. `git push --porcelain --force-with-lease=main:B origin <кандидат>:main`.
- **Выход:** один из четырёх исходов:
  - `published` — квитанция с B, OID кандидата и дайджестом содержимого;
  - `base_changed` — porcelain-отказ `stale info` / `fetch first` / `non-fast-forward`: origin сдвинулся, перечитать базу и повторить;
  - `push_refused` — `remote rejected`: хук или защита ветки, вслепую не повторять;
  - `push_unknown` — тайм-аут или неразборчивый ответ.

## Почему работает

- `--force-with-lease=main:B` превращает push в атомарную операцию compare-and-swap на сервере: ссылка меняется, только если она всё ещё равна B. Из двух одновременных публикаторов на одной базе побеждает ровно один.
- Кандидат с единственным родителем B, только с добавлениями, гарантирует: при успехе в ветке ровно B плюс эти файлы. Ничего чужого не теряется и не переписывается.
- Потерянный ответ не требует восстановления: следующий проход читает свежий origin и находит записи уже опубликованными, поэтому повтор не дублирует.

## Антипаттерны

- Сводить все отказы push к «база сдвинулась» и повторять. Отказ хука при повторе не исчезнет, а цикл скроет настоящую причину.
- Сверять CAS по fetch-URL, а пушить в другой push-URL.
- Строить кандидата в общей рабочей копии: чужие незакоммиченные изменения попадут в коммит.
- Строить кандидата `commit-tree` от устаревшей локальной ссылки и пушить без lease: параллельные коммиты затираются (AS.FM.168).

## Forces

| Сила 1 | Сила 2 | Как метод их удерживает |
|---|---|---|
| Несколько писателей одновременно | Нет общего замка | CAS на сервере: побеждает ровно один, остальные перечитывают базу |
| Повторять при гонке | Не повторять при отказе хука | Раздельные исходы отказа push |
| Публиковать быстро | Публиковать ровно проверенное | Кандидат только с добавлениями, сверка diff-tree |

## Bias-Annotation

- **Смещение к append-only:** метод верен только для журнала, который лишь дописывается; для правок существующих строк нужен другой путь (AS.M.107).
- **Смещение живой пробы:** проверено на одноразовой ветке GitHub и 6 локальных тестах; на момент коммита в CLI не подключён, эксплуатационной нагрузки не было.
- **Смещение транспорта:** CAS решает, чья запись прошла, но не кому разрешено писать (AS.D.039).

## Проверка (живая проба источника)

Публикация на одноразовой ветке GitHub заняла 15,4 с. Устаревшая база отклонена, повтор не дублирует, из двух одновременных публикаторов на одной базе побеждает ровно один. 6 локальных тестов.
