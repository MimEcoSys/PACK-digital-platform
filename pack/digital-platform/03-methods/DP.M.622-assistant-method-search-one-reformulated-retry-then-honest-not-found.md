# DP.M.622 — Один переформулированный повторный поиск, затем честное «не нашёл»

## Проблема

Помощник ищет метод в библиотеке методов по описанию задачи человека. Человек не знает названий методов и говорит своими словами, а библиотека написана своим словарём. В 16 проверочных разговорах WP-406 Ф40 поиск по обычным русским фразам в 4 случаях не нашёл ничего.

Возможны две симметричные ошибки:

1. **Ложный отказ.** Первый пустой поиск принят за «метода нет», хотя метод есть под другим названием.
2. **Подмена.** Чтобы не отказывать, помощник берёт ближайший по словам, но неподходящий метод или придумывает несуществующий. Человек получает уверенный ответ, который не решает его задачу.

## Метод

1. **Первый поиск** — по смыслу задачи в словах человека.
2. **Если первый поиск ничего не дал** — один раз повторить его с переформулированным запросом:
   - синонимы и термины предметной области;
   - тот же запрос на русском и английском;
   - уровень обобщения выше («как договориться о сроках» → «согласование обязательств»).
3. **Если подходящий метод найден** — применять его по шагам метода.
4. **Если подходящего метода нет и после повторного поиска или библиотека не отвечает** — прямо сказать: «в библиотеке не нашёл метода для этой задачи». Не притягивать неподходящий метод и не выдумывать несуществующий. Для сервера с договором исходов сбой библиотеки отвечают иначе: см. дополнение 2026-11-20, граница у шага 4.
5. Повтор ровно один — это норма источника, а не измеренный оптимум. Она ограничивает дрейф запросов от исходной задачи; эффективность числа повторов отдельно не измерялась.

## Тест применения

- Помощник сказал «метода нет» после одного поиска? → нарушен шаг 2.
- Помощник предложил метод, шаги которого не относятся к задаче, вместо «не нашёл»? → нарушен шаг 4.
- Проверочный набор: фразы, у которых метод в библиотеке есть, но названия расходятся (ожидается «найден со второй попытки»), и фразы, для которых метода заведомо нет (например, «подбери рецепт борща», ожидается честный отказ).

## Forces

- Повторный поиск с другими словами снижает риск ложного отказа ↔ каждая новая переформулировка может уводить запрос от задачи человека.
- Честный отказ оставляет задачу без метода ↔ принудительный подбор создаёт видимость помощи, но подменяет задачу.

## Bias-Annotation

- Желание дать любой полезный ответ смещает помощника к подмене метода; ограничение — соответствие шагов исходной задаче.
- Первый пустой результат смещает к ложному выводу об отсутствии метода; ограничение — один переформулированный поиск и честная граница результата.

## Границы

- Метод смягчает расхождение словарей, но не устраняет его. В источнике полное снятие риска отнесено к отдельному сценарию «найти и применить метод» (WP-608).
- Это правило поведения помощника перед человеком. Запасной путь внутри поискового сервиса (пустой векторный результат → полнотекстовый поиск) описан в DP.FM.514 и действует на другом уровне.
- Отказ «не нашёл» ограничен проверенной областью и способом поиска (см. VR.FM.042). Он не утверждает, что метода не существует вообще.

## Дополнение 2026-11-17: стороны решения «метода нет»

Если сервер библиотеки получает только имя метода (текст человека до него не доходит — DP.M.628), решение «подходящего метода нет» принимает ИИ человека, а не сервер.

| | Сервер библиотеки | ИИ человека (клиент) |
|---|---|---|
| Что получает | только имя метода | запрос человека целиком |
| Какое решение принимает | «метода с таким именем нет» | «подходящего метода в перечне нет» (шаги 2–4 выше) |
| Что проверяет приёмка | явный ответ на несуществующее имя | качество подбора по строкам «когда применять» в перечне |

Сценарии приёмки делятся по сторонам: проверка подбора («рецепт борща» → честный отказ) — проверка ИИ клиента и строк «когда применять», а не сервера.

## Дополнение 2026-11-20: «найден» значит прошедший проверку карточки; граница сбоя у шага 4

**К шагу 3.** «Подходящий метод найден» значит: кандидат из выдачи поиска прошёл проверку по прочитанной карточке (условия применения, ограничения, порог модели). Непустая выдача применимости не означает: поиск возвращает кандидатов, а не подходящие методы (договор о сервере, коммит 743702f, §1; рабочий документ версии 4 РП-581, этап 0, шаг 4). Различаются два случая без метода: поиск ничего не вернул; кандидаты есть, но ни один не подходит. В обоих случаях ИИ не выдаёт свой совет за метод библиотеки (этап 0, шаг 5). Фраза человека «помоги разобраться» согласием на метод не считается (этап 0, шаг 6).

**Граница у шага 4.** Шаг 4 сводит «подходящего метода нет» и «библиотека не отвечает» к одному ответу «не нашёл». Для сервера с договором исходов (DP.M.635, дополнение 2026-11-20) это разные исходы. Любой ответ, кроме успеха, `not_found` и `invalid_arguments`, или отсутствие ответа: ИИ говорит «ответ Библиотеки получить не удалось», вид сбоя не называет и не угадывает и не подменяет сбой фразой «подходящий метод не найден» (требование Т34 рабочего документа версии 4).

**Оговорка к дополнению 2026-11-17.** Посылка «сервер библиотеки получает только имя метода» неприменима к случаю РП-581 после решения 10.11 п.(2): тестовый MCP делают сразу со смысловым поиском, и запрос человека уходит на сервер (карточка РП-581, «Решения 10.11»). Таблица сторон решения описывает случай без поиска на сервере.

Договор и требования версии 4 существуют как текст: запрос на слияние №3 в `aisystant/method-library` не слит, с 12.11 тема перезапущена (карточка РП-581, раздел «Перезапуск темы с 12.11.2026»); работающим сервером это не подтверждено.
