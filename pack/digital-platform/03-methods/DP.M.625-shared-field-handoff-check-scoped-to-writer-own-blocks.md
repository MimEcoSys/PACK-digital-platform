# DP.M.625 — Проверка общего поля по собственным блокам писателя

## Проблема

Несколько сессий одновременно работают над разными фазами одного РП и пишут в одно поле карточки («Следующий шаг»). При закрытии каждой сессии проверка сравнивает поле с состоянием при открытии и требует, чтобы оно было обновлено и непротиворечиво. Если сравнивать поле целиком, правка чужой фазы другой сессией выглядит как постороннее изменение, и закрытие падает, хотя писатель всё сделал правильно.

## IPO-паттерн

| Элемент | Описание |
|---|---|
| Входы | Общее поле с разметкой блоками фаз; список фаз, объявленных писателем при открытии; состояние поля при открытии и при закрытии |
| Обработка | Шаги 1–8 |
| Выходы | Вердикт закрытия, зависящий только от блоков писателя; откат к сравнению всего поля, когда разметка не позволяет выделить свои блоки |

## Шаги

1. **Область сравнения — свои блоки.** Блоки писателя берутся из его собственного текста следующего шага (в прецеденте `--what-next-file`); сравнивать только их. Чужие блоки того же поля в вердикт не входят.
2. **Объявленные фазы не теряются.** Список фаз, объявленных при открытии, писатель передаёт отдельно (в прецеденте задача семафора через `--declared-text`). Если у объявленной фазы в поле есть блок, писатель обязан привести этот блок в своём тексте; не привёл — провал. Объявленная фаза без блока в поле провалом не считается.
3. **«Не изменилось» — по своим блокам.** Требование «писатель обновил поле» проверяется на его блоках. Изменение чужого блока не засчитывается как обновление и не мешает.
4. **Неоднозначность — откат к старой проверке.** Текст до первого блока, тот же текст с иным переносом строк, отсутствие разметки → сравнение всего поля, как раньше. Ослабление проверки действует только там, где область однозначно выделена.

## Дополнение 2026-11-20: по какому снимку проверять

Шаги 1–4 задают область сравнения, но не версию карточки. Передача адресована следующей сессии, а та прочитает карточку из origin, а не из рабочей копии текущей сессии.

5. **Проверять опубликованный снимок.** На прогон берётся один снимок origin/main, и карточка (с архивом и перечнем допустимых фаз) проверяется в том виде, в каком её прочитает следующая сессия. Ложное расхождение «not_on_origin» в РП-484 09.11 источники объясняют по-разному: сообщение коммита `3fbe10e` указывает, что рабочая копия отличалась от origin, а карточка РП-484 (сводка журнала Ф285) указывает сравнение с origin до публикации карточки. Первую причину закрывает этот шаг, вторую шаг 6. Тот же принцип «проверять доставляемое, а не рабочее дерево» записан в DP.FM.466.
6. **Сначала публикация, потом проверка.** До публикации свежий origin закономерно не содержит передачи, и проверка по нему даёт ложный отказ (по записи карточки РП-484, тот же случай 09.11). В прецеденте тексты пир-сессий обновлены: Kimi публикует карточку до проверки и останавливается на коде 10.
7. **Записывать, с чем сверено.** В вердикт пишется `checked_against`: `origin@<sha12>`, `origin_verified_new` или `origin_unreachable`.
8. **Блок узкий.** Код 10 ставится только для трёх кодов собственных фаз этой карточки (`HANDOFF_AGENT_NEXT_MISSING`, `HANDOFF_AGENT_PHASE_MISSING`, `HANDOFF_UNKNOWN_PHASE`) и только при вердикте `origin@` от актуальной версии проверяющего (ср. DP.FM.697); остальное предупреждает. Закрытие сессии отказывает по коду 10 только при новом закрытии, возобновлённая доставка проверяется в режиме shadow. Откат: переключатель `IWE_HANDOFF_CHECK_MODE=shadow`, а не удаление проверки (ср. DP.M.525).

Источник: git commit `3fbe10e` в iwe-local-config (РП-484 Ф285, решение пилота 10.11; проверяемый скрипт `wp-handoff-peer-check.sh`, обёртка над `wp-handoff-check`), по сообщению коммита, код не открывался. Шаг 6 добавлен по возражению Кодекса при разборе кандидата. Эффект на частоту ложных провалов не измерен. Отчёт `DS-my-strategy/inbox/extraction-reports/2026-11-19-inbox-check-3.md`, кандидат 3.

## Тест применения

«Упадёт ли закрытие сессии A, если сессия B между открытием и закрытием A поменяла только свою фазу?» Да → область сравнения шире писателя. «Пройдёт ли закрытие A, если в поле есть блок объявленной фазы A, а A не привела его в своём тексте?» Да → шаг 2 не выполнен.

## Forces

| Сила 1 | Сила 2 | Как метод их удерживает |
|---|---|---|
| Параллельная работа в одном поле | Строгая проверка обновления при закрытии | Строгость сохраняется, но только на своих блоках |
| Меньше ложных провалов | Не открыть лазейку «ничего не обновил» | Объявленные фазы обязательны, «не изменилось» судится по своим блокам |
| Новая логика | Старые записи без разметки | Откат к сравнению всего поля |

## Ограничения

- Один случай (trust: low). Покрытие — тест `test_wp_handoff_check` 78/78 в источнике; эффект на частоту ложных провалов закрытия не измерен.
- Вызывающий и проверяльщик лежат в разных репозиториях и обновляются несинхронно. Старый проверяльщик отвергает новый флаг (rc 2), и вызов повторяется без него. Этот класс описан в DP.FM.697.
