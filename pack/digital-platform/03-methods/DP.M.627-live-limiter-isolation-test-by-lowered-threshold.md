# DP.M.627 — Живая проверка изоляции ограничителя заниженным порогом

## Проблема

Новый лимит или потолок расхода должен резать только свой класс вызовов. Естественное исчерпание проверяет это только постфактум, в аварии, а разделение ключей (DP.M.201) само по себе не доказывает, что разметка трафика полная (DP.FM.780).

## Метод

1. Поставить порог заведомо ниже любого реального расхода (в источнике — $0,01) на пару минут.
2. Вызвать от ограничиваемого класса (автоматика) → ожидать явный отказ с понятной причиной (HTTP 429, «потолок внутренней автоматики исчерпан, бот и пользователи не затронуты»).
3. В ту же минуту вызвать от защищаемого потребителя → ожидать успех (HTTP 200).
4. Вернуть рабочий порог, выбранный по данным наблюдения, а не по исходной оценке, и назначить дату пересмотра. В источнике обещали $2, автоматика одна к обеду потратила $2,42 — поставлено $5.

## Тест применения

- Лимит включён в прод без одновременного вызова обеих сторон при заниженном пороге → проверка изоляции не сделана.
- Рабочий порог взят из обещания, а не из наблюдённого расхода → нарушен шаг 4.

## Forces

| Сила | Напряжение |
|---|---|
| Чистый сигнал ↔ риск для прода | Заниженный порог даёт немедленный ответ «кого режет», но на эти минуты реальная автоматика тоже получит отказ |
| Одна минута ↔ независимые вызовы | Вызовы в одну минуту исключают смену состояния между ними, но требуют подготовить оба вызова заранее |

## Bias-Annotation

- **Уверенность в разметке** → смещает к пропуску живого теста: «ключи разделены, значит изолировано». Противовес — наблюдаемый отказ и успех на живом вызове.
- **Якорь исходной оценки** → тянет вернуть порог к обещанному значению; шаг 4 требует числа из наблюдения.

## Границы

Один источник (шлюз языковых моделей, РП-568 Ф12). Вывод: применимо к ограничителю, который можно временно перенастроить без выкладки кода.

## Связи

- `DP.FM.780` — риск, который метод проверяет.
- `DP.M.201` — разделение ключей по нагрузке: метод проверяет, что оно действительно изолирует.
- `DP.METHOD.178` — живая приёмка пользовательского инструмента: тот же принцип «проверить на живом, а не по чтению».
