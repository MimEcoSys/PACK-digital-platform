# DP.M.630 — Горячий путь чтения из git: пакетно, кэш по oid, свежий объект, один парсер

## Когда применять

Процесс за один проход много раз читает одни и те же объекты из git (журнал, записи, конфиги), и время прохода растёт с числом объектов до границы нормы.

## Вход

- Список путей и ревизий, которые нужно прочитать за проход.
- Лимит размера одного объекта.
- Норма времени прохода.

## Шаги

1. **Размеры — одним пакетным запросом.** `git cat-file --batch-check` по всем объектам. Лимит размера проверяется *до* чтения содержимого: слишком большой объект отклоняется, не попав в память.
2. **Содержимое — одним пакетным запросом.** `git cat-file --batch` вместо двух вызовов на файл. Нечитаемый или обрезанный пакетный вывод — повторяемая ошибка, а не остановка процесса.
3. **Быстрый разборщик.** Для YAML — libyaml (`CSafeLoader`); если его нет, работать на чистом Python и явно предупредить, а не деградировать молча.
4. **Кэш разбора по неизменяемому ключу.** Ключ — oid (содержимое по oid не меняется), размер кэша ограничен (в исправлении — 2 коммита). Инвалидация не нужна, потому что ключ неизменяем.
5. **Свежий объект каждому вызывающему.** Из кэша берутся разобранные данные, но каждый вызывающий получает заново собранный и проверенный объект. Иначе кэш становится общим изменяемым состоянием: правка объекта одним читателем меняет его для всех.
6. **Один парсер на всех читателей одного файла.** Хост-читатель истории, предпроверка миграции и проход доставки разбирают файл одной функцией. Разные парсеры дают одному файлу разные вердикты («валиден» в одном месте, «битый» в другом).

## Выход

Проход укладывается в норму с запасом; вердикт о файле одинаков во всех читателях.

## Критерий успеха

Замер свежим процессом на целевом хосте: 1000 записей — 5,3 с, 4000 — 21,6 с, 8000 — 42,8 с (было 61 с на 1000 при норме 60 с).

## Типовые ошибки

- Кэшировать готовый изменяемый объект и раздавать одну ссылку всем вызывающим.
- Ключ кэша — путь или имя ветки, а не oid: содержимое под ними меняется.
- Ускорить один читатель своим парсером и получить расхождение вердиктов с остальными.

## Дополнение 2026-11-20: старый алгоритм как оракул эквивалентности

Ускорение пакетным путём подтверждают сверкой со старым алгоритмом, оставленным в тестах как оракул. Это отдельное правило для обхода истории на хосте (один `diff-tree --stdin --raw` и предвыборка объектов, бюджет 32 МиБ, файлы больше 4 МиБ не читаются); шаг 2 описывает другой пакетный путь (`cat-file --batch` в читателе моста).

1. Новый путь сверяется со старым на тех же входах по порядку и по кодам отказов, а не только по итогу «прошло / не прошло». Сверку дополняет случайный перебор входов; в прецеденте расхождений ноль (коммит `d57ea5bf3`, «0 mismatches»).
2. Если проверку разбили на части ради скорости, части сливаются в исходном порядке, и прежний порядок отказов сохраняется.
3. Откат на поштучный путь допустим только при сбое самого пакетного механизма (транспорт, ресурсы), а не при любой ошибке пакетного пути: повреждение данных медленным путём не лечится, содержательный отказ остаётся отказом. В прецеденте код откатывается на поштучный обход при любом сбое пакета, чтобы отказы шли в порядке коммитов; сужение условия отката предложено Кодексом при разборе и вошло в принятую пилотом 20.11 таблицу решений; код прецедента (`06670c469`) не менялся, довод Кодекса отдельно не проверялся.

Тот же приём «прежний код как эталон» для раннего выхода и кэша: DP.M.468, дополнение 2026-11-10, шаг 3 (дифференциальный тест).
