# DP.M.635 — Порядок составления инструкции для ИИ к MCP-серверу

## 1. Определение

Порядок, в котором составляются тексты для ИИ человека, работающего с MCP-сервером (общая инструкция сервера, описания операций): сначала сценарий и договор о сервере, затем случаи и требования, потом доставка и размещение, и только после этого текст с версией, сверка, приёмка и подтверждение.

## 2. Проблема

Требования к ИИ опираются на то, что сервер принимает и отдаёт. Пока это не зафиксировано, после каждого изменения или уточнения устройства сервера составителю приходится переписывать инструкцию. В РП-581 редакции 1–3 «Инструкции Open для ИИ человека» (09–10.11.2026) писались без утверждённых требований и без договора о сервере. По выводу сессии, агент переписывал их вслед за изменениями и уточнениями устройства сервера: в тест добавился смысловой поиск; повторное ревью PR #3 показало, что страница метода гостю недоступна, что поиск и чтение карточки не отдают статус черновика, что предел запроса в 300 знаков — только указание ИИ, сервер его не обеспечивает. Редакцию 3 пилот не утвердил: по записи в РП-581, сначала нужны порядок работы и требования.

## 3. Шаги метода

Этапы 0–3 пройдены в случае-источнике. Этапы 4–9 ещё не пройдены: это проектируемая часть, их содержание взято из плана (итерация 1 и перечень этапов в карточке РП-581), а не из исполнения.

| Этап | Что делается | Выход |
|---|---|---|
| 0. Сценарий | Основной сценарий: кто приходит, с какой задачей, что получает. Сценарий составляется первым, до договора | Принятый сценарий |
| 1. Договор о сервере | Что принимает каждая операция, что отдаёт, как отказывает, какие исходы программа различает | Договор в документе о карточке метода; разработчика сервера просят подтвердить реализуемость в ревью |
| 2. Случаи и проверочные фразы | Общие случаи поведения ИИ (их набор не растёт с числом единиц каталога) отдельно от проверок отдельной карточки, которые приходят вместе с карточкой | Перечень случаев с проверочными фразами |
| 3. Требования с источниками | У каждого требования к ИИ — источник сведения: поле ответа операции или текст, который клиент показывает модели. Нет источника у требования → вернуться к этапу 1 и искать способ дать источник (например, поле в ответе операции); «сведений пока нет, не угадывать» годится только как временная мера, она не заменяет принятое решение. Для заготовки (метки подстановки) записывается правило заполнения: откуда берётся значение | Таблица «правило → источник → место → проверка» |
| 4. Доставка и поведение в клиентах *(не пройден)* | Какие тексты сервера доходят до модели в каждом целевом клиенте; сервер («отправил») и клиент («модель получила») проверяются на разных этапах | Отметка по каждому клиенту |
| 5. Размещение *(не пройден)* | Правило, без которого сценарий ломается, кладётся в текст, доходящий до модели во всех целевых клиентах; общая инструкция остаётся выжимкой в своём бюджете знаков | Раскладка правил по местам |
| 6. Файл текста с версией *(не пройден)* | Текст собирается из принятого на этапах 0–5 и выкладывается файлом с номером версии | Файл с версией |
| 7. Сверка обещаний *(не пройден)* | То, что ИИ по тексту говорит человеку о данных и гарантиях, сверяется с обещаниями платформы и договором о сервере; указание ИИ не выдаётся за гарантию сервера | Отметка сверки |
| 8. Приёмка *(не пройден)* | Случаи этапа 2 проверяются на этой версии текста в каждом целевом клиенте | Протокол приёмки |
| 9. Подтверждение *(не пройден)* | Разработчик сервера подтверждает выложенную версию | Подтверждённая версия |

Пояснения к этапам:

- Этап 3, иллюстрация. В итерации 3 агент заменил решение пилота «ИИ сам об авторах не говорит, но на вопрос честно называет» (РП-581, «Поправка об авторах») запасным «сведений пока нет», потому что отпала ссылка на страницу метода. По замечанию пилота источник дали в договоре: чтение карточки метода отдаёт авторов метода, авторов описания и лицензию (коммит 02533da в PR #3 aisystant/method-library), и решение восстановлено.
- Этап 5. Правило размещения — DP.SOTA.042, контрмера 1: правила, без которых сценарий ломается, класть в описания операций, потому что общая инструкция сервера доходит до модели не во всех клиентах. DP.M.505 — пример такого правила в описании операции (граница доверия к найденным документам).
- Этапы 4 и 8 — частный случай приёмки в каждой среде доставки (VR.M.049): здесь средами служат клиенты MCP.

## 4. Тест применения

«Может ли изменение того, что сервер принимает или отдаёт, заставить переписать уже написанные требования к ИИ?» Да → договор о сервере не зафиксирован или требования написаны раньше него: вернуться к этапу 1.

## 5. Границы

- Один случай: инструкция Open для ИИ человека (РП-581 Ф30). Пройдены этапы 0–3 (10–11.11.2026); этапы 4–9 не исполнялись.
- Предотвращает ли порядок переписывания, пока не проверено: версия 4 ещё не прошла доставку, приёмку и подтверждение.
- Метод описывает тексты для ИИ и договор, на который они опираются; код MCP-сервера пак не описывает.

## 6. Наблюдённый случай

РП-581 Ф30 «пересмотреть инструкции для ИИ» (10–11.11.2026). Пилот не утвердил редакцию 3 и решил составлять версию 4 в Zulip с ИИ-агентом команды Hermes по итерациям: одно сообщение пилота, ответ Hermes, согласованное приращение.

- Итерация 1: что такое инструкция и план. Принято с уточнениями Hermes: доставку проверять на своём подключении; гарантии сервера отдельно от правил ИИ; сервер и клиент проверяются на разных этапах; таблица «правило → источник → место → проверка».
- Итерация 2: пилот отправил порядок этапов 0–9 (сценарий раньше договора) и основной сценарий; Hermes принял с поправками.
- Итерация 3: договор о сервере (этап 1). Поиск принимает одно поле запроса длиной 1–300 знаков; пустой запрос, запрос из пробелов, не того типа, длиннее предела или с лишними полями отклоняется без обрезания, ошибка называет условие и не повторяет присланный текст; исходы различимы программой. Договор внесён в PR #3 (коммит 743702f, документ о карточке метода); сообщение разработчику сервера с просьбой подтвердить реализуемость в ревью — черновик 10.11.
- Итерации 4–5: случаи (этап 2), общие отдельно от проверок карточки метода.
- Итерация 6: требования (этап 3), 41 требование с источниками; Hermes согласовал этап 3 11.11.

В перечне этапов карточки РП-581 этап 6: английский файл с версией в `aisystant/method-library`; этап 9: подтверждение версии разработчиком сервера.
