# DP.M.637 — Диагностика красной итоговой проверки CI

## 1. Определение

Способ разобрать красную итоговую проверку выпуска шаблона (release-receipt): найти задание, из-за которого она красная, и по его исходу решить, чинить ли код или перезапустить задание.

## 2. Проблема

Итоговая проверка собирает результаты обязательных заданий того же запуска в одну квитанцию. Отменённое задание она считает так же, как упавшее: «Failure/cancelled/unknown … produces false» (`scripts/release-receipt.sh:17`). Так сделано намеренно: квитанция не выдаёт «можно выпускать» без подтверждённого результата. Но на красной итоговой проверке не видно, что именно случилось: дефект кода или задание, которому GitHub не выдал машину. Во втором случае поиск дефекта в правке — пустая работа.

## 3. Шаги метода

1. **Не искать дефект в самой итоговой проверке.** Открыть запуск и найти обязательные задания с исходом не «успех».
2. **Посмотреть исход и шаги исходного задания.** Отменено и не выполнило ни одного шага → машина не была выдана. Упало с выполненными шагами → обычная диагностика по журналу задания.
3. **Отмена без машины → код не трогать.** Перезапустить только неуспешные задания запуска; итоговая проверка перезапускается вместе с ними и собирает результаты заново.
4. **Отмена повторяется** → сверить состояние GitHub Actions: при сбое сервиса задания отменяются снова. Сливать в обход обязательной проверки — решение пилота, не исполнителя.

## 4. Тест применения

«Сколько шагов выполнило задание, из-за которого итоговая проверка красная?» Ноль и исход «отменено» → машину не дали, это не дефект правки.

## 5. Границы

- Два случая, оба на одном задании (проверка установки на macOS, integration-contract-macos) в репозитории шаблона.
- Метод не меняет правило квитанции: отменённое задание по-прежнему блокирует выпуск. Отличать «машину не дали» от «упало» в самой квитанции пока только предлагается как правка CI шаблона (РП-529, журнал сессии 04.11); в скрипте на 20.11 (FMT a3c1b117, стр. 17) отмена по-прежнему даёт «не к выпуску».
- Почему GitHub отменил задание без машины, источники не называют; 04.11 совпало со сбоем GitHub Actions (статус partial_outage).

## 6. Наблюдённые случаи

Код не менялся; сливать в обход обязательной проверки — решение пилота.

**10.11.2026, FMT #1518** (навык /find-method, запуск 42859590492; время UTC, в DP.FM.619 те же события указаны по +02:00). ## 7. Связанные документы

- DP.FM.451 — проверка с двумя исходами схлопывает «не смог проверить» в «всё в порядке». Здесь обратная сторона того же различения: квитанция схлопывает «не смог проверить» в «провал»; для выпуска это верно, а для диагностики нужен третий исход.
- VR.FM.043 (PACK-verification) — подтверждённое отсутствие объекта проверки зачтено как провал содержательной проверки: тот же тип смешения исходов.
- DP.FM.497 — проверки PR, открытого встроенным токеном, не запускаются: другая причина остановки обязательной проверки.
- DP.FM.571 — красный обязательный CI провоцирует правку в обход PR: чем грозит красная проверка, если причину не нашли.
