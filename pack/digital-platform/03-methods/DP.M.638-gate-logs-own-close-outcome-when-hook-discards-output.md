# DP.M.638 — Гейт, чей вывод отбрасывает хук, сам журналирует исход закрытия

## 1. Определение

Способ сделать наблюдаемыми исходы гейта, которого вызывают из хука, отбрасывающего вывод: гейт сам пишет в свой журнал причину каждого отказа и итог каждого закрытия, считая итог по одному снимку входа.

## 2. Проблема

Гейт намерений (WP-561 Ф33) объявляет намерение из точки фиксации файла (`note-file`), а она запускается из хука PostToolUse, который отбрасывает вывод. Комментарий в `scripts/session-guard.sh`: «note-file runs from a PostToolUse hook that discards its output, so stderr alone would never reach anyone». Поэтому срабатывания проверки и раньше писались в отдельный журнал (`.iwe-runtime/intent-gate-note-file.log`), но строка об отказе объявления не несла причины, а потерянные при закрытии намерения нигде не считались: их пришлось бы выводить задним числом.

## 3. Шаги метода

1. **Писать исход в свой журнал.** Если вызывающий хук отбрасывает вывод, гейт не полагается на stderr и пишет строку в свой файл журнала.
2. **Отказ объявления несёт причину.** Строка `declare_failed` получает последнюю строку stderr объявления, похожую на ошибку: префиксы `ERROR`, `ORIGIN_UNREACHABLE`, `LEDGER_UNREADABLE`, `INTERNAL_ERROR`, `Traceback`, `…Error:`. Нет такой строки → последняя непустая. Табуляции и управляющие символы заменяются пробелами, чтобы причина осталась одним полем; длина не больше 200 знаков. Пустой stderr → «no stderr»; не удалось создать временный файл → «stderr not captured (mktemp failed)».
3. **Одна строка итога на закрытие.** На каждое закрытие сессии, у которой записаны намерения, гейт пишет одну строку `close_resolve` со счётчиками `resolved`, `failed`, `skipped`. `skipped` означает «не пытались»: исчерпан общий бюджет закрытия (по умолчанию 30 с), нет скрипта гейта или номера РП. Обоснование в коде: «lapsed intents are counted where they happen instead of being inferred later».
4. **Итог и обход по одному снимку.** Файл намерений читается один раз, и по этому снимку считается и общее число, и обход. Объявление, которое ещё идёт, может дописать файл в это время; второе чтение учло бы такую запись как разрешённую, не учтя её в общем числе.
5. **Приёмка сквозным тестом на настоящем гейте.** Тест запускает настоящие `intent-gate.sh` и `ledger-append.sh` за `session-guard.sh` с агентами разных имён в одном РП: (K1) два агента фиксируют один файл, позднее объявление записано как конфликт; (K2) после обычного закрытия первой сессии фиксация её файла другим агентом не конфликт, а строка `close_resolve` показывает оба намерения разрешёнными; (K3) сессия, удалённая без закрытия, оставляет намерение открытым, и фиксация её файла другим агентом остаётся конфликтом; окно проверки: сегодня и вчера по UTC, намерение позавчерашнего дня уже не мешает.

## 4. Тест применения

«Куда попадает вывод этого гейта, когда он отказывает или когда что-то теряется при закрытии?» Если ответ «в stderr хука, который вывод отбрасывает», исход никто не увидит, и шаги 1–3 нужны.

## 5. Границы

- Гейт работает в режиме наблюдения и включается переменной `IWE_INTENT_GATE_NOTE_FILE=warn`; режима отказа нет, потому что точка фиксации срабатывает уже после записи файла. Разрешение намерений при закрытии выполняется всегда, когда намерения записаны, независимо от переменной: у закрывающего процесса может быть другое окружение.
- По ключу и правилам гейта не считаются конфликтом сессии разных РП на одном общем файле и две сессии агента с одним именем.
- Метод описывает наблюдаемость конкретного гейта (реализация свидетельства «лог отказов хука» из `DP.SC.204`), а не продолжение самого обещания.
- Один случай; ревью в две итерации (пир-сессия 2026-11-10-06-wp561-intent-gate-review).
