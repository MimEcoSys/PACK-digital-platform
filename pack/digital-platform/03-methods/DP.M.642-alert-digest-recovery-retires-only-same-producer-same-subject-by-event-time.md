# DP.M.642 — Восстановление снимает только свою тревогу и только по времени события

## Проблема

Сводка уведомлений показывает человеку, что ещё требует внимания, и для этого сопоставляет тревоги с сообщениями о восстановлении. Ошибки сопоставления дают противоположные отказы.

- **Восстановление снимает чужую тревогу.** Сообщение «всё в порядке» другого отправителя (пульс) принято за «всё починилось», или совпал общий заголовок до «:» у разных проблем. Открытая проблема исчезает из сводки.
- **Восстановление не находит свою тревогу.** Тревога о свежести копии (в двух старых формах текста) и сообщение о её восстановлении имеют разные заголовки до «:», и сопоставление по заголовку их не связывает. Решённая проблема продолжает висеть.
- **Порядок.** Сообщения приходят не в том порядке, в каком происходили события. Восстановление, событие которого было раньше новой тревоги, но которое пришло после неё, снимет новую тревогу.

## Метод

1. **Идентичность — пара «производитель + точный предмет».** Предмет извлекается из точных форм текста этого производителя (для свежести копии — хост и репозиторий; для публикации — вся причина целиком, включая двоеточия внутри неё). Формы других производителей не угадываются. Если предмет не извлечён, точного сопоставления нет.
2. **Восстановление снимает только тревогу с той же идентичностью.** Пульс другого отправителя для этого не годится.
3. **Порядок — по времени события, а не по времени поступления.** Восстановление, событие которого раньше события тревоги, тревогу не снимает. Если время есть только у одного из двух сообщений, восстановление ничего не снимает.
4. **Близость времён отправки ничего не доказывает.** Фраза «N пришли одной пачкой — это один случай» неверна: по времени отправки число разных проблем не определить (вывод разбора в пир-сессии, не правило кода).

## Как это реализовано в коде (на 20.11)

Скрипт сводки `scripts/lib/notify-digest-render.py`, origin/main DS-my-strategy:

- **Только два производителя.** Точный предмет и фильтр по времени (шаги 1–3) работают для iwe-verified-sync (`_freshness_subject`, коммит 0535e71d75) и для публикации изменений (`_publication_subject`, коммит b5a777ecb7). Для остальных производителей предмет — заголовок до «:» (`_subject`), и восстановление того же производителя с тем же заголовком снимает тревогу без сверки времени.
- **Приём наблюдения (`_accept_observation`).** Новое наблюдение о той же паре принимается, только если его событие не раньше прежнего. При равном времени тревога остаётся (восстановление отклоняется). Если время есть только у одной из двух записей, восстановление отклоняется; восстановление без времени принимается только тогда, когда времени нет у обеих.
- **Свёртка инцидента (`_fold_incident`, коммит 3a5a55cc32).** Инцидент считается восстановившимся, если есть датированное восстановление не раньше последней тревоги; при равном времени побеждает восстановление. Тревога без времени здесь не закрывается никогда.
- **«Снова заработало» у публикации** снимает тревоги того же производителя (по началу причины до «:»), событие которых не позже восстановления; при равном времени побеждает восстановление.

Правило ничьей, таким образом, в коде не единое: при приёме наблюдения ничья — в пользу тревоги, при свёртке инцидента и у «снова заработало» — в пользу восстановления.

## Тест применения

Ожидаемый результат задаётся заранее и независимо от кода сопоставления, для производителя с точным предметом:

- тревога и более позднее восстановление того же производителя о том же предмете → тревога снята;
- восстановление пришло после тревоги, но его событие раньше → тревога остаётся;
- восстановление без времени при датированной тревоге → тревога остаётся;
- зелёный пульс другого отправителя → тревога остаётся.

Случай равного времени проверяется отдельно для каждого места кода, потому что правило ничьей в них разное. В источнике ревью нашло дефект именно во временном фильтре (коммит 0535e71d75), поэтому проверку порядка нельзя считать очевидной.

## Границы

- **Граница с DP.M.453.** DP.M.453 отвечает на вопрос, какие сообщения считать повтором одного инцидента, чтобы подавить их в окне (ключ окна подавления повторов — класс инцидента, а не идентификатор запуска). Здесь вопрос другой: какое восстановление какую тревогу снимает и в каком порядке. Идентичность для сопоставления — пара «производитель + точный предмет», без статуса. Это не ключ окна из DP.M.453: в её первоисточнике в ключ включён статус, которым тревога и восстановление одного инцидента как раз различаются. Общее у двух карточек — производитель в составе ключа (третий прецедент DP.M.453); метод добавляет сопоставление «тревога — восстановление» и порядок по времени события.
- Нужно время события, а не только время отправки. Без него безопасный исход при приёме наблюдения один: тревога остаётся открытой.
- Метод описывает сторону потребителя (сводку). Чтобы было что сопоставлять, производитель должен посылать восстановление (DP.M.420, DP.M.516).
- «Снято в сводке» не значит «причина устранена» (DP.D.325).
- Решение из карточки РП-568 Ф14 «смена ключа идентичности не закрывает старые записи: автоматическое закрытие недопустимо, выпуск нового ключа ждёт проверки перехода старой записи» — решение, в коде сводки не реализовано.
- Единичный прецедент одного скрипта сводки. Работа на живом сервере для этого правила не проверялась (РП-568 Ф14: живые исходы восьми уведомлений о таймауте не установлены; семидневная приёмка открыта).

## Связи

- DP.M.453 — ключ окна подавления повторов; граница — выше.
- DP.M.420, DP.M.516 — сторона производителя: явное сообщение о восстановлении и маркер «разрешено источником».
- DP.D.325 — «восстановлено» ≠ причина устранена.
- DP.M.422 — упоминает построчную защиту от записи не по порядку как исходное условие; сама карточка о другом.
