# DP.METHOD.124 — Stateless windowed recompute: идемпотентная агрегация без состояния между запусками

## Описание

Паттерн для агрегаторов-воркеров: каждый запуск целиком пересчитывает нужные данные через SQL с оконными фильтрами по времени. Нет курсора, нет журнала применённых событий, нет накопления в памяти между запусками. Идемпотентность обеспечивает `ON CONFLICT DO NOTHING`.

## IPO

**Input:** таблица событий с временными метками; целевая таблица агрегатов

**Process:**
1. SQL-запрос с `WHERE timestamp BETWEEN window_start AND window_end`
2. «Последнее событие» получить через `ORDER BY timestamp DESC, id DESC LIMIT 1` (без гонки между пакетами)
3. Вставить в таблицу агрегатов: `INSERT ... ON CONFLICT DO NOTHING`
4. Повторный запуск: тот же запрос, тот же диапазон — конфликт, no-op, без дубликатов

**Output:** агрегаты в целевой таблице; идемпотентный при повторных запусках

## Граница окна

Окно пересчёта — полуоткрытый интервал `[window_start, window_end)`: `timestamp >= window_start AND timestamp < window_end`. Шаг 1 IPO с `BETWEEN` читать именно так: `BETWEEN` в SQL включает обе границы, и событие с меткой ровно на границе попадает в два соседних окна — учитывается в агрегатах обоих, то есть считается дважды. Полуоткрытое окно даёт ровно одно попадание для любого события: событие на границе открывает следующее окно и не входит в предыдущее.

Прецедент вне SQL: окно «вчера» для сбора коммитов при закрытии дня в шаблоне — `[YESTERDAY, TODAY)`; коммит точно на границе суток открывает новый день, ни один коммит не считается дважды; решение покрыто регрессионным тестом (FMT-exocortex-template PR #1207, issue #924, WP-7 Ф223). Захват: `DS-my-strategy/inbox/captures/2026-10.md:2986` (отчёт `2026-10-13-inbox-check.md`, кандидат #2).

## Пример

WP-463 Ф1: `stage_evaluator.py` — весь расчёт одним SQL с оконными фильтрами, `ON CONFLICT DO NOTHING`. Успешно работает в проде. Аналог выбран для нового сборщика WP-463 вместо накопления в памяти + курсора.

## Условия применения

- Агрегация не order-sensitive (или ORDER BY явно задан в SQL)
- Таблица событий не удаляет записи (append-only или с TTL > окна пересчёта)
- Объём таблицы событий не превышает порог, при котором полный scan дороже инкрементального

## Трейдоф и условие выхода

Стоимость прогона растёт с объёмом всей таблицы, а не только новых событий. При превышении порога (задокументировать в комментарии воркера):
- Переход на паттерн с курсором (checkpoint last processed id)
- Или отдельный журнал применённых событий

## Антипаттерн

Накопление агрегатов в памяти между запусками + flush в конце — теряет прогресс при краше воркера; не является идемпотентным.
