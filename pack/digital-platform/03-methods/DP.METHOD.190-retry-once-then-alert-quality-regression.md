# DP.METHOD.190 — Retry-once-then-alert

## Определение

Стратегия порога алертинга для систем с **немедленным эффектом плохого вывода на пользователя**: алертить после **одного retry**, а не после накопления N последовательных сбоев.

## IPO

- **Вход:** система с retry-механизмом; каждый плохой результат достигает пользователя немедленно (нет буфера)
- **Процесс:** при первом красном вердикте — retry; если после retry снова красный → алерт немедленно
- **Выход:** минимальная задержка между первой деградацией качества и уведомлением

## Условия применения

Retry-once-then-alert предпочтительнее «accumulate N failures → alert» если выполнены оба условия:
1. **(а) Немедленный user impact:** каждый плохой вывод доставляется пользователю без задержки (нельзя «подождать следующую попытку»)
2. **(б) Retry устраняет transient:** retry убирает случайные сбои, поэтому оставшийся красный вердикт после retry = структурная регрессия, не случайность

## Ступенчатая калибровка (best practice)

1. Развернуть наблюдаемость без защиты (ФК1: метрики, логи)
2. Собрать 1-2 периода реальных данных о частоте срабатывания
3. Калибровать порог защиты (ФК2: retry + guard) на основе собранных данных

Нельзя откалибровать порог ФК2 до получения реальных данных из ФК1.

WP-149 ФК1 (2026-07-10): порог был «2-й consecutive red-day». Пилот изменил до 1-го красного после retry: при персональном руководстве 2 ночи с плохим выводом = 2 дня деградации без реакции. Ступенчатая модель ФК1→ФК2 подтверждена как best practice.

## Дополнение 2026-11-11: второй подряд отказ при допустимой задержке

**Область.** При сбое обновления данных вред может возникать не немедленно, а только после потери их пригодности. Владелец может разрешить тревогу на втором подряд неудачном запуске по тому же объекту, если цена задержки явно принята и остальные критичные последствия сбоя не требуют немедленного сообщения. Класс ошибки сам по себе не устанавливает эту цену: отказ авторизации может требовать более раннего сообщения независимо от свежести данных.

**Проверка запаса.** На момент первого отказа определить остаточный запас пригодности данных `R`: сколько времени осталось до момента, после которого их использовать нельзя. Оценить верхнюю границу `D` времени до завершения следующего запуска и отправки тревоги при его отказе — с учётом расписания, длительности попытки, повторов и канала уведомления. Если обещано сообщить до истечения пригодности, требуется `D < R` с выбранным запасом на неопределённость. При недоказанной границе задержки или недостаточном запасе ожидание следующего запуска этим способом не обосновано.

Неравенство «наибольший интервал между запусками меньше полного TTL» недостаточно: к первому отказу часть TTL уже могла истечь. Сравнивать надо будущую задержку с остатком, а не с полной продолжительностью.

**Порядок.** Счётчик последовательных отказов ведётся отдельно по объектам. Успешное обновление сбрасывает серию молча; второй подряд отказ вызывает тревогу с наблюдаемой причиной. Независимая проверка пригодности данных продолжает запрещать работу с недопустимо старыми данными: подавление сообщения о первом отказе не должно отключать эту проверку. Успех между отказами прекращает непрерывную серию; окно «N отказов за T» описывает другую политику и не заменяет её без отдельного решения.

**Граница с основным методом.** При немедленном вреде пользователю или ином критичном последствии, не покрытом запасом свежести, действует основной порядок «один повтор → тревога». Наличие проверки свежести не доказывает, что все виды вреда исключены. Повтор внутри запуска и ожидание следующего запуска — разные задержки; обе учитываются в выбранной политике.

**Прецедент и предел вывода.** В разборе 05.11 по РП-545 Ф28 пилот выбрал второй подряд отказ для четырёх классов отказа получения обновлений, включая авторизацию. Основание в записи сессии: следующий запуск не позже примерно 3 часов при шестичасовом TTL; разовые отказы ранее проходили к следующему запуску. Кими сохранял возражение о задержке сообщения при реальной потере доступа; пилот выбрал ожидание второго отказа. Это локальный выбор владельца, а не доказательство универсальной оптимальности порога или временного характера ошибок авторизации. Фактические таймеры и доставка тревог при подготовке этого дополнения заново не проверялись.
