# DP.METHOD.242 — параметризация governance-репо

## Суть метода

Скрипты, обращающиеся к персональному governance-репозиторию пилота (например, `DS-my-strategy`), принимают его путь как обязательный явный параметр (аргумент CLI или переменную окружения), а не содержат путь захардкоженным внутри логики.

При переносе личного инструмента в общий шаблон у параметра не должно быть персонального значения по умолчанию. Отсутствие параметра означает явный отказ с понятной диагностикой: молчаливый fallback на репозиторий автора делает конфигурацию формально параметризованной, но фактически сохраняет хардкод.

## Обоснование

Хардкод пути привязывает скрипт к одной конкретной установке — при переносе на другую машину/другого пользователя с иным именем или расположением governance-репо скрипт перестаёт работать без правки исходного кода. Параметр делает скрипт переносимым по конструкции.

Персональный default скрывает отсутствие конфигурации: у автора всё работает, а у получателя шаблон обращается к несуществующему или, хуже, чужому репозиторию. Обязательность параметра переносит ошибку к границе запуска и не позволяет личному контексту автора стать неявной частью поставки.

## Применение

Любой платформенный скрипт, обращающийся к персональному репозиторию конкретного пилота, если скрипт предполагается использовать не только автором.

## Проверка

«Запустится ли общий шаблон без явного указания governance-репозитория за счёт имени или пути из установки автора?» Да — параметризация неполна. Корректный контракт требует явное значение и отказывает до обращения к git, если его нет.
