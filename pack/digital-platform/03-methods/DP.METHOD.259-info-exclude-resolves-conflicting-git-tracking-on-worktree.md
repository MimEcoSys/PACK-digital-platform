# DP.METHOD.259 — info/exclude на конкретном worktree разводит конфликтующие ожидания git-tracking одного пути

## Описание

Два механизма платформы предъявляют противоположные требования к git-tracking одного и того же файла: канонический процесс коммитит служебную RUN-карточку (`inbox/agent/tasks/RUN-*.md`) как часть обычной истории, а `relocate-card` (`process-runner.py cmd_relocate_card`) отказывается переносить tracked source, чтобы сохранить чистой git-историю одноразовой isolate-ветки. Оба ожидания корректны в своём контексте, но не могут одновременно выполняться для одного пути в одном и том же git-дереве.

## Метод

Вместо изменения инварианта любой из сторон путь исключается из индекса КОНКРЕТНОГО worktree через `info/exclude` (per-base-dir, не глобальный `.gitignore`) сразу после `git worktree add`, до того как файл может быть создан в этом дереве. Это разводит оба инварианта без изменения кода ни одного из компонентов: в основном дереве файл остаётся tracked и коммитится как обычно, в isolate-worktree он невидим для git с момента создания дерева.

**Критичное требование к размещению:** проверка/запись в `info/exclude` обязана выполняться на ветке ПЕРВОГО создания worktree, а не на ветке повторного входа (resume) — иначе при восстановлении живого worktree после частичного сбоя close его может снести операция восстановления (`--force` или аналог), которая не проходит через тот же путь инициализации. Эту ошибку размещения нашёл cold-review.

## Применение

К любой ситуации, где два компонента платформы предъявляют противоположные ожидания к git-tracking одного пути в контексте git worktree (один коммитит, другой требует untracked). Переносимо на любой другой конфликт «канон коммитит X» vs «одноразовая копия не должна коммитить X» — `info/exclude` на стороне одноразовой копии, без изменения канона.
