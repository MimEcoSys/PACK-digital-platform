# DP.FM.233 — Форма записи append-only журнала изменена без подъёма schema_version

## Паттерн

При изменении структуры записи append-only журнала (добавлено, убрано или переименовано поле) разработчик не поднимает `schema_version`. Под одним номером версии сосуществуют два разных формата → парсер-потребитель не может надёжно разобрать запись.

## Механизм ошибки

Append-only журнал содержит записи вида `{"schema_version": 1, "field_a": ..., "field_b": ...}`. После рефакторинга добавляется поле `field_c`, но `schema_version` остаётся 1. Парсер видит смесь старых (без `field_c`) и новых записей (с `field_c`) под одним номером версии — не может различить форматы без дополнительной эвристики.

При отсутствии `field_c` в старой записи потребитель получает: `KeyError` или silent fallback с неверным поведением. Дефект незаметен при добавлении поля, если у нового поля есть default: старые записи «работают», но контракт версионирования нарушен.

## Условия возникновения

- Append-only журнал с полем `schema_version`
- Изменение структуры записи (добавление / удаление / переименование поля)
- `schema_version` не обновлён одновременно с изменением структуры

## Симптом

Парсер-потребитель: `KeyError`, или невозможность различить формат без дополнительной эвристики. Возможен silent failure (неверное поведение без exception) при наличии default-значений.

## Fix

При любом изменении структуры записи журнала — **одновременно** поднять `schema_version`. Дешёвая страховка, ловится на code review при любой правке формата записи.

```python
# Было: schema_version 1, поле source отсутствует
{"schema_version": 1, "timestamp": "...", "verdict": "...", "input": "..."}

# Стало: добавлено поле source → schema_version обязан стать 2
{"schema_version": 2, "timestamp": "...", "verdict": "...", "input": "...", "source": "..."}
```

## Тест обнаружения

«Изменена форма записи журнала (добавлено / убрано / переименовано поле) — поднята ли `schema_version`?» Нет → DP.FM.233. Применять при code review любой правки формата записи журнала.

## Грань

Отличие от DP.FM.166 (schema-consumer contract breach): DP.FM.166 — убрать поле из `required`-set JSON Schema без обновления потребителя (ошибка одного контракта). DP.FM.233 — изменить форму записи без подъёма версии схемы: нарушен контракт версионирования, под одним номером сосуществуют разные форматы.

## Применимость

Любой append-only журнал решений, событий, gate-decisions, trace-log — где поле `schema_version` используется как контракт с парсером-потребителем.

## Вариант B: детектор дрейфа, который сравнивает только версию

Тот же забытый бамп в другом месте. Контракт (состав проверок §1 и его читатели) версионировался константой; проверка дрейфа сравнивала только номер версии. После добавления нового читателя версию не подняли (правило кода требует бампа при изменении состава §1), и проверка перестала отличать синхронизированное состояние от отставшего. Здесь версия не ломает потребителя данных: забытый бамп отключает сам детектор, и он одинаково молчит и при актуальном, и при отставшем предмете проверки.

Факт: в `manifest.json` уже был `sha256`, но детектор сравнивал только версию. Исправление в источнике — сам бамп версии; детектор по-прежнему зависит от ручной дисциплины.

Предложение (не проверено, исходной реализацией не подтверждено): ключ детектора выводить из содержимого (хэш состава), либо дать детектору самотест, при котором изменение состава без бампа обязано его покрасить (`DP.METHOD.128`). Критерий приёмки такого исправления: синтетическое изменение состава §1 без подъёма версии → детектор красный.

Дополнение к тесту обнаружения: «детектор дрейфа сравнивает только значение, которое обновляется вручную (версия, дата)? Есть ли самотест на забытый бамп?»
