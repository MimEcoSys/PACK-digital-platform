# DP.FM.335 — Install/update скрипт безусловно перезаписывает конфиг пользователя

## Симптом

Пользователь добавил кастомизацию в конфигурационный файл (security-хуки, правила, расширения). После очередного `update.sh` / `repair.sh` кастомизация пропала без предупреждения и без ошибки.

## Механизм

```bash
# Антипаттерн: безусловная перезапись
cp default_settings.json .claude/settings.json

# Фикс: seed-if-absent
[[ -f .claude/settings.json ]] || cp default_settings.json .claude/settings.json
```

Скрипт не проверяет, существует ли файл уже. Команда «overwrite» стирает любые изменения пользователя с момента установки.

## Отличие от DP.FM.115

| Аспект | DP.FM.115 | DP.FM.335 |
|--------|-----------|-----------|
| Субъект | Peer-агент (runtime) | Install/update скрипт (deployment) |
| Контекст | Shared-файл при параллельной работе | Конфигурационный файл при обновлении |
| Симптом | Потеря контента при записи | Потеря кастомизаций при update |

## Фикс

Три стратегии, в порядке предпочтения:
1. **seed-if-absent**: скрипт пишет файл ТОЛЬКО если он отсутствует
2. **merge**: скрипт делает merge платформенных defaults + пользовательских значений
3. **backup-and-replace**: скрипт сохраняет старый файл перед заменой и сообщает о конфликте

## Третья стратегия на практике: структурный merge по списку пользовательских ключей (launchd plist)

Эволюция решения в `roles/strategist/install.sh` (launchd-plist стратега, обновляется `update.sh`): сначала — безусловная перезапись при каждом обновлении (правка расписания молча терялась, ровно этот FM). Затем — «backup + warn» вместо «skip-if-diverged»: пропуск навсегда заморозил бы апстрим-фиксы plist у ЛЮБОГО пользователя, хоть раз поправившего файл по несвязанной причине (решение пир-сессии с Codex, 2026-09-09). «Backup + warn» всё равно оказался неполным фиксом — issue #981: бэкап сохранял СЛЕД правки, но не её ДЕЙСТВИЕ, и обновление возвращало ежедневный запуск поверх Weekday-ограничения пользователя.

Рабочее решение — третья стратегия из списка выше («merge»), конкретно: `merge-launchd-schedule.py` (plistlib, только stdlib) переносит из УСТАНОВЛЕННОЙ копии только ключи расписания (`StartCalendarInterval`, `RunAtLoad`); путь, окружение и метки берутся из ШАБЛОНА, поэтому апстрим-фиксы доезжают. Если пользователь убрал ключ намеренно (выключил автозапуск) — ключ не подставляется обратно: **отсутствие ключа в установленной копии — тоже пользовательское решение, не пробел для заполнения**. Бэкап остаётся страховкой на случай сбоя самого СЛИЯНИЯ (ставится шаблон + предупреждение в stderr), а не основным механизмом сохранения правки.

Критерий выбора между тремя стратегиями: «skip-if-diverged» годится только когда дивергенция РЕДКА и диагностируема вручную; merge по явному списку ключей — когда множество «что пользователю разрешено менять» заранее известно и невелико (как расписание в plist); backup-and-replace без доработки до merge решает только «не потерять историю», не «сохранить эффект».

## Четвёртый случай: охват и копия как предусловие замены (защитные файлы)

Добавлено 2026-10-30 (source: captures/2026-10.md; коммит `ebff72ad` в FMT-exocortex-template-index, WP-529 Ф246; тест `setup/test-update-modified-hook.sh`).

Правка пользователя в `.claude/hooks/*` терялась при обновлении шаблона бесследно: копия перед заменой сохранялась только для `.claude/rules/*`, предупреждения не было. Это пробел охвата того же класса, что DP.FM.394 (сквозная забота реализована не во всех путях). Для защитных файлов, которые обязаны быть актуальными, чтобы установка оставалась защищённой, «оставить версию пользователя» не годится (установка молча останется без защиты), а «затереть» теряет правку без следа. Рабочий порядок:

1. Сравнить рабочую копию с ПРЕЖНЕЙ версией шаблона. Совпала: правок пользователя нет, обновить молча. Отличается: правка есть.
2. Перед заменой сохранить копию правки вне обновляемого дерева (`.backups/hooks-pre-update/<время>-<pid>/`, с сохранением атрибутов) и вывести предупреждение у файла.
3. Копию сохранить не удалось: файл не трогать и сказать об этом. Потеря правки хуже, чем устаревший хук с предупреждением.
4. В конце обновления вывести общую сводку замен (и в пути «обновлено», и в пути «всё актуально») и указать, куда переносить свои изменения (`extensions/`).

Основание: код и тест в коммите; полевого сбоя за пределами обнаружения при проверке не наблюдалось. Смежно: DP.M.563 (снимок файла до перезаписи как база диффа): тот же приём «копия до перезаписи», другая цель.

## Тест

«Есть ли у пользователя право расширять этот конфиг-файл?» Да → команда `cp` / `echo >` без проверки = FM. Seed-if-absent или merge = фикс.

«Пользователь жалуется "пропало правило", а в diff его нет» → вероятно DP.FM.335.
