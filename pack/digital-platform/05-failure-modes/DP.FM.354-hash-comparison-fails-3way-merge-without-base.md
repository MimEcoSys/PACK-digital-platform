# DP.FM.354 — Сравнение хэшей без базового хэша не работает для 3-way-merge

## Паттерн

Скрипт обновления (`update.sh`) сравнивает хэш живого локального файла напрямую с хэшем чистого апстрима, чтобы решить, изменял ли пользователь файл. Для файлов, требующих трёхстороннего слияния (3-way-merge: база, локальные изменения, апстрим-изменения), такое прямое сравнение структурно никогда не сходится — оно не может отличить «пользователь изменил файл» от «апстрим изменил файл с прошлого обновления».

## Механизм

1. Скрипт хранит только хэш текущего апстрима, не хэш базовой версии (на момент последней синхронизации)
2. При сравнении: `hash(local) != hash(upstream_current)` — истинно почти всегда, даже если пользователь ничего не менял, просто апстрим успел обновиться
3. Без базового хэша невозможно различить три случая: «не менялось», «менял пользователь», «менял апстрим»

## Почему опасен

- Ложные срабатывания «пользователь изменил файл» на файлах, которые пользователь не трогал — апстрим просто ушёл вперёд
- Или наоборот: пропуск реальных пользовательских изменений, если сравнение устроено слишком грубо

## Лечение

1. Для файлов, требующих 3-way-merge — хранить хэш базовой версии (снимок на момент последней успешной синхронизации)
2. Сравнивать три хэша: base, local, upstream — только тогда можно корректно решить, что произошло
3. Прямое двустороннее сравнение (local vs upstream) допустимо только для файлов без ожидаемого дрейфа апстрима между синхронизациями

## Дополнение 2026-11-02: несколько машин публикуют в одну общую копию

**Случай (WP-7 Ф286, FMT-exocortex-template#1422).** Каждая машина отправляла файлы памяти в общий репозиторий, и последняя отправка молча затирала правки другой машины («последний пишет»). Исправление — трёхсторонняя сверка при отправке, со своими особенностями для нескольких писателей:

1. **База своя у каждой машины:** версия файла, которую *эта* машина отправила в прошлый раз (берётся из последнего отправленного ею коммита). Общая «последняя синхронизация» не годится: другая машина могла отправить после неё.
2. **Решение по трём версиям:** серверная = базе → отправлять свою; своя = базе → взять серверную; обе отличаются от базы → файл не отправлять, пометить как спорный и показывать при открытии и закрытии дня, пока его не сведут вручную и не подтвердят (`accept <файл>`). Пометка снимается и сама, если взять серверную версию.
3. **Серверную версию сравнивать по объекту в репозитории (git-блоб), а не по файлу на диске.** Файл на диске проходит через преобразование переводов строк (Windows), и без изменений по содержанию даёт ложное «отличается».
4. **Цена.** Файл, который постоянно правят на обеих машинах (оглавление), будет помечаться до каждого сведения. Это плата за то, что раньше правки в нём терялись молча.

Что делать, когда базы ещё нет (первая отправка после выкладки механизма), — отдельный отказ: `DP.FM.722`.
