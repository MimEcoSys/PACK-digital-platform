# DP.FM.384: Canonical repo path breaks under worktree isolation

## Симптом

Gate/verifier-скрипт конвейера закрытия сессии (например, шаг `commit-push` раннера через `confirmed_clean_repos`, или `session-guard.sh close`) резолвит состояние git-репозитория через захардкоженный «канонический» путь (`$IWE_ROOT/<repo>`, `~/IWE/DS-my-strategy`) вместо места фактического запуска. В среде с несколькими параллельными агентами, где git worktree — штатный механизм изоляции конкурентной записи, каноническая копия в этот момент может быть занята другой активной сессией на нестандартной ветке без upstream.

## Корневая причина

Инструмент читает git-состояние ЧУЖОЙ ветки/копии и молча интерпретирует его как своё собственное. Он не различает «моя работа не отправлена» и «кто-то другой сейчас работает в другом месте того же репозитория» — оба случая дают одинаковый симптом (`ahead=notrack`, незакоммиченные изменения), поэтому gate ложно блокирует закрытие сессии, не отражающее реальное состояние текущего worktree.

## Антипаттерн → Паттерн

- **Антипаттерн:** резолвить репозиторий как захардкоженный «домашний» корень (`$IWE_ROOT/<repo>`, `~/IWE/...`), общий для всех вызовов независимо от места запуска.
- **Паттерн:** резолвить репозиторий относительно места своего запуска (`git rev-parse --show-toplevel`) или принимать путь явным параметром — не подставлять захардкоженный «канонический» корень.

## Тест обнаружения

Один и тот же класс бага пойман 4 раза за один день в двух независимых точках входа (commit-push.sh и session-guard.sh close), оба раза через один и тот же корень причины. Проверка: запустить gate из non-canonical worktree, пока каноническая копия репозитория занята другой веткой без upstream — если gate репортит состояние канонической копии вместо состояния своего worktree, паттерн подтверждён.

## Манифестация записи: скрипт изменяет другую рабочую копию

Тот же неверный выбор корня опасен при записи: инструмент, вызванный из отдельной рабочей копии, вычисляет путь от общего канонического каталога, изменяет его и сообщает об успехе. В копии, которую вызывающий собирается публиковать, нужной правки при этом нет.

Исторический баг-репорт DS-my-strategy `da3860a14` описывает такой вызов `wp-inbox.sh mark` 04.11.2026. На момент отчёта исправление самого скрипта не было заявлено. Текущий статус исправления этой карточкой не устанавливается; наличие параметра --repo в нынешнем интерфейсе само по себе не доказывает, какой адрес выбирает любой конкретный вызов.

Пишущий инструмент явно выбирает целевой репозиторий по предусмотренному контрактом параметру или рабочей копии вызова и проверяет допустимость записи до изменения. Сообщение об успехе относится именно к выбранной цели. Проверка команд на внешнем уровне может не видеть вычисляемый внутри скрипта адрес; защита в самом инструменте полезна, но не является единственным возможным способом — доступ также может ограничивать песочница среды исполнения.

Критерий проверки: безопасный прогон на заготовках должен показать изменение только выбранной копии и явный отказ при запрете записи в цель. Новый прогон здесь не выполнялся. Смежное различение — DP.D.307 (путь для мутации и путь для диагностики).
