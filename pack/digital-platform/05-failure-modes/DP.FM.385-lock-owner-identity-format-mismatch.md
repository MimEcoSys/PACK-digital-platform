# DP.FM.385: Lock ownership check compares mismatched identity formats

## Симптом

Механизм блокировки отклонил собственный только что взятый лок как «чужой»: `AGENT_ID` в момент проверки принимал дефолтное значение `claude-code` (без суффикса конкретной сессии), тогда как владелец лока был записан полным `harness_session_id`. Сравнение двух разных по детализации форматов идентичности одного и того же агента дало ложное «не мой» — самоблокировка при отсутствии реального конфликта.

## Корневая причина

Writer лока (тот, кто его захватывает) и checker (тот, кто проверяет «свой/чужой») используют разные представления идентичности одного и того же держателя — полный session id vs короткий дефолтный agent id. Формально оба описывают одного держателя, но как строки не совпадают, поэтому checker считает лок чужим.

## Антипаттерн → Паттерн

- **Антипаттерн:** writer лока пишет владельца в одном формате идентификатора (полный `harness_session_id`), checker сравнивает с другим, более коротким или дефолтным форматом (`AGENT_ID`) — без нормализации к общему представлению.
- **Паттерн:** writer и checker одного lock-механизма обязаны использовать единый канонический формат идентичности держателя; если источник идентичности может быть не установлен — явно проверять его наличие, а не молча подставлять дефолт.

## Тест обнаружения

Взять лок под своей сессией и сразу проверить его тем же checker'ом в той же сессии. Если результат «чужой» — checker и writer используют разные форматы идентичности одного держателя.

## Дополнение 2026-09-21 (РП-170)

**Второе проявление: собственный ID агента (Codex) против session ID Claude, который отслеживает guard.** Идентификатор сеанса Codex и номер сессии session-guard — разные сущности. При открытии сессии guard сохранял только переменную Claude, поэтому проверка закрытия сравнивала родной идентификатор Codex с номером guard и отклоняла собственную опубликованную работу как «чужую». Как и в первом проявлении, writer и checker используют разные представления идентичности одного держателя. Отличие в механизме: там расходятся форматы внутри одного канала (полный session id против дефолтного agent id), здесь канал идентичности при открытии заполняется не для всех рантаймов одинаково.
- Общий класс: система, различающая «своё/чужое» по identity-каналу, заполняемому не для всех участников одинаково, ошибочно отклоняет легитимных участников, чей канал не был заполнен при открытии.
- Парный дефект того же семейства — `DP.FM.488` (владение путём ≠ владение репозиторием при нескольких checkout одного git-репо). Починка канала идентичности не чинит разбиение по пути: дефекты независимы, но правило проектирования одно — сравнивать владельца по канонической идентичности сущности (сессия, репозиторий), а не по представлению (формат идентификатора, буквальный путь).
- Смежно: `DP.FM.217` (PID временной оболочки как прокси жизни — ошибка выбора идентифицирующего сигнала).

## Дополнение 2026-09-27 (WP-484/WP-589)

Финальная форма фикса того же дефекта: `marker_matches = harness == marker_session_id if harness else guard == marker_session_id` — терминальная квитанция сверяется с сессией текущего исполнителя (harness) как основным каналом, а при его отсутствии — с guard (тем же каналом, что описан в дополнении 21.09). Отдельно закреплено по итогам этого коммита: append-only записи (заявки на коммиты, heartbeats) исключены из проверки уникальности identity-канала — по конструкции реестра у них может быть несколько легитимных записей одного держателя; скалярные же поля идентичности (текущий владелец, статус) остаются fail-closed и не получают того же послабления. Пир-сессии проверяются по терминальным квитанциям тем же механизмом, что и основной исполнитель — не отдельным путём.
