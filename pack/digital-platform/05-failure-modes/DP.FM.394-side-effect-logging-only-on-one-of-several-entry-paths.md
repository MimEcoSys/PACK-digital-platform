# DP.FM.394 — Сквозной побочный эффект реализован только в одном из нескольких входных путей операции

## Паттерн

У операции (закрытие сессии) два легитимных входа: через оркестратор и напрямую (защитный скрипт закрытия). Запись события в общий дневной журнал реализована только в оркестраторском пути. Прямое закрытие технически корректно — семафор снят, коммит ушёл на remote — но невидимо для всего, что читает журнал: подсчёты, дашборды, приёмочные проверки. Потери работы нет; есть слепая зона в наблюдаемости и заниженная метрика.

Структурный класс: **N входных путей в одну операцию, сквозная забота (логирование, повтор, подавление, гейт) реализована в одном из них.** Уже зафиксированные инстансы: `DP.FM.137` (подавление алертов), `DP.FM.142` (повтор), `DP.FM.151` (гейт подписки). Этот — инстанс для журналирования/наблюдаемости.

## Механизм

1. Сквозная забота (запись события) добавляется в тот путь, который был первым или основным на момент реализации
2. Позже появляется второй вход в ту же операцию (прямой вызов, ручной запуск, другой инициатор) — он копирует существенные шаги операции (семафор, коммит), но не побочный эффект, потому что он воспринимается как принадлежность оркестратора, а не операции
3. Потребители журнала (метрики, дашборды, приёмочные проверки) не знают, что у операции есть путь, не оставляющий следа — считают отсутствие события отсутствием операции

## Почему опасен

- Ошибка тихая и «доброкачественная»: ничего не ломается, ничего не теряется — только цифры врут. Обнаруживается лишь при сверке двух источников истины (журнал ↔ фактические коммиты/семафоры), что мало кто делает регулярно.
- Разъезд накапливается: каждый прямой вызов — минус одно событие; метрика систематически занижена, а не случайно.
- Приёмка проверяет «операция выполнилась» (семафор, коммит) — и проходит; побочный эффект не входит в определение «выполнилась».

## Лечение

1. Побочный эффект принадлежит операции, не вызывающему: вынести запись события в общую функцию/шаг операции, которую проходят все входы (ср. `DP.M.159` — единая точка входа; `DP.FM.137` — единая точка эмиссии алерта).
2. Аудит входов при добавлении сквозной заботы: «сколько мест могут инициировать эту операцию?» — каждый должен проходить через тот же побочный эффект (ср. тест `DP.FM.137`).
3. Приёмочный критерий операции включает побочный эффект: «после закрытия по любому пути событие есть в журнале».

## Тест обнаружения

«Перечислите все способы вызвать операцию. Для каждого: оставляет ли он тот же след (событие, повтор, подавление, гейт), что и основной путь?» Хотя бы один «нет» → слепая зона. Практическая сверка: число событий в журнале за период должно совпадать с числом фактических завершений по независимому источнику (семафоры, коммиты); систематическая недостача = путь без побочного эффекта.

## Второй прецедент: ветка возобновления закрытия не пишет `session_closed`

Тот же класс, другой вход: двухшаговое закрытие сессии (`PREPARED`, затем ручной `--abandon-prepared`) имело ветку возобновления, которая пропускала `FORCED_CARD`. Из-за этого события `session_closed_direct` и `session_closed` не писались вовсе. Ветка возобновления копировала существенные шаги операции, но не сквозной побочный эффект (запись события).

Исправление (commit `7af3da5` в iwe-local-config, WP-561 Ч1): ветка возобновления заново читает `close_path` из семафора, записанного на первом шаге, и проходит тот же побочный эффект, что и обычный путь. Тест обнаружения тот же: «для каждого способа вызвать операцию, включая возобновление, оставляет ли он то же событие в журнале?»

Источник: кандидат 10/01.2#3 (`2026-10-01-inbox-check-2.md`).

## Третий прецедент: путь peer-session, событие ищется по `slug`, а пишется с `session_file`

Другая форма асимметрии: у одного логического события («сессия закрыта») несколько путей завершения, и они расходятся по ключу корреляции. Путь закрытия peer-session не пишет в журнал дня событие `session_closed`; его пишет только раннер Quick Close, и с полем `session_file`, без `slug`. Шаг приёмки 4.5.4 скилла peer-conversation ищет событие по `slug`. Для пути peer-session приёмка структурно не находит совпадения: не ошибка, а слепое пятно, которое выглядит как «событие ещё не наступило».

Проверка: «все ли пути завершения пишут одно и то же событие с одним набором полей корреляции (включая факт присутствия поля, а не только его значение), и по какому полю ищет потребитель?»

Источник: git commit `d8415c8b0` в DS-my-strategy (WP-561, запись «Что узнали»); кандидат 10/01.3#2 (`2026-10-01-inbox-check-3.md`).
