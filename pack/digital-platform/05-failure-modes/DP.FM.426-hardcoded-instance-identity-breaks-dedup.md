# DP.FM.426 — Захардкоженная строка вместо machine id ломает дедупликацию при втором инстансе

## Симптом
Расширение публиковало метку десктоп-инстанса в общий dashboard API как захардкоженную строку `'mac'`, независимо от физической машины. Пока существовал ровно один десктопный инстанс, ничего не ломалось. Как только открылись два инстанса одновременно (реальный Mac и Linux-хост через Remote-SSH), оба стали неразличимы для панели, а клиентская логика дедупликации (`excludePublishedSelfCopy`), сравнивавшая с той же фиксированной строкой, скрыла присутствие одной машины за другой.

## Механизм
Решение молчаливо предполагало «объект такого рода всегда один» и закодировало это как литеральную константу вместо выведенного идентификатора. Пока предположение верно — код работает; как только оно нарушается, поломка проявляется не как ошибка (exception, лог), а как тихое исчезновение одного из двух объектов за дедупликацией другого.

## Фикс
Стабильный per-machine id выводится из `os.hostname()` и протягивается через локальную метку, публикуемые site_id/session id и саму логику дедупликации. Серверная сторона уже трактовала site_id как непрозрачную строку — серверных изменений не потребовалось.

## Тест обнаружения
«Идентификатор инстанса/сессии/машины в коде — захардкоженная строка-метка или выведен из чего-то, что реально идентифицирует источник (hostname, PID+start-time, UUID)?» Строка-метка → работает только пока «объектов такого рода» действительно один; искать точку, где может появиться второй одновременный экземпляр, и явно проверить там дедупликацию/идентификацию.

## Применимость
Любая общая панель/дашборд/алерт/лог, публикующая ИЛИ упоминающая идентичность источника (агент, сессия, устройство, воркер, хост) под захардкоженной меткой вместо выведенного идентификатора — включая случаи, где «единственность» исторически верна, но не гарантирована архитектурой.

## Второй прецедент (другая подсистема: текст алерта, не дедупликация)

`tsekh1-git-sync.sh` хардкодил «Сервер tsekh-1» в тексте алерта, хотя скрипт по дизайну вызывается как шаг конвергенции с ЛЮБОГО хоста после каждой публикации журнала (`ledger-publish.sh:1154`), а не только через systemd-таймер сервера. Пилот неделями получал настоящие (не ложные), но неверно подписанные алерты про собственный Мак, принимая их за проблему на сервере. Фикс — подставлять реальный hostname вместо фиксированной метки. Тот же абстрактный паттерн, что в «Механизме» этой карточки (захардкоженная identity-строка вместо выведенного идентификатора), но здесь ломается не дедупликация объектов, а АТРИБУЦИЯ алерта источнику.
