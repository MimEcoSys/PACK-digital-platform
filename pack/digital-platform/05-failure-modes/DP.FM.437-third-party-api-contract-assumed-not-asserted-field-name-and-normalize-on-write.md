# DP.FM.437: Предположение о форме стороннего контракта без ассерта на границе записи

## Симптом

Скрипт провижининга правил уведомлений впервые запущен против боевого инстанса стороннего сервиса (Grafana Cloud). Два предположения о формате API, на которых был написан скрипт, оказались неверны сразу:

1. **Имя и форма поля.** Условия матчинга ожидались в поле `object_matchers` (массив троек); реальное поле — `matchers` (массив строк вида `label"op"value`).
2. **Нормализация значений при записи.** Строка длительности ожидалась «как записана»; сервер нормализует её при сохранении (`"24h"` → `"1d"`). Сравнение прочитанного назад значения с исходной строкой ложно показывает расхождение (drift) — либо, в другой конфигурации сравнения, ложно скрывает его.

Проверка `assert_matcher_schema` обнаружила первое неверное предположение — имя и форму поля — при живом вызове и остановила некорректную запись. Второе предположение касалось нормализации длительности сервером; его устранили канонизацией сравниваемых значений. Исходный коммит отдельно сообщает, что записанные данные проверены прямым GET и корректны. Он не подтверждает, что проверка схемы обнаружила обе ошибки до записи.

## Причина

Форма контракта стороннего API была выведена из документации/примера/памяти и закодирована как факт, без канала, который проверил бы её против живого сервера ДО записи. Для чужого API это норма, не исключение: имя поля меняется между версиями, а сервер имеет право переписывать значения в каноническую форму — оба свойства невидимы, пока не сделан боевой запрос.

## Антипаттерн → Паттерн

- **Антипаттерн:** записывать в сторонний API структуру, форма которой предположена; сравнивать read-back с исходной строкой, полагая, что сервер хранит значение дословно.
- **Паттерн:** (1) явный ассерт формы на границе записи — имена и типы полей проверяются против фактического ответа сервера (GET существующего объекта или dry-run), любое расхождение останавливает запись с понятной ошибкой; (2) для полей, которые сервер может нормализовать (длительности, регистр, порядок ключей, единицы), сравнение «желаемое vs фактическое» ведётся на канонизированных формах обеих сторон, а не на сырых строках (см. DP.FM.438 о том, как эта канонизация сама может тихо отказать).

## Переносимый принцип

Предположение о форме чужого контракта нужно не только задокументировать, но и защитить исполняемой проверкой в той точке, где оно впервые встречается с реальностью — на границе записи. Тогда неверное предположение стоит одного пойманного прогона, а не порчи боевых данных и ручного разбора. Отдельно: у стороннего хранилища нужно спрашивать не «что я записал», а «что ты сохранил» — и сравнивать канонизированно.

## Тест обнаружения

«Скрипт пишет в сторонний API структуру, имена/типы полей которой не сверены с живым ответом этого же API, или сравнивает read-back с исходной строкой без канонизации?» Да → первое боевое исполнение и есть тест формы; без ассерта на границе записи цена этого теста — прод-данные.

## Применимость

Провижининг/синхронизация конфигурации во внешний сервис (алерты, дашборды, правила маршрутизации, DNS, IAM), idempotent-скрипты «desired state → apply», любые drift-детекторы против стороннего API.

## Отличие от смежного

- **DP.FM.043 (CASE по enum без SELECT DISTINCT):** тот же принцип «проверь фактические данные, не предполагай», но субстрат — своя БД и чтение; здесь — чужой API и запись, где защита — ассерт на границе записи, а не предварительная выборка.
- **DP.FM.399 (nullable boolean стороннего API), DP.FM.273 (тихая пагинация GitHub):** тот же класс «предположение о стороннем контракте», другие механизмы (семантика значения, полнота списка); здесь — имя/форма поля и нормализация при записи.
- **DP.M.196 (UPSERT runtime-verify двойной дельтой):** post-write проверка, что запись реально исполнилась; здесь — pre-write проверка формы, чтобы неверная запись не исполнилась вообще.
- **DP.FM.438 (непроверенный код возврата канонизатора):** тот же коммит и скрипт — там отказывает уже сама канонизация, введённая как лечение механизма 2 отсюда.
