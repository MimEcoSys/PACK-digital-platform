# DP.FM.440 — Fail-safe гейт закрытия верно отказывает легитимному пути, для которого не спроектирован путь восстановления

## Симптом

В один день — два независимых отказа гейта закрытия сессии. Оба технически корректны (fail-safe отработал по своей логике), оба блокируют легитимное завершение и не предлагают безопасного выхода:

1. **Поле не записано при open для одного из путей вызова.** Семафор сессии, открытой через путь `peer-session`, не получил полей `governance_worktree` / `isolated_worktree` / `orz_sessions_dir`. Проверка на close (`semaphore_governance_worktree()`) справедливо отказывает: у неё нет данных. Корень не в проверке — `open` для этого конкретного пути вызова не пишет то, что `close` требует.
2. **Патч-эквивалентный контент не распознаётся строгой проверкой.** Сессия опубликовалась двумя ручными cherry-pick из изолированного worktree (оба прямых push были отклонены разошедшимся `origin/main`). Строгая проверка «HEAD — предок» для роли «sessions checkout» не признаёт патч-эквивалентный контент (тот же результат, другой SHA), хотя соседняя проверка claimed-commit для note-commit в том же инструменте это уже умеет. Единственная операция, которая свела бы дерево к распознаваемому виду (`git reset --hard`), справедливо блокируется guard'ом деструктивных операций. Два корректных guard'а — ни одного разрешённого хода.

## Причина

Гейт спроектирован как fail-safe: отказывает всему, что не совпадает с известной «хорошей» формой. Полнота множества «хороших» форм требованием не была. Легитимные пути к состоянию «на самом деле всё готово к закрытию» появляются после гейта — новый путь вызова, задокументированная ручная процедура восстановления после конфликта — и в распознаваемые случаи не добавляются. Каждый такой путь при первом же прохождении упирается в корректный отказ.

Механизмы (оба — инстансы уже записанных классов):
- (a) сторона производителя: один из режимов/путей открытия создаёт семафор без полного набора полей, нужных потребителю (класс DP.FM.264; семейство «сквозная забота реализована в одном из N входных путей» DP.FM.394/151/142/137);
- (b) понятие эквивалентности в одной проверке строже, чем в соседней проверке того же инструмента: SHA-предок вместо патч-эквивалентности (принцип DP.M.414 / DP.M.439 / DP.M.430; частичный апгрейд одного из соседних чеков — DP.FM.347 на уровне проверок).

Новое относительно инстансов — динамика: корректный отказ воспринимается как «не баг» («fail-safe, not a bug in that function»), поэтому дефект покрытия не чинится на стороне гейта, а решается ad-hoc — обходом, ручным reset (который блокирует другой guard) или зависшей сессией.

## Антипаттерн → Паттерн

- **Антипаттерн:** считать корректный отказ fail-safe гейта концом разбора; разрешать каждый такой случай вручную (обход, ручной reset, «закрою в другой раз»).
- **Паттерн:**
  1. Контракт гейта — две половины: никогда не пропускать нелегитимное **и** распознавать каждый легитимный путь к готовности. Корректный отказ легитимному случаю — дефект покрытия гейта, а не ошибка пользователя.
  2. Чинить на стороне производителя (open пишет требуемые поля для **каждого** пути вызова; тест — матрица «путь вызова × поля, требуемые close») или в понятии эквивалентности проверки (patch-id / `git cherry` / сравнение содержимого — как у соседней проверки), никогда — обходом гейта.
  3. Каждый новый легитимный путь (новый режим вызова, задокументированная ручная процедура восстановления) поставляется вместе с изменением гейта, который его распознаёт.
  4. Если два guard'а в композиции не оставляют разрешённого хода — спроектировать путь восстановления (например, распознаваемую гейтом операцию сверки состояния), а не ослаблять один из guard'ов.

## Переносимый принцип

Fail-safe гейт, который верно отказывает, — не то же самое, что гейт с полным покрытием легитимных путей. Полнота не возникает сама: её нужно поддерживать при каждом добавлении пути к готовности. Иначе гейт систематически копит блокировки легитимных, но нестандартных путей, и каждая из них превращается либо в обход, либо в зависшую работу.

## Тест обнаружения

«Гейт отказал; отказ по его логике верен; при этом состояние по существу готово (контент на origin, работа сохранена, семафор реален)?» Да → дефект покрытия гейта. Дополнительно: «Существует ли операция, которой можно привести состояние к распознаваемому гейтом виду, не нарушая другой guard?» Нет → композиция guard'ов без пути восстановления; проектировать путь, не отключать guard. Признак накопления: один и тот же гейт отказывает по разным «правильным» причинам чаще одного раза в день.

## Применимость

Любой гейт закрытия/финализации с несколькими путями вызова и строгими проверками идентичности в многоагентной git-среде: session-guard, day-close, гейты публикации, защита веток. Не применяется к отказам по действительно нелегитимному состоянию — там гейт прав по обеим половинам контракта.

## Отличие от смежного

- **DP.FM.416** (режим-исключение проходит там, где обычный режим отказывает) — зеркало: там альтернативный вход обходит проверку (ложный проход, опасно), здесь альтернативный путь блокируется (ложный отказ, копится). Тот же тест «перечислить все режимы вызова», противоположное направление вреда.
- **DP.FM.424** (новое ограничение ломает штатный конвейер) — гейт введён после путей; здесь пути появляются после гейта. Две стороны одной дисциплины «покрытие гейта × пути».
- **DP.FM.264** (housekeeping-семафор без slug) — механизм (a) — новый инстанс этого класса, другой потребитель; карточка не заявляет его заново.
- **DP.M.414 / DP.M.439 / DP.M.430** — механизм (b): патч-эквивалентность вместо SHA уже записана; здесь новое лишь то, что одна проверка инструмента обновлена, а соседняя — нет.
- **DP.FM.272, DP.FM.384** — ранние инстансы ложной блокировки закрытия (mtime; канонический путь) с узкими критериями; эта карточка называет общую динамику и требование пути восстановления.
- **DP.M.218** (close-check + open-autofix) — дополняет: здесь дефект на стороне open для конкретного пути.
- **AS.FM.064** (окно «последние N коммитов» даёт ложное «коммит отсутствует») — смежная ложная тревога верификатора в мультиагентном репо; лечение то же по духу (прямой поиск по SHA/содержимому).
- **DP.FM.450** (плановый гейт отказывает на канонической копии, которая структурно никогда не чистая) — другая ось той же дисциплины «покрытие гейта × пути»: здесь легитимный путь не распознан; там путь распознан верно, но precondition проверяется в точке, где он структурно невыполним по конструкции, а не отсутствует в списке случаев.

## Дополнение 2026-09-21 (РП-170)

С этим дополнением механизмов три: (a), (b), (c).

**Часть 1. Механизм (c) — гейт владения без ветки «легитимно вне git».** Хук трассировки области действия (scope-tracking) регистрирует любой тронутый Edit/Write путь как claim, требующий владельца из известного набора git-репозиториев. Личный файл auto-memory агента существует, но не лежит ни в одном git-репо; гейт не знает категории «путь легитимно вне периметра владения» и отказывает close с `owners=0`. Отказ честный по факту и неверный по содержанию: файл не бесхозный, он вне модели «владение = git-репозиторий». Это третий механизм к (a) и (b): гейт устроен как закрытый список, и категория легитимных путей в нём не предусмотрена.
- Рецидивирующий класс, не единичный случай: повторяется для любой сессии, трогавшей auto-memory (WP-484, находка 3).
- Fix сознательно отложен (консенсус с Kimi) как отдельная сессия: ветка «легитимно вне git» без отдельного проектирования рискует замаскировать следующий класс дыры.
- Тест: «Гейт требует владельца из закрытого списка для каждого тронутого пути — и отказывает, если путь легитимно вне списка по архитектуре?» Смежно: `AS.FM.040` (пробел гейта не помечен как его ограничение).

**Часть 2. Симптом 2 повторился: 4-е независимое обнаружение за 9 дней.** Ложный отказ проверки «HEAD — предок» после cherry-pick — частный случай общего класса: критерий «моя работа опубликована» строится на identity общего чекаута (SHA/ancestry), а не на content-эквивалентности (patch-id). Любой путь публикации, меняющий SHA при сохранении содержимого (cherry-pick, isolate, rebase), делает такую проверку несостоятельной навсегда для этого коммита. Цепочка (пир-сессия 2026-09-17, Claude+Kimi, 5 ходов до консенсуса):
- Усилитель: каждый инцидент закрывается точечной fail-closed проверкой без автоматического пути восстановления; выход — ручной пилот или костыль.
- Мультипликатор: порядка 16 параллельных сессий в день на одном общем чекауте сужают окно гонки «взять HEAD → опубликовать»; столкновения частые, не редкие.
- Следствие: деградировавшее общее состояние оказывается ничьим; правило «нашёл чужую проблему — доложи, не чини» верно в одной сессии, но блокирует всех до ручного вмешательства пилота.
- Конвергенция двух независимых сессий одного дня (утро и вечер 17.09) стала основанием повысить приоритет архитектурного фикса: перевести критерий «опубликовано» с identity на patch-id системно, а не точечным патчем на каждый новый случай. Живой инстанс того же корня: bug-файл `bug-2026-09-17-close-prepared-state-frozen-against-incrementally-republished-own-commits.md` (commit fde59d54a). Смежно: `AS.FM.093` (тот же трек WP-484, другой механизм; общий корень — общий чекаут без учёта параллельных писателей).

## Дополнение 2026-10-30 (РП-170): проверка допускает не те места, где код ищет доказательство

Ещё один инстанс класса (a) «сквозная забота реализована в одном из N путей» (смежно: DP.FM.260). Проверка чистоты закрываемой копии искала карточку-доказательство владения в двух местах, а карточка лежала в третьем, каноническом общем хранилище, которое код уже безусловно использует для поиска и верификации. Список «где ищем» и список «что принимаем» разошлись, и проверка ложно отказала на чистом дереве; сессия зависла. Исправление (коммит `8f37956` в iwe-local-config, сессия 2026-10-29-02-fix-close-check-cross-repo; тест из 3 сценариев): путь берётся из тех же переменных, что использует поиск; комментарий о том, что резервная ветка теперь покрывает только «вне всех известных мест»; защита от пустого или некорректного нового пути. Расширение не открывает обход: карточка к этому моменту уже прошла проверку владельца, типа файла, числа жёстких ссылок и соответствия сессии.

Тест: «Перечень мест у проверки и перечень мест у поиска заданы одним источником?» Нет → разойдутся при следующем добавлении места.
