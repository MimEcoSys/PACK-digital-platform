# DP.FM.451 — Health-check с бинарным исходом схлопывает «не смог проверить» в «всё в порядке»

## Тезис и механизм ошибки

Проверка отставания от origin (`check_repo_drift`) была добавлена как независимый от Telegram канал наблюдения за тем же фактом. Её первая версия сама повторила класс дефекта, который должна была страховать: функция выполняла `git fetch` и сравнивала с origin, возвращая «ok» и тогда, когда расхождения нет, и тогда, когда `fetch` не удался из-за отсутствия сети. Оба случая давали на выходе один и тот же положительный статус — отсутствие сети физически не позволяет узнать реальное состояние, но проверка отвечала так, будто состояние известно и благополучно.

## Диагностический принцип

У любой защитной проверки, дающей внешнему наблюдателю один статус, минимум три содержательных исхода: «ок» (проверено, проблемы нет), «проблема» (проверено, проблема есть), «не смог проверить» (сама проверка не выполнилась). Третий исход не должен схлопываться в первый — сбой инструмента проверки (нет сети, нет доступа, таймаут) не есть доказательство благополучия объекта проверки.

## Границы

Различение не требует отдельного явного three-valued API у каждой проверки без исключения — там, где сама проверка не имеет внешних зависимостей в пути выполнения (не может физически «не выполниться» независимо от объекта), двузначный статус безопасен. Правило применимо именно там, где проверка зависит от внешнего ресурса (сеть, файл, процесс), который может быть недоступен независимо от состояния объекта проверки.

Наличие третьего статуса само по себе не спасает: если batch-конвейер, агрегирующий десятки однотипных проверок, кладёт любой ненулевой код проверки в нейтральную корзину «пропущено» (SKIPPED) без тревоги, сводка `skipped=N, проблем 0, алертов 0` читается наблюдателем как «всё чисто» — тот же коллапс «не смог проверить» → «ок», перенесённый с одной проверки на итог батча. «Пропущено» допустимо только для детерминированно известного «нечего проверять»; «проверка не выполнилась» обязана иметь собственный счётчик и порог тревоги. Тот же коллапс проходит и через путь данных, не только через статус: `OUT=$(check) || OUT=""` превращает ненулевой код в пустую строку, которую следующий шаг читает как `0` («дрейфа нет»).

## Проверка

Тест-сценарий «офлайн» (отключённая сеть/недоступный внешний ресурс) обязателен в smoke-наборе любой защитной проверки. «Пропустить fetch/запрос через проверку, эмулируя недоступность сети — возвращает ли она нейтральный „не смог проверить“, отличимый от „ok“?» Нет → воспроизведён DP.FM.451.

Для batch-агрегаторов: «Подать на вход конвейера проверку, заведомо завершающуюся ненулевым кодом (нет сети, сломанный путь). Появляется ли она в сводке отдельным счётчиком/событием «не проверено» с тревогой — или растворяется в `skipped` либо в пустом выводе, прочитанном как ноль?» Второе → воспроизведён DP.FM.451 на уровне агрегации. Особенно критично для ночных прогонов без человека: именно там ложное «всё в порядке» никто не перепроверит до утра.
