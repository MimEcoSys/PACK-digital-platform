# DP.FM.460 — `trap RETURN` в bash не ограничена функцией, в которой поставлена

## Тезис и механизм ошибки

Функция ставила `trap ... RETURN`, ссылаясь на свои локальные переменные, в расчёте, что ловушка сработает один раз при выходе именно из неё. В bash `trap RETURN` не имеет такой границы — он остаётся активным глобально и срабатывает на возврате из ЛЮБОЙ последующей функции, включая те, что выполняются намного позже в другом вызове хука. В штатном сценарии без активной репетиции это привело к падению «unbound variable», когда тот же хук позже сорсил не связанный с этой функцией файл, и оставленная ловушка сработала повторно, ссылаясь на уже недоступные локальные переменные исходной функции.

## Диагностический принцип

`trap ... RETURN`, поставленный внутри функции bash, — не «функциональная» ловушка с автоматической границей действия, а глобальная ловушка с отложенным и неожиданным местом срабатывания, если её явно не снять. Предположение «ловушка сработает и исчезнет при выходе из моей функции» неверно для bash и требует явной очистки.

## Границы

Различение специфично для bash (в других шеллах поведение `trap RETURN` может отличаться) и касается именно `RETURN`-ловушек, ссылающихся на локальные переменные или состояние конкретной функции. Глобальные ловушки, спроектированные как глобальные с самого начала, вне scope этой находки.

## Проверка

«Функция ставит `trap ... RETURN`, и обработчик не снимает себя сам?» Да → воспроизведён DP.FM.460: ловушка переживёт функцию и сработает повторно при возврате вызывающей функции или по завершении файла, позже подключённого через `source`. Фикс — обработчик снимает себя сам: `trap '…; trap - RETURN' RETURN` (см. дополнение 2026-11-10). Тест — вызов изнутри другой функции под `set -u`. (Раздел и `summary` исправлены 2026-11-10: прежняя формулировка «срабатывает на возврате из любой последующей функции» шире наблюдаемого, а фикс «снимать trap перед собственным `return`» молча отменяет очистку.)

## Дополнение 2026-11-10 (РП-170, отчёт 2026-11-09-inbox-check-8, кандидат 1): где ловушка срабатывает повторно и как её снимать

Второй случай — публикатор DS-my-strategy (коммит `c86a70a7a1`, функция `content_equivalent_to_head`, сессия 2026-11-04). RETURN-ловушка убирала временную копию. После возврата из функции она срабатывала повторно при возврате вызывающей функции и обращалась к уже недоступным переменным; под `set -u` публикация аварийно завершалась. Дефект нашёлся при живом прогоне правки, а не на ревью.

**Где срабатывает оставленная ловушка** (воспроизведено в bash 3.2.57 и 5.3.15 при разборе 2026-11-09 и повторно в bash 5.2.37 при записи 2026-11-10):

| Что происходит после возврата функции | Повторное срабатывание |
|---|---|
| Возвращается вызывающая функция | да; под `set -u` — аварийный выход |
| Завершается файл, позже подключённый через `.` / `source` | да (исходный случай этой карточки) |
| Возвращается обычная функция, вызванная позже | нет: на время вызова функции bash снимает RETURN-ловушку и потом восстанавливает |

Поэтому прежняя формулировка «на возврате из любой последующей функции» (раздел «Тезис и механизм ошибки») шире наблюдаемого. Опция `set -T` (`functrace`) меняет наследование ловушки функциями; этот режим не проверялся.

**Исправление.** Если снять ловушку (`trap - RETURN`) перед собственным `return`, аварии не будет, но очистка на этом выходе молча не выполнится: ловушка уже снята. Надёжная форма — обработчик снимает себя сам и покрывает все выходы из функции:

```bash
trap 'rm -rf -- "$tmpdir"; trap - RETURN' RETURN
```

Другой вариант — явная очистка без RETURN-ловушки.

**Тест.** Вызывать функцию изнутри другой функции под `set -u` или подключать после неё файл через `source`:

```bash
set -u
f() { local tmp=/tmp/x; trap 'echo "cleanup $tmp"' RETURN; }
g() { f; }
g   # tmp: unbound variable — ловушка сработала повторно при возврате g
```

Вызов с верхнего уровня скрипта с последующими вызовами других функций дефект не показывает: такой тест проходит ложно.
