# DP.FM.461 — Молчаливый fallback маскирует всегда-ломаный primary path

## Тезис и механизм ошибки

Промпт (`day-plan.md` шаг 0) искал вспомогательный скрипт `day-open-scaffold.sh` по устаревшему пути (`$IWE_WORKSPACE/scripts/` вместо реального `$IWE_SCRIPTS`); путь никогда не совпадал с реальным расположением, поэтому код всегда уходил в заранее подготовленный fallback (минимальный DayPlan с PENDING-маркерами вместо полного скелета). Fallback работал достаточно правдоподобно, чтобы ошибку резолюции пути никто не замечал — деградированный, но не падающий режим неотличим от штатного без явного WARN на каждом входе. Верификация этого фикса вскрыла рядом ВТОРОЙ такой же баг — сам скрипт-скелет тоже искал свой конфиг (`day-rhythm-config.yaml`) по несуществующему пути.

## Диагностический принцип

Fallback-ветка, которая «прилично» отрабатывает без явной ошибки, — плохой сигнал для обнаружения поломки primary path; она откладывает обнаружение неограниченно долго, если не логировать вход в неё отдельно. Чем правдоподобнее деградированный режим, тем дольше живёт постоянно ломаный primary path незамеченным — правдоподобность fallback'а работает против обнаружения, а не за него.

## Границы

Различение применимо к fallback-веткам, чей результат достаточно похож на штатный, чтобы не вызывать подозрений (минимальный/усечённый, но не пустой и не ошибочный вывод). Fallback, дающий явно неполноценный или помеченный как деградированный результат, не подвержен этому классу маскировки.

Дополнение: при ужесточении политики проверять, что основной путь поддерживает новый режим; иначе запасной путь становится основным, а «зелёный» итог маскирует поломку. Пример: доля закрытий сессий через запасной peer-session путь (растущая доля = штатный путь снова сломан).

## Проверка

«Вход в fallback-ветку логируется отдельным явным сигналом (WARN/метрика) при каждом срабатывании, отличимым от штатного успеха primary path?» Нет → воспроизведён DP.FM.461: постоянная поломка primary path может оставаться незамеченной сколь угодно долго.
