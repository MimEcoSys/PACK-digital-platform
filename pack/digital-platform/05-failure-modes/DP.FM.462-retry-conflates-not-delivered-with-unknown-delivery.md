# DP.FM.462 — Retry совмещает «точно не дошло» с «неизвестно, дошло ли»: повтор дублирует побочный эффект

## Тезис и механизм ошибки

Retry-цикл вокруг HTTP-клиента срабатывает на любой ненулевой код клиента (или на любой «класс сетевых ошибок») как на один класс «retryable». В этот класс попадают два принципиально разных исхода:

- **запрос точно не дошёл** — ошибка резолва DNS, отказ соединения (curl exit 6/7): сервер ничего не получил, повтор безопасен;
- **неизвестно, дошёл ли** — таймаут ожидания ответа, обрыв после отправки тела (curl exit 28): сервер мог уже принять и обработать запрос, повтор — классический at-least-once дубль.

Прецедент: `telegram_send()` в общей библиотеке `scripts/lib/telegram.sh` (DS-my-strategy) — «retries up to 3 times on any curl network error, without distinguishing exit 6/7 … from exit 28». Под нагрузкой 7+ параллельных сессий (медленные ответы Telegram API) пилот получил три идентичных сообщения «Осиротевшая сессия» подряд.

Для неидемпотентного побочного эффекта (отправить сообщение, создать запись, списать средства) правильность повтора определяется не «была ли ошибка», а «мог ли сервер уже выполнить действие». Схлопывание двух исходов в один флаг лишает код информации, от которой зависит безопасность повтора. Ошибка проявляется только под нагрузкой (таймауты редки при свободном API), поэтому месяцами выглядит как «надёжный ретрай», а затем — как дубли у живого получателя.

## Диагностический принцип

Исход классифицируется ДО решения о повторе на три класса:

- **(а) «точно не дошло»** (DNS/connect/refused) → повтор безопасен;
- **(б) «неизвестно»** (таймаут ответа, обрыв после отправки) → повтор только при идемпотентном запросе (ключ дедупа на стороне получателя или свой idempotency-лог — DP.M.086, DP.M.412), иначе — без повтора, с отдельной строкой лога и счётчиком;
- **(в) «дошло и отвергнуто»** (HTTP 4xx/5xx) → по политике HTTP-кодов (DP.FM.425).

Антипаттерн: `for attempt in 1 2 3; do curl … && break; done` — повтор на любом ненулевом коде клиента; политика «сколько раз повторять» зашита в общую библиотеку одинаково для всех вызывающих.

## Границы

Симметричный анти-фикс — отключить ретрай целиком — теряет безопасные повторы на DNS/connect, которые как раз и лечат кратковременные сетевые сбои. Минимальный первый шаг, принятый в источнике: различить (б) от (а) и логировать отдельно, не меняя политику повтора до появления телеметрии по частоте таймаутов — решение об асимметрии риска «дубль vs потеря» принадлежит вызывающему, а не общей библиотеке (см. DP.FM.463).

## Проверка

«Retry-цикл вокруг HTTP-клиента срабатывает на любой ненулевой код клиента / любой "network error" без различения "до сервера не дошло" и "ответ не получен"? Запрос неидемпотентен (send/create/pay) и у получателя нет ключа дедупа?» Оба «да» → воспроизведён DP.FM.462: под нагрузкой повтор на таймауте ответа создаст дубль побочного эффекта. Проверка: эмулировать exit 28 (ответ, задержанный дольше `--max-time`) — ожидаемое поведение: отдельная строка лога «доставка неизвестна», без слепого повтора.

## Второй прецедент: «неизвестно» прочитано как «объекта нет» — запасной путь «создать заново» (WP-568 Ф11, 2026-11-02)

Тот же класс (б), другое направление ошибки. Счётчик центра уведомлений правит закреплённое сообщение (`editMessageText`). При **любой** ошибке правки он создавал сообщение заново. 01.11 в 23:58 сетевой сбой (HTTP 000, ответа нет) породил новое сообщение со звуком ночью, хотя старое сообщение существовало.

Здесь неопределённый исход не повторён, а истолкован как доказательство отсутствия объекта. Запасной путь при этом разрушительный или шумный: новый объект, звук, потерянная привязка к старому.

Правило: разрушительный или шумный запасной путь включается **только по ответу, доказывающему причину**.

- (в) Явный отказ API о том, что объекта нет (у Telegram — 400 «message to edit not found») → создать заново.
- (б) Таймаут, 5xx, нет ответа → «неизвестно»: состояние не менять, повторить правку на следующем такте.
- Пересоздание по возможности без звука (`disable_notification=true`), чтобы даже верное срабатывание не будило получателя.

Проверка: «Какой код ошибки включает запасной путь? Доказывает ли он причину, ради которой путь существует?» Если запасной путь включается на любой ненулевой исход, воспроизведён DP.FM.462 во втором направлении.
