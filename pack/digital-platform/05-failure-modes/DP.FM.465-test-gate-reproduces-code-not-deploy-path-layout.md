# DP.FM.465 — Тестовый гейт воспроизводит код, но не структуру путей деплоя

## Тезис и механизм ошибки

Раскладка каталогов в git и раскладка на исполняющей машине — разные артефакты, если между ними стоит шаг деплоя. Прод собирал `.claude/lib/` из хранимого в git `claude-lib/` (без точки) во время Nix-деплоя, поэтому на проде разрыва не было вообще: скрипты находили библиотеку по ожидаемому пути. Тестовый гейт запускал те же ~15 скриптов **прямо из чекаута**, где каталог с точкой ещё не существует, — то есть проверял код в раскладке, которой в момент исполнения никогда не бывает.

Отказ поэтому не «иногда флаки», а детерминированный: он срабатывал на любом изменении любого из зависящих скриптов, независимо от содержания изменения. Это делает симптом обманчивым — гейт выглядит как реагирующий на правку, хотя реагирует на само её наличие.

## Диагностический принцип

Тестовое окружение обязано воспроизводить **целевую структуру путей**, а не только содержимое файлов. Если между git и исполнением есть шаг деплоя, переименовывающий или перекладывающий каталоги, то «код тот же» не означает «прогон эквивалентен». Признак: гейт падает на 100% попыток по классу файлов, а ручной запуск того же скрипта на целевой машине проходит.

## Границы

Лечение временными симлинками на время прогона (`setup_test_env` / `cleanup_test_env`) корректно только с двумя защитами: (1) явный ABORT при коллизии с уже существующим каталогом — иначе прогон затрёт настоящее состояние; (2) явный вызов cleanup **перед** `git add`, не только через exit-трап, — иначе симлинки успевают попасть в коммит. Альтернатива (выполнять шаг деплоя перед тестами) сильнее по точности, но дороже; карточка не утверждает предпочтительность одной из них.

## Проверка

«Совпадает ли раскладка каталогов, в которой гейт запускает скрипт, с раскладкой, в которой он исполняется на целевой машине?» Прямой тест: взять путь, который скрипт резолвит при старте (source/import общей библиотеки), и проверить его существование в чекауте без шага деплоя. Не существует → воспроизведён DP.FM.465. Дополнительно: отказ гейта, повторяющийся 100% раз по целому классу файлов, а не по содержанию правки, — сам по себе указывает на дефект окружения, а не на дефект правки.

## Триггер 2: песочница теста без замыкания зависимостей

Добавлено 2026-10-30 (source: captures/2026-10.md, сессия 2026-10-28; extraction report 2026-10-30-inbox-check.md, кандидат #4).

Тот же класс («тестовое окружение не воспроизводит то, в чём код исполняется»), другой субстрат: не раскладка каталогов деплоя, а фикстура самого теста. Смоук-тест `session-guard-peer-obligation-clear-smoke.sh` копировал во временную песочницу только `close_obligation.py`. Тот импортирует соседние модули (`close_expect`, `lib.ledger_path`) и лениво `session_local_release`, поэтому тест детерминированно падал с `ModuleNotFoundError`. По сообщению коммита, тестовый гейт автосинхронизации прочитал красный тест как дефект кода и исключил `session-guard.sh` из доставки на сервер, так что исправления не доезжали, хотя код был исправен.

Исправление (commit `e9771d0`, iwe-local-config, WP-484): песочница копирует все соседние `.py` и `lib/`, включая модули с ленивыми импортами.

Добавка к паттерну карточки:
1. Песочница теста строится по замыканию зависимостей исполняемого файла, а не по одному файлу. Ленивые импорты входят в замыкание: статический просмотр шапки их не видит (ср. «целевая структура путей» выше).
2. Предложение (не реализовано в этом коммите): гейт, исключающий файл из доставки, сообщает об исключении отдельным сигналом: имя файла, упавший тест, класс ошибки; для `ModuleNotFoundError` / `ImportError` — пометка «вероятно, дефект окружения теста». Исключение без отдельного сигнала превращает поломку тестовой обвязки в бессрочную заморозку доставки (наличие такого сигнала в гейте при извлечении не проверялось).

Тест обнаружения: «Импортирует ли тестируемый скрипт что-то вне файла, который тест копирует в песочницу?» Прямая проверка — запустить тест на заведомо исправной версии файла: падение с ошибкой импорта означает дефект песочницы, а не кода.

Смежные: DP.FM.466 (неверный субстрат — грязное дерево), DP.FM.505 (радиус отмены одного провала).

## Триггер 3: подмена HOME прячет пакеты pip --user

Добавлено 2026-10-30 (source: captures/2026-10.md, коммит `61a6f9f98` в DS-my-strategy, WP-530).

Тот же класс, третий субстрат: окружение процесса. Смоук публикации (`ds-publish-smoke.sh`) подменяет `HOME` на временный каталог, чтобы паспорта попыток не засоряли реестр оператора. Пакеты, поставленные через `pip --user` (например PyYAML), живут под настоящим `HOME`. После подмены каждый шаг публикации с импортом такого пакета падал по причине, не связанной с проверяемым кодом (утверждение «все шаги с PyYAML падали» взято из комментария в коде, прогон не воспроизводился).

Исправление: до подмены `HOME` взять `python3 -c 'import site; print(site.getusersitepackages())'` и добавить результат в `PYTHONPATH`. Тот же приём уже стоит ещё в трёх скриптах репозитория.

Добавка к паттерну: подмена `HOME` (или любой переменной, от которой зависит поиск зависимостей) входит в то, что песочница обязана воспроизвести. Признак: тест красный на исправном коде, ошибка импорта, а не нарушение утверждения. Смежно: VR.FM.010 (обратное направление: среда протекает в фикстуру).
