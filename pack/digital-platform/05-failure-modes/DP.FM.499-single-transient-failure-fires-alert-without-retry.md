# DP.FM.499 — Одиночный транзитный сбой без ретрая поднимает тревогу

**Симптом.** Транзитные обрывы SSH/GitHub-соединения (самоустраняющиеся уже на следующей попытке) поднимали OnFailure-тревогу в Telegram на каждый одиночный неудачный прогон refs-sync-broker — команда получала алерт на шум, а не на реальный устойчивый отказ.

**Правило.** Один повтор операции перед объявлением сбоя такта; тревога — только за отказ, переживший повтор, не за первую неудачу.

**Чем отличается от соседних карточек.**
- `DP.M.045` уже приводит «retry 1×, при fail → alert» как пример оси «Режим исключения» для SC автопроцесса — но как иллюстрацию шаблона, без обоснования и без конкретного инцидента. Эта карточка — подтверждённый случай, где дефолт НЕ был применён, с конкретным триггером (транзитный SSH/GitHub drop).
- `DP.METHOD.190` — тот же механизм «retry-once-then-alert», откалиброван для регрессии качества LLM-вывода с немедленным user impact; здесь — операционный алертинг связности, другой субстрат и другое обоснование порога.
- `DP.M.420` — дедуп повторных алертов внутри уже открытого длящегося инцидента (state-file, окно). Эта карточка — про порог до первого алерта, до того как инцидент подтверждён.
- `DP.FM.137` — асимметрия suppression между несколькими alert-путями; здесь один путь, вопрос в пороге retry.
