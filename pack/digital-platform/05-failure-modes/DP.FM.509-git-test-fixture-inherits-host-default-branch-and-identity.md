# DP.FM.509 — Тестовая git-фикстура наследует конфигурацию хоста

## Тезис и механизм ошибки

Smoke-тест проверки ancestry создавал «origin» командой `git init -q --bare "$ORIGIN"` без `-b`. HEAD bare-репозитория при этом указывает на то, во что на данной машине разрешается `init.defaultBranch`. На машине автора это `main` и тест зелёный. На GitHub-раннере `ubuntu-latest` дефолт `master`: HEAD bare-репозитория ссылался на ветку, которую тест не создавал, и каждый последующий `git clone` из этого origin падал с «remote HEAD refers to nonexistent ref». Отказ детерминированный на любом хосте с другим дефолтом, это не флак.

## Диагностический принцип

Фикстура, создающая git-объекты (репозиторий, коммит, ветку) без явного задания параметров, которые git берёт из конфигурации, переносит в тест скрытую зависимость от gitconfig хоста: глобального, системного или встроенного дефолта версии git. Один и тот же скрипт детерминирован на машине автора и по-другому детерминирован на чужой. Зелёный локальный прогон такого теста доказывает наличие побочной конфигурации у автора, а не корректность проверяемого кода. Всё, что git может взять из конфигурации, фикстура задаёт инлайн: `git init -b <branch>`, `git -c user.name=… -c user.email=… commit`, `-c init.defaultBranch=…`.

## Второй инстанс того же класса: identity коммита из побочного глобального gitconfig

Во втором раунде того же CI-прогона, после исправления ветки по умолчанию, упал единственный в файле сырой вызов `git commit-tree`, который не передавал identity инлайн (`-c user.name=… -c user.email=…`), тогда как все остальные commit-создающие вызовы фикстуры это делали. Локально вызов работал лишь потому, что глобальный gitconfig автора содержит identity; на голом GitHub-раннере без identity вызов упал («empty ident name»). Механизм тот же, что в тезисе: параметр, который git берёт из конфигурации, не задан явно, и тест наследует конфигурацию хоста. Дыра была в одном вызове из многих: частичное применение правила «identity инлайн» не защищает фикстуру (ср. `DP.FM.347`, частичный фикс одного класса бага оставляет пробелы). Два инстанса в двух раундах говорят за прогон всей фикстуры под симуляцией голого раннера после первого найденного дефекта класса, а не за точечный фикс.

Независимое повторение в другом репозитории: регрессионный тест в FMT-exocortex-template (WP-7 Ф171, PR #916) дважды упал на CI по тем же двум причинам (HEAD bare origin следовал `init.defaultBranch` раннера: master на GitHub Actions, main на машине разработки; на раннере без глобальной identity каждый commit в тесте падал с «Author identity unknown»). Оба фикса проверены локально в изолированном HOME с `GIT_CONFIG_GLOBAL=/dev/null`.

## Границы

Применимо к тестовым и CI-фикстурам, которые сами создают git-репозитории и коммиты (bash-скрипты smoke-тестов, pytest-фикстуры с `subprocess`), и к любым shell-обёрткам над git, запускаемым на разнородных хостах. Не относится к рабочим скриптам, читающим уже существующий чужой репозиторий и определяющим его основную ветку: это `DP.M.419` (цепочка fallback вместо хардкода `main`). Отличие от `DP.FM.403`, `DP.FM.414`, `DP.FM.465`: та же семья «окружение автора ≠ окружение исполнения», но другая ось: не шелл, переменные окружения планировщика или раскладка путей деплоя, а конфигурация git. Противоядие класса на уровне процесса: `DP.M.033` (matrix-CI) и раздел ниже.

## Проверка

«Каждый `git init` и `git init --bare` в фикстуре передаёт `-b <branch>` явно (или `-c init.defaultBranch=<branch>`)?» Нет → на хосте с другим `init.defaultBranch` HEAD созданного репозитория укажет на несуществующую ветку; локальный зелёный прогон это не выявит.

«Каждый вызов git в фикстуре, создающий коммит (`commit`, `commit-tree`, `merge`, `cherry-pick`, `rebase`, `tag -a`), передаёт identity инлайн через `-c user.name=… -c user.email=…` (или задаёт `GIT_AUTHOR_*` и `GIT_COMMITTER_*` в окружении фикстуры), включая сырые plumbing-вызовы?» Нет → на хосте без глобальной identity вызов падает; локальный зелёный прогон это не выявит.

Дополнительная проверка класса: прогнать фикстуру с пустым `GIT_CONFIG_GLOBAL` и `GIT_CONFIG_SYSTEM` и намеренно изменённым `init.defaultBranch`; тест обязан остаться зелёным.

## Противоядие: локальная симуляция голого CI-раннера

Метод из отчёта пир-сессии 2026-09-22-11-wp7-ci-ancestry-smoke (§6): поймать локально скрытую зависимость теста от личных настроек автора, которую не ловят ни код-ревью, ни зелёный прогон с обычным окружением.

1. Обнулить `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null`.
2. Принудительно задать ветку по умолчанию через `GIT_CONFIG_KEY/VALUE` (`init.defaultBranch=master`), а не полагаться на настройку хоста.
3. Воспроизвести исходные падения на коде до фикса под этой симуляцией: убедиться, что симуляция действительно ловит дефект.
4. Исправить дефект, подтвердить фикс под той же симуляцией.
5. После первого найденного дефекта класса «скрытая зависимость от окружения автора» прогнать под той же симуляцией все соседние тесты семейства, включая уже проходившие: не только изменённый тест. В источнике так перепрогнаны все остальные тесты.
6. Финальная приёмка: свежий субагент без контекста сессии повторяет прогон в тех же условиях.

Граница противоядия: живой прогон на целевом раннере остаётся обязательным финальным классом верификации CI-изменений; симуляция снижает число итераций до него, но не заменяет его. Пир-ревью (4 находки, все исправлены) и зелёный обычный локальный прогон не поймали эти два дефекта: их нашёл только живой прогон на GitHub Actions. Смежный метод живого прогона на реальном remote: `DP.METHOD.140`.
