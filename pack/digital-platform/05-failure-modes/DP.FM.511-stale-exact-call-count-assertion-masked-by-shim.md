# DP.FM.511 — Тест на точное число вызовов хука устарел из-за собственного шима

## Тезис и механизм ошибки

Тест `pull-on-touch-safe-pull-smoke.sh` фиксировал инвариант «хук делает ровно 2 вызова git» через шим окружения. Когда хук легитимно вырос на один вызов (добавлена проверка staged-diff, коммит 2ace3fa от 11.09), тест не упал явной ошибкой: собственный git-шим теста не имел case на третий вызов и в каждом сценарии трактовал его как «unexpected command», проглатывая без assert. Расхождение шима с реальностью замаскировало расхождение теста с реальностью, и обе ошибки молчали одновременно десять дней, до холодного ревью в отдельной пир-сессии.

## Диагностический принцип

Точное число вызовов в тесте есть хрупкий инвариант. Если тест держит шим окружения, а не настоящую систему, у шима должен быть явный, отдельно проверяемый case на каждый вызов реализации. Иначе любой незапланированный вызов шим поглощает молча, и тест остаётся «зелёным», когда реализация уже разошлась с тестируемым контрактом. Смежно: `DP.FM.413` (раннер тестов засчитывает падение как успех) и `DP.D.230` (тест-гард обязан валидировать): здесь тот же итог «зелёный сигнал без проверки», другой механизм.

## Границы

Применимо к любому тесту, который утверждает точное количество вызовов внешней команды или API через самодельный шим (не через spy уровня библиотеки с явным assert на каждый вызов). Не относится к тестам, где шим является сквозным проксированием к реальной команде с последующей проверкой побочного эффекта.

## Проверка

«У шима, которым тест эмулирует внешние вызовы, есть явный case на каждый вызов, который реально делает текущая реализация? Если шим получает вызов без case, тест падает явной ошибкой, а не продолжает молча?» Нет → воспроизведён DP.FM.511: рост числа вызовов в реализации проходит мимо теста, зафиксировавшего старое число.
