# DP.FM.518 — bash 3.2: брейс-экспансия внутри $(...) ломает инлайновый eval

## Симптом

Тестовый файл извлекал тело функции конструкцией `eval "$(sed -n "/^f() {/,/^}/p" "$1")"`. Под системным `/bin/bash` 3.2 (macOS) каждая проверка отвечала «функция не найдена» (exit 90). Автоматическая доставка конфигурации с Mac на сервер простояла пять дней (19-24.09): гейт тестов запускал файл голым `bash`, который при ограниченном PATH задачи launchd резолвился в 3.2, и на каждом двухчасовом тике падали 16 проверок из 25. Вручную всё работало, потому что интерактивная оболочка автора была Homebrew bash 5.3.15.

## Причина

В bash 3.2 сканер раскрытия фигурных скобок не пропускает `$(...)`, поэтому `{/,/^}` внутри адреса sed раскрывался, и единственный вызов sed расщеплялся на два невалидных. Воспроизведено на затронутом Mac: `env -i PATH=... bash` даёт `bash=3.2.57(1)` и раскрывает `{a,b}` в два слова. Правая часть простого присваивания не раскрывается, поэтому 3.2 и 5.x разбирают её одинаково.

Вторая причина длительности: `2>/dev/null` скрывал ошибки sed все пять дней, и сбой выглядел как логическая ошибка теста, а не как ошибка разбора оболочкой.

## Антипаттерн → Паттерн

- **Антипаттерн:** инлайновый `eval "$(cmd)"`, где вывод или текст команды содержит `{...}`; подавление stderr вокруг такой подстановки.
- **Паттерн:** сначала присвоить результат переменной, затем выполнить `eval` над переменной. Не подавлять stderr подстановки. В сообщение «не найдено» добавить `$BASH_VERSION`: в источнике это сделано, чтобы повтор был диагностируем по одному журналу.

## Тест обнаружения

«Есть ли инлайновый `eval "$(...)"` с фигурными скобками внутри подстановки в скрипте, который может исполняться системным `/bin/bash` (launchd, cron, git-хук)?» Да → возможно воспроизведение DP.FM.518. «Скрыт ли stderr у подстановки, чья ошибка единственный сигнал?» Да → диагностика отложена.
