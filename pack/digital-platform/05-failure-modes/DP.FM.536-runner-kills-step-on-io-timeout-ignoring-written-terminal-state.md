# DP.FM.536 — Раннер путает «не вернулся io-канал» с «не завершилась задача»

## Симптом

Минимум 6 карточек за 3 суток помечались `failed`: раннер ждал завершения канала stdout/stderr дочернего процесса и по истечении порога (сначала 180 с, затем 900 с — повышение порога не лечило) убивал группу процессов и фиксировал неудачу. При этом сам процесс уже записал на диск подтверждённое терминальное состояние «closed» за 16 секунд до убийства. Последняя карточка упала уже при увеличенном пороге в 900 с — это зависание именно канала, а не медленная работа.

## Причина

Раннер определяет успех/неудачу шага по возврату/таймауту внешнего вызова, то есть измеряет «вернулся ли io-канал», а не «записано ли терминальное состояние задачи». После реального завершения работы что-то (вероятно, потомок процесса, унаследовавший дескриптор stdout) не давало EOF — и это маскировалось под зависшую работу, хотя сама задача была закрыта секундами ранее.

## Противодействие

Источник истины о завершении задачи — её собственное терминальное состояние на диске/в API, а не факт закрытия io-канала вызывающего процесса. Эти два события могут разойтись. Раннер обязан проверять терминальное состояние отдельно от ожидания канала и не перезаписывать уже записанный успешный результат меткой `failed` по таймауту канала.

## Тест обнаружения

«Если шаг помечен `failed` по истечении таймаута ожидания вывода — проверено ли терминальное состояние задачи на диске/в API за то же окно времени, прежде чем доверять метке `failed`?» Нет → возможен этот класс ложного `failed` поверх уже успешно закрытой задачи.
