# DP.FM.544 — Переизбыточный glob в guard'е «от коллизии имени» ловит любой исторический файл

## Тезис и механизм ошибки

Фикс конфликта двух инвариантов git-tracking одного пути (отдельно захвачен тем же днём — `info/exclude` на создании worktree) сам принёс побочную защитную проверку: «если `git ls-files` по маске `RUN-*.md` непусто — отказать» (защита от коллизии имени новой карточки с уже существующей). Проверка не отличала КОНКРЕТНОЕ новое имя карточки текущего прогона от ЛЮБОГО совпадения по общему шаблону в истории репозитория. В `origin/main` уже отслеживается 1125+ исторических карточек с именами вида `RUN-*.md` (принятая практика нумерации) — проверка отказывала бы на КАЖДОМ будущем вызове `--isolate`, а не только в том редком случае реальной коллизии конкретного имени, для которого задумывалась. Дефект не успел дойти до живого прогона — пойман фикстурой холодного ревью той же пир-сессии.

## Диагностический принцип

Защитная проверка «от коллизии нового идентификатора» обязана сверяться с КОНКРЕТНЫМ именем/идентификатором текущей операции, а не с фактом наличия любого файла, подходящего под общий шаблон, в истории репозитория. Если под шаблон уже массово попадают легитимные исторические записи (принятая конвенция именования), проверка «шаблон непуст» вырождается из «редкий edge-case заблокирован» в «всегда заблокировано» — ровно обратный исходному замыслу результат.

## Границы

Применимо к любому guard'у, реализующему идею «эта операция не должна создать повторяющийся идентификатор» через широкий glob/grep по каталогу/истории, где легитимные повторяющиеся по шаблону (но разные по факту) записи уже являются нормой. Отличие от `DP.FM.361` (ID-коллизия promise-кодов, `max+1`): там защита — вычисление следующего свободного номера, механизм отличается; здесь — защита «отказать при любом совпадении по маске», которая ошибочно не сужена до конкретного имени.

## Проверка

«Защитная проверка «нет коллизии» реализована как «совпадений по glob/grep-шаблону в каталоге/истории — ноль»? Легитимных записей, уже подходящих под этот шаблон, в истории больше нуля?» Да на оба → проверка откажет всегда, а не только в целевом редком случае; нужно сузить сравнение до конкретного проверяемого имени/идентификатора, а не шаблона.
