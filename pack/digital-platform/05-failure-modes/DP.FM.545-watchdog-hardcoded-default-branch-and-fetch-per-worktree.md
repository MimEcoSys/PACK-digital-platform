# DP.FM.545 — Watchdog worktree: захардкоженный default-branch и fetch по копии, не по репозиторию

## Тезис и механизм ошибки

Новый watchdog заброшенных изолированных worktree должен был сравнить последний коммит каждого worktree с origin по patch-id. Валидация на ~280 РЕАЛЬНЫХ worktree этой машины (не синтетика) нашла две системные ошибки до того, как сторож стал верным: (1) скрипт жёстко подразумевал `main` как default branch репозитория; у одного конкретного репозитория (бот) реальная рабочая ветка — `new-architecture`, и сравнение против `origin/main` показало 2000+ «неопубликованных» коммитов, которые на деле просто находились не в той ветке, которую скрипт проверял; (2) скрипт делал `git fetch` на каждую копию worktree отдельно, хотя все worktree одного репозитория делят одну object-базу и один набор remote-tracking refs — fetch нужен и корректен ровно один раз на уникальный репозиторий, а не на каждую его копию (7 минут прогона против 3.5 после объединения).

## Диагностический принцип

«Основная/дефолтная ветка» репозитория — не универсальная константа (`main`), а конкретное значение `refs/remotes/origin/HEAD`, которое может отличаться по репозиторию (переименованная или унаследованная ветка разработки). Скрипт, сравнивающий состояние рабочей копии с «основной веткой», обязан читать это значение из самого репозитория, а не захардкоживать имя — иначе ложно классифицирует легитимную работу на нестандартной ветке как «неопубликованную». Отдельно: операции с удалённым концом (fetch) логически привязаны к РЕПОЗИТОРИЮ (общая object-база), а не к каждой его рабочей копии (worktree) — повторение такой операции на каждый worktree не просто расходует время, а противоречит модели данных git worktree.

## Границы

Применимо к любому скрипту/сторожу, сравнивающему состояние одной или нескольких рабочих копий (worktree) с «основной веткой» или выполняющему fetch/операции с remote в цикле по множеству worktree одного репозитория. Отличие от `DP.FM.513` (чекаут стоит на устаревшей/чужой ветке — отсутствует pre-flight проверка перед началом правки) и `DP.FM.488` (владение путём ≠ владение репозиторием — проверка принадлежности ресурса путает путь с git-базой): здесь — сам сторож содержит две самостоятельные ошибки предположения (имя ветки, кардинальность fetch), а не ошибку пользователя/агента, начавшего правку. Смежный, но отдельный баг того же нового скрипта: единственный незащищённый git-вызов внутри цикла под `set -e` обрывает весь скан на первом сбое — это другой механизм (fail-fast цикла, а не неверное значение/кардинальность операции), пока не оформлен отдельной карточкой.

## Проверка

«Скрипт сравнивает состояние worktree/чекаута с «основной веткой» репозитория по захардкоженному имени (`main`, `master`)?» Да → подтвердить, что имя читается из `refs/remotes/origin/HEAD`, а не из константы; воспроизводимо на любом репозитории с переименованной/нестандартной веткой разработки. Отдельно: «Скрипт выполняет `fetch` или другую операцию с remote внутри цикла по worktree одного репозитория?» Да, более одного раза на уникальный репозиторий → лишняя работа минимум, потенциальное нарушение модели данных (shared object database) максимум.
