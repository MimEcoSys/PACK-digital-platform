# DP.FM.550 — Squash базового PR осиротил зависимый PR стопки

## Симптом

Три шага работы выложены стопкой: каждая ветка основана на предыдущей, каждый PR нацелен не на `main`, а на ветку-основание — так ревью видит только свой диф. Базовый PR (#51) слит стратегией squash. Зависимый PR (#52) отображается как «merged», но его содержимое в `main` отсутствует; понадобилось открыть новый PR (#54), приземляющий шаг 2 прямо в `main`.

## Механизм

1. Squash-мердж создаёт в целевой ветке **новый** коммит: то же дерево, другая история.
2. База зависимого PR (вершина ветки шага 1) после этого не является предком `main` — в `main` живёт её squash-двойник с другим SHA.
3. Зависимый PR продолжает указывать на промежуточную ветку как на цель. Он действительно вливается в неё — GitHub честно пишет «merged».
4. Промежуточная ветка сама уже не на пути в `main`. Ни один коммит зависимого PR целевой ветки не достигает.

Ядро дефекта — индикатор: метка «merged» означает «влит в свою базу», а читается как «доставлен в продукт». Различия между этими двумя состояниями статус PR не выражает.

## Асимметрия защиты

Защита ветки настроена только на `main`, поэтому промежуточные PR в неё не упираются: обязательные проверки, ревью и гейты на них не распространяются. У шага, который оказался потерян, не было и автоматики, способной заметить потерю.

## Исправление

1. **Правило на стопку:** после слияния базового PR зависимые перенацеливаются на целевую ветку и проверяются на предковость базы относительно неё.
2. **Признак доставки — достижимость из целевой ветки** (`git merge-base --is-ancestor`, а при переписывающем публикаторе — сравнение содержимого, см. `DP.D.316`), а не метка «merged».
3. **Не смешивать стопки с переписывающими историю стратегиями слияния** (squash, rebase) без правила из п. 1. Если стратегия слияния в репозитории фиксирована как squash, стопка перестаёт быть безопасной формой подачи работы по умолчанию.

## Тест обнаружения

«Нацелен ли PR на ветку, отличную от целевой, и может ли базовый PR быть слит переписывающей историю стратегией?» Да и да → зависимый PR под риском DP.FM.550. Проверка факта: для каждого PR со статусом «merged» — достижим ли хотя бы один его коммит (или его содержимое) из целевой ветки.

## Границы

Карточка о стопке PR на одном форже со squash/rebase-слиянием. Merge-commit-стратегия этот дефект не воспроизводит: база остаётся предком целевой ветки. Карточка не о корректности самого squash как стратегии и не о переписывании истории вообще (`DP.FM.401`).

## Связанные документы

- `DP.D.316` — «коммит доставлен» ≠ «содержимое доставлено»: там переписывающий публикатор даёт ложное «не запушено»; здесь переписывающее слияние даёт ложное «слит». Обе ошибки от того, что индикатор говорит о SHA, а предмет — содержимое в целевой ветке.
- `DP.D.329` — «запушено в ветку» ≠ «доставлено в целевую ветку»: ось различения; эта карточка — её конкретный механизм на стопке PR.
- `DP.M.300` — проверка реального scope PR на ветке-поверх-ветки: смежный приём для той же конфигурации.
- `DP.FM.401` — переписывание истории ломает постороннюю автоматику: другой потребитель того же свойства squash/rebase.
