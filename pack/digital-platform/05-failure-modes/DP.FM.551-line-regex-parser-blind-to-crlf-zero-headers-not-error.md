# DP.FM.551 — Построчный regex-парсер слеп к CRLF: ноль заголовков вместо ошибки

## Симптом

Разбор markdown-файла на заголовки шёл построчно: файл делился по `\n`, и к каждой строке применялись регексы на frontmatter, ограждение кода и заголовок. В файле, сохранённом с CRLF (Windows-перенос), каждая строка оканчивается на `\r`. Этот `\r` остаётся «хвостом» после разбиения по `\n`, и якорь конца строки в использованных регексах его не перепрыгивает — ни одно из трёх правил не срабатывало. Результат: разбор возвращал пустой список заголовков — полный отказ функции, замаскированный под «в файле нет заголовков», без исключения и без кода ошибки.

## Причина

Построчные регулярные выражения над содержимым, пришедшим извне (включая файлы с чужим форматом переноса строк), не нормализовали окончание строки до сопоставления. `\r`, молча перенесённый в каждую строку после split по `\n`, ломает совпадение якоря `$`/конца строки в паттернах, рассчитанных на Unix-перенос.

## Исправление

`\r` снимается (`stripCR()`) только для сопоставления регексом. Накопление байтовых смещений обязано продолжать считать СЫРУЮ (неочищенную) длину строки — иначе чтение секции по смещению начнёт отдавать сдвинутый на число строк фрагмент. То есть нормализация входа для сопоставления и адресация внутри входа для позиционирования обязаны работать на разных представлениях одной и той же строки.

## Тест обнаружения

«Прогонялся ли парсер на образце в чужом формате переноса строк (CRLF), а не только на собственных Unix-файлах репозитория?» Нет → класс ошибки «ноль результатов вместо отказа» останется незамеченным при чтении кода и обнаружится только на реальном чужеродном артефакте.
