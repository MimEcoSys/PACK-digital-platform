# DP.FM.556 — Git-dirty-state как proxy «пользователь редактировал» ломается, если инструмент сам пишет без коммита

## Симптом

`update.sh`/`day-open-llm-fill.py` копируют seed-данные поверх tracked-пути, не делая `git add`/`commit`. Guard от 25.08 корректно отказывается трогать файл дальше, если видит его dirty — но живое воспроизведение на двух из трёх потребителей функции показало отказ в обе стороны: guard одинаково блокирует настоящую правку пользователя (регрессию, которую и должен поймать) и собственный незакоммиченный след инструмента (легитимное повышение версии, которое должно пройти).

## Причина

Git-dirty-state («рабочее дерево отличается от HEAD») использовался как proxy для «файл трогал человек». Предпосылка верна только если ни один автоматический инструмент не модифицирует tracked-файл без коммита. Как только тот же файл может легитимно измениться самим инструментом без коммита, признак становится неоднозначным: одна и та же наблюдаемая величина (dirty=true) соответствует двум несовместимым причинам.

Источник истины на основе содержимого, а не git-статуса — companion-находка того же WP (`captures/2026-10.md:1029`, на момент этого отчёта ещё не формализована в Pack) предлагает конкретный путь: переиспользовать уже существующий content-based классификатор вместо параллельной git-state эвристики.

## Тест обнаружения

«Guard использует `git status`/dirty-state рабочего дерева как сигнал "файл трогал человек", и при этом хотя бы один легитимный путь кода того же инструмента может записать в тот же tracked-путь без `git add`/`commit`?» Да и да → признак неоднозначен, guard одинаково блокирует регрессию и легитимное собственное изменение инструмента.
