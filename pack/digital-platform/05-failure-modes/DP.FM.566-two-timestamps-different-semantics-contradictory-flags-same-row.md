# DP.FM.566 — Два поля времени с разной семантикой в одном подзапросе

## Симптом

Подзапрос табло наставника считал «последнюю активность» по `message_at` (момент написания сообщения), а окна давности 7/30 дней — по `sent_at` (момент отправки/видимости) — в одном и том же подзапросе на одной строке. Черновик может лежать днями до отправки, поэтому `message_at` и `sent_at` законно расходятся: одна и та же строка участника одновременно показывала «наставник писал на этой неделе» (по `sent_at` — свежо) и `staleArchiveActivity=true` (по `message_at` — старо), два взаимоисключающих утверждения разом.

## Причина / механизм

1. У сущности переписки два момента времени с разной легитимной семантикой: когда сообщение написано и когда оно отправлено/стало видимым; разница легитимна (черновики).
2. Новая функция сводила оба назначения (текущая активность и давность) из одного подзапроса, но каждое — по своему полю, без явного решения «какое поле — единственный источник давности для ВСЕХ сравнений модуля».
3. Соседняя функция в том же модуле это решение уже приняла правильно: там `message_at` — чисто информационное поле, никогда не участвует в сравнениях давности. Новая функция не переиспользовала это решение.

## Противодействие

Если у сущности несколько временных меток с разной легитимной семантикой, одна и только одна должна быть явно объявлена «временем давности» для ВСЕХ сравнений внутри модуля — не «то поле, что было под рукой» для каждого конкретного вычисления по отдельности. Фикс: все сравнения давности — по `sent_at`, как в соседней функции карточки участника. Регрессионный тест обязан допускать тестовый мир, где метки заданы раздельно и намеренно расходятся на недели — иначе тест не отличает «метки синхронны» от «поля не перепутаны».

## Тест обнаружения

«У сущности несколько временных меток с разной легитимной семантикой (написано vs отправлено, создано vs опубликовано)? Есть ли тест, где эти метки намеренно расходятся на недели?» Нет такого теста → смешение полей в разных частях одного вычисления не поймано, и одна строка может нести два взаимоисключающих флага давности.

## Второй случай: метка внешнего источника — день, а не момент; исправление экрана не лечит расчёт

Тот же класс — две метки с разной семантикой, и давность считается не от той — вскрылся на границе с внешним источником данных. Табло показывало «возраст данных» от поля `observed_at`, которое отдаёт внешний API. Имя обещало момент наблюдения, но значение оказалось меткой дня (полночь UTC), поэтому «N минут назад» росло весь день и достигало сотен минут (в прецеденте — около 600). Первая правка убрала только ложное «в HH:MM» на экране: расчёт возраста по-прежнему читал то же поле. Вторая правка перевела расчёт на собственную отметку «наш сервер последний раз сверился с источником» (`generated_at`) сразу в трёх потребителях — `/health`, статус источников и свободный диалог; третьего потребителя первая правка пропустила, его нашло независимое холодное ревью.

Что это добавляет к карточке:

1. **Смысл поля внешнего источника устанавливают по данным, а не по имени.** Если давность строится от поля, которое отдаёт не наша система, его смысл надо выяснить наблюдением (например, сравнить значения поля в разные часы одного дня: у метки дня они совпадают). Базой давности для таких данных служит собственная отметка последней успешной сверки с источником.
2. **Исправление отображения не лечит ложное поле.** Пока вычисления читают то же поле, ложь остаётся — меняется лишь место, где её видно. Потребителей ищут по имени поля (поиск по полю), а не по симптому на экране; это частный случай `DP.FM.347`, а принцип «чинить источник расчёта, а не вход» — `AS.M.067`.
3. **Тест различает метки.** Прежние фикстуры задавали обеим меткам одно значение и не отличили бы подмену одного поля другим; после правки регрессионные тесты задают РАЗНЫЕ значения `observed_at` и `generated_at` (требование уже сформулировано в разделе «Противодействие» — второй случай его подтверждает).

Тест обнаружения для этого варианта: «Давность считается от поля, которое отдаёт внешняя система? Установлено ли по данным, что поле — момент, а не метка периода? Найдены ли все потребители этого поля поиском по имени поля, а не по симптому на экране?»
