# DP.FM.568 — Парсер carry-over знал два формата маркера из трёх реальных, молчал нулём на третьем

## Симптом

Блок «Carry-over из Day Close вчера» пишется LLM-шагом (`day-open-llm-fill.py`) как свободный текст, не по шаблону; пунктуация маркера списка дрейфовала день ото дня. Парсер следующего шага знал два жёстких формата из трёх реально встретившихся — на третьем он не падал, а молча возвращал пустой список шагов: пилот увидел «не вижу подтверждённого шага» при валидном плане.

## Причина / механизм

1. Производитель текста (LLM-шаг) не связан фиксированным шаблоном — каждый день формулирует маркер списка немного иначе.
2. Парсер-потребитель захардкодил ровно два варианта пунктуации маркера, встретившиеся на момент его написания.
3. На третьем, реально встретившемся варианте парсер не бросает ошибку — он просто не находит совпадений и возвращает пустой список, который неотличим от легитимного «carry-over пуст, вчера всё закрыли».
4. Класс не ограничен верификаторами: это общий риск для любого потребителя регулярно генерируемого LLM свободного текста, не только для LLM-output-проверок.

## Тест обнаружения

«Потребитель регулярно генерируемого LLM свободного текста распознаёт фиксированный, заранее перечисленный набор форматов маркера/пунктуации? При непустом входе и нуле распознанных элементов — парсер отказывает громко или молча возвращает пустой результат?» Молча — риск воспроизведения: дрейф формата у производителя даёт тихий пустой результат вместо ошибки.

## Fix / критерий приёмки

Один толерантный паттерн вместо перечисления жёстких форматов (применено в этом случае, commit `bd4845233`, WP-389). При непустом входе и нуле распознанных элементов — парсер обязан отказывать громко (DP.FM.040, DP.FM.551), не возвращать тихий пустой результат. Радикальное лечение, не формализованное этой карточкой, — перевести блок у производителя со свободного текста на фиксированный машиночитаемый формат (общая грамматика у писателя и читателя, DP.FM.496).
