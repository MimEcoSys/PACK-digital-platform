# DP.FM.571 — Красный CI-гейт провоцирует хотфикс в обход PR: канон расходится с origin

## Тезис и механизм ошибки

Обязательный CI-гейт (например, changelog-entry) становится красным после слияния PR без нужного обновления. Под давлением «надо быстро починить» правку делают прямо в каноническом локальном чекауте вместо создания нового PR. В результате канон опережает origin/main, и любая автоматизация, неявно полагающаяся на «канон всегда равен origin» (шаблонная синхронизация, pipeline-шаги), корректно диагностирует расхождение как риск и отказывается трогать репозиторий.

Паттерн рецидивирующий: произошёл дважды за 48 часов на двух разных PR (#1113 от 05.10 и #1142 от 06-07.10).

## Диагностический принцип

Красный обязательный гейт создаёт давление к процессному обходу (правка мимо PR). Любая автоматизация, неявно полагающаяся на инвариант «канон = origin», обнаруживает расхождение и корректно «отказывается» — не это ошибка, а сам обход PR.

## Проверка

«Последнее изменение в каноническом чекауте прошло через PR и оказалось на origin/main?» Нет → риск DP.FM.571.

## Фикс

Доставка изменений только через PR + auto-merge; прямой push в main безусловно отклоняется (enforce_admins + release-receipt). Любая автоматизация, работающая с каноном, должна либо явно проверять `git status` vs origin, либо сама доставляться только через полный процессный путь (deliver_via_pr).

## Границы

Применимо к любому репозиторию, где (а) есть обязательные CI-гейты с возможностью провала после merge, и (б) есть автоматизация, неявно полагающаяся на «канон = origin». Не описывает дизайн самих гейтов.
