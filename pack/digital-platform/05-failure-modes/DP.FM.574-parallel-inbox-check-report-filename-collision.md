# DP.FM.574 — Параллельный inbox-check: коллизия имени файла отчёта, не коллизия знания

## Тезис и механизм ошибки

Два прогона `inbox-check` (launchd-цикл + ручной запуск, либо два launchd-тика на разных машинах без общего lock) читают каталог `inbox/extraction-reports/` и независимо вычисляют следующий порядковый суффикс для имени нового отчёта (`YYYY-MM-DD-inbox-check-N.md`) — каждый по снимку каталога на момент старта СВОЕГО прогона. Содержательно отчёты не пересекаются (разные captures, разные кандидаты), но оба претендуют на один путь файла. При публикации второй коммит получает **`add/add` CONFLICT**: git не может молча принять два разных новых файла по одному пути — в отличие от трёхстороннего слияния правок существующего файла, здесь слияние контента бессмысленно (это два независимых артефакта, не два изменения одного).

**Контраст, подтверждающий механизм:** общий агрегирующий файл (`captures.md`/`captures/*.md`), в который оба прогона писали в то же окно, слился автоматически («Auto-merging … прошло чисто») — формат «только дозапись новых строк/маркеров» устойчив к параллельной записи по построению (DP.SC.042: captures.md — single aggregation point именно с этим свойством). У имени файла отчёта такого свойства нет: он не дозаписывается, он присваивается целиком новому артефакту при каждом прогоне.

## Диагностический принцип

Два класса гонки в одном пайплайне требуют разных проверок: (1) коллизия **Pack-ID знания** внутри отчётов — ловится cross-batch grep очереди перед присвоением ID (AR.242); (2) коллизия **имени файла-контейнера** самих отчётов — ловится только на шаге публикации, retry с перечитыванием каталога на origin.

## Проверка

«Имя нового файла отчёта вычислено один раз в начале прогона (`ls | max+1`) и не перепроверено непосредственно перед commit/push на актуальном origin?» Да → открыто окно гонки класса DP.FM.574, даже если captures.md при этом защищён.

## Фикс и ограничение фикса

При обнаружении `add/add` на пути `extraction-reports/*-inbox-check-N.md` раннер не должен пытаться слить содержимое — следует переименовать свою копию в следующий **реально** свободный суффикс (перечитав каталог на origin заново, не по старому снимку) и повторить публикацию. Профилактика: сделать суффикс неоднозначным по построению (компонент hostname/run-id/первые символы commit sha вместо чистого `max+1`), либо резервировать номер через origin до генерации содержимого отчёта. Фикс не отменяет необходимости cross-batch проверки Pack-ID внутри отчётов (AR.242) — это два независимых слоя защиты одного пайплайна.

## Границы

Применимо к любому pipeline-артефакту, чьё имя — локально вычисленный порядковый номер, а производителей несколько и они не координируются через общий lock или origin перед присвоением имени. Не описывает ситуацию, где сам контент (а не имя) задублирован параллельными прогонами — это P-KE-011 (cross-session parallel duplicates), отдельный, хотя родственный класс.
