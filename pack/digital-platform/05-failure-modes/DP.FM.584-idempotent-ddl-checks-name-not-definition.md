# DP.FM.584 — Идемпотентность по имени вместо определения

## Тезис и механизм ошибки

Хелпер `ensure_service_read_policy()` создаёт узкую RLS-политику-исключение для каждой reader-роли. Первоначально идемпотентность проверялась по ИМЕНИ политики: если политика с таким именем уже есть — пропустить. Если у существующей политики другое (устаревшее) определение, повторный запуск молча оставлял старое правило вместо обновления.

«Объект с этим именем существует» ≠ «объект с этим именем имеет нужное определение».

## Признаки

- Идемпотентная DDL-обёртка (`IF NOT EXISTS`, проверка по `pg_policies.policyname`) без сравнения тела объекта.
- После изменения определения в коде на уже мигрированной базе поведение не меняется, ошибок нет.

## Митигация

Сравнивать полное определение (для политики — команду, роли, `USING`, `WITH CHECK`) с желаемым; при расхождении — пересоздавать (`DROP` + `CREATE` или `ALTER`). Распространяется на любые идемпотентные DDL-обёртки, не только RLS.

## Тест обнаружения

«Сравнивает ли идемпотентная проверка определение объекта или только его имя?» Только имя → повторный запуск не обновит устаревший объект.
