# DP.FM.591 — Таймаут замка записи, обработанный как `|| exit 0`, молча теряет запись

## Тезис и механизм ошибки

Скрипт дописывал ключ уведомления в файл под `flock -w 10 8 || exit 0`. Если замок не удавалось получить за 10 секунд, ветка `|| exit 0` завершала скрипт с кодом успеха, не записав ключ: запись терялась молча, без ошибки и без следа. Дефект нашло ревью субагента (git commit 76a7d1352 в DS-my-strategy, WP-568 Ф4).

## Диагностический принцип

`flock -n … || exit 0` — штатная идиома охраны от повторного запуска: «замок занят — работу уже делает другой экземпляр, выхожу» (см. `DP.M.413`, `DP.M.372`). Для замка, охраняющего ЗАПИСЬ, смысл другой: занятый или недоступный за таймаут замок не означает, что кто-то уже сделал ту же запись. Таймаут ожидания такого замка — путь отказа, а не путь успеха; идиома, верная для охраны запуска, на охране записи отбрасывает данные, которых больше нигде нет. Код возврата 0 при этом не отличает «записал» от «потерял» ни для планировщика, ни для вызывающего. (Различение «охрана запуска ≠ охрана записи» — вывод экстрактора из источника и `DP.M.413`; в самом источнике не сформулировано.)

## Что делать (фикс из источника)

1. На таймауте завершаться ненулевым кодом, чтобы потеря была видна; в источнике — `exit 75` (примечание экстрактора: 75 — `EX_TEMPFAIL` из `sysexits.h`, «временный сбой, повторить позже»; смысл кода в источнике не объяснён).
2. Если запись — одна короткая строка, дописать её без замка: по формулировке источника, запись одной короткой строки через `O_APPEND` безопасна и без блокировки. Тогда таймаут замка не приводит к потере ключа вообще.

## Границы

Относится к замкам, охраняющим ЗАПИСЬ, которая обязана состояться (журнал, ключи уведомлений, очередь). Не относится к охране от повторного запуска: там `|| exit 0` на занятом замке корректен. Безлоковый fallback обоснован в источнике только для дозаписи одной короткой строки; для чтения-изменения-записи и многострочных блоков такой вывод не делался, и при таймауте им нужен повтор или громкий отказ, а не запись без замка. Причину самих таймаутов (медленная операция внутри критической секции) разбирает `DP.M.490`, здесь — поведение претендента, когда таймаут всё же наступил.

## Проверка

«Для каждого `flock -w N <fd> || <выход с кодом успеха>`: что теряется, если замок не получен за N секунд — повторяемый запуск (допустимо) или запись, которой больше не будет (нарушение)?» Второе → при таймауте нужен ненулевой код и / или безопасный безлоковый путь.

«Что видит планировщик или вызывающий при таймауте: ошибку или успех?» Успех → потеря невидима.
