# DP.FM.597 — `$value` вплотную к не-ASCII символу: первый байт символа уходит в имя переменной

## Симптом

При добавлении настраиваемого стиля заголовков DayPlan новая функция печатала предупреждение вида `«$value»` для неизвестного значения параметра и падала под `set -u` с «unbound variable»: имя переменной «съедало» первый байт закрывающей кавычки-«ёлочки», получалось несуществующее имя с мусорным символом. Дефект сидел в ветке WARN (неизвестное значение параметра) и найден при тестировании, а не на обычном прогоне; починен записью `«${value}»`. Тот же шаблон остался в соседней функции чтения параметра календаря (issue #942) — осознанно не тронут (вне объёма PR), помечен к отдельной правке.

## Причина

bash допускает в имени переменной байты, которые `isalnum()` текущей локали считает буквами. В UTF-8-локали macOS `isalnum()` считает буквами начальные байты многобайтовых символов (проверено на 0xC2, 0xC3, 0xD0, 0xD1, 0xE2, 0xE4, 0xF0), но не продолжающие (0x80, 0xAB, 0xBB) и не 0xD7; в локали `C` все эти байты — не буквы. Поэтому `$value»` читается как переменная `value\302`. Роль `isalnum()` установлена по поведению bash и проверке C-библиотеки; исходный код bash не читался.

## Воспроизведение (экстрактор, 2026-10-12, macOS, Darwin 25.5.0)

| Окружение | Код | Результат |
|---|---|---|
| `/bin/bash` 3.2.57, `LC_ALL=en_US.UTF-8`, `set -u` | `"«$value»"` | `value\302: unbound variable` |
| то же | `"$valueтест"`, `"$value中"`, `"$value😀"`, `"$valueé"` | `unbound variable` — имя плюс первый байт символа (`\321`, `\344`, `\360`, `\303`) |
| то же | `"$value,"` | `x,` — ASCII-символ после имени безопасен |
| то же | `"«${value}»"`, `"${value}тест"` | `«x»`, `xтест` |
| то же, без `set -u` | `"[«$value»]"` | `[«`, одинокий байт `\273`, `]` — значение `x` исчезло молча, в выводе невалидный UTF-8 |
| Homebrew bash 5.3.15, `en_US.UTF-8` | те же коды | те же результаты — дело не в версии bash |
| любой из двух bash, `LC_ALL=C` | те же коды | дефекта нет: `«x»`, `xтест` |
| zsh, `en_US.UTF-8`, `setopt nounset` | `"«$value»"` | `«x»` |

## Антипаттерн → Паттерн

- **Антипаттерн:** `"…$value»"`, `"$name—"`, `"$count…"`, `"$nameтест"` — имя переменной вплотную к символу не из ASCII (кавычки-«ёлочки», типографские кавычки и тире, кириллица, эмодзи).
- **Паттерн:** брать в фигурные скобки любую переменную, после которой в строке идёт не пробел и не ASCII-пунктуация: `${value}`. Тесты скриптов с нелатинским текстом запускать с явной UTF-8-локалью (`LC_ALL=en_US.UTF-8`): в окружении без `LANG` / `LC_*` (например, в задаче планировщика) работает локаль `C`, и дефект не виден.

## Тест обнаружения

«В скрипте есть `$имя` вплотную к символу не из ASCII (в строке сообщения, WARN, форматировании)? Проверен ли скрипт в UTF-8-локали?» Статически: `rg -n '\$[A-Za-z_][A-Za-z0-9_]*[^\x00-\x7F]' *.sh` — проверено на образце: находит `«$value»`, `$value—dash`, `$valueтест`, не находит `${value}` и `$value,`. Без `set -u` дефект тихий — значение пропадает, остаётся одинокий байт: проверять не только падения, но и невалидный UTF-8 в выводе.

## Границы

Проверено на macOS (Darwin 25.5.0) с двумя версиями bash; Linux / glibc не проверялся. Поведение зависит от локали и от таблицы классификации символов в C-библиотеке, поэтому скрипт, прошедший проверку на сервере без `LANG`, может упасть на интерактивной машине автора.
