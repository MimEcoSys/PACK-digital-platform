# DP.FM.599 — Квадратичная склейка продолжений строк в защитном хуке

## Описание

`destructive-guard.sh` — PreToolUse-хук, разбирающий команду агента перед выполнением. Функция «продолжается ли заголовок» (`continued_header`), склеивающая многострочные команды с завершающим `\`, на каждом новом переносе заново посимвольно проходила ВСЮ уже накопленную строку — O(n²): 2000 переносов ≈ 10с на двухъядерной машине CI (1.15–1.29с на быстрой машине).

## Механизм

1. Цикл «приклеить очередной сегмент → пересканировать всё склеенное целиком» — каждый новый сегмент требует прохода по всей накопленной длине, не только по себе.
2. Рост числа переносов (`\`) в команде агента линеен — время разбора растёт квадратично.
3. На горячем пути (перехват КАЖДОЙ команды агента перед выполнением) это превращается в заметную задержку задолго до таймаута.

## Почему опасен

Разбор защитного хука — не опциональная аналитика, а барьер перед исполнением; квадратичное замедление здесь не просто «медленный скрипт», а потенциальный источник задержки/таймаута на обычных многострочных heredoc-командах, которые агенты генерируют регулярно.

## Фикс

Чистая функция `scan_quote_state(строка, состояние)`: каждый новый сегмент сканируется ровно один раз, состояние кавычек (открыта/закрыта) передаётся явно между сегментами; сегменты копятся в списке и склеиваются одним `join` в конце. После фикса: 2000 переносов — 0.13с, 5000 переносов — 0.20с (рост линейный).

## Тест обнаружения / регресс-тест

«Код приклеивает кусок к уже накопленной строке и затем пересканивает результат ЦЕЛИКОМ (не только новый кусок)?» Да → квадратичное время при росте числа кусков. Регресс-тест по времени (`perf_cases.py`): 2000 переносов, порог с кратным запасом (не менее 4× к медленному CI) — на старом коде красный, на новом зелёный; тест по времени без запаса флакает.

## Переносимый принцип

Цикл «приклеить → пересканировать всё склеенное» квадратичен независимо от предметной области; сканировать инкрементально с явным переносимым состоянием. Защитный хук на горячем пути требует отдельного теста по времени выполнения, не только теста корректности.

## Отличие от соседей

- `AS.FM.071` (O(N×M) без параллелизма деградирует до зависания при росте базы) — тот же общий принцип «деградация не видна на одном замере», но другой субстрат и другой триггер: там рост данных ВО ВРЕМЕНИ (база растёт между замерами), здесь — рост входа В ОДНОМ вызове (число переносов строки в одной команде); разные защиты (там — параллелизм/кэш/таймаут, здесь — инкрементальное сканирование состояния).
- `AS.FM.081` (гейт коммита сканирует весь общий индекс, а не файлы команды) — смежная тема «сканирование большего, чем нужно», но про охват данных (чужие файлы), не про алгоритмическую сложность повторного прохода.
