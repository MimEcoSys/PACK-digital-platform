# DP.FM.608 — Счётчик и список одного набора расходятся при независимом вычислении

## Тезис и механизм ошибки

Заголовок статусного бандла («Открытых фаз: N») считал число верно через отдельную функцию `count_open_phases()`, не имевшую ограничения на размер. Список фаз под заголовком собирался другой функцией (`extract_open_phases()`), где `head -20` стоял «на случай» в обеих её ветках — хотя сам смысл списка (только открытые фазы) уже естественно ограничивал размер, и отдельный потолок был избыточен. Живой пример: РП-7 показывал 61 в счётчике и только 19 записей в списке. Баг найден 07.10, не исправлен в той же сессии — дожил до 13.10 (шесть дней).

## Диагностический принцип

Когда одно видимое число (счётчик) и видимый под ним список относятся к одному и тому же логическому набору, но вычисляются двумя независимыми путями одной функции/модуля — скрытый лимит в одном из путей, не продублированный в другом, создаёт расхождение, которое не поймает ни один путь по отдельности (каждый «прав» сам по себе).

## Границы

Не то же самое, что усечение самого вывода одной операции (`DP.FM.428`, tail-truncation одного лога) — там единственный поток данных обрезается и прячет часть своего же содержимого. Здесь — рассинхрон МЕЖДУ ДВУМЯ независимо вычисленными представлениями одного множества (счётчик без лимита ≠ список с произвольным лимитом); разные корневые причины, не сворачивать в одну карточку.

## Проверка

На наборе данных, где реальный размер превышает вероятный зашитый лимит (>20 элементов), сравнить число счётчика с фактической длиной списка под ним. Расхождение воспроизводится детерминированно при превышении лимита; тест обязан включать случай N > 20.
