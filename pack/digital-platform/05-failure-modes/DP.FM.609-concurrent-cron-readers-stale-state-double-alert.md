# DP.FM.609 — Гонка двух конкурентных читателей-писателей одного state-файла

## Тезис и механизм ошибки

RunAtLoad и часовой таймер launchd сработали близко по времени. Каждый прочитал одно и то же, ещё не обновлённое состояние («96 unresolved») и каждый отправил одинаковый telegram-алерт — `send_alert()` не имела идемпотентности вообще. Проверка «уже алертили?» непосредственно перед записью не закрывает гонку: оба конкурентных процесса успевают пройти эту проверку, пока ни один ещё не записал новое состояние.

## Фикс

Лок на всю транзакцию целиком (read state → decide → send → write state), а не отдельная проверка дедупа перед записью. Дополнительно — составной ключ дедупа `hash(delta_ids) + age-bucket(возраст // 7 дней)`, чтобы та же композиция непогашенных элементов, пересекающая недельную границу SLA-возраста, всё равно алертила повторно, а не оставалась задушенной навсегда одноразовым дедупом.

## Вариант: пара begin/finish и неблокирующий лок

Та же гонка встречается в паре вызовов begin/finish одного прогона над общим state.json (WP-530 Ф154, `scripts/mac-canon-sync-backstop.sh`; блокер B1 код-ревью Kimi+Grok). Два уточнения к фиксу:

- **Неблокирующий захват.** `LOCK_EX|LOCK_NB` берётся до первого чтения и держится на всё read → observe → write в обоих вызовах. Конкурентный вызов сразу получает явную ошибку (`state_transaction_busy`) до любых чтений и записей, а не ждёт и не гоняется молча.
- **Идентичность прогона.** Повторный finish с тем же `run_id` после завершения отклоняется отдельной проверкой (`outcome != "running"` → `run_identity_mismatch`): лок защищает от одновременности, но не от повтора после завершения.

Проверка: поведенческий тест с отдельными процессами begin/finish при занятом замке — оба файла состояния остаются неизменными. Источник: git commit `2634a7a60` в MC-sessions; захват `DS-my-strategy/inbox/captures/2026-10.md:6811`.

## Границы

Отличие от уже формализованного метода «дедуп через файл состояния + явное сообщение о восстановлении» — там лечился повтор ОДНОГО И ТОГО ЖЕ источника по времени (проба каждые 5 минут, тот же процесс). Здесь — гонка ДВУХ конкурентных читателей-писателей одного state-файла (два разных триггера launchd). Отличие от `DP.FM.436` (одновременные отказы кронов = сигнал проверить общую причину вроде rate limit) — там задания независимо ПАДАЮТ от внешнего лимита; здесь задания УСПЕШНО выполняются, но гонка за общим state-файлом даёт дублирующийся побочный эффект (двойной алерт), а не отказ.

## Проверка

Синтетический прогон с двумя почти одновременными вызовами (RunAtLoad + таймер, разнесённые на миллисекунды) на одном и том же устаревшем состоянии должен давать ровно один исходящий алерт, а не два. Отдельно — элемент, пересекающий недельную границу age-bucket, обязан алертить повторно, а не блокироваться прежним дедупом навсегда.
