# DP.FM.611 — Platform-specific divergence date-парсера переворачивает эффект на мусорном вводе

## Тезис и механизм ошибки

`intent-gate-check.sh` вычислял возраст заявленного намерения (`declared_at`) через `date`, не проверив сначала формат входной строки. Один и тот же нечитаемый/мусорный ввод даёт на двух реализациях `date` не просто разный, а ПРОТИВОПОЛОЖНЫЙ по эффекту на безопасность результат:
- GNU `date -d ""` молча возвращает «сегодня 00:00 UTC» (успех, не ошибка) → на Linux мусорный `declared_at` читается как «объявлено только что» — гейт обходится.
- BSD `date -j -f` на том же вводе завершается ошибкой → на macOS тот же мусорный ввод читается как «бесконечно устарело» — гейт блокирует навсегда.

## Фикс

Валидировать формат `declared_at` как ISO-8601 явной проверкой ДО передачи в `date`; на плохом формате выдавать отдельную явную причину отказа, а не доверять числу, вычисленному `date` из невалидной строки.

## Диагностический принцип

Когда разные реализации одной и той же стандартной команды обрабатывают невалидный ввод не единообразно (одна — ошибкой, другая — тихим «успехом» с произвольным значением), последствие расходится не только по форме, но и по НАПРАВЛЕНИЮ эффекта там, где результат команды питает решение gate/security-логики (bypass на одной платформе, permanent-block на другой).

## Границы

Отличается от `DP.FM.201` (BSD sed vs GNU sed, `&` в replacement) — там расхождение в ФОРМЕ результата одной благополучно выполнившейся операции; здесь — расхождение в том, считать ли операцию вообще успешной, с противоположным эффектом для security-решения.

## Проверка

«Разные реализации одной стандартной команды дают разный по НАПРАВЛЕНИЮ эффект (успех/ошибка), а не только разный формат, на одном и том же невалидном вводе, питающем security-решение?» Да → валидировать формат до парсинга; тест обязан прогнать пустую и мусорную строку на обеих платформах (или на эмулированных exit-кодах обеих реализаций).
