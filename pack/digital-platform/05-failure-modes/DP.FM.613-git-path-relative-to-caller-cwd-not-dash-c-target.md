# DP.FM.613 — `--git-path` резолвится по cwd вызывающего, не по `-C`-таргету

## Симптом

Скрипт раннего предупреждения о хронически грязном canon искал файл-маркер через `git -C "$REPO" rev-parse --git-path <имя>`, ожидая путь относительно `$REPO`. Из интерактивной сессии внутри самого репозитория это случайно работало (cwd совпадал с `$REPO`). Из любого вызова не из каталога репозитория (cron, systemd без `WorkingDirectory=`, любой другой cwd) путь резолвился в несуществующий относительный путь и молча читался как «маркера нет» — детектор сообщал «всё здорово» вместо реальной ошибки. Обнаружено только живым тестом на tsekh-1.

## Причина

`-C <dir>` у git влияет не на все относительные пути, которые печатают его подкоманды. `--git-path` конкретно остаётся завязан на cwd вызывающего процесса, а не на таргет `-C`. Скрипт, предназначенный для cron/systemd/произвольного cwd, должен об этом явно знать — иначе расхождение не проявляется при обычном ручном тестовом запуске из интерактивной сессии разработчика.

## Исправление

`--absolute-git-dir` (резолвится предсказуемо независимо от cwd) + ручная склейка имени файла-маркера, вместо `--git-path`.

## Тест обнаружения

«Скрипт вызывает `git -C <dir> ...--git-path...` (или любую `--git-*`-подкоманду, печатающую путь) и может быть запущен НЕ из каталога `<dir>` (cron, systemd, другой cwd)?» Да на оба → риск: путь резолвится относительно cwd вызывающего, не `<dir>`, и несуществующий относительный путь молча читается как «состояние отсутствует», а не как ошибка резолвинга.
