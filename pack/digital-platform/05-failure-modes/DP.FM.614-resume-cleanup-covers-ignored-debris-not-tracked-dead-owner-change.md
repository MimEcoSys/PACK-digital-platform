# DP.FM.614 — Резюме-очистка не покрывала трекаемый мусор мёртвого владельца

## Симптом

`night-cycle-runner.sh` на резюме после мёртвого владельца чистил только gitignored-мусор (`scripts/__pycache__/`, `*.lock`) через `clean_day_open_ignored_debris()`. Незакоммиченное изменение ТРЕКАЕМОГО файла (например, `git rm` на середине прерванного пайплайна), оставленное мёртвым процессом, не покрывалось ничем. Проверка «worktree чист» отказывала навсегда на резюме — автоматическое открытие дня блокировалось два подряд цикла.

## Причина

Функция очистки резюме была спроектирована под один класс мусора (gitignored-артефакты), и это неявно стало границей «весь мусор, который нужно чистить». Трекаемый незакоммиченный след мёртвого процесса — другой класс (меняет состояние worktree относительно HEAD, а не просто добавляет лишние файлы вне git) — остался за периметром функции. Тот же класс инцидента фиксировался 27.08 и не сдвинулся 47 дней — обнаружение одного конкретного проявления не привело к пересмотру границы функции очистки.

## Исправление

`git reset --hard HEAD` на резюме-пути — но не безусловный: добавлена та же защита, что уже используется в `session-guard.sh` для его собственных деструктивных resets (путь строго под `.iwe-runtime/isolated-worktrees/`, `git-dir` ≠ `common-dir`), и отбрасываемый diff сначала пишется в stderr. Независимое ревью субагентом (2 раунда) до коммита.

## Тест обнаружения

«Функция очистки на резюме перечисляет КОНКРЕТНЫЕ классы мусора (gitignored-паттерны, временные файлы) или проверяет ОБЩЕЕ условие "worktree == HEAD"?» Первое — риск того, что следующий класс мусора (трекаемое изменение, не только gitignored) останется за периметром до отдельного инцидента.

## Переносимый принцип

Очистка состояния после мёртвого владельца, спроектированная под один наблюдаемый класс мусора, не покрывает автоматически другие классы (трекаемое vs gitignored) — граница функции очистки должна быть по ОБЩЕМУ инварианту («дерево чистое относительно HEAD»), а не по перечислению конкретных паттернов, если цель — разблокировать резюме при ЛЮБОМ оставленном мёртвым владельцем состоянии, а не только при уже виденных.
