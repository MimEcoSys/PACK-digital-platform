# DP.FM.616 — Разные потребители одного поля дефолтят отсутствие по-разному

## Тезис и механизм ошибки

Два скрипта одного конвейера (`gather-session-facts.sh`, `session-ledger-append.sh`) читают одно и то же поле `wp` и по-разному сворачивают его отсутствие: один — в пустую строку `""`, другой — в строку `"unknown"`. Вызывающий код, буквально передавший строку `"unknown"` вместо `null`, не распознаётся как «пусто» ни одним из двух guard'ов (`[[ -z "$WP" ]]` ловит только `""`) — задача проходит молча, без диагностики.

## Признаки

- Задача/запись зависает без ошибки там, где ожидалась явная диагностика отсутствующего поля.
- Разные скрипты одного pipeline используют разные literal-дефолты (`""`, `"unknown"`, `"null"`) для одного и того же отсутствующего значения.
- Guard на пустоту (`-z`, `== null` и т.п.) написан под один конкретный дефолт, не под весь класс представлений.

## Диагностика

Проверить все точки конвейера, читающие одно поле: совпадает ли дефолт «отсутствует» у каждого потребителя? Если нет — любое значение, буквально равное дефолту ОДНОГО потребителя, пройдёт мимо guard'а ДРУГОГО.

## Митигация

Нормализовать множество представлений пустоты (`null`, `""`, `"null"`, `"unknown"`, case-insensitive) в один канонический JSON `null` один раз, в одной точке, до разветвления на обработчики. Любая другая нераспознанная строка — явная ошибка, не угадывание.

## Тест обнаружения

«У всех потребителей одного поля один и тот же набор literal-представлений "отсутствует"?» Нет → потенциальный DP.FM.616.

## Отличие от смежного

- `DP.FM.040` (Silent-Null Parser on Unknown Syntax) — силентный null на уровне ОДНОГО парсера, не распознавшего синтаксис. Здесь ни один компонент не «ошибается» в одиночку — расходятся дефолты МЕЖДУ несколькими корректно работающими потребителями.
- `DP.FM.038` (Silent-Pass Validator on Missing Input) — силентный pass валидатора на пустом/отсутствующем входе. Родственный «silent-fail»-класс, но не про межкомпонентное расхождение представлений одного и того же отсутствия.
