# DP.FM.619 — Долгоживущий PR против среза релиза: три красных проверки, один корень

## Симптом

PR #1202 стоял одновременно с конфликтом и тремя красными проверками: (1) конфликт в CHANGELOG.md — независимые дописывания разных PR в одну точку; (2) просроченный сгенерированный манифест (`update-manifest.json`), не перегенерированный после чужих мерджей на main; (3) запись журнала изменений без номера PR и под заголовком уже датированного релиза, а не под `[Unreleased]` (гейт `check-changelog-entry.sh` требует запись именно там).

## Причина

PR открыт до среза релиза v0.41.8; пока он стоял, main ушёл вперёд — релиз переименовал секцию `[Unreleased]` в датированную `[0.41.8]` и завёл новую пустую `[Unreleased]`, поэтому запись PR при будущем мердже оказалась бы внутри уже выпущенного релиза; параллельные PR дописывали в ту же точку CHANGELOG (конфликт); сгенерированный артефакт устарел относительно main. Три проверки выглядят как три разных дефекта, но чинятся одним порядком — все три являются проявлениями одного отставания от main.

## Противодействие

Единый порядок разморозки долгоживущего PR в репозитории с автосрезом релизов: слить main → перегенерировать производные артефакты (манифест) → перенести запись журнала изменений под текущий `[Unreleased]` с номером PR → прогнать тесты и валидатор локально → пушить.

## Тест обнаружения

«PR стоит дольше, чем прошло срезов релиза с момента его создания, и красных проверок больше одной одновременно?» Да → диагностика начинается с подсчёта отставания от main (сколько релизов срезано с момента ветвления), а не с разбора каждой красной проверки по отдельности.

## Дополнение 20.11.2026: черновик PR, когда пересобирать манифест и кто снимает конфликт

Механизм тот же (сгенерированный `update-manifest.json` устаревает после чужих слияний в main), но без среза релиза: PR отстаёт от main, пока висит черновиком.

**Случай 10.11.2026** (время по git, пояс +02:00; в DP.M.637 запуск проверок этого PR указан по UTC). PR #1518 в FMT-exocortex-template (навык подбора метода, РП-608 Ф11) висел черновиком. Первая пересборка манифеста после rebase на main была в 15:09 (коммит `f671e558`, в main не попал). Пока PR висел, в main влили #1519 (15:32) и #1520 (16:24); ветку снова переставили на main и манифест пересобрали ещё раз (коммит `f8d8ea6a`: автор 15:09, записан в 16:55, уже содержит #1519 и #1520). После него в main влили #1521 (17:11), он тоже менял `update-manifest.json`, и манифест разошёлся снова. Конфликт сняли слиянием main в ветку PR (коммит `e4c47a77`, 18:55) тем же заходом, что вписал в журнал изменений код результата Ц49-12; PR влит в 19:16 (`172ebcd8`).

Уточнение порядка разморозки для черновика PR:

1. **Когда пересобирать.** Сгенерированный манифест черновика пересобирают на свежей main в момент снятия черновика или перед слиянием. Пересборка после каждого чужого слияния устаревает до следующего.
2. **Кто снимает конфликт.** Тот, кто вносит последний недостающий элемент PR (в случае 10.11 это код результата), одним заходом: слияние main в ветку или rebase, пересборка манифеста, пуш.
3. **Когда «готов к слиянию».** Случай, когда готовность объявляют по локальному прогону вместо проверок на самом PR, описывает `VR.FM.006` (дополнение 03.11.2026: ревью и локальные проверки не заменяют серверные условия). 10.11 PR #1518 открыли без ожидания проверок, конфликт нашёл пилот (`MC-sessions/2026-11/10/2026-11-10-09-wp608-phases-actualize-581/report.md`, раздел 6).
