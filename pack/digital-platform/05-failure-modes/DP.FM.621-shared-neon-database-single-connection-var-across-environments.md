# DP.FM.621 — «Применено на пилоте, не на проде» не доказано без проверки физической изоляции баз

## Тезис и механизм ошибки

План переноса pilot-only правок в production строился на предположении «миграции 047/048 применены только на базе пилотного бота». Холодное ревью без контекста сессии (независимый субагент) нашло: обе миграции подключаются через `REWARDS_URL` — отдельную Neon-базу `rewards`, общую для pilot и production (та же архитектура, что у других сервисных Neon-баз бота: одна база на сервис, не на окружение). Они уже фактически применены в production. Единственная миграция, завязанная на собственную (разную у pilot/prod) `DATABASE_URL`, оказалась третьей (049).

## Признаки

- Предположение об изоляции окружений не проверено явным запросом «какая переменная подключения у этой миграции и сколько окружений её читают».
- Переменная подключения именована по сервису (`REWARDS_URL`), а не по окружению (`PILOT_DATABASE_URL` / `PROD_DATABASE_URL`).
- Несколько сервисных Neon-баз в этой системе исторически устроены «одна база на сервис», что ломает интуицию «своя база у каждого окружения» по умолчанию.

## Диагностика

Для каждой миграции/правки спросить: «через какую переменную подключения она идёт, и сколько окружений (pilot, production, …) физически читают эту же переменную?» Если переменная одна на несколько окружений — изоляции нет, независимо от того, что по коду/документации «предполагалось» разделение.

## Митигация

Безопасный откат миграции, завязанной на окруженно-специфичную `DATABASE_URL` (здесь — 049), требует дождаться опустевшей очереди недоставленных событий — иначе откат кода молча теряет уже оплаченное через Telegram событие.

## Тест обнаружения

«Доказано ли, что окружение A и окружение B читают физически разные базы для данной миграции — проверкой имени переменной подключения, а не по умолчанию из общей архитектурной интуиции?» Нет → потенциальный DP.FM.621.
