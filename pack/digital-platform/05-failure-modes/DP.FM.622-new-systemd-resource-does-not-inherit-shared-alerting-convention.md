# DP.FM.622 — Новый systemd-ресурс не наследует общую алертинг-конвенцию файла

## Паттерн

Инфраструктурный файл конвенционально даёт всем своим сервисам/таймерам общий `unitConfig` с хуком `OnFailure`-алерта (например, в Telegram). Новый ресурс (сервис/таймер/job), добавленный в тот же файл, не ссылается на этот общий конфиг автоматически — конвенция не применяется сама, её нужно явно подключить. Снаружи сбой нового ресурса выглядит не как ошибка с сигналом, а как молчаливо устаревшие данные.

## Следствие

- Сбой нового сервиса не детектируется через существующий алертинг-канал
- Внешний симптом («панель показывает старые данные») не указывает на причину
- Обнаруживается только холодным ревью после выкладки или случайным наблюдением пилота

## Условия возникновения

1. Инфраструктурный файл содержит общую конвенцию (`unitConfig`/`commonUnitConfig`) для алертинга, применяемую большинством, но не всеми ресурсами автоматически (не наследуется по умолчанию)
2. Новый ресурс добавлен без явной сверки с конвенцией файла
3. Отказ нового ресурса не покрыт никаким другим мониторингом

## Тест обнаружения

«Новый сервис/таймер в файле со значимым числом (`N из M`) ресурсов, использующих общий alerting-config — явно ссылается на этот общий config?» Нет → риск: сбой будет молчаливым.

## Профилактика

При добавлении нового ресурса в инфраструктурный файл с общей конвенцией алертинга/мониторинга — явно сверять, что новый ресурс подключает общий конфиг, не полагаясь на то, что конвенция применится сама. Холодное ревью после выкладки (не вместо проверки при добавлении) — рабочая, но не единственная страховка.

## Прецедент

Холодное ревью нашло пропуск уже после выкладки нового таймера `iwe-wp-panel-snapshot` (WP-494): 30 из 38 сервисов файла используют общий `unitConfig` с хуком `OnFailure`-алерта в Telegram, новый сервис его не унаследовал.
