# DP.FM.627 — `git reset --soft/--mixed` незаметно страндит worktree на старом снэпшоте

## Тезис и механизм ошибки

`git reset --soft` и `git reset --mixed` переставляют HEAD (и, для `--mixed`, индекс) на целевой коммит, но не гарантируют, что содержимое working tree соответствует этой цели — в отличие от `--hard`, они не отбрасывают tracked-изменения напрямую. Возможна ситуация, когда HEAD и индекс уже указывают на цель (например, `origin/main`), `git status` сравнивает именно их и честно репортует «0 ahead/0 behind», а реальные файлы на диске остаются снэпшотом из прошлого — визуально неотличимым от «чисто» ни по `git status`, ни по поверхностному `ls`.

## Диагностический принцип

Проверка вида «`git status` чист → working tree соответствует HEAD» ложна именно для `--soft`/`--mixed` reset: эти команды гарантируют согласованность HEAD/индекса с целью, но не working tree. Расхождение обнаруживается не через git-метаданные, а только через прямое сравнение содержимого файлов (хеш/diff) с ожидаемым состоянием.

## Проверка

«После `reset --soft`/`--mixed` на цель, отличную от предыдущего HEAD, проверено ли содержимое файлов (не только `git status`/`ls`), что working tree действительно соответствует цели?» Нет → риск воспроизвести DP.FM.627.

## Границы

Применимо только к `--soft`/`--mixed` reset на цель, отличную от текущего HEAD. Не относится к `--hard` (working tree принудительно синхронизируется с целью) и не описывает сам инцидент перезаписи канонического чекаута — только диагностический разрыв между «git-метаданные чисты» и «файлы актуальны».

## Связи

- `DP.FM.628` — тот же инцидент-кластер (canon sync review 2026-10-15), другой механизм: там ложно блокируется коммит из-за worktree чужого репозитория, здесь — снэпшот молча устаревает после reset.
- Источник: WP-530/WP-561, tsekh-mac sync review 2026-10-15. Фикс: destructive-guard разрешает такой reset только если цель уже содержит HEAD, либо worktree уже побайтово совпадает с целью; иначе — через `canon-reconcile-published.sh`.

## Второй пример

Тот же механизм подтверждён независимым живым инцидентом того же дня (WP-484 Ф189, сессия канонического рассинхрона Мак↔Цех): агент выполнил `git reset --mixed` для выравнивания указателя канонического чекаута на состояние сервера. HEAD совпал с `origin` (дата актуальная), но рабочее дерево осталось на снимке на 4 дня старее — около 189 файлов выглядели как «незакоммиченные правки». Поверхностная проверка результата (только по тому, что HEAD/индекс совпали с ожидаемым указателем) не отличила это от обычных незакоммиченных изменений; следующий `git commit -a` закрепил бы откат рабочего дерева как новую, настоящую правку, скрыв инцидент внутри обычной истории. DP.FM.623 (прикладной случай этого же механизма, без отдельной карточки) — предложенный фикс там: гейт на `git reset --soft/--mixed` должен блокировать такой reset на нелинейную (не предок) цель, если файлы на диске ещё не приведены в соответствие с целью.
