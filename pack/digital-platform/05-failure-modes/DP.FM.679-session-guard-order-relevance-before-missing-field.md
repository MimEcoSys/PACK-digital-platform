# DP.FM.679 — Порядок проверок охранника: релевантность записи раньше трактовки отсутствующего поля

## Тезис и механизм ошибки

После закрытия семафора без поля `host` проверка хоста не отличала «поля нет» от «поле продублировано» и навсегда блокировала новый `open`, даже для несвязанной работы. Очевидная починка («host отсутствует → всегда пропустить») оказалась дырой с другой стороны: запись, совпадающая по `wp` И `slug` с новым запросом, но без `host`, под слепым `continue` давала бы повторное открытие уже закрытой или уже открытой работы — именно ту двойную запись, от которой охранник существует.

## Исправление

Порядок проверок переставлен: блок wp/slug — раньше, host/agent — после.
- wp/slug не совпали → запись нерелевантна, host не смотрится вовсе.
- wp/slug совпали (это та же заявленная работа):
  - host отсутствует → явный отказ «принадлежность неопределена» (не continue и не тихий успех);
  - host есть и другой → пропуск (разные хосты штатно держат свои записи под одним wp/slug);
  - host продублирован → отказ, как и раньше.

## Диагностический принцип

У охранника над записями с необязательными атрибутами порядок проверок — часть контракта, не деталь реализации: «поле отсутствует» разрешается по-разному для релевантной и для нерелевантной записи. Упрощающее предложение («просто всегда continue/always deny при отсутствии поля») нужно проверять именно на записи, совпавшей по ключевым полям, а не на общем случае.

## Проверка

«Для записи, совпадающей по wp и slug с текущим запросом, но без host — какое решение принимает охранник?» Если ответ совпадает с ответом для записи, НЕ совпадающей по wp/slug, — порядок проверок не учитывает релевантность, риск DP.FM.679.
