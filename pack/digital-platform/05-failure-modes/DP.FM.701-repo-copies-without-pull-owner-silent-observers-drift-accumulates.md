# DP.FM.701 — Копии репозиториев без владельца подтягивания

## Симптом

Исправление хука лежало в origin сутки и не доехало до Мака, потому что корень Мака никто не подтягивал. Зеркало панели РП стояло с 3 сентября по 29 октября (позади на 1495 коммитов) из-за отсутствия одной утилиты и немых наблюдателей. Pull-on-Touch исполнялся буквально, но синхронизацией никогда не был: он подтягивает репозиторий при первом касании сессии, а не поддерживает сходимость хостов.

## Механизм

1. За подтягивание копий на хосте никто не отвечает: ни у какого репозитория нет назначенного владельца.
2. Наблюдатели, которые могли бы заметить отставание, молчат (тревога уходила в карантин мессенджера: скрипт не в списке допуска) или падают (нет утилиты), а отсутствие тревоги читается как «всё в порядке».
3. Каждая единичная поломка выглядит отдельным багом, поэтому чинится отдельно, а причина первого порядка остаётся.

## Модель состояния копии (для наблюдателя)

Состояние копии описывают тремя независимыми полями плюс полнотой обхода, иначе наблюдатель смешивает разные вещи:

| Поле | Что отвечает | Чем нельзя заменить |
|------|--------------|---------------------|
| Отношение к upstream | впереди / позади / разошлись, по известной ссылке, без сети | свежестью |
| Подтверждённая свежесть | возраст последнего успешного получения этой ветки; нет подтверждения = «неизвестно» | датой коммита ссылки |
| Блокировка | причина и возраст | отставанием |

Полнота обхода: сколько репозиториев вообще осмотрено. Дата коммита, на который указывает ссылка, это не момент последней проверки сервера (смежно: DP.D.190). «Свежесть неизвестна» не равна «отстаёт» (смежно: DP.D.331). Модель проверена тестом сводки на 9 репозиториях в разных состояниях и разовым живым прогоном на обоих хостах; суточная приёмка на обоих хостах на момент записи не проведена.

## Направление лечения (не проверено практикой)

Порядок, принятый в разборе: видимость (состояние каждой копии видно пилоту, тревога доходит), реестр и канон, перемотка читательских копий только под общим замком «синхронизатор, старт сессии, писатели» с перепроверкой условий под замком, уборка по доказательствам сохранности. Фазы этого лечения на момент записи не приняты, поэтому порядок остаётся предложением. Отклонённые альтернативы (автоотбрасывание патч-эквивалентных коммитов, уборка по возрасту, принудительная перемотка по сроку, перемотка по «двум сигналам» без замка) вынесены в отложенное правило агентов; опора: VR.FM.023 (patch-id ломается под дрейфом), AR.296.

### Условия перемотки читательской копии (реализовано 03.11.2026)

Дополнение 2026-11-10 (РП-170, отчёт 2026-11-09-inbox-check-2, кандидат 3). Коммит `6f2dde6` в iwe-local-config (WP-539 Ф21) реализует на Маке часть порядка выше. Исходная причина в этом случае: паки, FPF, SPF, ZP и два репозитория только для чтения не имели исполнителя обновления, и хуки стиля читали правила с отставанием до 31 коммита. Теперь у каждой копии в реестре есть роль на своём хосте (читательская, служебная, рабочая), а у каждой роли — исполнитель обновления.

Читательская копия перематывается только по ff-only. Если выполняется хотя бы одно условие ниже, копия получает BLOCKED и не меняется:

- копия не на своей ветке;
- в рабочем дереве или индексе есть правки;
- есть свои коммиты, которых нет в upstream;
- не завершена операция git (слияние, перебазирование и подобные);
- есть скрытые правки (так в источнике, состав не раскрыт; например, пути с `skip-worktree` из DP.FM.581 или stash);
- есть игнорируемые файлы, которые перемотка заменила бы.

Последнее условие неочевидно. Допустим, upstream начал отслеживать файл, который в копии лежит как игнорируемый. По умолчанию `git merge --ff-only` и `git pull --ff-only` молча перезапишут его (код возврата 0), а `git status --porcelain` такой файл не показывает, так что проверка «дерево чистое» его не заметит. С `git merge --ff-only --no-overwrite-ignore` перемотка вместо этого прерывается с ошибкой, и локальный файл остаётся. Воспроизведено во временном репозитории на git 2.50.1 (10.11.2026); у `git pull` в этой версии флага `--no-overwrite-ignore` нет (неизвестная опция), поэтому защищённая перемотка — это `git fetch` и затем `git merge --ff-only --no-overwrite-ignore`. Тот же риск есть у любого `pull --ff-only` в копии с локальными игнорируемыми файлами, например у шага синхронизации DP.M.425.

BLOCKED заполняет поле «Блокировка» модели состояния выше, поэтому причина видна наблюдателю, а не теряется в молчаливом пропуске. Идёт ли перемотка под общим замком из порядка лечения, источник не сообщает. Влияние на дрейф на момент записи не подтверждено.

## Тест обнаружения

«У каждой копии репозитория на каждом хосте есть названный владелец подтягивания, и что произойдёт с его тревогой, если отправитель сломан?» Нет владельца или тревога не доходит до человека → сбой активен.

## Границы

Диагноз опирается на один разбор двух хостов; число репозиториев и отставание взяты из отчёта сессии. Формулировка исходной записи «два месяца» заменена точной датой: зеркало панели отставало с 3 сентября.
