# DP.FM.704 — Допуск по изменяемому нику

## Симптом

Пилот перечислил избранных пользователей Telegram-никами. Пока ник у владельца, всё работает. Если владелец сменил ник, а другой человек занял освободившийся, этот человек проходит по списку без ведома пилота.

## Механизм

1. Список допуска хранит псевдоним, а не идентификатор человека.
2. Ник изменяем и после освобождения переиспользуем.
3. Проверка сверяет строку, поэтому «тот же ник» не означает «тот же человек».

Семейство «идентичность по изменяемому имени» в базе уже есть в другом направлении: DP.FM.606 (список по имени перестал покрывать после переименования, дыра охвата) и DP.M.484 (устойчивая метка не равна имени и хэшу). Здесь вектор захвата личности; DP.FM.512 про чужое поле другого типа и не дубль.

## Лечение

При первом входе записать пару «ник → числовой идентификатор». Дальше проверять только числовой идентификатор; при занятом нике с другим идентификатором отказывать. В журналах хранить идентификатор в защищённом виде, как личные данные.

## Граница

Пока избранный не вошёл ни разу, ник не закреплён и окно перехвата открыто: первым войти может тот, кто занял ник. Если это важно, сопоставить ник и идентификатор вручную до первого входа.

## Тест обнаружения

«Список допуска сверяет поле, которое владелец может сменить или освободить?» Да → риск этого сбоя.
