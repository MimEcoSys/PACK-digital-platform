# DP.FM.706 — `git -C` в каталоге без репозитория проверяет родителя

## Симптом

При уборке пустых каталогов публикации проверка «каталог чист» строилась на `git -C <каталог>`. Для вложенного каталога, не являющегося репозиторием, git не сообщает об ошибке: он поднимается к ближайшему родительскому репозиторию (корню) и отвечает про него. Первая версия проверки вернула «222 чистых», и этот вердикт относился к корню, а не к проверяемым каталогам. Число 222 — результат ошибочной проверки; о числе реально пустых каталогов оно ничего не говорит (в контексте capture упоминается 164 каталога уборки).

## Механизм

1. Проверяемый каталог лежит внутри другого репозитория, но своего `.git` не имеет.
2. `git -C <каталог>` ищет репозиторий вверх по дереву и находит родительский.
3. Вердикт (например, «чисто») получен про родительский репозиторий, но читается как вердикт про каталог.

## Почему опасно

Вердикт выглядит валидным (чистый вывод, без ошибки), а следом идёт необратимое удаление. Расхождение видно только при сверке с содержимым.

## Лечение

1. Перед необратимым удалением пересчитать вердикт по содержимому (список файлов в каталоге).
2. Если нужен именно вердикт git, сначала сравнить `git -C <каталог> rev-parse --show-toplevel` с самим каталогом.

## Граница

Один случай. Поймано до удаления пересчётом по содержимому, потерь не было. Карточка фиксирует класс ошибки, а не частоту.

## Тест обнаружения

«Вердикт git о каталоге получен для каталога, у которого нет собственного `.git`, и за ним идёт необратимое действие?» Да → вердикт может относиться к родителю.

## Отличие от соседей

DP.FM.613 — другая причина: путь `--git-path` читается от текущего каталога, а не от `-C`. Здесь `git -C` работает как задумано, но в каталоге без репозитория молча берёт родителя.
