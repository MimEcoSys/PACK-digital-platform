# DP.FM.712 — Маркер незавершённого обновления от постоянной причины блокирует потребителя

## Симптом

По описанию коммитов 6d9ad4ff и 0dcae3e6, маркер `.update-incomplete`, оставленный прогоном обновления 22.10, блокировал утреннего Стратега 10 дней. В источнике: `cp` в каталог-зеркало только для чтения прерывал обновление и оставлял маркер.

## Механизм

1. Скрипт обновления оставляет маркер при сбое шага.
2. Другой агент (Стратег) блокируется на этом маркере. Это взято из текста коммитов; код чтения маркера Стратегом не проверялся, поэтому формулировка осторожная.
3. Причина сбоя не событие одного прогона, а постоянное свойство хоста: запись в зеркало только для чтения завершается ошибкой каждый раз. Второй случай из тех же коммитов (режим автора, где у файла нет базы для слияния) приведён по их описанию.
4. Каждый следующий прогон повторяет ошибку, а маркер, по замыслу, снимается успешным прогоном, которого на этом хосте не бывает.
5. Сбой выглядит как неисправность потребителя, а не обновления, пока никто не прочитал вывод обновления.

## Почему опасно

Маркер защищает от реального риска (работа на полуобновлённой установке), поэтому его не хочется ослаблять. Но он не отличает «прогон прервался» от «на этом хосте шаг невыполним всегда». Во втором случае защита превращается в бессрочную блокировку постороннего процесса. По описанию коммитов, блокировка длилась 10 дней.

## Лечение (направление из коммитов)

- Отделять известные постоянные состояния хоста от сбоя прогона: для них один раз предупреждать и не ставить маркер.
- Разрешать такой пропуск только в режиме, где состояние ожидаемо (режим автора); в других режимах ошибка остаётся жёсткой.
- Регрессионная проверка: два прогона подряд на хосте с постоянным условием — маркера нет, потребитель не блокируется.

## Тест обнаружения

«Маркер незавершённости блокирует другой процесс и снимается только успешным прогоном. Может ли причина сбоя быть постоянной для этого хоста?» Да → блокировка бессрочна, пока человек не заметит. Второй признак: один маркер переживает несколько плановых прогонов подряд.

## Отличие от соседей

- AS.FM.139 — там маркер попытки намеренно не снимается по замыслу; здесь он остаётся из-за постоянной причины сбоя, постоянная причина и есть дефект.
- DP.METHOD.134 — отложенный выход ради доставки остальных компонентов; о маркере и его потребителях там ничего нет.
- AS.FM.098 — неоднозначность одного семафора превращается в глобальный отказ, другая причина.
- DP.FM.674 — временная мера без владельца становится постоянной.

## Второй носитель: исход «ждать» для ссылки, которая не может появиться, блокирует хвост очереди (дополнение 2026-11-11, РП-170, отчёт 2026-11-11-inbox-check-5, кандидат 5)

**Случай (WP-561 Ф58, 06.11.2026).** Мост событий плана решает по каждому запросу пакета: принять, отклонить или «ждать». Запрос, ссылающийся на родительскую запись, получал незавершающий исход «ждать», пока родитель не принят. Очередь обрабатывается по порядку, поэтому ждущий запрос держал за собой все следующие. Если родителя нет ни в опубликованном плане, ни раньше в том же пакете, он не появится никогда: всё, что было до пакета, уже опубликовано, а у очереди один вход. Одна ошибочная ссылка останавливала очередь навсегда (зафиксировано разбором DR-06 как дефект до исправления).

**Тот же механизм, что у маркера.** Как и маркер незавершённого обновления выше, исход «ждать» рассчитан на временное условие и снимается только событием, которое при постоянной причине не наступит. Разница носителя: блокируется не посторонний процесс, а хвост упорядоченной очереди того же процесса.

**Лечение (из источника).** Для условия, неразрешимость которого можно доказать по устройству очереди, исход делается окончательным: отказ с причиной `unknown_dependency` и ссылкой на отсутствующего родителя; незавершающий исход «ждать» удалён из допустимых, допустимы только «принят» и «отклонён». Доказательство неразрешимости опирается на два предусловия: всё до пакета опубликовано, и вход у очереди один (другого пути появиться у родителя нет). Без этих предусловий «родителя пока нет» не доказывает «родителя не будет», и окончательный отказ был бы ошибкой.

**Тест.** «Есть ли у упорядоченной очереди незавершающий исход („ждать“, „повторить позже“)? Чем он снимается, и может ли это событие не наступить никогда?» Может → нужен либо доказуемый критерий окончательного отказа, либо срок ожидания с окончательным исходом по его истечении; иначе один запрос держит хвост бессрочно.

## Граница

Прецедентов два разных носителя: маркер обновления (WP-568 Ф11) и исход «ждать» в очереди моста (WP-561 Ф58). Как именно Стратег читает маркер, не сверено с кодом `update.sh` и потребителя.
