# DP.FM.739 — Цикл устаревания по наличию полей: неполная запись становится вечной

## Симптом

Часть записей памяти агента годами остаётся в активном слое, хотя по типу должна была давно уйти в архив. В отчёте цикла понижения эти записи не упоминаются вовсе: ни как понижённые, ни как оставленные.

## Механизм

Цикл понижения сначала отбирает кандидатов по наличию полей жизненного цикла (`horizon`, `valid_from`, `status`), потом решает по их значениям. Запись без полей отсекается на первом шаге. Её не сравнивают с горизонтом, не понижают и не выводят в отчёт. Отсутствие поля молча читается как «срок не наступит никогда». Чем старше и небрежнее запись, тем вероятнее, что полей у неё нет. Поэтому выпадают как раз те записи, которые сильнее всего нуждаются в устаревании.

## Исправление

1. Не исключать запись из цикла за отсутствие полей.
2. Недостающему полю давать значение по умолчанию **по типу записи**. Это должно быть консервативное значение, при котором запись рано или поздно проходит обычный путь устаревания.
3. Перечислять такие записи в отдельном разделе предупреждения отчёта, чтобы неполноту можно было исправить в источнике.

## Граница: какое значение по умолчанию безопасно

Направление умолчания зависит от того, какое действие необратимо:
- Понижение — обратимое перемещение в менее активный слой. Недостающий срок можно заменить умолчанием, и цикл продолжает работать.
- Разрушительное действие (снятие чужого замка, удаление) — другой случай. Недостающие данные там сохраняют защитный отказ (DP.FM.644: возраст записи без PID не даёт права на удаление).

В обоих случаях неполная запись должна быть видна в отчёте, а не исчезать молча.

## Тест (триггер распознавания)

Цикл очистки, архивации или понижения отбирает записи по наличию полей до сравнения их значений? Есть ли записи без этих полей, и упоминаются ли они в отчёте цикла? Если отбор по наличию есть, а в отчёте их нет, неполные записи вечны.
