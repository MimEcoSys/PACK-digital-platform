# DP.FM.763: check-then-act race в access-control адаптерах

## Симптом
Один и тот же класс дефекта найден холодным ревью трижды подряд в трёх файлах одной сессии: раздельные `fetch (проверить) → решить → execute (записать)` вместо одного атомарного SQL. Паттерн повторился даже после того, как первый экземпляр был найден и исправлен — находку не обобщили на остальной код той же сессии.

## Причина
В паузе между чтением и записью параллельный писатель легитимно меняет строку, последующая безусловная запись тихо затирает изменение.

## Почему это дорого
Цена ошибки в access control выше обычного CRUD: тихо затёртое состояние = неправомерная потеря доступа или его выдача.

## Антипаттерн → Паттерн
- **Антипаттерн:** «окно гонки маловероятно».
- **Паттерн:** один атомарный statement — `INSERT … ON CONFLICT … WHERE … RETURNING` / `UPDATE … WHERE … RETURNING`; RETURNING детектирует исход.

## Тест обнаружения
При ревью любого read-model/access-control адаптера с шаблоном «прочитать state → решить → записать» — специально искать разнесение проверки и записи на два запроса.
