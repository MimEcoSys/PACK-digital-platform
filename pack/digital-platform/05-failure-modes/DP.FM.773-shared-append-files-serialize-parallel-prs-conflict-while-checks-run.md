# DP.FM.773 — Общие дописываемые файлы сериализуют параллельные PR

## Симптом

Пока идут 10-минутные проверки запроса на слияние, в основную ветку сливается соседний запрос. Он тоже правил журнал изменений (CHANGELOG) и генерируемый список файлов поставки — отсюда конфликт. Наблюдалось дважды за одну сессию (FMT-exocortex-template #1485 и #1490).

## Механизм

Файл, который обязан править каждый запрос, превращает параллельную работу в очередь: любой слитый соседний запрос делает остальные устаревшими. Дополнительное трение: обязательная проверка журнала требовала номер запроса в записи, а номер известен только после открытия запроса — лишний коммит и повторный прогон проверок.

## Лечение

- Конфликт журнала: сохранить обе записи.
- Генерируемые части (список поставки) — пересобрать генератором, не сливать руками.
- Рассмотреть фрагменты журнала «файл на запрос» (changelog fragments) вместо одного общего файла.

## Отличие от соседей

- DP.FM.619 — отставание давно живущей ветки от основной после среза релиза. Здесь ветка свежая; корень — общий файл, который правит каждый запрос.
- DP.FM.506 — отказ синхронизации при грязном дереве разводит дописываемые артефакты. Здесь отказа синхронизации нет, конфликт создаёт сама параллельность.
- DP.FM.719 — после разрешения конфликта манифеста записи об удалении молча теряются. Поэтому после пересборки списка поставки сверить записи об удалении с обеими ветками.

## Границы

Два наблюдения одного класса в одной сессии, поэтому `trust: low`.
