# DP.FM.774 — Календарная сетка для oneshot: тик сливается с идущим прогоном

**Суть:** срабатывание таймера, пришедшее во время идущего прохода oneshot-службы, не ставит второй проход в очередь, а сливается с текущим. Следующий запуск ждёт следующего шага сетки, и промежуток между проходами превышает границу задержки, хотя шаг сетки меньше границы.

## Различение

**Фиксированная частота ≠ фиксированная пауза.**

- Сетка (`OnCalendar=*:*:00,25,50`) — фиксированная частота. Промежуток до следующего прохода зависит от того, попал ли тик в идущий проход: в худшем случае он равен шагу сетки плюс длина прохода.
- Пауза от конца прохода (`OnUnitInactiveSec=N`) — фиксированная пауза. Промежуток равен длине прохода плюс N, его можно оценить сверху по максимальной измеренной длине прохода.

При границе задержки и проходах переменной длины годится только второе.

## Механизм (прецедент)

```
Граница K14: заявка забирается не позже чем через 30 с.
Сетка: 00, 25, 50 с → «запас 5 с».
Проход: до 17 с (максимум за 7 дней на хосте).
Тик в t=25 приходит, пока идёт проход, начатый с задержкой старта (≥ 8 с при проходе 17 с) → сливается.
Следующий запуск — t=50 → промежуток ~35 с > 30 с.
```

## Лечение

1. `OnUnitInactiveSec=5s`: пауза считается от конца прошлого прохода. Первый запуск задаётся отдельно: `OnActiveSec=5s` / `OnBootSec=30s`.
2. Убрать `OnCalendar` и `Persistent`: второй триггер возвращает слияние.
3. Оценка: максимальный промежуток = max(длина прохода) + пауза; сравнить с границей.
4. Живой таймер хоста и генератор таймера в коде приводятся к одному виду. Тест генератора запрещает `OnCalendar`/`Persistent` и требует ключи неактивности.

## Тест применения

«Может ли тик прийти, пока проход ещё идёт?» Да, и у задачи есть граница задержки → сетка не годится, нужна пауза от конца прохода.

## Ограничения

Один случай (trust: low). Механизм специфичен для systemd, но различение «частота ≠ пауза» переносимо на любой планировщик, который не ставит в очередь повторный запуск идущей задачи.
