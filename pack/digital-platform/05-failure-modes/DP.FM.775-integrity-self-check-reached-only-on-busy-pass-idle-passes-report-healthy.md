# DP.FM.775 — Самопроверка, которую исполняют только рабочие проходы

## Описание

Служба (мост плана) доверяет только коду, совпадающему с опубликованной базой: установленная копия (вендор в репозитории конфигурации сервера) сверяется с main репозитория-источника. При расхождении служба отказывает в доставке (`CODE_NOT_AT_BASE`). Но сверка стоит после проверки «есть ли заявки». Проходы на пустой очереди до неё не доходят и пишут «confirmed».

Правка генератора в репозитории-источнике ушла в main без обновления установленной копии. Расхождение возникло сразу, а журнал оставался зелёным до первой заявки. Доставка стояла около 3 минут.

## Механизм

1. Проверка целостности привязана к рабочему пути, а не к каждому проходу.
2. Признак здоровья («confirmed») пишет каждый проход, включая холостые.
3. Значит, «зелёный журнал» означает «холостой путь жив», а не «рабочий путь жив».
4. Два репозитория проверяют друг друга (копия ↔ источник). Правка одного без другого ломает рабочий путь, и это видно только под нагрузкой.

## Принцип

**Здоровье холостого прохода ≠ здоровье рабочего пути.** Признак здоровья свидетельствует только о коде, который проход действительно исполнил.

## Лечение

1. **Сверку целостности — в каждый проход** или отдельной периодической проверкой, независимой от очереди. Как минимум: после публикации, затрагивающей проверяемый код, смотреть журнал на отказ сверки при непустой очереди (синтетическая заявка).
2. **Правку проверяемого кода выпускать вместе с обновлением установленной копии** (в прецеденте: копия → деплой → публикация исходника в окне 2 мин, иначе заранее названный откат).
3. Сверять по хешам содержимого (объектов), а не по SHA коммитов: cherry-pick меняет SHA при том же содержимом.

## Тест применения

«Какие проверки выполняет проход, когда работы нет?» Если проверка целостности в этот список не входит, а признак здоровья пишется всё равно, — карточка применима.
