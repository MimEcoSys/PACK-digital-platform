# DP.FM.780 — Потолок по остаточному классу задевает неразмеченного потребителя

## Симптом

Перед включением дневного потолка расхода для класса «внутренняя автоматика» проверка на живых данных показала: под подписью «бот + пользователь» прошло около 70 вызовов, а почти весь остальной трафик бота (включая подготовку материалов для дайджестов) шлюз относил к той же «автоматике». Потолок ударил бы по самому боту, а не только по фоновым задачам.

## Механизм

1. Класс «автоматика» определён остаточно — как всё, что идёт без подписи пользователя, а не по источнику вызова.
2. Защищаемый потребитель размечен не полностью: часть его вызовов идёт без подписи.
3. Любое ограничение, наложенное на остаточный класс, обязательно задевает неразмеченные вызовы защищаемого потребителя.

## Лечение (порядок внедрения)

1. Защищаемый потребитель помечает **все** свои вызовы явным признаком (заголовок `X-IWE-Consumer`), не только те, что пришли с подписью пользователя.
2. Потолок ставится только на неразмеченные вызовы, и только после того, как разметка выкачена и покрытие проверено.
3. У защищённого потребителя — свой ключ, не общий с автоматикой (DP.M.201).
4. Изоляцию проверить живым тестом до включения рабочего порога (DP.M.627).

## Диагностика

Перед потолком на класс трафика: как класс определён — по признаку источника или остаточно («всё прочее»)? Какая доля защищаемого потребителя размечена? Посчитать по журналу вызовов, а не по ожиданию.

## Границы

Наблюдение одно (РП-568 Ф12). Признак-заголовок может подделать любой держатель общего пароля шлюза; отдельные пароли на потребителя отложены отдельной работой.

## Связи

- `DP.FM.779` — та же сессия, другой механизм: потолок слеп к стоимости, не попавшей в учёт; здесь — к тому, кого задевает класс.
- `DP.M.201` — отдельный ключ на рабочую нагрузку: шаг 3 лечения.
- `DP.M.627` — живая проверка изоляции ограничителя: шаг 4 лечения.
- `DP.FM.436` — одновременные отказы кронов: смежная тема квот, механизм другой.
