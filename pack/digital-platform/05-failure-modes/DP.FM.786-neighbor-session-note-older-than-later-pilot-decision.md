# DP.FM.786 — Сведения соседней сессии устаревают: записка относительно решений пилота, состояние общего объекта относительно живого

## Симптом

Сессия получает записку от соседней и исполняет её пункты целиком, включая те, что уже отменены более поздним решением пилота.

## Механизм

1. Записка фиксирует состояние на момент написания.
2. Пилот принимает решения после неё, часто в другой сессии.
3. Принимающая сессия читает записку как действующее поручение, не сверяя её время с решениями, принятыми позже.

## Лечение

Перед учётом записки сверить её время с решениями пилота, принятыми после. Пункты, предшествующие более позднему решению, считать устаревшими и не применять. (Вывод, в источнике не проверялся: назвать пилоту, какие пункты отброшены и почему.)

## Диагностика

Когда написана записка и какие решения по тому же предмету приняты после? Если между ними есть решение, каждый пункт записки сверять с ним.

Для второго вида: сведения о состоянии общего объекта (PR, проверки) получены от другой сессии, а не прочитаны сейчас? Да → до действия сверить с живым объектом; разошлись → отправить источнику поправку (Дополнение 20.11.2026).

## Границы

Два вида, по одному случаю каждый: записка относительно более позднего решения пилота (РП-581/РП-608, 09.11) и состояние общего объекта относительно живого (PR #1518, 10.11, см. дополнение). Отличие от устаревшего снимка данных (`DP.FM.100`): там устаревают собственные данные анализа, здесь устаревают сведения, полученные от соседней сессии.

## Дополнение 20.11.2026: второй вид, состояние общего объекта из соседней сессии

Устаревает не только поручение, но и сведения о состоянии общего объекта. 10.11.2026 пилот вставил в сессию, которая вела PR #1518 в FMT-exocortex-template (навык подбора метода, РП-608 Ф11), сообщение сессии РП-529 о конфликте и красных проверках этого PR. Сессия РП-529 видела PR до исправлений, конфликт к этому моменту уже был снят. Сессия, ведущая PR, отправила РП-529 поправку напрямую, чтобы та не начала снимать конфликт второй раз.

Лечение для этого вида:

1. Сверить принесённые сведения с живым состоянием объекта, а не с пересказом: вопрос «сделано ли уже?» отвечается текущим состоянием (тест `DP.D.314`).
2. **Новое:** если сведения разошлись, вернуть поправку сессии-источнику. Иначе она действует по своему снимку, и две сессии чинят одно и то же.
3. **Новое:** назвать владельца объекта. На тот момент было назначено, что код результата в PR подставляет сессия РП-608, а РП-529 PR не трогает; позже код Ц49-12, выданный РП-611, вписан в ветку PR коммитом `e4c47a77`.

Отличие от `DP.FM.100`: там устаревает собственный снимок данных анализа, здесь устаревают сведения, полученные от другой сессии. Шаги 2–3 наблюдались один раз; trust карточки остаётся low.
