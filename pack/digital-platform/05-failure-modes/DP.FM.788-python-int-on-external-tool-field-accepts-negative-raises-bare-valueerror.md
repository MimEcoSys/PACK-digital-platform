# DP.FM.788 — `int(поле)` слишком мягок для чужого вывода и слишком груб при отказе

## Симптом

Разбор заголовка пакетного режима `git cat-file --batch` (`<oid> <type> <size>`) брал размер через `int(fields[2])`. Отрицательный размер проходил и дальше ломал чтение содержимого. Нечисловое поле поднимало голый `ValueError`, и вызывающий код получал исключение вместо понятного статуса.

## Механизм

Python `int()` принимает больше, чем «неотрицательное целое из цифр»: знак (`-5`, `+5`), пробелы по краям, подчёркивания (`1_000`), не-ASCII цифры Юникода. Отказывает он исключением, которое не говорит, что случилось с утилитой. Искажённый или обрезанный вывод внешнего процесса — обычно признак временной проблемы (процесс умер, поток оборван), а не повода для окончательной остановки.

## Тест обнаружения

«Что вернёт разбор, если поле размера равно `-1`, `abc`, `+7`, `١٢` или строка обрезана посередине?» Если хоть один из этих вариантов проходит как число или вылетает необработанным исключением, сбой воспроизводится.

## Противодействие

- Поле размера проверять как строку: только ASCII-цифры (`re.fullmatch(r"[0-9]+", s)`), и только после этого приводить к числу.
- Любой искажённый, обрезанный или неожиданный вывод классифицировать как **повторяемую** ошибку «утилита недоступна» (в исправлении — `GIT_UNAVAILABLE`, `stop=False`), а не как исключение и не как окончательный «стоп».
- Тестами покрыть отрицательный, нечисловой и обрезанный вывод.
