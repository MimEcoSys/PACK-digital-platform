# DP.FM.790 — Статус последнего задания управляет видимостью источника, и единичные сбои прячут его целиком

## Симптом

Источник (~400 файлов) периодически пропадал из поиска knowledge-mcp целиком. В каждом полном прогоне индексации 3–10 файлов падали на временных отказах: 403 от посредника ключа и 520 от базы (Neon). Задание завершалось с ошибкой, источник получал `index_state = 'failed'`, а поиск показывает только `ready`. Пользователь терял доступ ко всем данным источника, хотя 97–99 % файлов были проиндексированы.

## Механизм

Один признак, статус последнего полного задания, отвечает на два разных вопроса:

1. «Прошло ли задание без ошибок?» — вопрос оператора.
2. «Можно ли искать по данным источника?» — вопрос читателя.

Когда эти вопросы склеены, единица отказа (весь источник) оказывается намного крупнее единицы сбоя (один файл). Временные отказы без повтора по файлу превращают обычный сетевой шум в постоянную невидимость.

Второй захват того же инцидента (отчёт 2026-11-16-inbox-check, кандидат #5) добавляет наблюдение: часть ответов 403 приходила примерно на 0,4 с быстрее успешных, и автор записи предположил, что это временный сбой посредника, выданный за отказ в доступе. Это догадка, не проверенный факт; если она верна, временные классы сбоев нужно распознавать не только по коду ответа.

## Тест обнаружения

«Если один файл из N упадёт при индексации, что увидит пользователь поиска?» Если ответ «ничего из источника», видимость привязана к статусу задания.

## Противодействие

- Повтор временных отказов **по файлу**: запрос ключа — 2 повтора с паузой 1 и 2 с, без повтора при неактивной привязке; идемпотентная транзакция записи — повтор при 429/5xx.
- Публиковать источник, если обработан **хотя бы один файл**. Задание остаётся `failed`, сбойные файлы — `error`: оператор видит честный статус, а читатель — доступные данные.
- Видимость не даёт доступа: каждый поиск заново проверяет привязку, поэтому ослабление правила публикации не открывает обход прав.
- Контроль после исправления: полная индексация 402/402 и проба записи во время индексации.

## Отличие от смежного

- DP.FM.487 и DP.FM.505 — один сбой отменяет *запись или доставку* всего набора. Здесь запись частично прошла, но *видимость* уже записанного отключена статусом задания.
- DP.FM.716 — сводный итог скрывает успех частей в *отчёте*. Здесь сводный статус скрывает сами *данные* от читателя.
- DP.FM.499 — нет повтора перед тревогой. Здесь нет повтора перед сменой статуса, который управляет видимостью.
