# DP.FM.803 — Отключение писателя снимает его неявную обязанность

## Механизм отказа

Задание по расписанию совмещает ритм и производство чего-то, что больше нигде не производится. Решение принимают про ритм и отключают задание целиком. Вторая обязанность пропадает вместе с ним, и это может вскрыться только тогда, когда её результат понадобится. Если другой писатель сливает общую запись по полям, поля отключённого писателя сохраняют старые правдоподобные значения, и потеря остаётся скрытой.

## Первый случай: выпуск шаблона

**03.11–10.11.2026, выпуск шаблона (FMT-exocortex-template).** 03.11 владелец отключил `weekly-release.yml`: недельный ритм выпуска отменён, выпуск идёт по решению Выпускающего. По сообщению коммита 26cd9c21, это задание было единственным местом, где ставились метки кандидатов rc, «so 0.42 had no way to get a candidate». В рабочих процессах и скриптах репозитория на коммите до исправления (26cd9c21^) метку кандидата ставит только `weekly-release.yml`; `release.yml` метки кандидатов только читает.

**Что это значило для выпуска.** Проверка тождества «выпуск = кандидат» не могла пройти: сверять было не с чем. В `release.yml` того времени отсутствие кандидата для версии давало только предупреждение «релиз без проверки тождества с кандидатом», и выпуск продолжался. Тестировщикам, которые ставят кандидата (`IWE_UPDATE_CHANNEL=rc`), ставить было нечего.

**Исправление (коммит 26cd9c21, WP-529 Ф251).** Задание переименовано в `release-candidate.yml`, расписание снято, запуск только вручную в двух режимах:
- `cut`: явный снимок основной ветки, подъём версии, ветка `release/vX.Y.Z`, PR выпуска;
- `next-rc`: следующая метка кандидата после откатов или исправлений на ветке выпуска.

Скрипт `tag-release-candidate.sh` отказывает, если содержимое вершины совпадает с последним кандидатом, и при гонке нумерации повторяет попытку (всего три). В 26cd9c21 режим `cut` сам ставил rc.1; с Ф252 (коммит e15e7a29) `cut` метку не ставит, и rc.1 тоже ставит `next-rc` после проверки полей записей CHANGELOG.

## Второй случай 11–12.11.2026: сборщик двойника и слияние по полям

**Что произошло.** По карточке WP-5 Ф74, старый сборщик бота (`dt_sync`) был отключён в апреле 2026. Только он писал разделы «уведомления» (`2_5_notifications`), «операции» (`2_8_operations`) и «аккаунт» (`2_1_account`). Новый сборщик (activity-hub) эти разделы не считал, а события уведомлений исключал сознательно. Отдельный механизм — события аккаунта под старым идентификатором — описан в DP.CONCEPT.008: он относится к потоку событий, а не к отсутствию писателя раздела `2_1_account`.

**Почему потерю не видели.** По захвату, новый сборщик сохраняет результат слиянием по полям (upsert-merge): пишет свои поля и не трогает остальные. Поля отключённого сборщика не обнулялись и не помечались устаревшими, поэтому хранили правдоподобные старые значения. Пилот заметил 11.11: уведомления стояли на 12.04, хотя события уведомлений продолжали попадать в журнал; раздел операций стоял на апреле. Более точную хронологию отключения из этих дат не выводим.

**Исправление.** По карточке WP-5, activity-hub PR #4 научил новый сборщик писать все три раздела. 12.11 в двойнике пилота уведомления обновились до 09.11, события аккаунта — до 11.11 вместе с правкой бота.

**Чем отличается от первого случая.** Там потеря вскрылась, когда понадобился результат. Здесь общая запись обновлялась каждую ночь, а застыли только отдельные поля, поэтому общая метка времени записи потерю не показывала.

**Дополнительные меры — вывод разбора кандидата:**
1. Перед отключением писателя общей записи перечислить поля и разделы, которые пишет только он, и назначить им нового писателя до отключения.
2. Если запись собирается слиянием по полям, у каждого поля или раздела должен быть текущий писатель или своя метка времени расчёта. Поле без писателя не должно выглядеть свежим.

**Тест обнаружения для этого варианта.** «Какие поля этой записи сейчас не пишет ни один включённый писатель?»

Источник: карточка WP-5 Ф74; код activity-hub при извлечении не проверялся. Наличие меток времени по полям не подтверждено.

## Тест обнаружения

«Что производит только это задание?» Перед отключением задания перечислить его выходы (метки, файлы, статусы, уведомления) и для каждого найти другой источник. Нет другого источника → отключение снимет и эту обязанность.

## Что делать

1. Перед отключением задания по расписанию перечислить, что производит только оно.
2. Обязанности, которые нужны и без ритма, вынести в отдельный запуск до отключения.
3. Проверку, которая при отсутствии входа только предупреждает, считать местом, где такая потеря пройдёт незаметно.

## Граница

Два случая: выпуск шаблона и сборщик двойника. В первом «единственное место» проверено по рабочим процессам и скриптам репозитория шаблона на коммите до исправления; ручная постановка меток вне репозитория не проверялась (замечание Кодекса при разборе пакета 32: сильная формулировка требует перечня всех путей). Неудачный прогон выпуска без кандидата не наблюдался: потеря вскрылась при подготовке 0.42. Во втором слияние по полям описано по захвату, код activity-hub при извлечении не проверялся.
