# DP.FM.805 — Поддельные секреты в доставляемых тестах блокируют сканер продукта у пользователя

## Механизм отказа

Тесты детектора секретов и правил хука нуждаются в образцах, похожих на настоящие секреты. Если такие тесты доставляются пользователю вместе с продуктом, а в продукте есть своя проверка секретов перед коммитом, то проверка находит образцы в доставленных файлах и останавливает коммит у пользователя. Сканер работает правильно: образец по тексту неотличим от секрета.

## Прецедент

**10.11.2026, шаблон IWE, issue #1492.** Два файла с образцами, у каждого своё исправление:

1. **Тесты guide-kit (`structurer/test_quarantine.py`, коммит e9151e0 в iwesys/guide-kit, PR #9).** Встроенная копия этого файла в шаблоне останавливала проверку секретов шаблона (`aws-access-key x6, private-key-header x1`), когда пользователь коммитил файлы, доставленные `update.sh`. Поддельные ключи AWS и заголовок приватного ключа разбиты на соседние строковые литералы Python (вида `"AK" "IA…"`, `"-----BEGIN" " … PRIVATE KEY-----"`): строки, которые тесты передают в `detect_quarantine`, не изменились. Проверено на идентичной встроенной копии (v0.1.4): `pytest structurer/test_quarantine.py`, 25 тестов прошли; проверка секретов шаблона останавливает старый файл и пропускает новый.
2. **Тест 29 правил хука шаблона (`.claude/hooks/rule-engine.sh`, коммит 4d7e9497 в FMT-exocortex-template).** Образец URL базы с паролем записан по частям, через склейку строк в кавычках. Сканер не менялся; тесты правил хука: 81 прошли, 0 упали.

Копию guide-kit в шаблоне правили не напрямую, а в исходном репозитории; коммит шаблона слит так, чтобы ветка не трогала встроенную копию.

## Тест обнаружения

«Пройдёт ли проверка секретов продукта на файлах, которые продукт доставляет пользователю?» Прогнать сканер продукта по доставляемому набору целиком, включая тесты и встроенные копии чужих библиотек.

## Что делать

1. Заведомо поддельные образцы в доставляемых тестах записывать по частям, чтобы строка во время выполнения осталась прежней, а исходник не совпадал с шаблоном сканера.
2. Закрепить приём проверкой конечного набора: сканер продукта прогоняется по доставляемым файлам (в прецеденте так проверен файл guide-kit). Разбиение строк обходит конкретный текстовый сканер и зависит от языка; сканер, который склеивает соседние литералы, снова совпадёт (замечание Кодекса при разборе пакета 32).
3. Встроенную копию чужого кода править в исходном репозитории и доставлять синхронизацией: правило и прецедент 2026-10-06 записаны в `DP.METHOD.228`; в этом случае копию guide-kit меняет только `guide-kit-sync.sh` под проверкой `guide-kit-drift`.

## Граница

Приём только для заведомо поддельных образцов. Настоящий секрет, записанный по частям, обходит сканер, и это уже не исправление, а утечка. Один случай в двух файлах, оба 10.11.

## Отличие от соседей

- `DP.METHOD.228` — встроенная копия по метке версии и проверка расхождения с исходником: откуда правило «править в исходном репозитории».
- `DP.FM.379` — маркер исключения сам содержит образец секрета; там же лечение тем же приёмом: образец записывается так, чтобы не совпадать с шаблоном обнаружения.
- `DP.FM.540` — исключение тестовых файлов из проверки секретов как альтернатива и её риск: ошибка в шаблоне имени пропускала лишние файлы.
