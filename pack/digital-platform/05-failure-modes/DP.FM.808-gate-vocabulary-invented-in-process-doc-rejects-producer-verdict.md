# DP.FM.808 — Словарь вердиктов шлюза придуман отдельно от производителя

## Тезис

Шлюз, который принимает вердикт другой программы, ждёт словарь, записанный в документе процесса, а не тот, что программа-производитель выдаёт на самом деле. Честный вердикт производителя отклоняется, выпуск блокируется без дефекта в проверяемом коде.

## Механизм

Словарь вердиктов записали в описании процесса выпуска, не сверив с программой, которая их производит. Шлюз написали по этому описанию.

**Случай (выпуск 0.42, РП-529, 10.11.2026).** Итоговая проверка решений перед слиянием выпуска (`ops/check_decisions.py --require-final`, DS-iwe-releases PR #17) принимала вердикт атаки только из набора STABLE / CAUTION / BLOCKED; описание проверки 0.42 (строка 13 протокола и образец `rc.K.yaml`) называло те же три слова. Навык атаки `iwe-platform-redteam`, существовавший с 27.08, выдаёт GO / CAUTION / BLOCKED, а при нехватке изоляции, доступа или свидетельств — `cannot_verify`. Положительное слово не совпало (STABLE вместо GO), а `cannot_verify` шлюз не знал: такой вердикт отклонялся бы общим сообщением «должен быть одним из…», без указания, что атака не смогла проверить кандидата. Честное GO было бы отклонено, и выпуск застрял бы.

Тесты шлюза в PR #17 подставляли в образец вердикта слово STABLE, то есть проверяли шлюз на том же придуманном словаре; вывод навыка в тестах не использовался (проверено по `ops/test_check_decisions.py` в PR #17). Что тесты писали именно по описанию процесса — вывод, не проверено.

## Отличие от смежных

- **DP.FM.476** сама исключает этот случай в «Границах»: она о словаре, который отправитель переводит на границе интеграции, после чего сравнение у потребителя молча даёт «ложь»; дрейф имён между документом и кодом там отнесён к DP.FM.161. Здесь трансляции нет, словарь потребителя изначально придуман, и отказ громкий (выпуск стоит).
- **DP.FM.161** — имя, записанное в паке, расходится с именем в коде. Здесь расходится словарь потребителя с выводом производителя, а документ процесса и шлюз согласованы между собой.
- **DP.FM.666** — сравнение спроектировано без производителя исходного снимка: тот же корень, потребитель спроектирован без сверки с производителем.
- **DP.FM.043** — общий корень: допустимые значения перечисления взяты из предположения, а не из источника (там — SQL CASE по данным базы).

## Противодействие

- Шлюз, который принимает вердикт другой программы, принимает её словарь. Источник словаря — производитель (его код, описание вывода или сохранённый реальный прогон), а не документ процесса.
- Каждому значению словаря производителя, включая промежуточные (CAUTION) и служебные («не смог проверить», `cannot_verify`), сопоставлено определённое решение шлюза; если нужен свой словарь, отображение «слово производителя → решение шлюза» записывается явно и полностью.
- Договор с производителем проверяется тестами на его выводе (договорные тесты потребителя, DP.SOTA.040), а не на рукописных примерах.

Исправление 10.11.2026: DS-iwe-releases PR #18 — набор GO / CAUTION / BLOCKED, отдельная ветка для `cannot_verify` («атака не смогла проверить кандидата — строка 13 не пройдена»), тест, что прежнее слово STABLE отклоняется; FMT-exocortex-template 4f30868e (PR #1523) — слова вердикта в описании процесса выпуска приведены к словарю навыка.

## Тест обнаружения

Подать в шлюз дословный вывод производителя (сохранённый реальный прогон), а не рукописный пример. Для каждого значения словаря производителя у шлюза есть определённое решение; значение, которое шлюз отклоняет как «неизвестное», — этот сбой.

## Границы

- Найдено автором при записи процесса выпуска, до первого реального прогона атаки; отклонённого живого вердикта не было.
- Карточка не утверждает, что после исправления шлюз проверен на реальном выводе навыка: тест PR #18 тоже подставляет вердикт вручную.
