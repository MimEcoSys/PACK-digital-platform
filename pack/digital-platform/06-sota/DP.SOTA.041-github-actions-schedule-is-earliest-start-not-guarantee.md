# DP.SOTA.041 — Расписание GitHub Actions: самый ранний момент, а не гарантия

## Наблюдение (ограничение платформы)

Время в `on.schedule.cron` у GitHub Actions — самый ранний момент, когда запуск может начаться. Под нагрузкой событие schedule задерживается, сильнее всего на начале часа. При высокой нагрузке запуск может и выпасть: так сказано в документации GitHub.

Измерение в репозитории шаблона: рабочий процесс `validate-template` на слоте `0 2 * * *` стартовал в 08:29–09:09 UTC каждый день с 02 по 07.11.2026. Опоздание составило 6,5–7 ч, стабильно 6 дней подряд.

## Следствие

Поставщик глоссария на том же слоте обещал «к утру» открыть запрос на слияние. При фактическом старте около 09:00 UTC (12:00 МСК) обещание не выполнялось бы ни разу.

## Контрмера

1. **Срок, обещанный человеку, считать от распределения фактических стартов,** а не от записи cron. Источник — история запусков соседнего рабочего процесса того же репозитория на том же или близком слоте.
2. **Слот — с запасом под измеренное опоздание и не на круглую минуту** (в прецеденте 21:17 UTC = 00:17 МСК; запас до утра — около 8 ч).
3. **Выпавший запуск ловить отдельно** (DP.M.075, no-op heartbeat): запас по времени не спасает от пропуска.
4. Если срок жёсткий (минуты, а не часы), schedule GitHub Actions не годится: нужен свой планировщик или внешний триггер (`workflow_dispatch` / `repository_dispatch`).

## Тест применения

«Что будет, если этот запуск стартует на 7 часов позже записи cron?» Обещание нарушено → слот выбран без запаса.

## Ограничения

Одно измерение в одном репозитории (trust: low). Величина опоздания зависит от нагрузки GitHub и может меняться, поэтому её надо перемерять, а не брать отсюда как константу.
