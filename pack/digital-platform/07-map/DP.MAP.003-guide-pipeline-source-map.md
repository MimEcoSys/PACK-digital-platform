# [DP.MAP.003] Карта источников конвейера генерации руководств и методических материалов

> **Назначение:** проверяемое обещание конвейера РП521 — откуда каждый из двух выходов
> (персональное руководство / методический материал) берёт данные, откуда берутся критерии
> качества (рубрики) и какие программы-источники допустимы как основной материал.
> Каждая строка фальсифицируема: можно открыть источник и убедиться.
>
> **Статус зрелости:** `draft-pending-F1` — строки с пометкой `[spike-validated: no]` являются
> проектными гипотезами до спайк-прогона одного занятия (нулевой шаг Ф1 РП521). После спайка
> пометки снимаются одним коммитом — это и есть условие снятия статуса.

## §А. Развязка: механизм один, конфигурации две

Механизм отбора материала — ОДИН код-путь из 5 шагов. Различия двух выходов — только
декларативные конфигурации; переопределяемы шаги 1/3/5, шаг 4 закрыт замком
(`mechanism.locked_steps: [4]`, валидатор отклоняет оверлей с ключами `steps.4.*`).

| Шаг механизма | Руководство (по запросу) | Методический материал (ежедневная петля) |
|---|---|---|
| 1. Цель сборки | квалификация / ступень (человек сам назвал программу) | текущее узкое место (bottleneck_slot) |
| 2. Основной материал + проверка предпосылок | общий: машинная проверка обязательна (см. §Г) | общий: машинная проверка обязательна (см. §Г) |
| 3. Внешняя поддержка из других программ | выключена | включена, ограниченно, с проверкой готовности |
| 4. Происхождение фрагмента + content_hash | **общий, не переопределяем** | **общий, не переопределяем** |
| 5. Скрытие меток программ в интерфейсе | выключено | включено (источник показывается по запросу) |

Схема происхождения фрагмента — 10 полей (решение пилота 11.08, здесь НЕ расширяется):
`fragment_id, role (main|support), source_program, source_unit, source_version, content_hash,
position_in_sequence, selection_basis (узкое место | квалификация), prerequisites_checked[],
rubric_ref`; плюс `assembled_by_run` на уровне объекта занятия/сборки.

### §А.1 Типизация схемы происхождения (Ф1, пир-сессия 2026-08-16-08-wp521-fragment-provenance-schema, Клод+Кодекс, консенсус за 3 хода)

Состав 10 полей закрыт (§А выше). Ниже — типы, ограничения и место хранения; вопрос
следующего уровня детализации, не пересмотр состава.

**Хранение.** JSON-массив фрагментов внутри объекта занятия/сборки (не отдельная
реляционная таблица) — коллекция небольшая (единицы-десятки), упорядоченная
(`position_in_sequence`), всегда читается и пишется целиком вместе с родительским
объектом (write-once, append-only на момент сборки). Запрос «все занятия/сборки с
данным `source_program`» (нужен для аудита §Г и для миграции/отзыва версии
программы при обнаруженном дрейфе через `content_hash`) обязан работать без full
scan — функциональный индекс (`jsonb_path_ops`/GIN на PostgreSQL или materialized
view) на `source_program` внутри массива; конкретный механизм — решение при
реализации Ф1/Ф7, не архитектурный вопрос этой карты.

**Типы полей фрагмента:**

| Поле | Тип | Ограничение |
|---|---|---|
| `fragment_id` | string | — |
| `role` | enum(`main`\|`support`) | — |
| `source_program` | string | — |
| `source_unit` | string | — |
| `source_version` | string | — |
| `content_hash` | string | формат `sha256:<hex>`; хэш **канонического исходного содержимого** `source_unit` на момент сборки — НЕ хэш сериализации самой записи происхождения (та меняется тривиально при правке метаданных, не при дрейфе материала) |
| `position_in_sequence` | integer | — |
| `selection_basis` | enum(`bottleneck`\|`qualification`) | — |
| `prerequisites_checked[]` | array of `{prerequisite_ref: string, status: enum(verified\|assumed\|failed), checked_against: string\|null}` | `role=main`: массив непустой, ВСЕ элементы `status=verified`. `role=support`: массив пустой или с любым статусом |
| `rubric_ref` | string | null запрещён (§В) |

**Три статуса `prerequisites_checked[].status`, не два.** `verified` — машинная
проверка реально выполнена и прошла (покрытые источники §Г: CAT.001-003 —
`entry_stage_ok`/`blocks_transition_ok` как конкретные значения `prerequisite_ref`
с `status: verified`). `assumed` — предпосылка заявлена без машинной проверки,
честно помечена как некрепкое основание (для источников без покрытия §Г —
альтернатива не «запретить материал совсем» и не «тихо считать проверенным»).
`failed` — проверка выполнялась и не прошла (история попытки; такой фрагмент не
должен был получить `role: main`, поле фиксирует факт для аудита, не разрешает
использование). Плоское `{checked: bool}` отклонено консенсусом сессии — непустой
массив из одних `false` формально прошёл бы правило `main`, не доказывая
покрытость.

**На уровне объекта занятия/сборки (не фрагмента):**

| Поле | Тип | Примечание |
|---|---|---|
| `assembled_by_run` | string | id прогона Портного; держит версию мета-конфигурации (§Б.3) |
| недельная петля | `{topic_ref: <A2w-id>, status: enum(open\|closed\|waived)}` | `topic_ref` — снимок ссылки на тему недели, пишется при `slot_opened` (не derived-поле, вычисляемое на лету из даты+WeekPlan на каждое чтение — иначе последующая правка WeekPlan незаметно переписывает историю уже прошедшего занятия; пересчёт из даты допустим только как sanity-check в момент создания). Статус меняет тот же владелец, что пишет `lesson_events` (ревизия-2 п.8 РП521, обёртка `/lesson`) |

## §Б. Карта данных: три подпотока

Конвейер собирает документ из трёх подпотоков; смешение происходит только в собранном
документе, поэтому шаг 4 (происхождение на каждый фрагмент) обязателен обоим выходам.
Ось типов 2.1-2.4 (`DATA-RESIDENCY.md §3`) типизирует только подпоток 1; учебный материал
программ — платформенное доменное знание, вне этой оси; мета-конфигурация — вне оси,
фиксируется через `assembled_by_run` (id прогона держит версию конфигурации), фрагментов
не порождает.

### Б.4 Агрегация происхождения: два слоя, не конфликт

Фрагмент-уровень (10 полей, вводится Ф1) — источник истины происхождения.
Документ-уровень (существующий: `verify_and_provenance.py`, 9 классов входа со статусами
работает/деградировал/запасной/отсутствует) — аудит выхода. Правило: документ-уровень
вычислим из фрагмент-уровня + статусов источников; расхождение слоёв = дефект сборки,
не «два мнения». Маппинг 10 полей → 9 классов документируется при реализации Ф1.
Версия реестра рубрик (§В) на момент сборки фиксируется в `assembled_by_run` — иначе
аудитор не восстановит, какая трактовка `rubric_source` действовала при сборке.

**Архитектурное решение по Ф1/Ф7 (пир-сессия 2026-08-13-01-wp521-f0-tech-review,
Клод+Кодекс):** ревизия кода показала, что `render_checklist.py` хеширует только
`primary_text` целого daily/weekly-документа, а `verify_and_provenance.py` строит
жёстко заданную таблицу 9 классов по frontmatter — ни один не читает БД и не знает
про фрагменты, 10 полей происхождения или инвариант «документ вычислим из
фрагментов» выше. Оба скрипта — наследие закрытого РП-149 под старую
однопродуктовую модель, полезны сохранить как есть для формы и обратной
совместимости с прежним потоком.

Решение: **не расширять** `render_checklist.py`/`verify_and_provenance.py` под
схему фрагментов. Для Ф1 нужен **отдельный новый модуль** — читатель/валидатор
происхождения фрагментов (валидация 10 полей + `content_hash` фрагмента, свёртка в
документный статус, сверка со статусами источников, тесты маппинга 10→9 классов).
`render_checklist.py` при реализации Ф7 становится потребителем/адаптером поверх
этого нового модуля, не его владельцем.

**Риск бюджета:** оценка Ф7 в 2.5h (РП-521.md) реалистична только для каркаса схемы
без полной интеграции. Для готового инварианта с обратной совместимостью, тестами и
адаптером бюджет вероятно занижен — решение о модуле и его декомпозиции нужно
зафиксировать до финальной оценки Ф7 (сигнал в WP-521.md, не эта карта).

## §В. Происхождение рубрик (закрывает разрыв Н4)

`rubric_ref` обязателен для КАЖДОГО фрагмента ОБОИХ выходов (null запрещён — единый shape
данных; аудитор отличает «рубрика = чеклист выхода» от «пусто = дефект записи»).

Правило происхождения рубрики (по приоритету):
1. Явный критерий качества в самом материале/задании программы → `rubric_source: explicit`.
2. Наследование от типа задания или области → `rubric_source: inherited-from-assignment-type | inherited-from-area`. Наследование — временное и видимое: происхождение рубрики читается по реестру ниже, не маскируется под явное.
3. Ни того ни другого → материал НЕ может быть основным (`role: main`), только поддержкой.

Реестр рубрик (стартовый):

| ID рубрики | Для чего | Чем является сегодня | rubric_source |
|---|---|---|---|
| RUB.GUIDE-OUTPUT-01 | выход «руководство» (все фрагменты) | многослойная рубрика (слои ниже): машинная пара + MVP fast-path + полный многошкальный профиль | explicit (пороги профиля обязательны только после записанного решения пилота по калибровке) |
| RUB.LESSON.* | основной материал занятия (судья Ф3) | **не существует** — рубрик per-материал в каталогах сегодня ноль | заполнение — обязательная работа Ф6 |

Правило версии: записи фрагментов, сделанные до расширения, читаются по состоянию реестра на момент записи (вырожденная машинная пара) — миграция старых вердиктов не проводится; версия реестра на момент сборки фиксируется в `assembled_by_run` (§Б выше).

**Честная строка:** рубрик в каталогах материалов сегодня НЕТ (CQR — рубрика авторов другого
каталога `cells/`, заполненных данных 0; deepeval-рубрика — качество бота, не материала).

## §Г. Аудит машиночитаемости программ-источников (закрывает разрыв Н5)

Критерий допуска материала в `role: main`: поле `prerequisites_checked[]` фрагмента НЕПУСТО —
хоть какая-то машинная проверка готовности/применимости реально выполнена кодом ДО выбора.
Пустой список → только `role: support`. Вид проверки — колонка аудита, не поле фрагмента.

**Типизация элемента (§А.1, Ф1):** таблица ниже упрощённо пишет `entry_stage_ok` —
это значение `prerequisite_ref` конкретного элемента с `status: verified`, не
голая строка в массиве. Полная форма: `{prerequisite_ref: "entry_stage_ok",
status: "verified", checked_against: <id проверки>}`.

| Источник | Последовательность | Предпосылки | Вид проверки | Как проверяется кодом | Вердикт |
|---|---|---|---|---|---|
| CAT.001-003 | нет (stage-gated, не DAG) | `entry_stage`, `blocks_transition` («2→3») | структурная | guide-kit `planner.py` (bottleneck-first + ступень) | main допустим; `prerequisites_checked: [entry_stage_ok, blocks_transition_ok]` (полная форма — см. типизацию выше) |
| `programs/{lr,rr,ir}/assignments.yaml` | нет | нет; селекция `bottleneck+domain+priority` | селекционная | `assignment_selector.py` (сортировка соответствия) | **пока только `support`** — селектор не возвращает `domain_match` вовсе (проверено в коде); `selection_basis` фиксирует релевантность, не готовность, см. оговорку |
| `cells/` (ZP/FPF, шаблон с prerequisites) | шаблон есть, данных 0 | прозаический шаблон | нет (не заполнено) | — | не источник, пока не заполнен |
| decomposer Mode Б (`topic_sections.yaml`) | DAG-структура (prerequisites/depends_on); сортировка — MVP-упрощение, НЕ полный topological sort (оговорка в коде `decomposer.py`) | машиночитаемые | структурная | `guide-kit/generator/decomposer.py` | **резерв**: в суточный конвейер не включён |

**Оговорка (пересмотрена пир-сессией 2026-08-13-01-wp521-f0-tech-review, Клод+Кодекс —
исходная трактовка ревизии п.5 РП521 отклонена по факту кода):** первоначальная запись
допускала селекционную проверку МШС-заданий как «покрытость» наравне со структурной
проверкой CAT.001-003. Ревизия кода (`assignment_selector.py`) показала: селектор
сортирует по соответствию (`bottleneck_match`), но **не возвращает `domain_match`
вообще** — заявленный список `[bottleneck_match, domain_match]` описывал факт,
которого в рантайме не существует. Сортировка по соответствию отвечает на вопрос
«это ли лучше всего подходит», а не «готов ли человек это читать сейчас» — две разные
оси, вторая не следует из первой.

**Исправленное правило:** `prerequisites_checked[]` — только реально выполненные и
успешно пройденные проверки готовности (как у CAT.001-003: `entry_stage_ok`,
`blocks_transition_ok`). Релевантность по bottleneck/domain — отдельно, через
`selection_basis` (карта §А), которое остаётся полем схемы происхождения, но
трактуется строго как «доказательство релевантности», не как заменитель
`prerequisites_checked[]`. Пока МШС-задания не получат отдельную проверку готовности
(структурную или иную) — они допустимы только как `role: support`, не `role: main`.
Базовое правило сохранено без изменений: ничего не проверено → только поддержка.
Судья Ф3 видит оба поля раздельно в пакете — знает, что перед ним: цепочка
предпосылок или только эвристический подбор по теме.
