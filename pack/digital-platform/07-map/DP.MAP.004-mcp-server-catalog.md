# [DP.MAP.004] MCP Server Catalog

> **Назначение:** Единая таблица всех MCP-серверов (точек входа по протоколу Model Context Protocol) платформы и личных MCP создателя. DP.MAP.002 каталогизирует МЕТОДЫ/workflow (что делается, кем, по какому триггеру); эта карта — другой срез: какие MCP-ПРОТОКОЛЬНЫЕ серверы существуют, собирает ли каждый данные сам или фан-аутит на другие, и какой набор инструментов он реально отдаёт.
>
> **Правило:** Строка без прямой проверки (код file:line, живой вызов или прямой список инструментов подключённой сессии) помечается «нужна проверка» в столбце «Источник» — не достраивается по аналогии с похожими серверами.
>
> **Различение «шлюз» (WP589 Ф23, 08.10.2026):** шлюз ПЕРЕД несколькими уже самостоятельными, чужими друг другу идентичностями (склеить ради удобства клиента) — архитектурно отвергнут. Агрегатор КАК собственная новая идентичность (сервис fan-out'ит внутри себя на несколько источников, но отдаёт результат под одним именем с сохранённой атрибуцией источника) — нормальный, уже дважды реализованный паттерн. Столбец «Тип» ниже различает именно это: агрегатор = ДА, самостоятельный источник без фан-аута = НЕТ.

## Backend-сервисы без собственного MCP-протокола (справочно, не строки реестра)

Подпроекты `DS-MCP/*`, вызываемые ЧЕРЕЗ Aisystant MCP как обычные internal-API, сами MCP JSON-RPC не говорят (нет зависимости `@modelcontextprotocol/sdk`, не найдено `tools/list`): `agent-runner`, `agent-status-service`, `bridge-scope-service`, `event-gateway`, `github-integration-service`, `learning-context-service`, `mentorship-service`, `observability-webhook`, `payment-receiver`, `simulator-proxy`, `status-proxy`, `trace-accountant`, `user-profile-service`. Эти функции уже видны в каталоге методов DP.MAP.002 (столбец «Исполнитель»/«Реализация»), сюда не дублируются.

## Как использовать

1. **При архитектурном решении про MCP:** сначала сверить эту таблицу — какие серверы уже есть, кто из них агрегатор, какие инструменты реально отданы. Не пересобирать факты заново (как потребовалось в пир-сессии 08.10 — РП589 Ф23).
2. **При добавлении нового MCP-сервера:** добавить строку сюда с источником проверки; при появлении независимого проверенного факта о сервере из раздела «Нужна проверка» — перенести строку в основную таблицу.
3. **При ArchGate нового MCP:** проверить столбец «Тип» — если предлагается шлюз ПЕРЕД уже существующими самостоятельными идентичностями (не агрегатор-как-новая-идентичность), см. запрет в РП589 Ф23.
