# [DP.SC.042] Извлечение знаний в Pack

## Обещание

**Держит:** владелец РП-170 (назначено пилотом 14.11.2026).

**Кому:** Эксплуатант платформы (R2 Экстрактор, R4 Автор, R15 Валидатор)

**Зачем:** Превращать практический опыт (сессии, feedback-логи, артефакты, коммиты) в формализованные Pack-сущности — knowledge-капитал платформы.

**Что получит:**
- **Кандидаты знаний (KE)** — извлечённые из сессионных артефактов структурированные фрагменты (правило, различение, роль, метод)
- **Pack-сущность** — интегрированная и валидированная запись в соответствующей категории Pack (04-work-products/, 05-failure-modes/, 02-domain-entities/, итд)
- **Feedback-лог** — история решений (принят/отклонён/отложен) с обоснованием для будущих решений

**Критерий приёмки:** 
- KE соответствует DP.D.033 (для ролей) или соответствующей схеме (для методов, WP, различений)
- ВДВ-таблица (Вход/Действие/Выход) заполнена полностью для каждого KE-кандидата
- Прошла валидацию R15 (семантика, уникальность, scope)
- Интегрирована в Pack в течение 3 рабочих дней после принятия

## Триггеры и Инварианты

| Триггер | Инвариант | SLA | Failure Mode |
|---------|-----------|-----|--------------|
| Завершение сессии (Close) с результатом, требующим фиксации | Все артефакты сессии (captures, feedback-лог, решения) доступны для KE | ≤3 дня до KE-отчёта | Неполная информация о контексте → KE невалидируется |
| Достижение consensus по процессу (WP-разрешение, расходящиеся интерпретации) | Решение задокументировано с обоснованием (feedback-лог запись) | ≤1 дня до интеграции в distinctions.md | Потеря контекста решения → будущие повторения |
| Обнаружение паттерна/антипаттерна в 3+ сессиях | Паттерн воспроизводим и описан в failure-modes | ≤5 дней до Draft-статуса | Ложный паттерн (не воспроизводится) → потеря времени на документирование |
| Инцидент или техдолг, отражающие пробел в знаниях | Корень инцидента проанализирован, знание для предотвращения выявлено | ≤2 дней до правила/различения | Лечение симптома вместо причины → рецидив инцидента |

## Каналы входа (WP-247 Ф-MULTI-SOURCE, 8 мая 2026)

> **Архитектурное решение:** `captures.md` остаётся **single aggregation point**. R2 читает один файл, но он наполняется автоматически из 4 каналов (вместо ручного ввода).

| Канал | Feeder | Триггер | Маркер в captures.md |
|-------|--------|---------|----------------------|
| **Ручные capture'ы** | пользователь сам пишет ### в `inbox/captures.md` | в любой момент | (без маркера feed) |
| **Session transcripts** | `extractor.sh session-close-feed` | post-Quick Close, auto >30мин / opt-in для коротких | `[feed:session-close YYYY-MM-DD]` |
| **Git diff sweep** | `extractor.sh git-diff-feed` | cron 06:00 / 21:00 (12h окно) | `[feed:git-diff YYYY-MM-DD]` |
| **Fleeting-notes** | `inbox-check` читает `inbox/fleeting-notes.md` как secondary inbox | cron 3h (вместе с captures.md) | (заголовки в fleeting-notes без feed-маркера, R2 различает по `source_file`) |

**Идемпотентность всех feeders:** не дублируют записи за тот же день. Маркер источника позволяет R15 при `/apply-captures` помечать правильный исходник `[analyzed]`/`[processed]`.

**Защита от дубля session-close-feed:** если за сессию уже был ручной `/ke` или `/apply-captures` — feeder пропускает (по новым маркерам в captures.md).

## Пользовательский путь (ВДВ-формат)

### Сценарий 1: KE из captures и feedback-лога

| Фаза | Вход | Действие | Выход | Роль | Инструмент |
|------|------|---------|--------|------|-----------|
| **Наблюдение** | Завершена сессия (Day Close / Close). Captures в файле `DS-my-strategy/captures/`. Feedback-лог содержит решения и обоснования | R2 читает captures и feedback-лог, выделяет фрагменты, требующие формализации в Pack | KE-кандидат (набор потенциальных Pack-сущностей) с ссылками на исходный контекст | R2 Экстрактор | VS Code + grep + memory |
| **Валидация** | KE-кандидат (наброски). Исходный контекст (ссылка на день/сессию). DP.D.033 шаблон (для ролей) или соответствующая схема | R15 Валидатор проверяет: (1) соответствие схеме; (2) уникальность (нет дублей в Pack); (3) scope (не размыто, не обобщено сверх меры); (4) семантика (смысл правильно схвачен); (5) сценарии применения (подтверждены контекстом) | **Решение:** принят / отклонён / отложен. **Feedback-лог запись** с причиной. Если принят → KE готов к интеграции | R15 Валидатор | `/apply-captures` skill (UI) + Pack repos (read + feedback-log.md write) |
| **Интеграция** | Валидированный KE. Решение = **принят**. DP.D.033 (или другая схема) полностью заполнена. Выбранное место в Pack (например, 02-domain-entities/ для ролей) | R4 Автор интегрирует KE в Pack: (1) коммит в соответствующую папку (с номером, именем KE); (2) обновляет смежные индексы (roles.md, если роль; SOTA.md, если метод); (3) синхронизирует MAP.002, если меняется сервис-выход | **Pack-сущность** — новый файл или обновленный раздел в Pack. Коммит в `PACK-digital-platform`. Синхронизирован с `WP-REGISTRY.md` | R4 Автор | Claude Code (Edit/Write) + git commit |

### Сценарий 2: KE из инцидента или техдолга

| Фаза | Вход | Действие | Выход | Роль | Инструмент |
|------|------|---------|--------|------|-----------|
| **Диагностика** | Инцидент (файл в `DS-ecosystem-development/.../Incidents/`). Постмортем-анализ. Root cause выявлена | R2 формулирует: (1) какое знание не было доступно/не следовалось; (2) как это знание должно быть зафиксировано в Pack (правило, различение, метод, failure-mode) | KE-кандидат (формулировка знания + сценарий предотвращения) с ссылкой на инцидент | R2 Экстрактор | incident/bugs/ файлы + grep failures.md |
| **Валидация** | KE-кандидат. Инцидент-документ. Обоснование (почему это знание = дефицит) | R15 Валидатор: (1) подтверждает, что дефицит знания был причиной; (2) проверяет, может ли это знание быть зафиксировано обобщённо (чтобы покрыло >1 инцидента) | Решение: принят (как failure-mode) / отклонён (не обобщаемо) / отложен. Feedback-лог | R15 Валидатор | feedback-log.md + Pack specs |
| **Интеграция** | Валидированный KE как failure-mode. Сценарий детектирования и recovery. Исправление кода (если требуется) | R4 добавляет в `05-failure-modes/` и связанные места; если требуется код-фикс → коммит в целевой сервис | **failure-mode запись** в Pack. Опционально: **код-фикс** коммит в `DS-*/` или целевой сервис | R4 Автор | Code repo + Pack edit |

### Сценарий 3: KE из паттерна в 3+ сессиях

| Фаза | Вход | Действие | Выход | Роль | Инструмент |
|------|------|---------|--------|------|-----------|
| **Обнаружение** | Логи сессий (≥3). Паттерн замечен: одна и та же проблема / ошибка / субоптимальное решение повторяется | R2 собирает контекст всех 3 сессий: dates, participants, контрастный пример (где паттерн не проявился). Формулирует гипотезу паттерна и условия его возникновения | Паттерн-гипотеза: (1) описание паттерна; (2) примеры; (3) гипотеза условий и причин; (4) предложенный способ фиксации (difference / distinction / anti-pattern / method) | R2 Экстрактор | session logs + capture-анализ |
| **Валидация** | Паттерн-гипотеза. Ссылки на 3+ сессии. Контекст-примеры | R15 Валидатор: (1) проверяет, что паттерн воспроизводим в примерах; (2) уточняет условие возникновения (когда точно срабатывает?); (3) проверяет, не является ли это ложным паттерном (чувствителен к выборке) | Решение: принят (как distinction / anti-pattern / method) / отклонён (ложный паттерн) / отложен (требуется больше примеров). Feedback-лог | R15 Валидатор | примеры из сессий + reasoning |
| **Интеграция** | Валидированная паттерн-запись. Статус = **принят**. Место в Pack выбрано: distinctions.md, failure-modes/, методы итд | R4 добавляет в Pack с меткой паттерна: как он проявляется, когда возникает, как его избежать | **Pack-сущность** (различение / anti-pattern / failure-mode / метод). Коммит в PACK-digital-platform | R4 Автор | VS Code + Pack repos |

## Связь с другими обещаниями

- **Потребляет:** результаты сессий (captures.md, feedback-log.md в DS-my-strategy), исходный код и логи (DS-ecosystem-development)
- **Порождает:** Pack-знания → используются всеми downstream системами (DP.SC.003 обучение, DP.SC.005 контент, DP.SC.021 персонализация)
- **Зависит от:** DP.SC.010 (рабочий ритм фиксирует captures), feedback-loop протокола Close
- **Связана с:** WP-247 (Knowledge Extractor pipeline), R2/R4/R15 ролевыми контрактами

## Примечания реализации

- **ВДВ-таблица обязательна** для каждого KE-кандидата: что входит на вход (Вход), как преобразуется (Действие), что выходит (Выход)
- **Feedback-лог** живёт в `DS-my-strategy/inbox/feedback-log.md` и используется для исторического контекста будущих решений
- **Валидация R15** — критический gate: это предотвращает попадание поспешных обобщений в Pack
- **Интеграция в Pack** должна быть атомарной: одна сущность = один коммит с ясным сообщением (Capture: X → Y)
