# DP.SC.053 «Локальная сборка персонального руководства (приватный IWE-контур)»

> **Один метод, два обещания.** Алгоритм генерации руководства — один (`DP.M.241`), исполняется по co-location: «сборка идёт туда, где живут данные; самый приватный участник определяет место сборки» ([[WP-415]]). Это НЕ второй сборщик — это **то же** обещание в другом локусе. Managed-обещание (платформа собирает) — `DP.SC.164`. Этот SC фиксирует **приватный IWE-контур** того же метода.

> **Ратификация (2026-06-20):** модель «платформа первична, IWE — доставляемый дистрибутив-клиент» официально принята. Данные пользователей хранятся в платформенной организации по юрисдикции (Aisystant — мир, МИМ — Россия); IWE подключается к платформе за derived-данными и универсальным знанием.

## Краткая формула обещания

Для пользователя, выбравшего приватный контур (точки `A-lite` / `L-B` / `L-S` оси Приватности), персональное руководство (`daily/`, `weekly/`, supporting-файлы — контракт секций см. `DP.SC.164` Элемент 3) собирается **локально в среде IWE пользователя**. Сырой личный контент (активные РП, `WeekPlan`, рефлексии, captures, `current_request`) **не покидает контур пользователя**. Платформа предоставляет только: (1) производные (derived) данные Памяти через MCP-шлюз под явным consent; (2) универсальное знание (Pack, универсальное руководство) — по запросу или бандлом. Выход доставляется в тайный гит (write-токен IWE) или подключённый «свой гит».

## Элемент 0 — Режимы и граница данных (обзор — полная карта в DP.SC.164)

> Полная 2-осевая карта (Приватность × Связность) — `DP.SC.164` Элемент 0. Этот SC детализирует приватный конец оси (`A-lite` / `L-B` / `L-S`). Концепция-источник — `DS-my-strategy/inbox/WP-425/WP-425.md` §«Архитектурное решение».

**Ось A (Приватность) — точки, покрытые этим SC:**

| Точка | Личное у платформы | Сборка | Кто пишет выход |
|-------|--------------------|--------|-----------------|
| `A-lite` | частичный эмбединг, только **грубый stateless derived-ranking**, ноль query-логов | локально | IWE (write-токен) |
| `L-B` | ничего; локальные эмбединги | локально | IWE (write-токен) / свой гит |
| `L-S` (строгий) | ничего; локальные эмбединги | локально | IWE / свой гит |
| *(L-T, TEE)* | технически да, но нечитаемо | TEE | — **deferred research** |

`M` / `A-managed` — обещание платформы (`DP.SC.164`), здесь не покрываются.

**`L-B` vs `L-S` — различие в исполнителе LLM-вызова локальной сборки** (концепция §2bis(а), не в составе данных у платформы): `L-B` допускает (а) локальную модель ([[WP-404]], MLX) ИЛИ (б) BYOK облачный LLM — сырьё уходит **доверенному провайдеру LLM**, но **не** на нашу платформу. `L-S` (строгий) — **только** локальная модель: сырьё не покидает машину вообще («локальная модель — единственно корректна для L-S»). Квота LLM платформы для обоих **неприменима** (платформа увидела бы контент промпта).

**Ось B (Связность) — сцепка с приватностью (критично):** строгий конец приватности **вынуждает** строгую связность. **`L-B`/`L-S` ⟹ ≥ `offline-first`** — иначе сам запрос «дай знание по теме X» раскрывает интересы пользователя (утечка тегов, см. Элемент 2). Для `A-lite` допустим `online-pull` (его запросы и так видны платформе).

## Элемент 1 — Триггер

| Режим | Источник триггера |
|-------|-------------------|
| `A-lite` / `L-B` / `L-S` | **Локальный планировщик** (launchd/cron, [[WP-357]]) ИЛИ контентно-пустой «тик» от платформы («пора собирать») |

- Контентно-пустой тик допустим даже для `L-B`: факт «готово к сборке» личных данных не содержит.
- **MCP-инструмента `subscribe_domain_events` не существует** (domain_event пишут воркеры платформы) — триггер опирается только на локальный планировщик / тик. Облачный планировщик платформы для local-режимов **не** используется.

## Элемент 2 — Входы и расщепление пайплайна по чувствительности

Один метод `DP.M.241`, но шаги исполняются в разных местах по чувствительности входа:

| Шаг | Вход | Где исполняется (local-режим) |
|-----|------|-------------------------------|
| Стабильный роутинг (cp-профиль, RCS, последний тест Диагноста ≤90д → кандидат skeleton) | чисто derived | данные тянутся с платформы (derived), решение — локально |
| Запросо-чувствительный роутинг (`current_request`, семантика активных РП) | сырьё | **только локально** (или `A-lite`: грубый stateless-выход) |
| Контентная композиция (мост универсальное знание ↔ сырые РП/рефлексии/captures) | сырьё | **только локально** |
| Резолюция universal slice (выбор фрагментов по темам) | темы выводятся из сырья | **локально над кэш-бандлом** для `L-B`/`L-S` |
| Вход «универсальное знание» (срез) | публичное | всегда с платформы (бандлом для `L-B`/`L-S`) |

**Источник Шага 1 (анализ контекста) в local-режиме:** локальные файлы IWE — `DS-my-strategy` (активные РП, `WeekPlan`/`WeekReport`, W-рефлексии), `personal_search` (локальный индекс), + derived с платформы через MCP (Элемент 6). Сравни managed (`DP.SC.164`): источник Шага 1 = `dt_read_digital_twin` напрямую.

**Две закрытые дыры (Ф1):**
1. Роутинг над `current_request` ошибочно казался derived — расщеплён на стабильный (платформа-безопасный) и запросо-чувствительный (локально).
2. **Утечка тегов через `universal_slice(tags)`** — сам запрос раскрывает, над чем работает человек. Следствие: для `L-B`/`L-S` универсальное знание обязано доставляться **бандлом** и резолвиться локально — это **требование приватности**, не удобство. Это и сцепляет ось Приватности с осью Связности.

## Элемент 3 — Выходы

- Контракт секций (`daily/`, `weekly/`, supporting) — **тот же**, что `DP.SC.164` Элемент 3 (не дублируем; один метод).
- **Кто пишет выход:** IWE по write-токену, выданному платформой для тайного гита (сборка была локальной). Контраст с managed: там пишет платформа (GitHub App).
- **Канал доставки тела** — тайный гит (приватный репо, который платформа создаёт; рендерится `guide.system-school.ru`) ИЛИ подключённый «свой гит». **Тело ≠ уведомление** ([[WP-418]]): в чат уходит только нудж «занятие готово» (класс `capped`, без личного контента — даже без темы), тело пользователь открывает сам (pull / страница).
- **Хост тайного гита — по юрисдикции пользователя:** РФ → организация МИМ, мир → Aisystant (следствие ратифицированной топологии «данные по юрисдикции»). См. Scoping-ноту.

## Элемент 4 — Граница данных и лицензионное предусловие бандла

**Таксономия классов (твёрдая опора границы — класс данных, не «личное вообще»):**

| Класс | Где живёт | Платформа видит (local-владелец)? |
|-------|-----------|-----------------------------------|
| Универсальное знание (Pack, универсальное руководство, `index.tags.json`) | Платформа | да — раздаёт |
| Память.Derived (cp-профиль FORM.089, RCS, bottleneck) | Neon | да — детерминированный агрегат, сырьё по нему не восстановить |
| Память.Observed (события на платформе: оплаты, прохождение) | Neon | да — собственные события платформы |
| Сырьё (РП, рефлексии, captures, `current_request`) | **IWE-локаль** | **нет** (инвариант P) |

**Лицензионное предусловие offline-first/air-gapped бандла** (ратификация 2026-06-20, **независимо** от privacy-инварианта — это право редистрибуции, не утечка личного):
- **Не-ЛР руководства** (профессиональные/рабочие/системные; МИМ + авторы, **открытая лицензия**) → входят в бандл, офлайн-редистрибуция легитимна.
- **ЛР-руководства** (Aisystant) → требуют отдельного лицензионного инструмента; в свободный бандл не идут.
- **Личный контент пилота** → в бандл не входит вообще (не universal knowledge).

Следствие: offline-first бандл реализуем для не-ЛР контента сразу, для ЛР — после лицензионного договора (handoff, см. Scoping-ноту). Без этой оговорки «offline-first bundle» выглядел бы юридически свободным для всего контента — он не для всего.

## Элемент 5 — Инварианты

### P (Privacy) — главный инвариант этого обещания
- Для `L-B`/`L-S` платформа **никогда** не получает сырой личный контент. В тайный гит уходит только **собранный выход** (готовый текст), не источники.
- Область «никогда» — строгий контур (`L-B`/`L-S`). Точки `A-managed`/`A-lite` — **сознательный consent-gated waiver** инварианта в объёме явного согласия (без consent режим по умолчанию = `L-B`).
- `A-lite`-защита **временна́я + гранулярная** (defense-in-depth): stateless-ranking **И** ноль query-логов **И** грубая гранулярность — временной ряд даже грубых рангов реконструирует траекторию = профиль.
- **Архитектурная гарантия, не промпт** (Парламент-модель, [[WP-410]]): для local-режимов GitHub App **не установлен** на личные репо (`DS-my-strategy`, локальный `personal-guide`, тайный гит) — платформа физически не может прочитать.
- **Расширение (WP-483 Ф4, peer session 2026-07-16/17): «сырьё» включает названия рабочих продуктов.** `guide-kit`'s опциональная секция `work_section: iwe` вставляет в собираемый выход заголовки активных РП пользователя (из локального `DayPlan`) — это тот же класс данных, что и остальное «сырьё» строки таблицы выше, не отдельная категория. Активация `work_section: iwe` на реальной инсталляции **не должна включаться дефолтом ни конфигом, ни самопроверяемым файлом-маркером** (антипаттерн — см. `lessons_self_touchable_gate_marker_is_not_a_real_gate.md`) — только явным решением пользователя в моменте, тем же способом, каким уже принимаются другие необратимые/видимые действия этого метода. Статус: **зафиксировано как принцип, механическая проверка не реализована** (`guide-kit.config.yaml.example`: `work_section: off` — дефолт во всех дистрибутивах).

### Наследуемые инварианты (от DP.M.241 / DP.SC.164)
K (контекст превыше плана), L (окно длины), D (детерминированный self-check), T (transparency), N (непрерывность нарратива) — **те же**, что в `DP.SC.164` Элемент 5 (один метод). Не дублируются; применяются к локально собранному выходу.

## Элемент 6 — MCP-контракт derived-данных (из Ф3, peer 2026-06-20-24)

Сборщик зовёт только инструменты, чувствительность которых ограничена **либо по построению** (purpose-built derived), **либо path-scope в data-service под gateway-asserted scope**.

### Матрица per-tool прав IWE-сборщика

| Инструмент | Право | Класс данных | Гейт | Enforcement |
|------------|-------|--------------|------|-------------|
| `dt_read_digital_twin` | R, **path-scoped** | allow `3_derived/*`; deny `1_declarative/*`, `2_collected/*` | consent (`data_analysis` — verify) **+ derived-only scope в gateway-assertion** | data-service path-guard |
| `get_cognitive_brief` | R | derived bundle | `text_analysis` (для `cognitive_profile`) | tool-owner (уже gated) |
| `knowledge_search` | R | публичное знание | — | tool-owner; для `L-B`/`L-S` — tag-leak → доставка локальным бандлом |
| `dt_write_digital_twin` / `personal_write` | **deny вверх** | — | — | узкий feedback-scope — отдельная строка, не отмена deny |
| `subscribe_domain_events` | **н/д** | — | — | не существует |

### Два инварианта авторизации
1. **Per-tool у шлюза + per-path у data-service.** Mode A ([[WP-410]]): шлюз разрешает инструмент (per-tool) и **mint'ит assertion с выданным scope**, но НЕ разбирает path (path-логика в шлюзе = прикладная логика = нарушение чистого шлюза). Path-guard (`3_derived/*` allow, raw deny) исполняет data-service по `user-JWT (Ory) + gateway-assertion (scope)`. **Scope живёт в gateway-assertion, не в Ory-JWT** (Ory не знает про «derived-only»; сборщик ходит от лица пользователя, не как отдельный OAuth-client). *Формат claim — verify с владельцем `gateway-mcp` при реализации.*
2. **Positive-list, не negative-exclude.** allow = `3_derived/*` (positive-list). Корректно, **пока** `3_derived` остаётся выходом единственного калькулятора (`recalculate_derived.py`, необратимые агрегаты). Появится lossy/обратимое поле внутри `3_derived` → сузить до явного path-list (`3_4_qualification`, RCS-слоты, `3_11_diagnostic`).

## Элемент 7 — Режим отказа и переходы

| Режим | Условие | Поведение |
|-------|---------|-----------|
| `local-offline` | Платформа недоступна | IWE собирает на последнем derived-снимке + локальном кэше универсального знания. Нет кэша → **нет сборки** в этот день. Это **не fallback** (второго генератора нет) — co-location ≠ fallback. |
| `degraded` / `welcome` / `paused` / `digest` | как `DP.SC.164` Элемент 6 | те же режимы (один метод) |

**Переход `managed → local`:** (1) `personal_purge_source` — стереть эмбединги личного на платформе, с **проверяемым** подтверждением (статус-код ≠ удалено; нужен независимый признак — пустой `personal_search` по контрольному запросу); (2) снять GitHub App с личных репо; (3) развернуть локальный `personal-knowledge-mcp` за Local Gateway + локальный кэш; (4) переключить выход на локальный/тайный репо; (5) проверить, что платформа перестала получать Observed-метаданные.

**Переход `local → managed`** — **самое высоко-утечное событие модели** (первая загрузка ранее-локального сырья наверх). Не симметричен purge: требует (а) отдельного явного `consent.index_embeddings` именно на этот акт; (б) явного выбора подмножества сырья; (в) понимания необратимости. **Запрещено** сливать с обычным переключением режима.

## Предусловия (вне обещания, фиксируются)

1. **Локальный кэш/бандл универсального знания** для `L-B`/`L-S` (формат не зафиксирован — open-dep; нужен `get_universal_bundle` + локальный резолвер `universal_slice(tags)`).
2. **Локальный LLM-исполнитель** ([[WP-404]], MLX/Apple Silicon) для строго-локальной сборки `L-S`, ИЛИ BYOK облачный LLM для `L-B` (сырьё уходит провайдеру LLM, **не** на нашу платформу). Квота LLM платформы для local-режимов **неприменима** (платформа увидела бы контент промпта).
3. **Local Gateway** (`DP.SC.034`) поднят; `personal-knowledge-mcp` локальный.
4. **GitHub App НЕ установлен** на личные репо (инвариант P, архитектурная гарантия).

## Scoping / ratification trace (мини-ArchGate Ф2)

Решение «платформа первична + данные по юрисдикции» ратифицировано (пилот/Андрей/Ильшат, 2026-06-20) — это и был архитектурный gate. Из него **следуют** (не новые решения):
- **Jurisdiction-routing тайного гита:** тайный гит держит собранный выход (данные пользователя) → по принятому правилу данные живут в орг по юрисдикции → гит там же (РФ → МИМ, мир → Aisystant).
- **Лицензионная ось бандла:** состав offline-бандла определяется лицензией контента (не-ЛР открытая → бандлуемо; ЛР Aisystant → нет).

**Открытые под-вопросы (handoff-items, НЕ блокируют этот SC):**
- (i) Точный механизм data-residency / compliance по юрисдикции (где именно и под чьим контролем GitHub-организация тайного гита).
- (ii) Лицензионный инструмент договора МИМ + авторы ↔ Aisystant (безотзывная открытая лицензия на не-ЛР руководства) — пилот: «нужен договор с конкретным лицензионным инструментом».
