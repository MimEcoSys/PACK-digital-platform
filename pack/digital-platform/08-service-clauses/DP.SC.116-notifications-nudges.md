# [DP.SC.116] Уведомления и nudges

## Обещание

**Кому:** Все роли (получают), платформа (отправляет автоматически), Администратор (настраивает).

**Зачем:** Проактивное сопровождение без навязчивости. Принцип: предлагать, не навязывать.

**Что получит:**

| Тип | Что | Канал | Кто получает |
|-----|-----|-------|-------------|
| ЦД-инсайт | «Ты не практиковал X 3 недели» | Бот (push) | Участник T3+ |
| Дедлайн ДЗ | «До дедлайна осталось 2 дня» | Бот + email | Участник в потоке |
| Streak | «5 дней подряд!» / «Ты пропустил день» | Бот (push) | Все участники |
| Milestone | «Месяц с нами! Прогресс: ...» | Бот | Все участники |
| Проверка ДЗ | «Ваше задание проверено» | Бот + email | Участник в потоке |
| Наставнику | «3 непроверенных ДЗ» | Бот + email | Наставник |
| Расписание | «Семинар через 2 дня» | Бот + email | Участники |
| Trial | «Бесплатный период заканчивается» | Бот | T1 (trial) |
| Конверсия | Триггеры C1–C7 | Бот | T1–T2 |

**Правила:** Opt-out по категориям, cooldown 7 дней между конверсионными (max 2/нед), по часовому поясу участника.

**Затухание напоминаний (РП-568 Ф15, 11.11.2026, потребность 16).** Об одном пропущенном действии (например, чек-ине марафона) — не больше двух напоминаний: на следующий день после пропуска и ещё раз через три дня. Дальше тишина, пока человек не вернётся (не сделает действие или не ответит); Доставщик (DP.SC.177) применяет тишину как фильтр (исход «отсечено: пауза»). Возвращение сбрасывает отсчёт. Решение пилота 11.11.2026 (РП-568 Ф16) вместо прежнего «до 3 дней подряд, затем вопрос». Основание: за 12.10–11.11 напоминание о пропущенном чек-ине марафона приходило почти ежедневно каждому из 95 человек.

**Личные настройки (РП-568 Ф16, решение пилота 11.11.2026).** Каждый пользователь сам настраивает свои уведомления: какие виды получать, тихие часы, частоту (каждое сообщение отдельно или одна сводка в день). Это обещание владеет перечнем видов и смыслом настроек; Доставщик (DP.SC.177) применяет их на доставке. Способ хранения и место, где человек меняет настройки, решает оценка архитектуры Ф16.

**Категории отписки на каждый некритический вид.** У каждого вида сообщения, кроме критического, есть категория отписки; кнопку «не присылать такое» показывает транспорт (DP.SC.134), отписку применяет Доставщик.

> **Колонка «Канал» — иллюстративная** (WP-117 Ф-integration). Фактический канал выбирает **Доставщик** (DP.SC.177), не это обещание: Nudge Engine канало-агностичен, отдаёт намерение через `enqueue` (см. § «Расширение Ф-integration»). Прибитая привязка «Бот/email» здесь — историческая, не контракт.

**Критерий приёмки:** Уведомления отправляются по правилам. Opt-out работает. Конверсионные не спамят. Об одном пропуске — не больше двух напоминаний, на следующий день и через три дня (журнал Центра уведомлений).

## Пользовательский путь

> Платформа анализирует состояние участника, отправляет уведомление в нужный момент и учитывает реакцию.

| # | Шаг | Кто | Сервис |
|---|-----|-----|--------|
| 1 | Анализирует состояние участника через Память.Derived | Платформа | — |
| 2 | Определяет подходящий тип уведомления и момент отправки | Платформа | — |
| 3 | Отправляет уведомление в выбранный канал | Платформа | — |
| 4 | Реагирует на уведомление (открывает, выполняет действие, отключает) | Участник | — |
| 5 | Учитывает реакцию для калибровки будущих уведомлений | Платформа | — |

## Ключевое различение: Nudge ≠ Task

> **Nudge (этот SC)** — мотивационное сообщение без трекинга выполнения. Цель: подтолкнуть, напомнить, вдохновить.
> **Task / Задание (SC.017)** — конкретное действие с результатом и статусом (pending → done). Цель: направить работу.
>
> Nudge и Task работают **параллельно**, не заменяют друг друга:
> - Nudge: «Ты не заходил 3 дня — попробуй вернуться» (нет статуса, нет трекинга)
> - Task: «Прочитай §3 и ответь на 2 вопроса» (статус: pending, трекается в Памяти)
>
> Nudge НЕ содержит конкретных заданий. Если нужно задание — это SC.017.

## Расширение Ф-integration (WP-117): Nudge Engine = L2-производитель

> Источник: ArchGate peer-сессия 2026-06-21-49 (профиль ЭМОГССБ — 6 ✅, 1 ⚠️, 0 ❌, проходит conjunctive screening). Полный design-артефакт: `DS-my-strategy/inbox/WP-117/f-integration-archgate.md`.

**Сдвиг обещания.** Nudge Engine — **платформенный сервис L2-производитель**: по состоянию пользователя (ЦД `2_collected`+`3_derived`, cp-профиль Диагноста, категориальные policy-facts Навигатора) решает, какой nudge уместен, и отдаёт **намерение** Доставчику (DP.SC.177) через узкий owned-контракт `enqueue`. Движок не знает про канал, не владеет доставкой, не трекает выполнение. Бот — один из потребителей доставки, не место движка.

### Контракт `enqueue` (зеркало канало-агностичного `send()` DP.SC.177)

```
enqueue(NudgeRequest) → {notification_id, status: queued | suppressed}
NudgeRequest = { user_id, nudge_type, opt_out_category,
                 delivery_class=capped, priority=4, dedup_key, content_spec }
```
- `content_spec` = i18n-ключ/шаблон (рендер канала — внутри Доставчика/транспорта). `scheduled_at` НЕ входит (оптимальное время — будущая data-driven политика).
- Внешний платформенный producer ходит через owned `enqueue` (API/RPC), **не** raw SQL в базу бота (DP.SC.177).

### Два шлюза подавления — один словарь категорий

Категории opt-out (владеет это обещание) переиспользуются двумя **разными** шлюзами на разных слоях enforcement — не сливать:

| Шлюз | Кто пишет | Время жизни | Где enforce |
|------|-----------|-------------|-------------|
| **User opt-out** | пользователь (предпочтение) | durable | **Доставщик** на доставке (hard-gate) |
| **Навигатор `nudge_policy_fact`** | Навигатор (роль) | time-boxed (`until`) | **движок** до `produce()` (нудж не создаётся) |

```
nudge_policy_fact = { scope: user_id, action: suppress|allow,
                      category: <этот словарь>, until: T, reason_ref: <event id> }
```
- **Модель Навигатора = (a) journey-state-как-вход** (не governor): движок читает факт как вход, сам себя подавляет. Guardrail: сигнал **только категориальный**, без journey-семантики PACK-MIM (движок не интерпретирует «что такое марафон»).
- **`allow`** = carve-out внутри `suppress` той же роли (напр. `suppress: engagement` + `allow: engagement_stage_upgrade`); **не может** переопределить user opt-out (backdoor неприменим: user opt-out — отдельный слой на Доставчике, движок его физически не видит).
- **Место:** `public.domain_event` (журнал РП-152/253), без новой таблицы; `until` owned пишущей ролью, движок без таймера.
- **⚠️ согласованность:** policy-fact, записанный в окно батча, может примениться следующим циклом (eventual consistency) — приемлемо для класса `capped`, принято осознанно.

### Граница реализации

Контракт + 2 шлюза + модель Навигатора — **design (Ф-integration, готово)**. Живая отправка через Доставщик и миграция `engagement_analyzer.py` бот→воркер — **Ф-decouple**, gated на РП-418 Ф5 verified. Прототип шва `NudgeProducer.produce()`: `DS-my-strategy/inbox/WP-117/nudge_producer_seam.py`.

> **Слой derivation категории (Ф-decouple work).** `analyze()` отдаёт `{rule_id, nudge_key, ...}`, **без** opt-out-категории. `opt_out_category` в `enqueue` заполняет seam — слой `rule_id → категория DP.SC.116`. Это не «чистая обёртка над analyze()», а расширение: без него Доставчик не применит opt-out hard-gate.
