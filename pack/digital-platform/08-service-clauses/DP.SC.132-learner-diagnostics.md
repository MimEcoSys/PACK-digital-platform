# [DP.SC.132] Диагностика ученика (Диагност)

## Правило (инвариант)

> Что ВСЕГДА выполняется. Нарушение = провал SC.

- cp_confirmed_stage вычисляется как `min(cp-оценок по 6 mandatory-слотам)`: cp.rhy, cp.wld, cp.skl, cp.iwe, cp.int, cp.agt — ни одно нельзя опустить.
- Диалог завершается не более чем за **5 вопросов** (Фазы 1+2 = hard limit). Фаза 3 автоматическая (bh-прокси, 0 вопросов).
- Диагноcт **не понижает** ступень пилота — только блокирует рост при cp_confirmed < bh_recommended (FORM.089 §5.1).
- Фоновый режим не пишет пилоту напрямую — только подсказывает активным ролям (Аттестатор, Навигатор, Портной).
- PII-правило: в `learning.cp_assessments` хранится только UUID (account_id), числовые cp_scores и bottleneck_slot. Никакого raw-текста ответов пилота.
- cp-срез не блокирует работу платформы: при недоступности БД диалог завершается, результат сохраняется при восстановлении.

## Обещание

**Кому:** Пилот (Ученик) / Аттестатор (DP.ROLE.041) / Портной (R?? WP-149) / Навигатор (MIM.R.007) / разработчик через VS Code

**Зачем:**
- Пилоту — честная оценка своего уровня и рекомендация, с какой ступени начинать (skip-level, не с S1).
- Аттестатору — cp-подтверждение для двойного gate (FORM.089 §5.1): переход ступени только если cp_confirmed ≥ bh_recommended.
- Портному — cp-профиль для персонализации personal-guide: bottleneck → выбор CAT-контента и нарратива.
- Навигатору — данные о текущем bottleneck пилота при ответе на вопрос «с чего начать».

**Что получит:** `cp-профиль`:
```
{
  "stage": 2,                        # cp_confirmed_stage (1-5)
  "bottleneck_slot": "cp.skl",       # слот с минимальным значением
  "cp_scores": {                     # по 6 mandatory-слотам
    "cp.rhy": 3, "cp.wld": 2, "cp.skl": 1, "cp.iwe": 2, "cp.int": 3, "cp.agt": 2
  },
  "recommended_stream": "S2",        # S1/S2/S3/S4
  "skip_to_stage": 2,                # с какой ступени начинать (skip-level)
  "assessed_at": "2026-05-16T...",
  "valid_until": "2026-11-16T...",   # TTL 6 месяцев для mandatory-срезов
  "source": "dialogue",             # dialogue / bh_proxy / import
  "interface": "tg"                 # tg / web / vscode / background
}
```

**Триггер:**
- Активный: `/diagnose` из TG-бота, браузера (`/diagnose`-страница) или VS Code (`IWE: Diagnose`)
- Пассивный (gate Аттестатора): bh_recommended > current_stage → запрос cp-подтверждения
- Фоновый: сигналы инвалидации (bh.inv +50%, cp-срез ≥90 дней, bh.sys скачок) → подсказка активной роли

**Время отклика:**
- ≤3 мин — полный диалог (5 вопросов + вычисление + сохранение)
- ≤500ms — ответ из кэша (TTL не истёк)
- ≤24h — фоновое предложение через активную роль (не SLA, но ориентир)

**Режим отказа:**
- БД недоступна во время диалога → завершить диалог, сохранить локально, записать при восстановлении.
- Аттестатор запрашивает cp, cp-среза нет → предложить пилоту пройти диалог, не блокировать текущую работу Аттестатора.
- Фоновый триггер не отработал → silent fail, следующий тик.

## 6 сценариев использования

1. **Новый участник через TG-бот** → `/diagnose` → рекомендация потока → skip-вход в S1/S2/S3/S4
2. **Опытный пользователь через браузер** (без логина) → страница `/diagnose` → быстрая оценка → CTA «начать с S3, не с S1»
3. **Разработчик через VS Code** → `IWE: Diagnose` → markdown-карточка в чате → автозапись в personal-guide
4. **Аттестатор:** bh_recommended > current_stage → запрос cp → cp_confirmed ≥ bh_recommended → переход подтверждён; cp_confirmed < bh_recommended → переход отложен + пилоту: «пройдите диагностику для подтверждения»
5. **Портной:** перед генерацией personal-guide → `get_cp_profile(account_id)` → bottleneck → выбор контента и нарратива + skip_to_stage → стартовая точка руководства
6. **Фоновый (Навигатор/Портной):** сигнал инвалидации → подсказка «cp-срез устарел, предложи переоценку» → Навигатор включает в ответ на «с чего начать?»

## Свидетельства (критерий приёмки)

**Данные** (что фактически существует):

| Критерий | Как проверить |
|----------|--------------|
| Запись в `learning.cp_assessments` с ненулевыми cp_scores | `SELECT * FROM learning.cp_assessments WHERE account_id=$1 ORDER BY assessed_at DESC LIMIT 1` |
| `valid_until` = assessed_at + 6 мес | Проверить разницу в днях ≈ 180 |
| `stage` = min(cp_scores.values) | Python: `assert result['stage'] == min(result['cp_scores'].values())` |
| `recommended_stream` соответствует stage | S1→ст.1, S2→ст.2, S3→ст.3, S4→ст.4+ |
| skip_to_stage = cp_confirmed_stage | `assert result['skip_to_stage'] == result['stage']` |

**Контекст** (при каких условиях действует):

| Условие | Проверка |
|---------|---------|
| account_id известен | наличие UUID в ответе |
| Не более 5 вопросов задано в диалоге | счётчик вопросов ≤ 5 |
| cp-срез в TTL | `valid_until > NOW()` |
| Фоновый: trigg = инвалидация | наличие события в `learning.cp_invalidation_signals` |

**Полномочия** (кто уполномочен подтвердить):

| Роль | Что подтверждает |
|------|-----------------|
| Диагност (DP.ROLE.042) | Корректность cp-оценки и вычисления stage |
| Платформа (aisystant) | Сохранение в Neon `learning.cp_assessments` |
| Аттестатор (DP.ROLE.041) | Использование cp-подтверждения в gate |

**Свидетельства** (как узнать, что обещание выполнено):

| Свидетельство | Источник |
|--------------|---------|
| Запись в `learning.cp_assessments` с valid_until | Neon `learning` DB |
| Аттестатор записал `cp_assessment_id` в `stage_transitions` | `SELECT cp_assessment_id FROM learning.stage_transitions WHERE account_id=$1` |
| Портной прочитал cp-профиль при генерации guide | лог `planner.py get_cp_profile` |
| Пилот получил результат в интерфейсе | `/progress` → блок «Диагностический профиль» |

## Skip-level инвариант

> Ключевое требование 16 мая 2026 (пилот WP-318): новый волонтёр **не обязан начинать с S1**.

`skip_to_stage = cp_confirmed_stage`. Если cp_confirmed_stage = 3, пилот получает рекомендацию потока S3 — минует S1-S2. Это инвариант SC: платформа обязана использовать `skip_to_stage` при формировании первого personal-guide и при рекомендации первого занятия.
