# [DP.SC.134] Доставка выпуска в канал

> # see DP.SC.134, DP.ROLE.044
>
> **Прежние имена:** Notification Dispatcher (до 18.11.2026). **Решение пилота 18.11.2026 (РП-568 Ф17):** обещание выполняет функциональная часть «Почтальон» (DP.ROLE.044) подсистемы «Вестник» (DP.ROLE.122) и расширено с Telegram на все каналы; каналы - варианты исполнителя, не разные обещания. Планирование времени перешло к Планировщику выпусков (DP.ROLE.124), очередь, повторы и устаревание - к Диспетчеру очереди (DP.ROLE.125), запись исходов - к Учётчику доставки (DP.ROLE.126). Разделы «Свидетельства», «Реализующие сервисы» и «Пользовательский путь» ниже описывают текущую реализацию в Telegram-боте, где эти части выполняются вместе.

## Правило (инвариант)

- **Все каналы.** Почтальон доставляет в любой канал, который выбрал Распорядитель доставки (DP.SC.177) по согласию человека: Telegram (исполнитель - Telegram-бот), почта (служба рассылки почты), толчок на телефон (мобильное приложение, РП-568 Ф22), толчок в браузер (исполнитель не выбран), событие в ChatGPT через MCP-сервер уведомлений (эксперимент; доставка на телефон вендором не обещана). Отдельное обещание на канал - только если у канала будет другое обещание (кандидат - события в ChatGPT, если там не будет подтверждения исхода).
- Каждое поручение доставляется **ровно один раз** (защита по ключу повтора).
- **Исход возвращается всегда:** доставлено / заблокирован / временный сбой / неизвестно.
- Если запрошено `schedule_at` — доставка происходит **не позже чем schedule_at + 2 мин** (время запуска ведёт Планировщик выпусков, DP.ROLE.124).
- Почтальон **не читает и не интерпретирует** содержимое сообщения — он транспорт, не редактор.
- Статус каждого сообщения (`queued → sent | failed`) фиксируется в `learning.domain_event` (Учётчик доставки, DP.ROLE.126).
- При временном сбое канала - повтор с отсрочкой (сейчас в Telegram 3×); после исчерпания попыток - статус `failed`, лог, НЕ молчать. Повторы и очередь отказов ведёт Диспетчер очереди (DP.ROLE.125).
- **Исход и реакции — в журнал Центра (РП-568 Ф15, 11.11.2026, потребности 16 и 104).** Почтальон возвращает исход каждой отправки (доставлено, ошибка доставки, бот заблокирован; статус `failed` выше различает два последних случая) Учётчику доставки (DP.ROLE.126); реакции человека (нажатие кнопки, ответ) передаёт Окно уведомлений. К каждому сообщению вида с категорией отписки (DP.SC.116) Почтальон добавляет кнопку «не присылать такое» (кнопки и разметка канала; текст пишет Оформитель выпуска).

## Обещание

**Кому:** Получатель любого уведомления Вестника, платформенного или своего; отправители, которым нужен исход доставки. Сейчас - пользователь платформы (через `/remind` в боте), Claude-агент (через MCP-tool), платформенный воркер (через внутренний вызов).

**Зачем:** Закрыть петлю обратной связи — платформа должна уметь инициировать контакт, а не только отвечать. Напоминания, ritual-триггеры (Day Open), уведомления о событиях — все требуют одного надёжного канала доставки.

**Что получит:**

| Потребитель | Входной интерфейс | Что получает |
|-------------|-------------------|-------------|
| Пользователь | `/remind [текст] [время]` в @aist_me_bot | Подтверждение немедленно + TG-сообщение в назначенное время |
| Claude-агент (VS Code / браузер) | MCP-tool `send_telegram_message` | `{reminder_id, scheduled_at, status}` |
| Платформенный воркер | Внутренний вызов API доставки | `{reminder_id, status}` |

**Триггер:** поручение из очереди Диспетчера очереди (DP.ROLE.125). Сейчас - явный запрос от потребителя; `/remind` - частный случай своего правила человека (DP.SC.116).

**Время отклика:**
- Подтверждение принятия (reminder_id): < 1 с
- Немедленная доставка: < 5 с
- Доставка по расписанию: в `schedule_at ± 2 мин`

**Режим отказа:**
- Канал недоступен (сейчас Telegram API) → повтор (сейчас 3×) → статус `failed` → лог в `learning.domain_event` → потребитель информирован (не молча).
- Пользователь не зарегистрирован (нет chat_id) → немедленный отказ с объяснением.
- Сообщение дублируется (тот же idempotency_key) → идемпотентный ответ (возвращает первый reminder_id, не создаёт дубль).

## Что НЕ делает Почтальон

- Не разбирает natural language время («через час») — это задача Claude выше.
- Не хранит задачи (todo) — это отдельное хранилище (DS-strategy/todo.md или inbox).
- Не интерпретирует содержимое сообщения.
- Не управляет подписками и opt-out категориями — это DP.SC.116.
- Не решает, слать ли выпуск, когда и в какой канал - это Распорядитель доставки (DP.SC.177).
- Не держит очередь и не планирует время - это Диспетчер очереди (DP.ROLE.125) и Планировщик выпусков (DP.ROLE.124).
- Сейчас реализован только канал Telegram; почта, толчки и события в ChatGPT - целевые исполнители (толчок на телефон - РП-568 Ф22; сроки остальных не заданы).

## Свидетельства (критерий приёмки)

**Данные:**

| Критерий | Как проверить |
|----------|--------------|
| Запись в `reminders` (scheduled) или `notification_log` (sent) | `SELECT * FROM reminders WHERE id = {reminder_id}` |
| Запись в `learning.domain_event` при доставке | `SELECT * FROM domain_event WHERE event_type = 'notification_sent' AND payload->>'reminder_id' = '{id}'` |
| Idempotency: дубль не создан | Повторный вызов с тем же key → тот же reminder_id, count не растёт |

**Контекст:**

| Условие | Проверка |
|---------|---------|
| Пользователь подключён к боту (chat_id известен) | `SELECT chat_id FROM users WHERE account_id = {id}` |
| Бот-токен активен | `curl https://api.telegram.org/bot{TOKEN}/getMe` → ok: true |

**Полномочия:**

| Роль | Что подтверждает |
|------|-----------------|
| DP.ROLE.044 Почтальон | Факт доставки и исход |
| DP.ROLE.125 Диспетчер очереди | Факт постановки в очередь |
| Пилот / Пользователь | Факт получения сообщения в TG |

**Свидетельства:**

| Свидетельство | Источник |
|--------------|---------|
| TG-сообщение получено пользователем | Telegram delivery status |
| Запись в `learning.domain_event` | Neon `public.domain_event` |
| Статус `sent` в `reminders` | Neon `bot_data.reminders` |

## Связь с другими обещаниями

- **Расширяется DP.SC.177** (Приём выпуска и решение о доставке: Приёмщик и Распорядитель доставки, DP.ROLE.123, 075; WP-418) — слой политики (глобальный потолок по классу, приоритет, дедуп-по-всем, hard-gate предпочтений) встаёт ПЕРЕД транспортом и зовёт его. DP.SC.134 остаётся чистым транспортом (exactly-once доставка), не берёт на себя лимиты/приоритеты — это инвариант «без интерпретации» сохраняется.
- **Дополняет DP.SC.116** (Уведомления и nudges): DP.SC.116 описывает правила, DP.SC.134 описывает доставку любого выпуска в канал.
- Использует: **`notification_log`** (idempotency, WP-152), **`learning.domain_event`** (WP-253)
- Потребляет: **DP.SC.019** (Autonomous Cloud Runtime — бот работает 24/7 на Railway)
