## Правило (инвариант)

- Каждое принятое сообщение доставляется пользователю **ровно один раз** (exactly-once через idempotency_key).
- Если запрошено `schedule_at` — доставка происходит **не позже чем schedule_at + 2 мин**.
- Dispatcher **не читает и не интерпретирует** содержимое сообщения — он транспорт, не редактор.
- Статус каждого сообщения (`queued → sent | failed`) фиксируется в `learning.domain_event`.
- При отказе Telegram API — retry 3× с экспоненциальным backoff; после 3 неудач — статус `failed`, лог, НЕ молчать.
- **Исход и реакции — в журнал Центра (РП-568 Ф15, 11.11.2026, потребности 16 и 104).** Транспорт передаёт Доставщику (DP.SC.177) фактический исход каждой отправки (доставлено, ошибка доставки, бот заблокирован; статус `failed` выше различает два последних случая) и реакции на неё (нажатие кнопки, ответ). К каждому сообщению вида с категорией отписки (DP.SC.116) транспорт добавляет кнопку «не присылать такое».

## Обещание

**Кому:** Пользователь платформы (через `/remind` в боте), Claude-агент (через MCP-tool), Платформенный воркер (через внутренний вызов).

**Зачем:** Закрыть петлю обратной связи — платформа должна уметь инициировать контакт, а не только отвечать. Напоминания, ritual-триггеры (Day Open), уведомления о событиях — все требуют одного надёжного канала доставки.

**Что получит:**

| Потребитель | Входной интерфейс | Что получает |
|-------------|-------------------|-------------|
| Пользователь | `/remind [текст] [время]` в @aist_me_bot | Подтверждение немедленно + TG-сообщение в назначенное время |
| Claude-агент (VS Code / браузер) | MCP-tool `send_telegram_message` | `{reminder_id, scheduled_at, status}` |
| Платформенный воркер | Внутренний вызов Dispatcher API | `{reminder_id, status}` |

**Триггер:** Явный запрос от потребителя (не автоматика платформы — это DP.SC.116).

**Время отклика:**
- Подтверждение принятия (reminder_id): < 1 с
- Немедленная доставка: < 5 с
- Доставка по расписанию: в `schedule_at ± 2 мин`

**Режим отказа:**
- Telegram API недоступен → retry 3× → статус `failed` → лог в `learning.domain_event` → потребитель информирован (не молча).
- Пользователь не зарегистрирован (нет chat_id) → немедленный отказ с объяснением.
- Сообщение дублируется (тот же idempotency_key) → идемпотентный ответ (возвращает первый reminder_id, не создаёт дубль).

## Что НЕ делает Dispatcher

- Не разбирает natural language время («через час») — это задача Claude выше.
- Не хранит задачи (todo) — это отдельное хранилище (DS-strategy/todo.md или inbox).
- Не интерпретирует содержимое сообщения.
- Не управляет подписками и opt-out категориями — это DP.SC.116.
- Не отправляет email или push-уведомления браузера (только Telegram в текущей версии).

## Свидетельства (критерий приёмки)

**Данные:**

| Критерий | Как проверить |
|----------|--------------|
| Запись в `reminders` (scheduled) или `notification_log` (sent) | `SELECT * FROM reminders WHERE id = {reminder_id}` |
| Запись в `learning.domain_event` при доставке | `SELECT * FROM domain_event WHERE event_type = 'notification_sent' AND payload->>'reminder_id' = '{id}'` |
| Idempotency: дубль не создан | Повторный вызов с тем же key → тот же reminder_id, count не растёт |

**Контекст:**

| Условие | Проверка |
|---------|---------|
| Пользователь подключён к боту (chat_id известен) | `SELECT chat_id FROM users WHERE account_id = {id}` |
| Бот-токен активен | `curl https://api.telegram.org/bot{TOKEN}/getMe` → ok: true |

**Полномочия:**

| Роль | Что подтверждает |
|------|-----------------|
| DP.ROLE.044 Notification Dispatcher | Факт постановки в очередь и доставки |
| Пилот / Пользователь | Факт получения сообщения в TG |

**Свидетельства:**

| Свидетельство | Источник |
|--------------|---------|
| TG-сообщение получено пользователем | Telegram delivery status |
| Запись в `learning.domain_event` | Neon `public.domain_event` |
| Статус `sent` в `reminders` | Neon `bot_data.reminders` |
