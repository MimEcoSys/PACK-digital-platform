# DP.SC.171 — Конвейер разработки IWE

> Сервисный контракт конвейера WP-403: 6 станций от Постановки до Закрытия с инвариантом двойного выхода (код + знание). Команда T4+ (TD1).

---

## Правило (инвариант)

> Что ВСЕГДА должно выполняться для данного сервиса. Нарушение = провал SC.

1. **Двойной выход.** Каждая задача рождает одновременно работающий код/артефакт и зафиксированное знание. Задача, после которой остался только код, считается незавершённой.
2. **Риск-ориентированный объём.** Каждая задача получает минимальный достаточный `verification_scope`
   S0–S3 по матрице ниже. Проверки вне выбранного объёма запрещены без объективного триггера.
3. **Merge gate.** Только Ведущий разработчик (TD1+TA4) вливает код в main. Никто другой — без явного делегирования.
4. **WIP-лимит.** Одновременно в работе не более 8–15 РП (правило S-47). Превышение — стоп и пересмотр бэклога.
5. **Барьер входа.** Конвейер допускает только разработчиков T4+ (TD1). T1–T3 — онбординг (WP-349), не конвейер.
6. **Контроль пилота.** Матрица, её пороги и триггеры принадлежат R01 Пилоту. Агент не изменяет их
   по инциденту, аналогии или собственной оценке; он может только предложить новую версию и ждать
   прямого согласия пилота.
7. **Воспроизводимый сигнал до исправления.** Исправление дефекта начинается только после того, как
   быстрый наблюдаемый сигнал на реальном пути сбоя показал дефект (`red`). После исправления тот же
   сигнал обязан показать отсутствие дефекта (`green`). Предпочтителен тест; допустимы команда,
   проба или снимок журнала, если корректного тестового шва нет.
8. **Две оси проверки.** Любое разрешённое матрицей ревью или самопроверка выдаёт два отдельных
   вердикта: (A) соответствие постановке и критериям приёмки; (B) соответствие инженерным стандартам
   репозитория. Это один проверяющий и один проход, а не дополнительное независимое ревью.
9. **Защита на повторе.** Второй подтверждённый сбой одного класса нельзя закрыть без самой дешёвой
   надёжной детерминированной защиты на ближайшем шве и её отрицательной самопроверки. Памятка без
   исполняемой проверки защитой не считается.

## Архитектурное решение: риск-ориентированные проверки

**Решение пилота от 2026-10-06.** Критические характеристики — безопасность и скорость. Из трёх вариантов
отклонены полный прогон после каждого изменения (блокер по скорости) и свободное усмотрение агента (блокер по
безопасности). Принята следующая матрица как единственный источник решения.

`verification_class` описывает тип неопределённости задачи (`trivial`, `closed-loop`, `open-loop`, `problem-framing`).
`verification_scope` описывает только объём технических проверок. Одно не заменяет другое.

| Объём | Когда применяется | Обязательные проверки | Что не запускается |
|---|---|---|---|
| **S0 — формальный** | Только текст, комментарий, опечатка или неисполняемые metadata; не изменяются контракты и инструкции агентов | `diff-check`; парсер только для изменённого структурированного файла | Тестовые наборы и независимое ревью |
| **S1 — локальный** | Один модуль; нет публичного интерфейса, постоянного состояния, safety/security или платформенной границы | Форматтер/линтер репо только для изменённых файлов; целевые тесты изменённого поведения; для defect fix — один воспроизводимый сигнал, наблюдённый `red` до правки и `green` после неё | Полный набор и независимое ревью |
| **S2 — связанный** | Несколько модулей одного репо; обратно совместимый публичный интерфейс; конфигурация, адаптер или инструкция агента | S1 + тесты прямых потребителей + один интеграционный или smoke-тест; platform-проверка только для затронутой платформы | Полный набор и независимое ревью |
| **S3 — критический** | Хотя бы один S3-триггер ниже | Целевые и негативные тесты; после стабилизации один полный прогон затронутого репо; одна специальная проверка по сработавшему риску; одно независимое ревью | Повторные зелёные full-run без изменения кода/контракта; второе ревью без согласия пилота |

### S3-триггеры

- аутентификация, авторизация, permissions, secrets, PII, шифрование или security boundary;
- схема постоянного хранения, migration, backup/restore или семантика сохранения данных;
- транзакция, concurrency, idempotency, crash recovery или необратимая запись;
- breaking contract или общий компонент с несколькими независимыми потребителями;
- обновление runtime, dependency, сборки или platform boundary с потенциально широким blast radius;
- release/deployment, для которого полный прогон указан как acceptance criterion.

### Алгоритм и жёсткие ограничения

1. До первой проверки агент называет `verification_scope` и конкретные проверки. Выбирается наименьший уровень, покрывающий все триггеры.
2. Полный набор разрешён только для S3 и запускается после целевых проверок на стабильном изменении, а не на каждой итерации.
3. После сбоя повторяются сбойная и прямо зависимые проверки. Объём повышается ровно на один уровень, только если сбой доказал больший blast radius.
4. Повторный full-run нужен только после изменения кода/контракта после предыдущего full-run. Документация, не меняющая контракт, не инвалидирует зелёный прогон.
5. Проверяются только затронутые репозитории, платформы и прямые потребители. Whole-workspace audit не запускается автоматически.
6. Независимое ревью обязательно только для S3; верификатор ≠ автор. Второе ревью или отдельный deep security scan требуют прямого разрешения пилота.
7. Агент не добавляет проверку «для уверенности»: для каждой проверки выше базовой он называет триггер из этой матрицы.
8. Снижение обязательного объёма возможно только по прямому решению пилота; результат тогда маркируется как неполностью проверенный.
9. Для defect fix команда или процедура воспроизводимого сигнала фиксируется до первой правки; гипотеза без наблюдаемого сигнала не даёт права менять реализацию.
10. Две оси проверки публикуются раздельно и не агрегируются: сильный результат по стандартам не скрывает неверную реализацию постановки, и наоборот.
11. При втором подтверждённом сбое одного класса выбирается минимальная достаточная защита в порядке стоимости: регрессионный тест → статическая проверка/линтер → хук/ограничение/детерминированный генератор → наблюдаемый алерт. Если детерминированного предиката нет, закрытие блокируется до решения пилота.

## Обещание

**Кому:** Команда разработки IWE (T4+ / TD1) и пилот как заказчик.

**Зачем:** Превратить ремесленную разработку IWE в воспроизводимый процесс с проверяемым результатом и накоплением знания.

**Что получит:**
- Проверяемый результат — работающий код/артефакт.
- Зафиксированное знание — обновления Pack, шаблонов, AGENTS.md/CLAUDE.md, memory.
- Закрытый РП в реестре с полным audit trail.

**Триггер:** Появилась задача разработки платформы или IWE, оформленная Постановщиком (DP.ROLE.068) с карточкой задачи.

**Время отклика:** По классу верификации:
- V1 (тривиальное): минуты
- V2 (сверка эталон): часы
- V3 (peer-review): дни
- V4 (problem-framing): недели

**Режим отказа:**
- Задача застряла дольше N дней (N по классу верификации) → статус `stalled`, возврат в бэклог или эскалация Ведущему разработчику (TD1+TA4) / пилоту.

## Свидетельства (критерий приёмки)

**Данные** (что фактически существует):

| Критерий | Как проверить |
|----------|--------------|
| Карточка задачи с `wp:`, `verification_class` и `verification_scope` | frontmatter карточки либо объявление перед проверкой |
| Выполнены только разрешённые для S0–S3 проверки | список команд/вердиктов и сработавший триггер |
| Исправление дефекта имеет сигнал `red → green` | одна и та же команда/процедура и её наблюдаемые результаты до и после правки |
| Проверка разделена на две оси | отдельные вердикты A «постановка» и B «стандарты» в одном отчёте |
| Повторный сбой получил автоматическую защиту | код паттерна, защита на ближайшем шве и отрицательная самопроверка защиты |
| S3 имеет один вердикт независимого Верификатора | GitHub PR label/комментарий или verdict отдельного review-agent |
| Двойной выход: код + знание | PR содержит код + связанный Pack-commit или memory-update |
| Merge выполнен Ведущим | Git log `--author` или `--trailer` |

**Контекст** (при каких условиях обещание действует):

| Условие | Проверка |
|---------|---------|
| Разработчик T4+ (TD1) | Проверка tier в реестре участников |
| Среда настроена (агенты, гайд) | Наличие `docs/developer-guide.md` в шаблоне |
| Задача оформлена Постановщиком | Frontmatter карточки: `framer: DP.ROLE.068` |

**Полномочия** (кто уполномочен подтвердить):

| Роль | Что подтверждает |
|------|-----------------|
| DP.ROLE.070 Верификатор | PASS/FAIL по критерию приёмки для S3 |
| DP.ROLE.071 Ведущий разработчик | Решение о merge и закрытии РП |
| R14 Заказчик (пилот) | Стратегические решения об изменении конвейера |

**Свидетельства** (как узнать, что обещание выполнено):

| Свидетельство | Источник |
|--------------|---------|
| Закрытый PR с merge-commit | GitHub / git log |
| Обновлённый WP-реестр | `inbox/WP-NNN.md` frontmatter `status: closed` |
| Захваченное знание | Pack-файл или memory/lessons или AGENTS.md diff |

## Сценарии использования

### SC1 — Производство (T4-разработчик)

- **Триггер:** Появилась задача разработки платформы или IWE.
- **Вход:** Оформленная карточка задачи (тег маршрутизации, `verification_class`, `verification_scope`, критерий приёмки).
- **Выход:** Проверяемый результат (код + capture), закрытый РП в реестре.
- **Режим отказа:** Задача застряла дольше N дней → статус `stalled`, эскалация Ведущему (DP.ROLE.071) / пилоту.
- **Роль:** Разработчик-исполнитель (DP.ROLE.072).
- **Станции:** все 6 (Постановка→Открытие→Проектирование→Работа→Проверка→Закрытие).

### SC2 — Надзор/архитектура (Ведущий разработчик TD1+TA4)

- **Триггер:** Разработчик запросил ArchGate/IntegrationGate или PR готов к merge.
- **Вход:** Архитектурное решение или PR с выполненным `verification_scope`; для S3 — также с вердиктом Верификатора.
- **Выход:** Архитектурное решение принято/отклонено; PR влит или возвращён на доработку.
- **Режим отказа:** Конфликт с roadmap или нарушение инварианта → блокировка merge с обоснованием.
- **Роль:** Ведущий разработчик (DP.ROLE.071).
- **Станции:** Проектирование (ArchGate), Закрытие (merge gate).

### SC3 — Внешняя обратная связь (пользователь T1–T3)

- **Триггер:** Пользователь платформы прислал замечание, баг-репорт или фидбек.
- **Вход:** Неструктурированное сообщение через баг-репорт или Наставника.
- **Выход:** Разработчик T4 оформил валидное замечание как карточку задачи для конвейера (SC1) или отклонил с обоснованием.
- **Режим отказа:** Замечание не валидно → ответ пользователю с разъяснением, без создания карточки.
- **Роль:** Постановщик задачи (DP.ROLE.068) по преобразованию сырого входа.
- **Станции:** Постановка (оформление карточки).
