## Проблема, которую закрывает

Доставка размазана: 26 файлов, ~107 точек прямой отправки, ~20 независимых проактивных отправителей. Каждый создаёт свой экземпляр бота и шлёт напрямую, не зная, что шлют другие в тот же момент. Единого слоя, который считает / ограничивает / приоритизирует / уважает предпочтения по ВСЕМ исходящим — нет. Следствие: нельзя обещать «не больше N сообщений в день», нельзя приоритизировать (урок важнее нуджа), нельзя единообразно уважать opt-out.

## Правило (инвариант)

- **Единая точка.** Каждое исходящее пользователю сообщение проходит через `NotificationService.send()`. Прямая отправка в обход — запрещена (миграция 107 точек, Ф3).
- **Глобальный потолок — по МЕСТУ, source-agnostic.** Дневной лимит класса `capped` считается по тому, сколько необязательных сообщений упало пользователю в его место (Telegram-чат), а не по источнику и не по каналу. Сумма по ВСЕМ отправителям, не per-sender; ни один отправитель не может его обойти. Жёсткий потолок видит ТОЛЬКО `capped`: `must-deliver` и `critical` по определению идут сверх и в счёт потолка не входят.
- **Честный потолок (формулировка обещания).** Пользователю обещается: «**≤N необязательных сообщений в день; подписочное (занятия, чек-ины) и критическое — сверх и не давится**». Не «не больше N сообщений в день вообще» — это было бы ложью, т.к. подписка обходит потолок. Вторичный монитор «`must-deliver` + `capped` ≤ M/день» работает как алерт-клапан (сигнал о перегрузе места), НЕ как жёсткий потолок.
- **Канало-агностичный контракт.** Вход `send(user_id, class, content_spec, priority, dedup_key)` не принимает Telegram-специфику (`chat_id`, `reply_markup`). Рендер канала — внутри dispatch-адаптера.
- **Приоритет при конкуренции.** При нескольких сообщениях одному пользователю в один тик дренажа — отправка в порядке приоритета класса; `capped` сверх дневного потолка подавляются (с логом, не молча).
- **Дедуп-по-всем.** Повтор с тем же `dedup_key` в окне класса не создаёт второй отправки.
- **Предпочтения — hard-gate.** Opt-out (категории владеет DP.SC.116) применяется на доставке как жёсткий фильтр, до постановки в очередь.
- **Очередь приватна.** Таблица-очередь — внутренняя деталь Доставщика. Снаружи модуля её схема не видна; raw SQL извне запрещён.

## Класс-модель (Ф2 — основной выход)

Пять классов с политикой на каждый:

| Класс | Дневной лимит | Приоритет | Дедуп-окно | Канал | Opt-out |
|-------|---------------|-----------|------------|-------|---------|
| `critical` (безопасность/деньги: смена пароля, подозрительный вход, сбой/возврат оплаты) | без лимита, обходит всё | 1 (высший) | 24 ч по `dedup_key` | user | **нельзя отключить** |
| `must-deliver` (подписочный урок, чек-ин подписки) | вне дневного потолка | 2 | 12 ч | user | только отпиской от самой подписки |
| `transactional` (`/remind` пользователя, OAuth «X подключён») | без дневного лимита, дедуп | 3 | 6 ч | user | `/remind` — нет (сам просил); OAuth — да |
| `capped` (реанимация, engagement/practice nudge) | **≤2/день суммарно по классу** | 4 | 48 ч на тип | user | да, по категориям (DP.SC.116) |
| `ops-alert` (autofix/health/dev) | без лимита | — | 1 ч | **dev-канал** (не пользовательский) | n/a |

Ключевая гарантия (урок РП406): дневной потолок `capped` = сумма по всем источникам реанимации/вовлечения, попавшим в одно место (чат) пользователя, а не отдельный счётчик у каждого отправителя. `must-deliver`/`critical` в потолок не входят (идут сверх).

## Обещание

**Кому:** платформенный воркер (будущий Nudge Engine РП117), Claude-агент, Онбордер (РП406), марафон (РП330), Лента, OAuth-колбэки, Навигатор, пользователь (через `/remind`).

**Зачем:** дать обещанию-транспорту (DP.SC.134) зубы — превратить «отправлено» в «отправлено в рамках единой политики»: с потолком, приоритетом, дедупом и уважением предпочтений.

**Что получит потребитель:**

| Потребитель | Входной интерфейс | Что получает |
|-------------|-------------------|-------------|
| In-bot отправитель (сейчас, ~20 шт.) | Прямой вызов `NotificationService.send(user, class, content_spec, priority, dedup_key)` | `{notification_id, status: queued\|suppressed\|sent}` + причина при `suppressed` |
| Внешний платформенный producer (будущее, РП117) | Узкий owned `enqueue`-контракт (API/RPC) — НЕ raw SQL в базу бота | `{notification_id, status}` |
| Пользователь | Эффект: «≤N необязательных (capped) в день; подписочное (занятие/чек-ин) и критическое — сверх и не давится»; важное не вытесняется нуджем; каждое сообщение понятно без знания внутренних слов платформы | — |

**Триггер:** любой потребитель хочет отправить сообщение пользователю.

**Время отклика:** постановка в очередь / решение suppress — < 1 с. Фактическая доставка — по контракту транспорта (DP.SC.134).

**Режим отказа:**
- Потолок класса исчерпан → `status: suppressed` + причина в `public.domain_event` (не молча).
- Opt-out по категории → `status: suppressed` (reason: opt-out), до очереди.
- Транспорт (DP.SC.134) не смог доставить → статус наследуется от транспорта (`failed` после 3 retry).

## Что НЕ делает Доставщик

- Не решает ЧТО и КОГДА слать по смыслу — это DP.SC.116 (Nudge Engine, РП117).
- Не интерпретирует содержимое сообщения (как и транспорт).
- Не владеет категориями opt-out — он их применяет; владеет DP.SC.116.
- Не доставляет физически — это транспорт DP.SC.134 (Доставщик зовёт его).
- Не отправляет email/web-push сейчас — мультиканальность отложена в будущую фазу (Apprise).

## Свидетельства (критерий приёмки)

| Критерий | Как проверить |
|----------|--------------|
| Все исходящие идут через единую точку | grep: 0 прямых `bot.send_message` вне dispatch-адаптера (после миграции Ф3) |
| Глобальный потолок `capped` соблюдается | За день у пользователя ≤2 сообщения класса `capped` в одном месте (чате), суммарно по всем источникам. **Предусловие измеримости:** drain штампует `delivered_via` в payload журнала — иначе доставленное слоем неотличимо от прямой отправки, метрика неизмерима (verify B, peer 2026-06-14-49). |
| `suppressed` логируется с причиной | `SELECT * FROM public.domain_event WHERE event_type='notification_suppressed'` содержит reason. NB: таблица — `public.domain_event` (не `learning.domain_event`, такой нет — проверено). |
| Дедуп работает | Повтор с тем же `dedup_key` в окне → второй отправки нет |
| Контракт канало-агностичен | Сигнатура `send()` не содержит `chat_id`/`reply_markup` |

## Связь с другими обещаниями

- **Расширяет DP.SC.134** (Notification Dispatcher): транспорт остаётся чистым, Доставщик добавляет слой политики поверх и зовёт транспорт.
- **Применяет DP.SC.116** (Уведомления и nudges): opt-out категории и cooldown-дизайн принадлежат SC.116; Доставщик enforce-ит их на доставке как hard-gate + глобальный потолок.
- **Заказчик: РП406** (Онбордер) — delivery_gate онбординг-нуджа ляжет на этот слой.
- **Будущий producer: РП117** (Nudge Engine L2) — через owned `enqueue`-контракт, не raw SQL.
- **Переиспользует:** `public.domain_event` (журнал + дедуп, РП152/РП253).

## Интерфейс для consumers (семантический контракт) — WP-418 Ф5

> Семантика входов и гарантии выхода. Без языковых типов — рендер на конкретный язык остаётся в коде (docstring = ссылка на этот раздел + Python-сигнатура как производная).

### Входные параметры

| Параметр | Смысл |
|----------|-------|
| **Идентификатор получателя** | Непрозрачный целочисленный ключ пользователя. Под ним хранятся ограничения доставки и opt-out предпочтения. В текущем канале (Telegram) совпадает с chat_id, но Доставщик не знает об этом — рендер канала внутри транспорта. |
| **Класс сообщения** | Один из пяти классов (`critical`, `must-deliver`, `transactional`, `capped`, `ops-alert`). Определяет: дневной лимит, приоритет, дедуп-окно, канал и opt-out-политику. Политики — в §Класс-модель. |
| **Содержимое (канало-нейтральное)** | Пакет: обязательный текст + опциональный формат (`plain`/`markdown`/`html`) + опциональные кнопки-действия (список `{label, action}`/`{label, url}`). Не содержит chat_id, reply_markup или parse_mode — они в транспорте. |
| **Приоритет** | Целое: меньше — важнее. Если не передан, берётся из политики класса. Явная передача позволяет повысить приоритет внутри класса (например, срочный `capped`). |
| **Ключ дедупликации** | Строка, уникальная для конкретного намерения отправки. Повтор с тем же ключом в дедуп-окне класса → не создаёт второй отправки. Опционален; без него дедуп не применяется. |
| **Семантический журнальный ключ** | Прежний idempotency_key для `domain_event`. Позволяет читателям журнала (`was_nudge_sent_recently` и пр.) видеть доставки через Доставщик в том же формате, что и прямые отправки до миграции. Опционален; без него — технический ключ `delivery:{id}`. |
| **Тип журнала** | Прежний `notification_type` в `domain_event` payload. Сохраняет контракт читателей (`nudge`, `marathon_nudge` и пр.). Опционален; без него — имя класса. |

### Гарантии выхода

| Статус ответа | Что означает |
|---------------|-------------|
| `queued` | Сообщение принято. Дренаж доставит при следующем запуске (≤1 мин). Запись в `notification_queue` создана. |
| `suppressed` | Сообщение не будет доставлено. Поле `reason` содержит причину: `cap-exceeded` (потолок класса исчерпан), `opt-out` (пользователь отписался от категории), `duplicate` (dedup_key уже в окне), `journal-dup` (семантический ключ уже в domain_event). Запись в `notification_queue` создана со статусом `suppressed`. |

`notification_id` — ID записи в очереди; `None` только при `duplicate` (без записи в очереди).

### Чего НЕ гарантирует интерфейс

- Немедленной доставки — физическая отправка в следующем дренажном тике.
- Упорядоченности относительно других получателей — только приоритет внутри одного тика.
- Конкретного текстового представления в канале — рендер канала в транспорте.
