# DP.SC.204 — Гейт объявления намерения агента

> **Контекст:** РП-561 Ф33, решение пилота 13.10 (пир-сессия `MC-sessions:2026-10/13/2026-10-13-07-wp561-f33-archgate-receiver/`) — вариант Б: отдельный от механики часов плана (DP.SC.201, DR-03) журнал, лёгкий, построенный тем же транспортным паттерном (flock + git-публикация), чтобы объединение в будущем оставалось дешёвым.

## Правило (инвариант)

> Что ВСЕГДА должно выполняться для данного сервиса. Нарушение = провал SC.

- [ ] Вызов инструмента любым агентом проверяется на наличие свежей записи намерения этого агента (РП или «вне РП»); нет записи → вызов блокируется с понятной причиной, не тихо пропускается.
- [ ] Проверка — локальное чтение, без сети и без тяжёлой admission-семантики (fencing token, generation, allocation_confirmed/started/expired) из DP.SC.201/plan_allocation.py — та механика остаётся отдельной, обслуживает только спорные часы плана.
- [ ] Отказ самой проверки (файл не читается, журнал повреждён) НЕ блокирует весь агент навсегда — блокируется только затронутый вызов (Protective Procedure Fallback, CLAUDE.md), не платформа целиком.
- [ ] Запись намерения не переинтерпретируется как «выполненная работа» — это объявление, не отчёт о факте (тот же принцип, что в DP.SC.201 различает намерение/факт/допуск).

## Обещание

**Кому:** пилот (видит, кто чем занят, без обхода) и будущие читатели конвейера дня (Ф34 табло может со временем подключить и этот журнал, не только часы плана).

**Зачем:** закрыть разрыв, что WP Gate (регистрация РП+задачи до работы) сейчас — инструкция агенту, а не технический предохранитель; агент может его пропустить без механического следа.

**Что получит:** технический блок вызова инструмента у агента без свежей записи намерения; читаемый журнал «кто что объявил и когда».

**Триггер:** каждый вызов инструмента любым агентом (PreToolUse hook).

**Время отклика:** мгновенно (локальное чтение одного файла/журнала, не сетевой вызов).

**Режим отказа:** см. правило выше — отказ проверки блокирует только текущий вызов, не все будущие; громкий лог, не тихий no-op.

## Свидетельства (критерий приёмки)

**Данные** (что фактически существует):

| Критерий | Как проверить |

| PreToolUse-хук зарегистрирован и реально вызывается на каждый tool-call | `.claude/hooks/`, запись в конфиге hooks |

| Условие | Проверка |

| Запись намерения «свежая» (есть порог давности, иначе старая запись не считается подтверждением текущего действия) | числовой порог в коде хука |

## Сценарии использования (минимум 3, разные потребители)

**Сценарий 1 — агент начинает работу над РП.** Кто: агент-исполнитель (Claude/Kimi/Codex). Когда: сразу после WP Gate (нашёл РП в плане). Зачем: продолжить к Write/Edit/Bash без отказа хука. Контекст: обычная рабочая сессия. Что делает с результатом: пишет лёгкую запись «РП-NNN» в журнал намерений, затем вызывает инструменты как обычно — хук пропускает, пока запись свежая.

**Сценарий 2 — агент работает вне какого-либо РП (исключение WP Gate, ≤15 мин/вопрос без изменений файлов).** Кто: тот же класс агента. Когда: короткая задача, под исключение из Ритуала согласования. Зачем: не получить отказ хука за отсутствие РП, когда РП по правилу и не требуется. Контекст: диагностика, быстрый вопрос. Что делает с результатом: пишет запись «вне РП» явно (не РП-N, а явный маркер), хук пропускает по той же логике — записи без conкретного РП не считаются нарушением.

**Сценарий 3 — пилот смотрит, кто чем занят прямо сейчас.** Кто: пилот (DP.ROLE.001), не агент-исполнитель. Когда: в любой момент дня, не привязан к конкретному вызову инструмента. Зачем: наблюдаемость — видеть параллельных агентов без необходимости спрашивать каждого в чате. Контекст: несколько параллельных сессий (несколько хостов/агентов одновременно — обычное состояние этой платформы). Что делает с результатом: читает журнал намерений напрямую (или через будущее подключение к табло Ф34) — не меняет его, чисто потребление.

**Сценарий 4 — фоновый процесс без интерактивного агента (night watchdog, cron-задача).** Кто: автоматизированный скрипт без LLM, работающий по расписанию. Когда: ночной цикл, автономное исполнение. Зачем: пройти тот же гейт, не получить блок из-за отсутствия «интерактивного» намерения. Контекст: такой процесс не ведёт диалог с пилотом и не проходит обычный WP Gate. Что делает с результатом: сам процесс должен писать свою запись намерения программно (например, «автоматический цикл Х») перед первым вызовом инструмента — иначе гейт либо ломает все автономные циклы платформы (если жёсткий с первого дня), либо требует отдельного исключения для известных автоматизаций. Это прямое следствие открытого вопроса ниже, не решённое этой карточкой.

## Открытый вопрос перед реализацией (не решён этой сессией)

Жёсткий блок с первого дня или мягкий (warn-only) запуск сначала — риск: если сам журнал/хук сломается, а режим жёсткий, ВСЕ агенты платформы теряют возможность действовать одновременно (сам механизм становится единой точкой отказа для всей работы). Решение — за пилотом, не за агентами, реализующими гейт.

**Решено 13.10 (commit `29280ab`):** warn-only запуск первым — см. `DP.M.525` (метод, обобщающий это решение для любого нового блокирующего гейта).
