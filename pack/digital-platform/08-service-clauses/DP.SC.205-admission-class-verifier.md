# DP.SC.205 — Верификатор реестра классов допуска

> **Контекст:** РП-561 Ф35/С1, пир-сессия `MC-sessions:2026-10/15/2026-10-15-21-wp561-dynamic-day-queue/` (раунды 7-8, Claude+Kimi+Codex, продолжена по слову пилота «давай все делайте»/«давай делаем далее»). Контракт полей класса допуска (`id`, `allowed_actions`, `allowed_resources`, `constraints`, `approved_by`, `approval_date`, `expiry`) зафиксирован 15.10 раундом 2 этой же сессии (секция Ф35 карточки). Эта карточка реализует только С1 (проверку исполнения из уже утверждённого класса), не сам процесс утверждения нового класса (тот — отдельный, человеком-владельцем, полный IntegrationGate).

## Правило (инвариант)

> Что ВСЕГДА должно выполняться для данного сервиса. Нарушение = провал SC.

- [ ] Проверка — чистое чтение: находит класс, покрывающий ОБА идентификатора (конкретное действие И конкретный ресурс) среди неистёкших утверждённых записей реестра, с учётом `constraints`; никогда не создаёт, не изменяет и не удаляет запись реестра.
- [ ] Неизвестное/непонятное ограничение в `constraints` НЕ трактуется как разрешение — отсутствие доказательства соответствия = отказ, не прохождение по умолчанию.
- [ ] Fail-closed на любую неуверенность: отсутствующий реестр, повреждённый реестр, истёкшая запись, недоступный сам верификатор — все эти случаи дают один и тот же внешний ответ «нет подтверждённого допуска», с разными внутренними причинами для диагностики (не одно и то же как по UX, так и по логам).
- [ ] Валидный, но пустой реестр (нет ни одной записи) — НЕ ошибка доступа, это обычный легальный случай «пока ничего не утверждено»; не путать с отсутствующим/повреждённым файлом.
- [ ] Отказ самого верификатора откладывает ТОЛЬКО действия, которые требуют этой проверки (вне уже утверждённого класса) — разрешённая и уже проверенная работа продолжается без блокировки (Protective Procedure Fallback, CLAUDE.md).
- [ ] Не дублирует и не заменяет DP.SC.204 (гейт объявления намерения — «связан ли вызов с объявленным РП», другой вопрос) — прохождение одного слоя не означает автоматического прохождения другого.

## Обещание

**Кому:** агент-исполнитель перед действием вне явно утверждённого класса; пилот (видит, какие классы утверждены и когда истекают); write-token-держатель (инициирует запрос расширения, не утверждает — решение 15.10).

**Зачем:** закрыть разрыв между «контракт класса допуска согласован на бумаге» (15.10) и «агент реально может проверить, покрыто ли конкретное действие допуском» — без этого слой `decision_intent`/`decision_outcome` (С1-С3) не имеет механизма, отличающего разрешённое действие от неразрешённого.

**Что получит:** да/нет-ответ с причиной на вопрос «это действие+ресурс покрыты утверждённым классом?»; читаемый реестр действующих классов.

**Триггер:** агент сам решает, когда спрашивать (не PreToolUse-хук на каждый вызов — это другой, более узкий вопрос, чем DP.SC.204).

## Сценарии использования (минимум 3, разные потребители)

**Сценарий 1 — агент-исполнитель перед действием вне текущего класса.** Кто: любой агент-исполнитель. Когда: встретил действие, для которого не уверен в допуске. Зачем: не выполнить неразрешённое действие молча. Контекст: обычная рабочая сессия, слой С1 Ф35. Что делает с результатом: нет допуска → откладывает действие (фиксирует запрос, не исполняет), продолжает разрешённую работу — цикл не блокируется (контракт 15.10).

**Сценарий 2 — пилот при обзоре дня.** Кто: пилот (DP.ROLE.001). Когда: любой момент. Зачем: видеть, какие классы утверждены, кем, когда истекают — без необходимости спрашивать каждого агента в чате. Контекст: несколько параллельных сессий — обычное состояние платформы. Что делает с результатом: читает реестр напрямую, не меняет.

**Сценарий 3 — write-token-держатель в пир-сессии.** Кто: агент, временно держащий write token (DP.SC.154). Когда: встретил действие вне всех утверждённых классов и считает расширение обоснованным. Зачем: инициировать запрос нового класса. Контекст: раунд пир-сессии. Что делает с результатом: пишет заявку на расширение (отдельная запись, не правка существующего класса) — утверждает только заранее назначенный человек (контракт 15.10, write token даёт право инициировать, не утверждать).

**Сценарий 4 — сам верификатор недоступен (файл реестра поврежден/заблокирован на чтение).** Кто: любой агент-исполнитель из сценария 1. Когда: инфраструктурный сбой, не связанный с содержанием запроса. Зачем: не потерять всю работу из-за одного сбоя. Контекст: тот же, что Protective Procedure Fallback (CLAUDE.md) описывает для любой защитной процедуры. Что делает с результатом: откладывает только действия, которые требуют этой конкретной проверки; продолжает работу в рамках уже подтверждённых допусков и действий, не требующих проверки вовсе.
