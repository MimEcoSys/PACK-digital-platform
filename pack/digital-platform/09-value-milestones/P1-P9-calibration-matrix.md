# Calibration Matrix — P1-P9 Value Milestones

Матрица задаёт прокси-метрики для фиксации каждой «пользы» (has_P{n} = true)
в таблице `user_milestones`. Proxy confidence отражает надёжность прокси
на момент MVP; план валидации — как проверить что прокси работает.

> **Архитектурное правило:** `user_milestones` хранит факты (кто что пережил).
> Логика «когда предлагать следующую пользу» — в Онбордере Фаза 2 (DP.SC.170 §11).
> Колонка `milestone_p_class` (pre/post onboarding) — не хранится в схеме;
> Онбордер Фаза 2 проверяет `onboarding_complete` + `user_milestones` напрямую.

## Таблица

| P | Польза | Прокси для has_P{n} = true | Proxy confidence | Условие в БД | План валидации |
|---|--------|---------------------------|-----------------|--------------|----------------|
| P1 | Первый полезный ответ от ИИ | `ai_response_count >= 1 AND user_message_count >= 3 AND session_active_sec > 90` | medium | INSERT в user_milestones при первом достижении условия в event log | Корреляция `has_p1` с `retention_7d` на первых 50 пользователях. Если корреляция < 0.2 — прокси слабый, пересмотр. |
| P2 | Пробная тема | Открыт хотя бы один урок бесплатного курса (`lesson_events.type = 'free_preview'`) | high | INSERT при первом событии типа `free_preview` | Воронка: P2 → P3. Если P2 не ведёт к P3 в 30% случаев — контент пробника слабый, не прокси. |
| P3 | Марафон на регулярной основе | Пользователь подписан на марафон И получил хотя бы 3 урока (`marathon_checkins >= 3`) | high | INSERT после 3-го зафиксированного чек-ина в `marathon_state` | Retention 14d у когорты has_p3=true vs false. Ожидаемое: +15%. |
| P4 | Профиль в Aisystant | `user_profile.completed_at IS NOT NULL` (имя + цель + выбранная ступень) | high | INSERT при первом `user_profile.completed_at` | Операционная; профиль либо заполнен, либо нет. Ложные срабатывания маловероятны. |
| P5 | Первая маленькая победа | Ответил на вопрос урока ИЛИ записал мысль (`quiz_attempts >= 1 OR note_events >= 1`) | medium | INSERT при первом quiz_attempt или note_event | Распределение по типу события (quiz vs note). Если >90% — note без quiz → победа формальная, не содержательная. |
| P6 | Персональная траектория | `user_profile.bottleneck IS NOT NULL AND user_profile.recommended_stream IS NOT NULL` | high | INSERT после заполнения bottleneck + recommended_stream (часть Х3 Онбордера) | Онбордер закрывает P6 как часть Х3 — двойного трекинга нет, Онбордер Фаза 2 просто видит has_p6=true. |
| P7 | Доступ к сообществу (клуб) | `club_memberships.active = true` | high | INSERT при первой активной записи в club_memberships | Операционная. Ложные срабатывания исключены FK-ограничением. |
| P8 | Цифровой двойник | `digital_twin.initialized_at IS NOT NULL` (хотя бы один cp-слот заполнен) | medium | INSERT при первом `digital_twin.initialized_at` | Качество цифрового двойника (cp-профиль vs эталон Диагноста) — отдельная метрика вне Онбордера. |
| P9 | Своя среда развития | Репозиторий DS-strategy создан И есть хотя бы 1 коммит (`github_repos.has_ds_strategy = true AND commit_count >= 1`) | medium | INSERT при первом коммите в DS-strategy репозиторий пользователя | Retention 30d у когорты has_p9=true. Ожидаемое: наивысший retention среди всех P. |

## Дорожка и доставка (P-граф)

Если таблица выше отвечает «как система **засекает**, что польза взята», то эта — «кто польза **доставляет**, что должно быть пройдено раньше, какую характеристику Стажёра она двигает и какой сигнал шлёт наверх». Вместе они делают матрицу полным input'ом для Фазы 2 Онбордера (DP.SC.170 §11) и для движка тиров.

| P | Кто доставляет (механизм) | Предусловие | Двигает характеристику | Событие-сигнал |
|---|---------------------------|-------------|------------------------|----------------|
| P1 | Бот — поиск по базе знаний МИМ (консультация / Гермес на T0) | вход (нет) | Х2 (зачатки: «система полезна») | — |
| P2 | Бот — бесплатный пробный материал (`free_preview`) | P1 | Х2 (понимание формата сообщества) | — |
| P3 | Планировщик марафона + регистрация Онбордера | P2 | Х1 (оснащение T1) + Х5 (ритм практики) | повышение тира (→T1) |
| P4 | Онбордер (заполнение профиля — часть Х3) | P3 | Х3 (фиксация ступени и цели) | — |
| P5 | Марафон — обработчик ответов на вопросы / заметок | P3 | Х5 (умеет работать, микро-победа) | повышение тира (→T2) |
| P6 | Онбордер + Диагност (DP.ROLE.042; узкое место + поток) | P4 | Х3 (траектория выбрана — закрытие Х3) | — |
| P7 | Движок тиров + членство в клубе | Стажёр (Х2+Х3) ∧ P5 | Х2 (среда сопроизводителей) | — |
| P8 | Воркер цифрового двойника + согласие на учёт | Стажёр (Х2+Х3) ∧ P6 | Х4 (костюм: персона + память) | повышение тира (→T3) |
| P9 | Портной + провижининг репозитория (`connect-guide`) | Стажёр (Х2+Х3) ∧ P8 | Х4 (костюм: своя среда развития) | повышение тира (→T4) |

**Как читать предусловие.** Граф не строго линеен (`∧` = «и то, и другое»). Ключевой гейт: пользы P7–P9 предлагаются только после статуса **Стажёр** (закрыты обе характеристики Х2 и Х3, `onboarding_complete = true`) — это инвариант обещания Онбордера (DP.SC.170 §11). Без него польза вроде клуба (P7) могла бы прийти к человеку, ещё не понявшему сообщество (Х2). Онбордер Фаза 2 предлагает следующую пользу только когда её предусловие выполнено — иначе пропускает и ждёт.

**Связь с целевой системой «Стажёр».** Стажёр = закрыты Х2 (понимает сообщество) и Х3 (выбрал траекторию). По графу это достигается к P6: ориентационная польза (P1, P2, P7) растит Х2, выбор и профиль (P4, P6) закрывают Х3. P8–P9 уже строят костюм (Х4) — за пределами зоны Онбордера, передаются Портному.

**Где НЕ эмитится событие.** P1, P2 (тир T0 — повышения нет), P4, P6 (внутри тира T1/T2 — это закрытие характеристики, не смена оснащения). Событие шлётся только на границах тиров: вход в T1 (P3), T2 (P5), T3 (P8), T4 (P9).

## Событие повышения тира (потребительское описание)

> **Событие УЖЕ существует в проде — `tier_changed`** (эмитится в боте при смене тира, `db/queries/identity.py`; каноническая проекция в персону — воркер РП270). Эта матрица **не вводит новый контракт**, а ссылается на фактический. Владелец доменного контракта (версия, гарантии) — РП349/РП270, не эта матрица.
>
> ⚠️ **Рассинхрон имени (открытый вопрос для РП349).** В коде событие называется `tier_changed`, а в текстах Pack (DP.SC.170, DP.ROLE.067) — `TierUpgraded`. Это расхождение Pack↔код возникло ДО этой матрицы; здесь приводим фактический контракт из кода, унификацию имени делать одной правкой на уровне РП349 (3 файла Pack + код).

**Фактический контракт (как в `db/queries/identity.py`):**

- **Имя:** `tier_changed` (`event_type`), `source: aist-bot`, `schema_version: v1`.
- **Триггер:** смена тира пользователя (обновление `users.tier`). По дорожке польз границы — P3 (→T1), P5 (→T2), P8 (→T3), P9 (→T4).
- **Полезная нагрузка (фактическая):** верхний уровень — `account_id` (ory_id), `external_id`, `occurred_at`, `schema_version`; `payload: { tier_from, tier_to }`.
- **Канал доставки:** доменное событие через `post_event` (таблица `domain_event`; маршрут «work» в `db/queries/events.py`).
- **Потребители (фактические + потенциальные):**
  - Воркер проекции в персону (РП270) — канонический потребитель, пишет `persona.ory_identity.traits.tier`.
  - Проводник (DP.ROLE.013) — открыть кнопки/команды нового тира (Х1, техническая ось).
  - Онбордер Фаза 2 (DP.ROLE.067) — пересчитать следующую пользу.
  - Контролёр развития (R46) — обновить маркеры мониторинга.
- **Идемпотентность:** событие эмитится только при реальном изменении `users.tier` (`UPDATE 0` → события нет).

**Предложение (НЕ в текущем коде, на решение РП349):** добавить в payload поле `milestone_p` — какая польза вызвала переход, чтобы Онбордер Фаза 2 связывал тир и дорожку польз напрямую. Сейчас этого поля нет; не выдавать за существующее.

## Примечания

- **P1 — medium confidence:** три сообщения за 90 секунд не гарантируют «полезный» ответ.
  Валидация по корреляции с retention — первый реальный сигнал. До накопления 50 пользователей
  с `has_p1=true` — прокси работает «на доверии».

- **P4 и P6 — закрываются Онбордером:** в процессе прохождения Х3 (DP.SC.170) Онбордер сам
  обновляет `user_profile`. Онбордер Фаза 2 видит уже заполненные `has_p4=true` / `has_p6=true`
  и не предлагает их повторно.

- **Escalate after declines:** параметр Онбордера `escalate_after_declines` (default: 2).
  Не хардкод в этой матрице.
